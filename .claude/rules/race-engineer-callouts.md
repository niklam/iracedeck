# Race Engineer Callouts

How to add or modify a Race Engineer voice callout. This threads through seven packages — once you've done it, the per-package details below are checklist material.

## Architecture at a glance

```text
iRacing telemetry (TrackWetness, PitSvStatus, …)
        │
        ▼ diff module — `packages/sim-events-iracing/src/diff/<name>.ts`
@iracedeck/event-bus  ───────────────────────────────────►  publishes a SimEvent
        │                                                   on `IEventBus`
        ▼ contract `where:` predicate — at event arrival
@iracedeck/audio-scenarios  ─────────────────►  the CONTRACT decides whether and when
        │                                       (wrapped with master-gate + opt-in);
        │                                       the active voice's SCRIPT says what
        ▼ script entry → `pool:<group>/<base>` → `voice/<voice>/<group>/<base>-NN.mp3`
@iracedeck/audio-assets  ───────────────────►  `voice/<voice>/callouts.json` + clips
        │                                       (grammar: @iracedeck/callout-script)
        ▼ contract `speakGate.admit` (#1138) — the code's second look, after the
        │   body expanded and before the line takes the bus
        ▼ playback via `@iracedeck/audio-service`
Driver hears the line.
```

Seven layers, one direction. The **opt-in** wraps the contract's `where:` so a
toggle at the Property Inspector silences future fires without cutting an
in-flight clip; the **master gate** (`pitCrewRaceEngineerEnabled`) wraps every
voice callout as the outermost short-circuit. A contract may take one more
look at the world after its body has expanded and before the line takes the
bus — its `speakGate` (#1138), the last thing between a fire and the speaker,
and the only one of these gates that can run seconds after the event arrived.

**Since #1064 a callout is two artifacts that pair by id.** The **contract** (`ScenarioContract`, in code) decides *whether and when* the engineer speaks and how the fire is scheduled — `when` / `where`, the optional `speakGate` (#1138), `weight`, `family`, `interrupt`, `queueable`, `cooldown`, `channel`, `bus`, `base`, the default `frame` — and registers every var, condition and case a script may name. The **script** (a `scenarios` entry in the voice's `callouts.json`) decides *what* he says: the `sequence`, plus `comment`, `test`, an optional `skip` and an optional `frame` override. A pack references the vocabulary by name and can never define one, change when a callout fires, or change what it may interrupt — scheduling, pacing and triggers are withheld deliberately, because a pack that got them wrong would present as a plugin bug. **#1138 closed the one leak in that:** the re-checks that keep a queued nag from arriving stale had been migrated into the script as `if` steps, which held the pacing promise only for a pack that kept them; they are contract `speakGate`s now, asked by the engine for every voice whatever its script says. **Absent means skipped:** a voice whose script has no entry for a contract is silent for it, at debug level, never an error. **Every family is scripted.** The flags went first (#1064) and #1065 moved the other 125 callouts across, one conditional step at a time; nothing in the catalog registers a `Scenario` (a contract with an inline `sequence`) any more — that type is an engine primitive the interpreter's tests use. A new callout, in an existing family or a new one, is a contract in code plus a script entry in the voice config, always both.

## Naming conventions

- **Per-callout opt-in setting key:** `callout<Polarity><Family><Subject>` (`.claude/rules/global-settings.md` is the canonical reference). Polarity is always `Enabled`; a callout ships on, so its registry entry carries no `default` — only an entry that ships the callout off writes `default: false`. Examples: `calloutEnabledFlagYellowLocal`, `calloutEnabledTrackWetness`.
- **Scenario id:** `pit-crew.<family>-<subject>` — `pit-crew.flag-yellow-local`, `pit-crew.pit-status-too-far-left`, `pit-crew.track-conditions-worsening-mostly-dry`.
- **Pool:** every line is a pool — all the clips sharing one `(group, base)`, `voice/<voice>/<group>/<base>-NN.mp3` — so future variants are clip-file additions with no code change (issue #664). A script addresses one directly as `pool:<group>/<base>` (`pool:flags/blue`); that spelling IS the pool, and the `(group, base)` is published the moment a script uses it — renaming a base is a rename in every pack's script and clip folder. A pool gets a **name** only when the name carries a decision the path does not: an alias onto a different group, or a second line that must not share a no-repeat tracker with the first (`pit-action-acknowledgment` beside `acknowledgment`) — and then the reason goes in its `comment`. A name that would merely restate the path (`flag-blue` → `flags`/`blue`) is not written; the thirty flag pools that once had one do not any more, and no family that followed in #1065 named one either — the reference voice's `pools` is `{}`.
- **Vocabulary name (var / condition / case):** `<family>.<camelCaseName>` — `session.type`, `flag.furledStillShown`, `readback.tirePattern`, `lapTime.minute`. Names and their one-sentence descriptions are the public API of the script format — they are published verbatim on the website's Vocabulary page (`/docs/voice-packs/reference/vocabulary/`, generated from `vocabulary()`; #1066) — so pick them for a pack author who has not read the resolver. A `case`'s key set is declared with the registration, not inferred.
- **Voice clip path:** `voice/{voice}/<group>/<name>.mp3` — group keys the `groups` map in the voice config; name keys the entry inside the group.
- **Family identifier (for preemption):** matches the directory naming: `flag`, `damage`, `pit-status`, `track-conditions`. All contracts in a family share the same `family:` value, so a newer fire supersedes an in-flight one cleanly.

## Adding a new callout — checklist

When adding to an existing family (e.g. another flag colour) you skip steps 1–2 and the bus-side wiring; when introducing a brand-new family you do all of it. Step 4 has two halves since #1064 — 4a is the contract in code, 4b is the script entry in the voice config — and every callout does both: the contract decides whether and when, the script entry decides what is said, and neither exists without the other (a contract with no entry is silent; an entry with no contract is a warn and a skip).

**An SFX cue is not a scenario: it skips steps 3 and 4 entirely, and the scenario half of step 6** (issue #912, the first one). A cue that must react instantly plays direct from an imperative engine — `getAudio().playOnChannel(...)`, the `radar-engine.ts` model — instead of firing through the interpreter, so it has no voice lines, no pool, no scenario, no `SCENARIO_ID_TO_*` map, no `wrapCalloutScenario` loop and no row in `callout-settings-coverage.test.ts`. Step 6 therefore splits: its **wiring** half is still required — the `<Family>CalloutId` type and the family's `enabledIn(...)` gate, handed to the engine's options in `registerPitCrew` (`registerPitSpeedingEngine`'s `getCueEnabled` is the precedent) — while its scenario-registration half does not apply. It still needs everything else too: the bus event (1), the diff and state (2), the registry entry (5), the fixtures (7) and the harness entries (8). The opt-in is read live inside the engine's own tick rather than by a scenario wrapper. Note what direct playback costs and buys: no weight, family or focus contest — so nothing to tune against other callouts, but equally no interpreter to keep it from overlapping one.

### 1. Define the bus event

In `packages/event-bus/src/event-catalog.ts`:
- If the event carries a sim-defined enum, define a **canonical enum** alongside `RadarState` / `FlagScope` / `PitServiceKind`. Use `export enum`, not just `export type`.
- Add a line to `SimEventMap`. Use `{ from, to }` for value-change events; `EmptySimEventPayload` for transition events with no payload.
- Export the enum from `packages/event-bus/src/index.ts` as a **value** (not just a type) so runtime consumers can reference it.

### 2. Translator diff + state

- **A key-triggered callout has no diff.** When the moment is a deck key press rather than a sim change, the action publishes the event itself and step 2's diff and state do not apply — Session Info's Speak value on press (#466) is the precedent: the action converts the value it shows to the driver's display unit before publishing, so the payload stays sim-agnostic.
- Add fields to `TranslatorState` in `packages/sim-events-iracing/src/state.ts` (typically `<name>Initialized: boolean` + a `last<Name>` cache). **Update both the type AND `createInitialState()`** — TypeScript catches the mismatch only via `pnpm build` (vitest's esbuild path is more permissive).
- Write the diff module under `packages/sim-events-iracing/src/diff/<name>.ts`. Pattern: seed silently on first tick, advance baseline every tick, emit the bus event only on real transitions. Suppress sentinel-state transitions (Unknown ↔ x for track-wetness; * → None for pit-status). A state the sim never reports gets its own event from whatever signal the captures show, not from a sentinel transition: pit-status publishes `pitService.stopEmpty` on the fall of a `PitstopActive` pulse shorter than `PIT_STATUS_EMPTY_STOP_MAX_MS` in the stall, tracked on every tick beside the status diff (#1180).
- Wire into `translator.ts` `handleTick`.
- Add tests: first-tick seeding, single-step transitions, unchanged ticks, sentinel handling, invalid input handling.

### 3. Voice lines

In `packages/audio-assets/configs/default.voice.json`, **and in every other first-party voice** — every voice a `VOICE_PACKS` entry in `src/build/voice-packs.mjs` publishes, today the Terse pack's `configs/shawn.voice.json` (#999). A first-party voice makes every callout Default makes, and `bundled-scripts.test.ts` fails on a contract its script does not carry, so author the Terse wording of the new line too (radio shorthand, the fact itself), then generate it for that voice separately: `generate:dry-run --voice shawn --group <group>` first, then `generate --voice shawn --group <group>`. An entry whose Terse text, settings and seed are verbatim Default's needs no paid call: copy Default's clip and its `generate.manifest.json` row under `voice/shawn/…`, and the dry-run reports it as a cache hit. Third-party packs stay optional — a voice without a clip skips that callout, issue #664. For every voice, what `script-coverage.test.ts` insists on is that every clip it authors in a group its script addresses is referenced by that script, and everything the script references exists (#1065):
- Add (or extend) a group with one entry per `(direction × subject)` combination.
- Each entry: `name` (kebab-case, suffix `-01` so future variants append as `-02`), `text`, optionally `seed` (omit it on new entries — the generator defaults an omitted seed to `1` — or set `"seed": 1` explicitly; NEVER an arbitrary/random value, since the seed only selects which take ElevenLabs produces. Bump it deliberately for a different take when the generated clip doesn't sound right — the seed feeds the hash, so the change re-cuts only that clip), optional `previous_request_ids` to bias prosody continuity.
- Use `<break time="0.3s" />` for natural pauses inside a single line.
- Per-entry overrides for `model_id`, `language_code` (inside `voice_settings`), `output_format`, normalization flags etc. are supported and shallow-merge on top of the voice's defaults.

Generate the clips:

```bash
pnpm --filter @iracedeck/audio-assets generate:dry-run --group <group-name>  # preview: must list ONLY the new entries
pnpm --filter @iracedeck/audio-assets generate --group <group-name>          # only the new group
pnpm --filter @iracedeck/audio-assets generate:manifest                      # rebuild runtime manifest
```

Each `configs/<voice-id>.voice.json` is the per-voice source of truth — voices are self-contained, no cross-voice fallback. `generate.manifest.json` is the per-voice hash cache (keys include `voice/<voice-id>/…` so changing one voice's settings invalidates only that voice's entries). `manifest.json` is the runtime asset listing. The `--group` filter keeps the generator from re-cutting unrelated entries (and saves API cost); `--voice <id>` scopes to one voice. ElevenLabs is a paid API — never run unfiltered `generate` casually.

### 4a. The contract in code (pools, vocabulary, scheduling)

- Pools: there is nothing to declare in code — the script addresses the clips as `pool:<group>/<base>` (step 4b), naming a pool only where the name carries a decision, and the `(group, base)` joins the family's literal `<FAMILY>_CLIP_SOURCES`. The pool's members are derived per-voice from the manifest (`voice/<voice>/<group>/<base>-NN.mp3` plus the bare `<base>.mp3`, issue #836) at fire time, so adding a *variant* later is a clip-file change only. Single-member pools are deterministic; multi-member pools are sampled uniform-random with a per-pool no-immediate-repeat guard (the interpreter's `pickFromPool` — not a sequential rotation; the tracker resets on voice change). A named pool is looked up in the active voice's script; there is no code registry to fall back on since #1065.
- **Value-indexed clips are pools too (issue #836).** A `var` resolver returns `poolRef(group, base)` from `dsl.ts` (the `pool:<group>/<base>` reference form) instead of a raw clip path — position numbers, lap-time digits, temperatures, speeds, and names all resolve this way, usually as size-1 pools. There are **no hardcoded value ranges or clamps**: the clips that exist for the active voice define what's speakable, and a value with no clip skips its `optional` clause or aborts the callout (per #835). Keep `where:` predicates to null/known checks only — never numeric range checks. A value that can go below zero is **spelled** `minus<N>` by its resolver, never `String(n)`: the pool rule reads `<base>-NN` as a take, so `-4` would be a take of an empty base and `minus-4` a take of `minus` (#1187, `temperature-number.ts`). And a figure whose fixed word follows it in speech is recorded WITH that word as one clip (`numbers-percent` carries "percent", `numbers-degrees` carries "degrees" — "one degree" at 1) rather than spliced to a word clip; a unit NAME a pack may optionally add stays a separate clip behind its own var (`sessionStart.degreesUnit` → `session-start/unit-celsius|fahrenheit`) — a number→unit join has as many predecessors as the group has values, and conditioning (`previous_request_ids`, at most three) cannot reach them (#1108, #1187).
- **Vocabulary.** Everything a script may name is registered in code, with prose, in a `register<Family>Vocabulary(engine)` the family exports and `registerPitCrew` calls before the registration loops (`registerFlagVocabulary` in `flag-alerts.ts` is the precedent):
  - `engine.defineVar(name, (ctx) => clipPathOrPoolRef | null, description)` — a value the script speaks with `"{{name}}"` / `{ var }`: a clip path or a `poolRef(group, base)`, `null` for "nothing to say".
  - `engine.defineCond(name, (ctx) => boolean, description)` — a yes/no the script branches on with `{ if: "name" }`; `"!name"` negates.
  - `engine.defineCase(name, (ctx) => key | null, { key: "what it means", … }, description)` — a multi-way choice the script maps with `{ case: "name", of: { key: […], default: […] } }`. **The key set is declared, not inferred** — it is what lets a pack author write the branch without reading the resolver, and what lets the compiler refuse a typo'd key. A resolver returning an undeclared key is a code bug (warned once) and takes the `default` branch; a `null` takes `default` too, and with no `default` the case says nothing.
  - Every resolver is a `VocabularyResolver<T>` (`dsl.ts`, #1065): it receives the `ScenarioContext` of the fire — `event`, `data`, `telemetry`, `now` — so a family can phrase a callout by WHY it fired (readback's opener reads the event's `reason`). `event` is `null` for an imperative `fire(id)`, so a resolver that reads it must tolerate that; a resolver that needs nothing from the fire is written as a zero-parameter function, which is assignable unchanged.
  - **Publish generously — more vars than our own script uses.** The vocabulary is exactly what bounds the phrasings a pack can express; a resolver is four lines and no runtime weight. Every description is one sentence written for the Vocabulary page (`/docs/voice-packs/reference/vocabulary/`), which shows it beside the callouts that use the name — and a var that draws from a clip group must NAME that group in its description (`incidents/points-2`, or "the session-start clip group"): `descriptionNamesGroup` is how the recording script and `lint:pack` attribute a group's lines to the var, since a resolver is a closure nothing can read (#1066).
- Write the family file under `packages/audio-scenarios/src/catalog/pit-crew/<family>.ts`. Mirror `flag-alerts.ts` (a static contract list with a `case`, and the furled pair's two contract `speakGate`s), `readback.ts` (a snapshot-driven body — the fifteen-way tire table as one declared-key `case`) or `pit-status.ts` (a family whose five repeat nags each carry a `speakGate`). Each contract has:
  - `id: "pit-crew.<family>-<subject>"`
  - `description:` — one sentence, for a pack author, on WHEN the callout fires, in the sim's terms rather than the code's ("The pace car pulls away on a rolling-start formation lap.", not the event name and the gate). US spelling ("tire", "meters", "color"), as the website writes. The Callouts page (`/docs/voice-packs/reference/callouts/`) shows it beside the reference voice's `comment` (what is said) and `test` (how to hear it), so it repeats neither. Optional on the type (the engine primitives the interpreter's tests register carry none) and **required for every catalog contract** — `bundled-scripts.test.ts` holds each to four rules: non-empty, ends with a full stop, at most 200 characters (`DESCRIPTION_MAX_LENGTH` — a table cell, not a paragraph on the gate's every clause), and does not open by restating its own id (#1066).
  - `family: "<family>"` (shared across the whole family — a newer same-family fire replaces the in-flight family-mate wholesale, regardless of weight)
  - `weight:` — omit for an ordinary callout (defaults to `WEIGHT.NORMAL = 50`). Use the named bands from `dsl.ts` (`WEIGHT.TRANSIENT = 5`, `CHATTER = 10`, `NORMAL = 50`, `SAFETY = 70`, `CRITICAL = 100`, `PROXIMITY = 120`; any integer allowed) so importance is a tunable number, not a fixed enum. Higher weight wins a busy bus. Flag callouts sit at `WEIGHT.SAFETY` (above routine chatter and a spotter focus floor); the meatball cut-through line is `weight: WEIGHT.CRITICAL` + `interrupt: true`. `PROXIMITY` (#867) is reserved for immediate-danger proximity information that must ALWAYS be heard — the spotter's transition calls are its only occupant; it sits strictly above CRITICAL because an equal-weight fire never cuts, and it pairs with `interrupt: true` + `queueable: false`. Don't put anything informational there: a repeating or non-danger line at PROXIMITY would chop up CRITICAL calls (that's why the spotter's "Clear."/still-there sibling stays at SAFETY).
  - `interrupt:` (default `false`) — `true` cuts an in-flight LOWER-weight fire mid-sentence; `false` waits for the current line to finish. Equal/lower-weight fires never cut. Reserve `interrupt: true` for safety-critical lines (meatball, fuel-critical) that must cut anything in flight.
  - `queueable:` (default `false`) — `true` defers a fire that can't take the bus now (equal/lower weight, or below a focus floor) for replay when the bus next idles; `false` drops it. Deferred fires wait in a per-bus queue (`PendingQueue`, #1185) and play one at a time as the bus idles: heaviest first, then the longest-waiting. Nothing leaves the queue by weight alone: a lighter fire waits behind a heavier one instead of being dropped on arrival, and a heavier one goes ahead of a lighter one instead of evicting it. The queue holds at most four fires, `queueBehind` followers not counted; an arrival above that drops the lightest, then the oldest, the newcomer included — one fire per arrival, so a follower freed by that drop stays, even when that leaves the queue over the cap until it drains. It is cleared on `session.changed`, before that event's own contracts run, and by `stopAll`. Every drop is logged at debug with its reason. A heavier fire without `interrupt` waits in the same queue for the line in flight, queueable or not. Use it for background commentary that should wait its turn rather than vanish, and for **every callout raised on a one-shot edge**, whatever its weight: an event the translator raises once per episode and never again (a penalty flag, #923; an incident flush or the damage edge, #1211/#1288) is lost for good when dropped, and a crash is exactly when the bus is busiest — the spotter's floor, the caution calls. A line that waits can go stale. The engine bounds every wait (`maxQueueWaitMs`, below), and for most queueable lines that bound is the only pacing they have. Where the line needs more, give it a pure `speakGate` saying what must still be true when it speaks: by **age** where the news is a moment (an incident older than 10 s is refused, since a new one may have begun) and by **live state** where it is a condition (damage asks the translator's debounced damage state and is skipped once the repair has settled — read the translator's settled state rather than a raw tick when the signal flickers). Deferred replays do NOT re-run `where:` — it decided at event time. What must still hold at speak time is the contract's `speakGate` (#1138), which the replay asks again; a pack may wrap its body in the same registered condition, but the bundled behaviour no longer depends on it. Freshness of the words themselves still comes from var resolvers reading live state at speak time.
  - `resumable:` (default `false`, requires `queueable: true` — validated at load time) — when an `interrupt` cuts this fire mid-playback, the idle-replay CONTINUES from the interrupted clip instead of re-firing from the top (issue #758). The replay re-expands the sequence first and falls back to a full fresh replay when the expansion changed while stashed (the #481 freshness guarantee) — compared by pool reference for a pool-drawn op and by clip path otherwise (#1136), so a second take of the same line is not a change while a var resolving to a different value still is; and because a pool reference is voice-independent and survives a redefinition of what the pool holds, a change of the ACTIVE VOICE, or of the scripts or manifest, while stashed replays the whole body too. Only for deterministic sequences with side-effect-free `if:` predicates; the pit-service readback is the reference consumer. A fire that already passed the gate — cut and stashed, resumed from the cut, or replayed whole — is never re-asked its `speakGate` (it is the same fire, and a claiming gate would otherwise refuse its own claim), so a contract that is both `queueable` and gated must tolerate that.
  - `queueBehind:` (optional, requires `queueable: true` — validated at load time, as is naming the contract itself) — the ids of contracts this callout must be heard AFTER (#1108). It is an ordering constraint between two fires that should both be heard, not a replacement rule (that is `supersedeGroup`, below). The queue orders by weight, so without it a callout published right behind another but heavier than it plays first: the tire-wear report, published in the same tick as the exit readback and the heavier of the two, would speak ahead of the pit-exit confirmation it is meant to follow (before #1185, when the bus kept one waiting fire, it displaced that confirmation outright). Use it for a callout meant to be heard after a specific other one: while a named contract waits in the bus's queue, this one is placed right after it (and after that leader's earlier followers), whatever the weights; a named contract that arrives to wait (stashed by an interrupt) while this one waits goes ahead of it, and this one links behind it. A leader may have several followers, in arrival order, and a follower does not count toward the queue's cap. Three guarantees, all pinned by interpreter tests: **never overtaken** — a follower never plays ahead of a waiting leader, even on an idle bus where the leader is held in the queue (a `pendingHoldMs` hold, a focus floor between the two weights): it is queued behind it there too, and one whose list names several waiting contracts is served only once none of them is still waiting — **never stranded** — a leader that leaves the queue without playing (its max wait, superseded, dropped by the cap, disabled) or fails to take the bus at replay (expansion aborted, `speakGate` refused, no script entry in the voice) leaves the follower to play as an ordinary entry, and a follower whose list also names the fire that superseded its leader re-links behind that fire instead (#1211: the damage line waiting behind an off-track line stays behind the escalation that replaces it) — **ordered, not bound** — the relation decides order and nothing else: the follower keeps its own weight, group and max wait, `stopAll` clears both, and disabling the follower's own opt-in removes only it. Once its leader has been taken off the queue to play, a follower waits as an ordinary entry, so a heavier fire arriving while the leader plays goes ahead of it, though it no longer replaces it. A follower replays as an ordinary fire — its own event, resume and admission. An id that is not registered is not an error, it just never matches; an id registered on another bus never matches either (the queue is per bus), and that is warned once at registration, whichever side registers second. Registration also warns once when the `queueBehind` relations on a bus close a cycle: two contracts that each wait behind the other would both sit in the queue, each holding the other back, until their max wait drops them. It orders only fires that wait: on an idle bus the first one published plays at once, so when the follower's event can arrive BEFORE the leader's, the translator must hold it until the leader's is out — #1211 holds the damage emit behind an open incident burst (2 s grace), so a flush tick publishes the incident events and then the damage event, and `queueBehind` keeps that order when the bus is held. Publication order decides an idle bus, `queueBehind` a busy one; a pair needs both.
  - `supersedeGroup:` (optional; defaults to the contract id; a non-empty string, validated at load time) — waiting fires of one group replace each other: a newer fire removes any older fire of its group still in the queue, logged as `dropped — superseded by "<id>"` (#1185). That holds whether the newer fire waits or takes the bus at once (a fuel-laps-left-3 clearing a focus floor drops the fuel-laps-left-5 still waiting below it), with one exception the other way round: a line an interrupt cut is the older fire, so its stash yields to a waiting fire of its group and is the one dropped. The default is why the same callout never stacks: a newer qualifying approval replaces the one still waiting. Name a shared group only when a newer line makes the waiting one wrong or redundant, never merely because it matters more: a DQ replaces a waiting black flag (`penalty`), go replaces ready (`start-light`), an escalation replaces the incident line it corrects (`incident`), the newest readout press wins (`readout`), a newer lap count replaces an older one (`fuel`). A family whose `where:` writes one shared stash that a resolver reads at speak time needs one group too, or two waiting fires would both speak the newer value (`opponent-flag-ahead` for `pendingAhead`; `incident` also keeps `lastIncidentPoints` in step). Weight plays no part — a newer, lighter fire replaces a heavier one of its group — so a group whose members differ in weight must be one where the newer line is always the one worth hearing (in `fuel` the newer, lower lap count is also the more urgent). Two groups were rejected on that test: `gap`, where a newer CHATTER trend line would have replaced a waiting NORMAL threshold call (ungrouped, both wait, the threshold call plays first, and the gap cooldown its gate claims refuses the second), and `opponent-pit`, which would have cut a queued pit train down to its last line (only the nearby line reads the `pendingNearby` stash, and its own id already keeps it to one waiting fire). It acts on WAITING fires only; `family` keeps acting on the playing one, and is no substitute for a group: the caution calls share `family: "flag"` with the penalty flags, so grouping by family would let a lineup change erase a waiting caution announcement. The groups in use are listed in the #1185 entry of `race-engineer-callout-examples.md`.
  - `maxQueueWaitMs:` (optional; a positive number, validated at load time; defaults to `DEFAULT_MAX_QUEUE_WAIT_MS`, 8000) — how long a deferred fire may wait for the bus before it is dropped (#1185). It runs from the fire's FIRST deferral: a replay deferred again keeps its original time, while a fire an interrupt cut starts a new wait. It is checked whenever the queue is read and logged as `dropped — waited N ms (max M ms)`. The default is the engine's pacing: a line runs two to four seconds, so 8 s is two or three lines of backlog, enough to clear a burst and short enough that the engineer never works through a backlog about a moment that has passed. **Give a longer wait only to a line that stays true for as long as it waits**: a sustained state (a penalty lasts until served: `flag-black`, `flag-disqualify`, `flag-dq-scoring-invalid` and `flag-meatball` wait 30 s), a condition its `speakGate` re-checks at speak time (`damage-repair-needed`, 30 s; the gated `caution-*` calls, 20 s, which re-check that the caution is still out, and the lineup and follow calls that the lineup still holds), news that cannot change before it is spoken (`tire-wear-report`, 30 s), or a moment whose own freshness rule reaches further than the default (the six incident lines take `INCIDENT_SPEAK_MAX_AGE_MS`, 10 s, the age their gate already allows). `flag-caution-waving` (20 s) is the one override without a re-check; it rests on a full-course caution lasting minutes. A line that is only true near its moment keeps the default, however much it matters; if it keeps losing the bus, the answer is its weight or its order, not a longer wait.
  - `speakGate:` (optional) — `{ description, admit }`: a second look, in code, taken after the active voice's script expanded and before the callout takes the bus (#1138). `admit(ctx)` returning `false` drops the fire like a required-step abort (debug, no cooldown stamp, never cancelling an in-flight line); it is asked when a fire deferred before it ever expanded replays at idle, and never again of a fire that already passed it — cut and stashed, resumed, or replayed whole. Use it for a whole-body re-check of live state — "is the car STILL too far left" — and for nothing that chooses words: a clause-level re-check (the readback's limiter pre-opener) stays a script `if`. It is the ONE place a cooldown claim is committed (#1137): `where:` keeps the pure check (`canAnnouncePosition()`), `admit` makes the claim (`tryClaimPositionAnnouncement()`). `description` is one sentence the reference renders as "Re-checked at speak time", held to the `description` rules. A registered condition a pack may name must stay pure — the furled pair's marking moved into the gate for that reason.
  - `pendingHoldMs:` — after this fire finishes, hold the drain of the bus's whole queue for N ms so a displaced line doesn't stutter back into the gaps of a train of related fires (issue #758, the whole queue since #1185; the pit-box count-in marks are the reference consumer). A new fire taking the bus cancels the hold; it re-arms at that fire's finish. `stopAll` and the session-change clear cancel it too.
  - `settle:` (optional) — `{ pending, maxWaitMs, pollMs }`: wait for the data the callout reads before deciding (issue #1284). After `triggerDelay` (zero when omitted) the engine asks `pending(ctx)` — `null` when everything is known, otherwise what is missing — every `pollMs` until it answers `null` or `maxWaitMs` has passed since the event, then runs `where:` ONCE and fires as usual; a fire that reaches the deadline still goes ahead and the engine logs `proceeding without <reason>` at info. So the callout must be able to speak with the data missing: make each value that can be unknown a nullable snapshot field and its clause `optional` (or branch on a condition and say it is unknown), rather than nulling the whole snapshot. Shares the `triggerDelay` timer, so a newer event, a disable and a redefinition cancel the wait. Reach for it instead of guessing a longer `triggerDelay` when the delay was standing in for "the sim has reported X"; the session-start and race-start briefs are the reference (3 s first look, 10 s cap, 500 ms polls). `pending` gets the envelope's telemetry, not live state — read live data through the family's own resolver.
  - `focusOwner:` (optional) — marks the scenario as belonging to an exclusive-focus owner. The engine's `acquireFocus(bus, ownerId, floorWeight)` / `releaseFocus(bus, ownerId)` raise a per-bus weight floor: while held, only fires with `weight` at or above the floor — or the owner's own (`focusOwner === ownerId`) — play; everything else defers (if `queueable`) or drops. Set the floor to the band you want to admit (e.g. `WEIGHT.SAFETY`). While the floor is held the drain skips the waiting fires below it, which keep their places, and plays the first one the floor admits; releasing it drains the queue (#1185). A heavier non-queueable fire that was waiting for a line in flight now waits for the floor like any other, bounded by its max wait — the pit-status nags are the case, and their `speakGate` re-checks how the car is parked when they speak.
  - `frame:` — omit it. The engine wraps every callout whose body expanded to at least one clip in the walkie-talkie frame (`DEFAULT_FRAME`, `"radio"`: open tick, ambience bed, close tick — defined by the voice's script, not by code); `frame: NO_FRAME` (`"none"`) is for the four terse families whose cadence would have the beeps drown the words (pit-box count-in, pit-status nags, corner names, spotter), each stating why beside it. **A sequence never spells the frame** — the former `["@pit-crew.radio-open", …, "@pit-crew.radio-close"]` includes are gone (a sequence carrying them would be framed twice), and **an empty body gets no frame**: a body-wrapping `if` a pack writes for itself produces no bare ticks when it expands to nothing (a contract's `speakGate` never gets that far — it drops the fire before any bus take). The user's Radio beeps / Pit ambience switches are applied inside the frame by position — to its steps, before any expands, so a switched-off step can never abort a callout — and every clip a frame plays rides the SFX channel, a pack's own beep included. The frame expands before the body (so a frame that aborts can never leave a body step's side effect standing — no body *condition* commits anything, since a registered condition must be pure since #1138, when the furled marking moved into its contract's `speakGate`; a var *resolver* may still keep a tracker, which is why the frame goes first — the position readout's intro was that example until #1138, and now only STASHES the lead-in decision it makes, for its contract's `speakGate` to commit, so a readout refused there records nothing for the next one), and its ops are tagged with their side, which is how the #758 resume re-keys with the frame's open rather than with a tick looked up by path.
  - `when: { event, where: (e) => …predicate… }`
  - **`where:` may stash what a resolver will read; it never claims (#1137).** It runs at event arrival, and an expansion that aborts afterwards leaves whatever it wrote behind — so a cooldown stamp, a per-lap latch or a spoken-marker set there is burned for a callout nobody heard, and the next real one goes silent. Split the check: the pure half stays in `where:` (`canAnnouncePosition()`, `canClaimGapCallout()`, `qualifyingLatchAllows()`) so a fire outside the cadence is still dropped cheaply at event time, and the `tryClaim…` half moves into `speakGate.admit`, which only a fire that goes on to play ever reaches. A **stash** is the deliberate exception and stays put — the incident point count, the two opponent-number pending values, the furled reset on a fresh raised episode, and the qualifying snapshot the `where:` approved (#1138: the gate latches THAT lap, so a fire parked while the driver crosses S/F cannot latch the next lap and silence its first incident) — because it is read by a var resolver, or by the gate, during the very fire the `where:` approved, and nothing downstream is silenced by one an abort left behind. **A stash the GATE reads is keyed per fire, never held in one slot**: approvals and gates do not alternate, so a fire waiting in the bus's queue can be overtaken by a later one whose `where:` also approved and which the engine then DROPS, and a stash held in one variable hands that dropped fire's state to the waiting one — the qualifying snapshot is keyed by the event envelope `where:` received and read back through `ctx.event`, the position readout's intro decision by the fire's own `ScenarioContext`. Note what the queued replay changed here: it never re-runs `where:`, which is why a claim there was always the wrong shape rather than a reason to keep it there. **One contract yielding to another is decided at `where:` too, through a stash, never by racing for the bus** (#1211): the qualifying lap-invalidation `where:` records the timestamp of the `incident.scored` it approved, and the incident contracts' `where:` refuses an `incident.occurred` with that timestamp — the same translator flush — before its own points stash write. Publication order used to decide it on an idle bus, which stopped protecting anything once both lines queued. The accepted cost: a yielded burst stays silent if the approved line later leaves the queue without playing (its max wait, the cap) or has no script entry.
  - No `sequence:` — a contract has none; its body is the script entry in step 4b. (The `Scenario` type that carries one is an engine primitive for the interpreter's tests, not a shape the catalog registers.)
- **Missing → skip the whole callout (issue #835).** At fire time every clip-producing step is checked against the manifest for the active voice; a required step that resolves to nothing (missing clip, null var, empty pool) aborts the entire callout — never a fragment, no cooldown stamped, and never cancelling an in-flight callout (the abort is decided before preemption). Wrap a genuinely-optional clause in `{ optional: [steps…] }` so it skips locally instead — use it only for self-contained add-on sentences (the setup-warning nudge, name greetings, the pit-speed / temperature / grid-position clauses, the incident point-count clause), never for a step mid-sentence.
- Export `<FAMILY>_CONTRACTS: readonly ScenarioContract[]`, plus `<FAMILY>_SCENARIO_IDS` and `<FAMILY>_CLIP_SOURCES: readonly { group, base }[]` — a **literal** list of the `(group, base)` sources its script addresses, since nothing derives it; the reference voice must ship a clip for each and its script must reference exactly that set (`[]` for a family that speaks only through var resolvers, as `lap-time.ts` does).
  - **Snapshot-driven variation (issue #558):** for a family whose lone contract reads a runtime resolver in its `where:` predicate — or whose vocabulary does — export `build<Family>Contract(getSnapshot)` and let `register<Family>Vocabulary(engine, getSnapshot)` close over the same resolver, **instead of** a static `<FAMILY>_CONTRACTS` array — the contract is materialized at wiring time inside `registerPitCrew()` — while still exporting `<FAMILY>_SCENARIO_IDS` / `<FAMILY>_CLIP_SOURCES`. See `session-start.ts`, `lap-time.ts` or `corner-name.ts` for the precedent; `readback.ts` is the same idea for a two-contract family.

### 4b. The script entry in the voice config

In `packages/audio-assets/configs/default.voice.json`, beside the `groups` you extended in step 3 — the same file, on purpose — add:

- Reference the clips as `pool:<group>/<base>` — the `(group, base)` from step 3, spelled in the step itself; there is nothing to declare. Give a pool a NAME under `pools` (`"<name>": { "group": "<group>", "base": "<base>", "comment": "…" }`) only when the name carries a decision — an alias onto a different group, or a second line that must not share a no-repeat tracker with the first — and then put the reason in its `comment`. A name that merely restates the path is not written.
- Under `scenarios`, keyed by the contract id:

```json
"pit-crew.<family>-<subject>": {
  "comment": "What it says and when — one or two sentences; this is the reference's text.",
  "test": "Harness → <Category> → <Button label>. In-sim: how to provoke it.",
  "sequence": ["pool:<group>/<base>"]
}
```

`comment` and `test` are **required in every first-party voice's script** (the completeness test insists), and the reference voice's are the source text of the published Callouts page (`/docs/voice-packs/reference/callouts/` — **Says** and **Hear it** under each callout, beside the contract's `description`; #1066), not decoration; `test` names the harness button from step 8, so keep the label in sync. A callout the reference voice deliberately does not speak carries `"skip": true` instead of a `sequence` — identical behaviour to an absent entry, but self-documenting and accepted by the completeness test as a declaration rather than an oversight. A `frame` override (`"none"`, or another frame the script defines) is the exception, not the rule.

The step grammar is the closure DSL's, serialised: `"pool:<group>/<base>"` (or `"pool:<name>"` for a named alias) / `{ pool, noRepeat? }`, `"{{var}}"` / `{ var }`, `{ clip }`, `{ pause }` / `"pause:<ms>"`, `{ include: "<fragment>" }` / `"@<fragment>"` (a sub-sequence the SAME script defines under `fragments`, inlined at compile time — #1065; cycles refused, an undefined name skips the entry), `{ optional: […] }`, `{ connector }`, `{ ambient }`, and the two branching forms — `{ "if": "<cond>", "then": […], "else": […] }` and `{ "case": "<case>", "of": { "<key>": […], "default": […] } }`. Use `if` for a binary choice and `case` for a multi-way one. Reach for a **fragment** only where a sub-sequence is genuinely shared between scenarios — the reference voice's script has two, `readback-body` (the entry and exit readbacks) and `gap-readout` (the gap family) — never to hide complexity inside one callout; `case` absorbed that job. Three rules govern what goes in one:

- **The only operator is `!`.** No `and`, no `or`, no comparisons, no field access, no arithmetic. A script needing `a && b` gets a named condition registered for it in 4a. This is what stops the format sliding into a predicate language one convenience at a time; every future addition to the grammar has to argue against it explicitly.
- **A lookup is a var; a condition is a choice.** A table over a closed set (the fifteen tire patterns, a session type) is not a script decision — it is a `case` with a declared key set, or a var, and the mapping stays in the script: with `case` a pack can collapse several keys onto one line or map a key to `[]` and stay silent, which a var returning the clip directly would take away. Writing the same thing as eighteen `if` blocks is the mechanical translation, and it is wrong.
- **A fragment may not be optional; a clause may.** `{ optional }` swallows a step that resolves to nothing, and whether that is correct depends on what is left behind: drop the number from "you're now P4" and the speech is broken or false; drop the tire clause from a readback and it is shorter and still true. So a whole clause may carry `{ optional }` or a `"default": []` branch, a sentence fragment never. (The lap-time minute is the boundary case, and it is a pack's *register* choice rather than a correctness rule — see the #1064 entry in the examples file.)

Then regenerate the artifact and commit it with the config — in a Claude Code session the post-edit hook already ran the extraction when the config was saved, so the first command below is for a run outside one (or after a hook failure) — and, once the package is built, the website's reference, which reads the reference voice's script and the contract you added, and the voice's catalog entry, because the script ships inside the pack archive (step 9 has the order):

```bash
pnpm generate:callout-scripts      # configs/*.voice.json → voice/<voice-id>/callouts.json (the post-edit hook runs this in a Claude session)
pnpm generate:pack-reference       # → packages/website/src/data/pack-reference.json, off the BUILT audio-scenarios dist
pnpm --filter @iracedeck/audio-assets pack:voice <pack-id>   # → packages/audio-assets/catalog/<pack-id>.json (iRaceDeck's own pack is `default`): callouts.json travels inside the archive, so a changed script is a changed archive, and the publish step refuses an archive whose bytes differ from the committed entry — a pack whose version is already published needs a `version` bump first (audio-assets CLAUDE.md, "Voice packs")
```

Other voices script the same ids in their own words, or leave them out — absent means skipped, and an unknown pool, var, condition, case key, include or frame skips that one callout for that voice with ONE warn naming the reference (never an exception, never a half-played line). Only first-party voices — every voice in audio-assets' `VOICE_PACKS` — are held to completeness; a third-party pack is not.

### 5. Declare the opt-in in the registry

In `packages/callout-settings/src/families/<family>.ts` — since #1350 the only place a `calloutEnabled*` key is declared (package overview: `packages/callout-settings/CLAUDE.md`):
- Add an entry to the family's `callouts`, keyed by the callout id `audio-scenarios` uses for it: `"<id>": { key: "calloutEnabled<Family><Subject>", label: "<checkbox label>" }`. Entries are in PI order, so put it where its checkbox should render, and put any rationale on the entry as a comment.
- Leave `default` out: a callout ships on. Write `default: false` only for one that deliberately ships off (six of the fuel countdown's counts are the precedent); `.claude/rules/global-settings.md` has the polarity rationale.
- A **new family** is a new file exporting `<FAMILY>_CALLOUTS = defineCalloutFamily({ id, callouts })`, re-exported from `src/index.ts`, and placed in one group's `families` in `CALLOUT_PI_GROUPS` (`src/pi-groups.ts`). Placing it there is what registers it: `CALLOUT_FAMILIES` and `CalloutSettingKey` are derived from the groups, and a test fails on a placed family the index does not export. A new heading is a new group there plus its `calloutGroupItem('<group-id>')` call in `packages/pi-components/partials/race-engineer-callouts.ejs`, which places each heading by hand among the card's non-callout items (ranges, thresholds) and nothing else of the opt-ins; its tests fail on a registry key it does not render. A scenario-backed family also gets a row in the `GATED` table of `audio-scenarios`' `src/catalog/pit-crew/callout-settings-coverage.test.ts`, which holds its `SCENARIO_ID_TO_*` map to the family in both directions; a family gated any other way is named in that test's comment instead.

That is the whole opt-in. The `GlobalSettingsSchema` field (deck-core's `calloutEnabledFields`, with the shared coercion and `.default(calloutDefault(key))`), the checkbox row in the settings window's Callouts card (`default="true"` exactly where the callout ships on), the id type and the runtime lookup all derive from the entry, and `PitCrewDeps` gains no key. There is no Zod field, no EJS row and no wiring closure to write, and nothing in `race-engineer-wiring` to touch: `PitCrewDeps.isCalloutEnabled` is one live-reading lookup for every family, filled there with deck-core's `isCalloutEnabled`, so a mid-session toggle takes effect on the next event without re-registering scenarios. Never rename or drop a key, nor change a default, without a migration: deck-core's frozen baseline (`callout-settings-baseline.test.ts`) fails on either.

### 6. Family wiring

In `packages/audio-scenarios/src/catalog/pit-crew/index.ts`, for a **new family** (an existing family's id type and gate already cover a new entry):
- Derive the id type from the registry rather than writing a union: `export type <Family>CalloutId = CalloutIdOf<typeof <FAMILY>_CALLOUTS>`.
- Add a `SCENARIO_ID_TO_<FAMILY>_ID: Record<string, <Family>CalloutId>` map covering every scenario id in the family — in `index.ts` or in the family's own file, beside its contracts, as its neighbours do. Adding a callout to an existing family adds its line here too; the coverage test fails until every id of the family is reached.
- Inside `registerPitCrew`, make the family's gate with `const get<Family>CalloutEnabled = enabledIn(<FAMILY>_CALLOUTS)` beside the others. It resolves the id to its key through the registry and asks the one `isCalloutEnabled` dependency, so it adds no `PitCrewDeps` key, no `DEFAULT_DEPS` entry and nothing at any call site.
- Wrap the family's contracts with `wrapWithMaster(wrapCalloutScenario(c, …))` in an `engine.defineContract(...)` registration loop. The family's `register<Family>Vocabulary(engine)` is called beside the other families' vocabulary registrations, before every loop, so the first `setScripts` compile sees every name.

A `PitCrewDeps` key of any other kind — a snapshot resolver, a live-position read — is still added by hand (issue #1052): the key on `PitCrewDeps`, its default in `DEFAULT_DEPS` and the matching line in the destructure at the top of `registerPitCrew`. All three: the `satisfies` clause catches a key with no default, but nothing checks the destructure — a missing one surfaces as "cannot find name" wherever you use it. **Placement is irrelevant** — the deps are keyed, so position carries no meaning. Such a key is then built in `packages/race-engineer-wiring/src/pit-crew-deps.ts`: `buildPitCrewDeps` returns `Required<PitCrewDeps>`, so `pnpm typecheck` fails until it is, and nothing is left to `DEFAULT_DEPS` in the plugins or the harness. A plugin-side cache an engine `where:` clause reads is subscribed in `subscribeRaceEngineerCaches` (`caches.ts`), which runs before `registerPitCrew`.

### 7. Update test fixtures

- **A family test that switches callouts off** passes `isCalloutEnabled: familyGate(<FAMILY>_CALLOUTS, (id) => …)` from `src/catalog/pit-crew/callout-gate.test-util.ts`, which answers per callout id and leaves every other family's keys on.
- **Call sites of `registerPitCrew(...)` need no edit when you add a `PitCrewDeps` key** (issue #1052) — and a callout adds none — with one deliberate exception: the deps of the plugins and the scenario harness come from `buildPitCrewDeps` through `wireRaceEngineer`, which must build every key (step 6). The harness's only explicit keys are its three snapshot overrides (`packages/scenario-harness/src/race-engineer-overrides.ts`), which win over the built ones. Every other call site — the tests — names what it passes, so a new `PitCrewDeps` key is simply absent from the ones that don't want it and takes its `DEFAULT_DEPS` entry. Adding a key cannot disturb an existing call site.
- **A new contract with no script entry fails `bundled-scripts.test.ts`** (audio-scenarios), and an edited config with a stale artifact fails `callout-scripts.test.ts` (audio-assets) — both name what is missing. Family tests that fire a scripted contract load the real artifact (`import defaultScript from "@iracedeck/audio-assets/voice/default/callouts.json" with { type: "json" }`) and hand it to `engine.setScripts(new Map([[voice, script]]))` AFTER `registerPitCrew`, as the plugins do — a contract with no script is silent, not unframed, so a test that forgets the artifact sees nothing fire.

  This used to be the most dangerous step on the page, and it is worth knowing why so nobody reinstates it. The parameters were positional and nearly all shared a shape, so inserting one shifted every later argument at every call site — and the result still type-checked, because a value landing in the wrong slot was usually assignable to it. It went wrong twice on 2026-08-28: once loudly, once silently and green. If you find surviving advice anywhere about adding `undefined` "at the new position" or keeping the masters last, it predates #1052 and is now wrong.

### 8. Scenario-harness shortcut

For QA convenience, add a button to `packages/scenario-harness/src/scenario-shortcuts.ts` so the harness UI can fire the event directly (bypassing the diff). Pick a `category` string — group related shortcuts under the same category for the UI. The script entry's `test` line (step 4b) names this button as `Harness → <Category> → <Label>`, so the two are written together.

If the bus event itself is **new**, also add an entry to `packages/scenario-harness/src/event-names.ts`. The compile-time completeness check forces this — `pnpm build` will fail otherwise.

**Bypassing the diff is what makes that button one click, and it is also its limit.** A published event reaches the scenario whatever the translator would have decided, so such a shortcut can audition a callout's *content* but never the translator's decision to emit it at all. When that decision is the thing under test, give the shortcut a `telemetrySequence` instead of an `event`: an ordered list of `{ patch, holdMs }` steps the UI applies through `/api/telemetry`, holding between them, with no `bus.publish` anywhere. The two shapes are a union (`BusEventShortcut | TelemetrySequenceShortcut`), so a shortcut carries one or the other and never neither — a button that drives nothing looks like a broken scenario rather than a broken button. `flag-caution-restart` (#1127) is the reference: it replays, in order and with only the holds compressed, the `SessionFlags` of a caution and restart captured at an oval (`local/telemetry-watch-20260917-191825-092.jsonl`) — caution waving, static caution, one to green, green held, the restart as `Green | Servicible | StartGo`, then `StartHidden` in place of `StartGo`, then no flag shown — and what it exists to demonstrate is the SILENCE where "Yellow cleared." used to land three seconds into the restart. Model such a sequence on a capture, not on what the flags ought to be: the button's first version raised a bare `Green` for the restart, which the measured restarts never did, so it played a green-flag line the sim does not produce there. Two obligations come with the shape — the sequence must end by restoring a sane `SessionFlags` so the harness is not left stuck under a flag, and its `description` must say which presets the promised lines need and that the mock SDK has to be CONNECTED, since a disconnected translator sees no ticks and the button is then silent for the wrong reason.

**A shortcut publishing an event whose contract reads `getOvertakeGate` must be wrapped in `atRacingSpeed(...)`** (#1349) — today `overtake.completed`, `overtake.lost`, `gap.trendChanged` and `gap.thresholdCrossed`. The harness runs the plugins' own wiring, so that gate reads live telemetry (on track, at least 50 km/h, off pit road, nobody alongside, no incident in the last 10 s) and refuses on the mock's boot telemetry. The wrap prepends the `AT_RACING_SPEED` step, whose `tick: true` has `/api/telemetry` tick the translator before the publish whatever the tick rate, and declares the `sdk-connected` precondition, so a press while the mock SDK is disconnected is refused with the reason instead of going silent. `overtake-gate-shortcuts.test.ts` derives the set by replaying every shortcut's publish at the catalog registered with a spy gate, so a new contract that reads the gate, or a new shortcut left unwrapped, fails there until the two agree; a new gated event's template in `event-names.ts` takes `OVERTAKE_GATE_NOTE`, which the same file checks. The test also presses every shortcut on its own and after an overtake button, and fails when the car left on track at racing speed changes what another shortcut publishes: a shortcut whose behaviour depends on `IsOnTrack`, `Speed` or `PlayerTrackSurface` sets them in its own patch.

Manual: trigger from the scenario harness (no iRacing required), then in iRacing for the real-telemetry path. Toggle the PI checkbox mid-session to confirm the live-read path silences future fires without cutting an in-flight clip.

### Auditioning a voice change in the sim (#1143, #1214)

Hearing a changed clip or wording in iRacing — as against in the harness — needs the plugin to play a tree you can edit, and since #1034 stage 3 the one it plays is the managed copy in `%LOCALAPPDATA%\iRaceDeck\Race Engineer\Voices\default`, which the launch step keeps matching the published catalog. So opt the machine into development voice mode once, and from then on every build of every worktree stages the voice and points the plugin at it:

```bash
setx IRACEDECK_DEV_VOICES 1   # once per machine, then open a new terminal
pnpm build                    # once, with the deck host STOPPED; then start the host
# edit clips, or configs/<voice-id>.voice.json
pnpm stage:voices             # restage only, no plugin build, so a running host is fine
# press "Rescan voices" in iRaceDeck Settings, then drive
pnpm dev:voices off           # before testing the real download path in this worktree; `auto` hands it back to the variable
```

Restage with `pnpm stage:voices` while the host runs, not `pnpm build`: a voice edit changes the stage task's hash, so `pnpm build` reruns all three plugin builds for nothing a running host would load before its next start, while the restage is all **Rescan voices** needs. (A running host no longer fails those builds — since #1258 a loaded native addon is moved aside and rebuilt.) `pnpm build` is for a code change or a mode switch — stop the host, build, then start it. Without the variable, `pnpm dev:voices on` turns the mode on for one worktree and the same loop applies. What plays is the bytes the packer stages — the radio-filtered clips a user would download — never the raw source tree, and the plugin never installs over what that root provides, so `default` stops being overwritten under you. Three things say the mode is on: `[dev-voices] development voice root on via <source>: <root>` in each plugin's build output, `Voice packs: development root active`, logged once per start, and the Installed Voices row, which badges *Development build* and names the directory instead of offering Remove. The build stages with `--stage-only`, which writes no archive and never touches the committed `catalog/default.json` — the release contract; the flagless `pack:voice` line in the checklist above is still what a change destined for a release needs, and it belongs in the same commit as the clips. A stage takes about 5 s: the audio-assets build already runs every clip through ffmpeg into the processed-clip cache on every build, with or without the mode, so the stage only copies. Turn the mode off before testing the real download path: `switch-test-env` and the `relink:*` scripts leave the marker alone by design, so nothing else will. Full mechanics — the resolution table, turbo hashing, and the guards that keep it build-time only — in `@.claude/rules/platform-feature-flags.md`.

A pack author auditions through the harness above rather than through the development root — a third-party pack sits in the packs folder under its own id, where nothing overwrites it, so the root buys them nothing — and there is deliberately no in-plugin tooling for it (#1066: authors are assumed to have cloned the repo; the per-callout Play button was dropped). The harness lists a sideloaded pack's voices, by composite id (`<pack id>::<voice id>`), beside `default` when `IRACEDECK_VOICE_PACKS_PATH` names the packs folder, and `pnpm lint:pack <packDir>` (repo root, after `pnpm build`) says loudly what the plugin would only skip quietly — the one place a pack is told anything, since skip-by-default is the design. Send authors to the tutorial (`/docs/voice-packs/first-pack/`), which walks both, rather than restating them.

## Why these rules exist

- **Live-read closures** — a toggle taking effect mid-session is a hard requirement; capturing the value at registration time means re-registering scenarios on every settings change, which the engine can't safely do without dropping in-flight audio.
- **Per-subject opt-in keys** — a future addition gets `default: true` for every existing user via Zod's `.passthrough()`. Array storage and bitmask encodings break this property; per-item booleans don't (`.claude/rules/global-settings.md`).
- **Family preemption** — rapid same-family transitions (a static yellow turning waving, TooFarLeft→TooFarRight while parking, MostlyDry→VeryLightlyWet→LightlyWet during a downpour) should never play back-to-back stale callouts. Sharing the `family:` string lets the engine cancel the older fire cleanly.
- **The contract/script split withholds scheduling, pacing and triggers from packs on purpose** (#1064) — with community packs dropped in a folder, a pack that demotes a safety flag below chatter, drops its `family`, or zeroes a `cooldown` produces behaviour that reads as a plugin bug; letting packs bind their own triggers would need a predicate language over telemetry, a public bus contract and a sandbox — five times the work, aimed at the half that does not vary by voice. Phrasing varies by voice; the moment does not.
- **Scripts can only name, never compose** — the `!`-only rule keeps the grammar a mapping rather than a language, so every branch a pack can take is a name the code declared with a description, and the generated reference (#1066) and the completeness test can both be built from `vocabulary()` instead of from a hand-kept list.
- **Every first-party voice's script is tested for completeness, a third-party one is not** — silence is the right failure for a pack that omits a callout ("a pack is never punished for what it does not say") and the wrong one for ours, where an omitted JSON key would otherwise be invisible until a user asked why the engineer stopped mentioning the red flag.
- **No test lists every callout key** (#1350) — a test that needs a whole `GlobalSettings` value parses its literal through `GlobalSettingsSchema` (deck-core's `simhub-service.test.ts` reaches the real schema with `vi.importActual` beside its mocked lookup), so every opt-in arrives at its default and a new callout needs no fixture edit. A hand-written exhaustive literal would bring that edit back, and a missing key there fails `pnpm typecheck` (tsc), not `pnpm test` (vitest's esbuild strips types).
- **Pre-guard emissions need a non-transient discriminator** — anything published before the `IsReplayPlaying` guard in `translator.ts` (the `session.changed` paths, `driver.firstOnTrack`, the #829 `diffStartCountdown`, and the #1203 `diffReplayLaps`) survives replay-mode ticks by design, which is correct for live session transitions (#568) and for callouts that must reach an out-of-car driver (#829), but lets standalone replay viewing leak callouts unless the emission is also gated on a signal that distinguishes "live, transiently in replay mode" from "watching a replay." Use `isReplayOnlySession(sessionInfo)` — a read on `WeekendInfo.SimMode === "replay"` (issue #604). Do not gate on `IsReplayPlaying` — that's the transient #568 is explicitly bypassing. A pre-guard diff that keeps per-tick state must also have that state preserved by `wipeStateForReplay` (the #771/#829 preserved cluster), or the replay edges reset it mid-episode. `diffReplayLaps` also gates on `replayOnlySession`, but is the exception to the `IsReplayPlaying` and preserved-state points, because it publishes no callout: it runs pre-guard to SEE the ticks it must not record, and its own gate (`IsReplayPlaying !== true`, not `replayOnlySession`, `SessionNum >= 0`, a readable frame) marks it unseeded on every other tick and re-seeds silently on the next eligible one — so its state sits in `wipeStateForReplay`'s wiped set on purpose.
