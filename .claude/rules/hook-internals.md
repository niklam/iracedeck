# Claude Code hooks — internals

How the hook guards decide, for whoever edits `scripts/claude-hooks/`. The policy — which guards exist and why — is `@.claude/rules/hooks.md`, which every session loads; this file holds the mechanics that only matter when changing them (moved out of it in #1465 to keep the always-loaded set inside its budget).

## The merge gate (`gh pr merge`)

`rules-bash.mjs` denies more than one merge per command, judged on its own words, and otherwise denies unless all of these hold: the PR is OPEN; the method is `--squash` (or `--merge` for a `release/*` head); `reviewDecision` is APPROVED; every rollup entry is green (it fails closed on unknown node types); the merge state is not BLOCKED or DIRTY; and CodeRabbit has reviewed the current head. `--admin` skips only the review checks.

**The repository comes first (#1393, #1534).** The gate can judge only a `niklam/iracedeck` PR, and reading this repository's PR of the same number is how a merge aimed elsewhere once passed on checks nobody ran there. The gate reads before the command runs, so it fails closed on anything that could change what gh resolves the merge to after that read:

- **A flag between `gh` and `merge`** is refused: `--repo` / `-R` is a flag of `gh pr` itself, which cobra takes ahead of the subcommand and even ahead of `pr`, where the merge shape never matched and the merge ran ungated.
- **Nothing may come ahead of the merge but a plain `cd <dir>`** (`cdsAhead` in `shell-lexer.mjs`, which also gives the directory the read runs in, from those `cd`s alone), **and nothing may run beside it**: a pipe or a background `&` anywhere in the command is refused, since a pipeline runs each command in its own subshell (`cd x | gh pr merge` never moves gh) and a concurrent `git checkout` or `git remote set-url` can win the race against gh's own reads. An enumerating parser cannot keep up with every way a command reaches gh's environment or checkout — an exported variable assigned again, `export A=1 GH_REPO=…`, `declare -gx`, `set -a`, PowerShell's `${env:…}`, `Set-Item Env:` or `SetEnvironmentVariable`, a `pushd`, a subshell `cd`, a branch switch, `gh repo set-default` — so a merge runs as its own command.
- **The merge's own prefix is an allow-list** (`plainMergePrefix`): the wrappers `!`, `command`, `env`, `exec`, `nohup` and `time` without options of their own, `timeout <duration>`, and assignments of any variable but gh's and git's (`GH_*`, `GIT_*`, compared in any case because Windows hands gh its environment case-blind), `GH_REPO=<owner/repo>` aside. So `GH_HOST` (which moves a bare `owner/repo` to another host), `GIT_DIR`, `env -C<dir>` in any spelling, and `env -i` / `env -u GH_REPO`, which drop a `GH_REPO` the gate's own read still sees, are refused.

Then, before any gh read, it takes the repository in gh's own order with the post-hook's helpers (`mergeRepo`, `assignedGhRepo` in `rules-post.mjs`): a PR URL, then `--repo` / `-R` (separate, `=`, attached, or combined with other short flags as pflag reads them, `-dR owner/repo`), then the prefix's `GH_REPO`; an empty value is none, as gh reads it. Another repository is refused, and so is a value it cannot read (a `$VAR`, a substitution, a flag with no value). It reads the PR in the directory the merge runs in, with a named repository passed as `GH_REPO`, and refuses unless the URL gh returns is `niklam/iracedeck`, which covers a followed `cd` into another repository's checkout and a `GH_REPO` or `GH_HOST` the hook process inherited. The summary comment and the base timeline are then read of that confirmed repository, passed as `GH_REPO`, never of whatever the session's checkout resolves `{owner}/{repo}` to: another repository's PR of the same number with no base events once read as "base unmoved". Not covered: a variable exported by the Bash tool's shell profile but absent from the hook's own environment, which the hook cannot see; a `gh alias` for `pr merge`; and a merge through `gh api`, which no rule reads.

**A head without a review object of its own.** Thread replies, which GitHub files as empty COMMENTED reviews, are not reviews. For such a head a back-merge is refused, and the merge must be pinned with the full `--match-head-commit <head>` before anything is read; then one of two things stands in for the review.

**CodeRabbit's summary comment** (#1386), which a clean incremental review edits instead of filing a review object, counts as the head's review when:

- exactly one summary exists, authored and last edited by the Bot `coderabbitai`, and every edit in its history (`userContentEdits`: at most 100, complete, newest first, the newest being the body read) was made by that Bot;
- it is not minimized, the PR has at most 100 comments, and there is no other auto-generated block (a `rate limited` one refuses);
- each statement is read only from its own block: one recent-review block whose one range line ends at the head and says no actionable comments, and exactly one `change_assessment_commit` and one `final_review_risk_coverage` (`kind: reviewed`, `sourceCommitId` equal to `coveredCommitId`) marker naming that same commit;
- the range's **start** is shown reviewed too: the newest review object's commit, a clean pure-rebase replay of it, or the range end of an earlier version of the same comment, walked back through its edit history at most 10 steps.

A base retargeted or force-pushed since the newest review object refuses before the summary is used.

**Otherwise a pure rebase** (#1307) of the commit CodeRabbit last saw — a passing summary's commit when the comment was written after the newest review object, else that object's; a summary that fails any condition, a rate-limited one included, is never a replay start. The reviewed change replayed onto the head's base must give the head's exact tree, and every file the replay reports as conflicted gets a line check that at best earns an **ask**. A follow-up push, a base retargeted or force-pushed since the newest review object, and criss-cross history are refused on that path.

A refusal names the condition that failed, so "rate limited, wait" reads differently from "not reviewed, ask `@coderabbitai review`".

Where the code lives: `lib.mjs`'s `replayRebase` (the replay, with `git merge-tree -X no-renames`) and `baseChangedSince`, the pure `change-signature.mjs` for conflicted files, `lib.mjs`'s `prComments` and the pure `coderabbit-summary.mjs` (`readSummary`, tested against verbatim bodies in `__fixtures__/coderabbit-summary/`), and `rules-bash.mjs`'s `unreviewedHeadVerdict`. `scripts/CLAUDE.md` has the module map.

**The replay writes objects.** It is the one path `IRACEDECK_HOOKS_DRY_RUN=1` does not make read-only: it writes the replay's trees, and any reviewed commit the checkout lacks, fetched from `origin` by sha without automatic maintenance, to the shared object store — never a ref or `FETCH_HEAD`.

## The Elgato manifest `Debug` guard

`git commit` is denied, naming `pnpm debug:plugin off`, when it would record the Elgato `manifest.json` with a `Debug` key in its `Nodejs` block (#1338). The manifest is read from the staged copy for a plain commit, from the working copy for `-a`, a pathspec or a chained `git add` that selects it, and from both when the selection is only decided at run time; a manifest dirty with the key but left out of the commit passes. `pack:plugin` and `manifest-no-debug.test.mjs` are the other two guards.

## What a commit records (#1594)

Both commit rules judge each `git commit` at command position on its own, in the tree its own `cd`s and `-C` land in, and read the files it records from that commit's words, located in the trusted mask and taken raw at the same index (`commitSelection`, `manifestSources`). Those words run to where the command ends (`commandEnd`), so the `)` or backtick closing the subshell or substitution it runs in is no part of its last word, while a `$( … )` among its own arguments stays inside it; and each `git add` chained ahead of it is read in its own directory (`addsAhead`), so `cd docs && git add superpowers/specs/x.md && cd .. && git commit` still sees the spec. A mention never decides the selection: until #1594 the spec rule took its arguments from the first `commit` anywhere in the text, so `echo "commit -- notes.md" && git commit -m x` read as a pathspec commit of `notes.md`, and a quoted `-a` or `git add` counted. Operands, with or without `--`, are a pathspec commit from the working copy (`-i` adds the plain selection); a parsed `-a` / `--all` takes the modified files too; otherwise the staged files plus those a `git add` chained ahead of the commit selects. A redirection is the shell's whatever its target expands to (`2>$null`), and an abbreviated long option is the one git takes it for (`--mess` is `--message`, against the option lists in `COMMIT_OPTIONS` / `ADD_OPTIONS`). A substitution or `--pathspec-from-file` on the commit or on such an add, a long option git would refuse as unknown or ambiguous, or a commit whose words cannot be lexed (a `-F - <<EOF` commit inside `$( … )`) leaves the selection unreadable, and every staged, added, modified and untracked spec is then judged from both the index and the working copy.

## Control bytes in a spec (#1466)

A push to `master` that changes only spec Markdown starts no CI run, so `scripts/no-control-bytes.test.mjs` would not see a spec until the next code push, where it would fail a change that never touched it. Two checks stand in for it at the commit. The spec-commit rule in `rules-bash.mjs` is the early message, in a Claude Code session only: it sees the Bash and PowerShell tools and nothing else, and it fails open on text it cannot read. Unlike the section check it is not forward-only, so an amendment is checked too, and one deny names the byte and any missing sections together. The guard every committer meets is `scripts/check-staged-spec-bytes.mjs`, the first step of `.husky/pre-commit`. It reads the index the commit records, so it also covers the PowerShell tool, a terminal and `git commit --only`. All three readers share `scripts/lib/control-bytes.mjs`.

## Which checkout's data a rule reads

Hooks run the scripts of the session's `CLAUDE_PROJECT_DIR`. The `pnpm --filter <pkg> <script>` rule is the one exception about *data*: it reads the package manifests of the checkout holding the session's cwd rather than always the main one (#1021). It does not follow a `cd` inside the command, so a `master` session running `cd ../ir-<n> && pnpm --filter …` is still judged by `master`'s manifests (`hooks.md` rule 5 keeps the short form).

## A shape trap fires at command position, not on a mention

`cmd()` in `shell-lexer.mjs` anchors each trap to the start of the string or of a line (after any indent), or to what follows a `|`, `;`, `&`, `(`, `)` or a backtick, with env-var prefixes, the shell keywords that open a command list (`if`, `then`, `do`, `else`, `elif`, `while`, `until`, `!`, `{`) and the wrappers `time`, `command`, `exec`, `env`, `nohup`, `timeout` and `xargs` with their own options allowed in between (#1307: `if …; then gh pr merge …` used to pass every trap unchecked).

A boundary counts only where the shell sees one (#1321): `maskInert` is one recursive lexer that blanks the inert text — single-quoted and `$'…'` text, double-quoted text and unquoted heredoc bodies except their substitutions, quoted-delimiter heredoc bodies, and `#` comments — at the same length, so a `|` in a grep pattern or a line of a commit message is no boundary, and a rule that reads its arguments finds the command in the masked text and reads them from the raw text at the same index (`matchAt`).

**The mask is trusted only when it is sure.** The lexer reports itself unsure whenever a construct runs off the end of the string or a `)` closes nothing — states bash refuses, so reaching one means a misread — and then the whole command is read raw, as before #1321. The mask is also set aside where live text hands a string or stdin to a shell (`bash -c`, `sh`, `eval`, `bash <<'EOF'`, `sudo`, `watch`, `trap`, `pwsh -Command`, `cmd /c` …), but since #1607 only over the top-level list element that does it (`fedSpans` in `shell-lexer.mjs`). The lexer knows where every substitution, backtick, `${ … }`, `$(( … ))`, paren group, quote, escape and heredoc body is, so it hands over a `top` text with all of them blanked, and the elements are read off that alone: they end at a newline, `;`, `&&`, `||` or lone `&` at the top level and outside every compound command (`if` … `fi`, `while`/`until`/`for`/`select` … `done`, `{` … `}`, `[[` … `]]`, counted at command position, where a newline is a boundary too, so a group opened on a later line or after `time -p` counts). A pipe ends none, nor does a newline the list goes on over (after `|`, `|&`, `&&` or `||`, past blanks, comments and heredoc bodies), so `echo '…' | bash`, a `|` with `bash` on the next line, `… | { cd x && bash; }`, `… | while …; do bash; done` and `[[ … && … ]] | bash` are one element each, and a shell inside a substitution sets aside the whole top-level element holding that substitution (`x=$(a; … | sh)`) and no more. The body of every heredoc whose `<<` is in the element goes with it; a newline that ends an element reaches over the heredoc bodies it read. `timeout` and `xargs` set nothing aside: they run a program, never shell text, and `COMMAND_LEAD` steps to the program word after them in the masked text. One `timeout` anywhere in a chain used to make the whole command raw, so a quoted `gh pr merge` in a `sed` or `grep` pattern elsewhere read as a merge, and the post-hook moved #1559's card for a PR nobody merged. One exception widens the span back to the whole command: a shell interpreter (any of those words but a `sudo` without `-s`, `-i`, `--shell` or `--login`, which runs a program; with one it hands its argument to a shell, `sudo -s "$X"`) whose own element holds it for a later element to feed — a function definition, an `exec` with a redirection or a `coproc` (`f() { bash; }; echo … | f`, `exec > >(bash); echo …`) — or that may run text another element stored — its own element expands a variable, or an element the mask stands over exports one (`export`, `declare`, `typeset`, `set -a`), defines an alias or a function, opens a descriptor with `exec`, runs `tee` or writes a file other than `/dev/null` (`x='…'; eval "$x"`, `echo '…' > f; bash f`, `f() { echo '…'; }; f | bash`, `exec 3< <(…); bash <&3`). A plain assignment is no such store, since another shell sees an unexported variable only through an expansion, which the first test catches. `view()` reports the spans as `fed` and keeps `trusted` for "the whole command is masked"; a consumer that reads one command's words (`mergeSegments`, `issueEdits`, `argTokens`) asks `trustedIn(command, a, b)` for its own range and reads raw words only where that range meets a span. The post-hook's merge trigger, `firstMerge`, follows the pre-hook's command-position rule in masked and raw text alike (CodeRabbit on PR #1632: `echo gh pr merge 1603` once read as a merge): it takes a `gh pr merge` only where `gh` is the program (`programAt`, also behind `sudo`, `nice`, `stdbuf`, `winpty` and `find -exec`): after a boundary and a `COMMAND_LEAD`, or as the first word a fed shell runs, past its options (sudo's valued ones with their value) and past a `COMMAND_LEAD` inside the string (`sudo -u me gh …`, `bash -c 'gh …'`, `bash -c 'GH_REPO=x gh …'`, `bash -c 'exec gh …'`, `fedCommandStart`), the shell word counting only where it is the program: at command position past a `COMMAND_LEAD`, behind `sudo`, `nice` or `stdbuf`, or after `find -exec` — never as an argument (`rg -t sh "gh pr merge 1603"`, `ls /bin/sh "…"`; CodeRabbit on PR #1632). It returns the merge's `index`, and the post-hook reads the repository prefix and the `cd`s ahead of it (`cwdAt`) at that merge, never at the first mention. The pre-hook is a safety gate, so it errs to deny: a doubt about the lex costs a false deny on a mention, not a missed command. That is a promise about the mask, not about what the anchor reaches. A trap word that is the FIRST word of a shell string is at command position for no pre-hook rule, raw text or not, so `bash -c 'gh pr merge 5'`, `eval "gh pr merge 5"` and `echo 'gh pr merge 5' | bash` pass the merge gate. Only a string with a separator before the trap word (`'ls; gh pr merge 5'`) is gated. The post-hook's `fedCommandStart` finds that first word for its follow-up, and nothing in the pre-hook shares it. For the same reason the one-merge backstop counts raw text, a quoted or substituted PR is refused rather than guessed, and a suppressor (`--dry-run`, `pipefail`, `MSYS_NO_PATHCONV`) counts only in live text that covers the command it excuses.

**The program word is read in any spelling (#1606).** `gh.exe pr merge`, `/usr/bin/gh …`, `"gh" …`, `g"h" …` and `& "C:\…\gh.exe" …` once reached no rule, since every trap named the bare word. So `view()` rewrites each program word at command position, in the masked and flat text alike and at the same length, to the name the shell runs. The word is decoded as bash reads it, cut to its last `/` or `\` segment, stripped of `.exe`, `.cmd`, `.bat`, `.com` or `.ps1` in any case, and lowercased unless bash finds the name only by its exact spelling (a builtin or keyword). The name is **right-aligned** in the word's own span with a space pad before it, so the anchor's `\s*` and `COMMAND_LEAD`'s `\s+` absorb the pad, a `cmd()` match covers the whole raw word and the arguments keep their indices. Only the literal directory part is blanked: a command substitution in it stays live (`$(git push …)/x.sh` reads as `$(git push …)  x.sh`), because blanking it once hid the command inside from every rule. A rule that finds a program by an unanchored regex and slices the raw text at that index takes the word's start from `programStart` instead, as the merge gate's prefix and the post-hook's merge read do. The pass repeats, so `/usr/bin/env /usr/bin/gh` is read through the wrapper. It runs before the shell-feed test, so `"bash" -c '…'` sets the mask aside over its element as bare `bash` already does. A word is an assignment only where bash takes one, an unquoted valid name with an optional index before `=` or `+=`, in the rewrite and in `COMMAND_LEAD` alike, so `"/c/a=b/gh.exe"` is a program. A word starting with `-` after a wrapper is that wrapper's option, never a program, and keeps its case. A quoted `NAME=VALUE` after `env` is the assignment env makes, written as `NAME=___` so the lead steps over it and the merge gate's prefix check still sees the name. An expanding `env` argument is judged four ways: as `gh`, as `git`, as `GH_REPO=<word>` and as `GIT_DIR=<word>`. `COMMAND_LEAD` also steps over a redirection ahead of the program (`2>/dev/null gh …`, `</dev/null gh …`). A redirect's own `&` (`2>&1`, `&>log`) is neither a command boundary nor a chain separator. The merge prefix accepts a plain redirection, though not one whose target runs a command. `$"…"` is decoded as bash's locale string. Whether env's arguments are assignments is decided by the lead's own token parse (`leadToken`, which also builds `COMMAND_LEAD`), so an option's value spelled like a wrapper (`env -u time …`) never counts as one. Where the mask is set aside the raw text is rewritten too, but only one word at a time, and only a word that stands on its own: no newline, `;`, `&`, `|`, paren or backtick in it, and every quote it opens closed within it. Anything else stays exactly as the raw text has it. A word read from inside a quoted string once swallowed the closing quote and the real commands after it, and the rewrite blanked them. A property test checks that every boundary and quote keeps its index, and that every trapped shape the raw text shows is still there. `powershellAsBash` blanks a statement-leading `&` (the call operator, not a background job) and a statement-leading `.` followed by a blank (dot-source, which runs the command the same way). It also lowercases each program word, since PowerShell resolves commands in any case. The one-merge backstop counts whichever is larger: raw mentions of `pr merge` after the program in any of these spellings (only the program's case is folded, so an upper-case mention in a body is not counted), or merges in the rewritten text. **A program word the hook cannot read**, one whose last segment expands or globs (`$GH`, `$(which gh)`, `g?`), is judged again as `gh`, as `git`, and blanked out as a wrapper that runs the words after it (`$W gh pr merge` with `W=command`) (`unreadablePrograms`, `checkBash`). Any verdict the substitution adds becomes a deny naming the word. An ask that another command of the chain raises anyway stays an ask. An unquoted expansion can split into several words, which no one-word stand-in models: `$(echo gh -R x/y) pr merge 5` once read this repository's PR through its `gh` stand-in. So when the word itself names `gh` or `git`, or the word after it is a subcommand a guard reads (`$CMD pr merge 5`), it is refused outright. Such a word may also split into a wrapper and an assignment, so it is judged as `GH_REPO=<word>` and `GIT_DIR=<word>` too, within its own command only, since an assignment reaches no later command. `$EDITOR notes.md` and `$PAGER git log` still pass.

The post-hook's triggers read the same trusted text, unanchored, so `xargs sed -i` and `nice gh pr merge` still get their follow-up; the merge trigger counts a `gh pr merge` only where `gh` is the program, as above. A rule that must fire on ANY occurrence stays unanchored and reads the raw text: `updateProjectV2Field`, the doubled-backslash heredoc and `/code-review … --fix` are the three, because there the damage is in the text the command carries rather than in the command being run.

## A `git -C <dir>` belongs to one command in a chain

**Git's global options are one fragment (#1606).** Every git trap is `git${GIT_GLOBALS}<verb>`, where `GIT_GLOBALS` in `shell-lexer.mjs` holds each option git takes before the verb: `-C`, `-c`, `--git-dir`, `--work-tree`, `--namespace`, `--config-env`, `--exec-path`, `--super-prefix`, `--attr-source` and `--list-cmds`, with their values, and `--no-pager`, `-p`, `--paginate`, `-P`, `--bare` and the pathspec, lock, advice and lazy-fetch switches without one. Each rule once hand-rolled `git\s+(-C\s+\S+\s+)?<verb>`, so `git -c user.name=x commit` passed the spec-commit deny outright, and only the worktree-remove rule took `-c`. A test in `shell-lexer.test.mjs` scans the hook modules for a git regex that skips the fragment. Every `-C` is read in order, each resolved against the one before as git does, with a quoted or escaped value taken whole (`gitPlaceAt`, `gitGlobals`). The options are read off the git program word that the lexer found at the command's own depth. A lead's option value spelled `git` (`exec -a git git -C …`) once had its options read in place of the real command's. `--git-dir`, or a `GIT_DIR` or `GIT_COMMON_DIR` that reaches the command, moves the repository away from the directory the hook judges. For a commit, `--work-tree`, `GIT_WORK_TREE`, `-c core.worktree=…` and `--config-env=core.worktree=…` (the key read in any case, as git reads it) do too: the commit then takes its files from that tree while its branch and index stay the cwd's. So does `GIT_INDEX_FILE`, which records from another index than the one `ctx.staged` reads. So does `core.worktree` reached through the environment: any `GIT_CONFIG_PARAMETERS`, or a `GIT_CONFIG_KEY_<n>` that names it or cannot be read. The key, there and in a `-c` or `--config-env`, is decoded as bash reads it (`c'ore.worktree'`), and one that expands counts, a command substitution included. An option's value takes a `$( … )` or backtick substitution whole, so `git -c x=$(echo a b) commit` is still read as a commit. None of these refuse a push, which reads neither. A reaching variable is any of these in live text ahead of the git word, in any case:

- a bash assignment with `=` or `+=`, `export`, or an `env` prefix;
- PowerShell's `$env:` or `${env:}`;
- `Set-Item`, `si`, `New-Item` or `ni` on `Env:`;
- `[Environment]::SetEnvironmentVariable`.

A `git add` ahead of the commit that moves any of these makes the commit refuse with the same message, naming the add. A `-C` that expands (`"$TARGET"`, `~/x`) counts as moving the repository too. The hook cannot resolve it, and its git reads in the literal path fail open. A rule that reads that repository's branch, index or files then denies and asks for `git -C <dir>` with the directory written out. Those rules are the commit rules, worktree add, and an integration push of the current branch; a push with a named refspec does not read the branch. Worktree remove reads only its target path, and the tag-push ask and the `diff master..` trap read only text, so they are unaffected.

`gitCwd(command, cwd, re)` in `shell-lexer.mjs` reads the `-C` off the segment (split at `&&`, `||`, `;`, `|`, newline in the trusted-masked text) that the rule's own regex matched, and finds each `cd` and `-C` in the masked text before reading its directory raw — so a `git -C ../master` quoted in a commit message moves nothing. Reading the first `-C` anywhere is how `git worktree add ../ir-N … && git -C ../ir-N log` resolved the new tree against itself, failed the repo-root lookup in a directory that did not exist yet, and was denied as "inside the repo". The `mainRoot` fallback in `pre-bash.mjs` is the second half of that fix: a dir git cannot answer for falls back to the session's repo root, never to the dir itself.

The post-hook's worktree trigger reads its target through the rule's own `worktreeAddTarget`, so the card that moves is the tree the rule judged, and a command that merely mentions the shape moves none. The rule's naming check, its spec gate and the trigger all read the issue number through `issueFromWorktreePath`, off the resolved path's last segment — the directory the add creates (#1358). An `ir-<n>` higher up is not the new tree, and reading the first one moved its card instead. The rule also requires a true sibling of the main checkout rather than only a path outside it, since `mainRoot` is the main checkout even when the add runs inside another `ir-*` worktree.

**The post-hook's board moves are for `niklam/iracedeck` only (#1527).** A card is found by issue number alone, so before this an issue filed in another repository (lint-staged/lint-staged#1865, from #1402) was added to the board and the iRaceDeck card with its number moved back to Backlog. Each trigger now settles the repository first, with `HOME_REPO` and the helpers in `rules-post.mjs`. `gh issue create` reads it off the URL gh printed — only a line that is an issue URL and nothing else, so a chain's `gh issue comment` (`…/issues/5#issuecomment-…`) or `gh issue view` output is not taken for the new issue, as the first URL anywhere once was. Each iRaceDeck issue it names must also be one GitHub created in the last ten minutes, however many creates the command ran — `gh issue edit` and `gh issue view --jq .url` print a bare URL too, while a `--web` or failed create prints none — and any whose age cannot be read is named for a hand move. An iRaceDeck URL is filed, and when none is the "add it by hand" reminder goes out, only if some create may have been home; one is not when every create was in another repository: the one its `-R` / `--repo` or a reaching `GH_REPO` names, else the checkout's (`gh repo view` in the directory it ran in, asked only then), so a foreign `--web` create is never sent to this board and a home one is never lost behind a foreign URL. `gh pr merge` takes it in gh's own order — a PR URL, then `--repo` / `-R` (`parseMerge`'s `repo`), then a `GH_REPO` that reaches the merge (its own prefix, or an `export` / `$env:` earlier in the chain; never another command's prefix or an unexported assignment) — and stops before any gh read when that names another repository or cannot be read (a bare `$VAR` included). Otherwise it reads the PR back with that repository as `GH_REPO` (gh refuses `--repo` without a PR argument), in the directory the merge ran in (the session's when the chain removed it), and checks the URL gh returns, which covers a `cd` into another checkout and an inherited `GH_REPO`. Its closing issues in other repositories are named and skipped, and its run list is asked of `niklam/iracedeck` explicitly. `git worktree add ../ir-<n>` looks the issue up from the checkout the add ran in, with an inherited `GH_REPO` cleared, and checks its URL, so an `ir-<n>` in another repository's checkout is that repository's issue. `gh issue edit … --milestone` (#1574; `-m`, `=` and attached forms, several issues, `parseIssueEdit` / `issueEdits`) takes the repository in gh's order too — an issue URL, then `-R` / `--repo`, then a reaching `GH_REPO` (`editTargets`) — and reads each issue back (`gh issue view --json url,milestone,state`) in the directory the edit ran in, since PostToolUse fires on a failed edit as well: only an open iRaceDeck issue that now has a milestone moves, Backlog to Planned. An empty value reads nothing; `--remove-milestone` reads nothing and prints one line saying the card stays and the move back is Niklas's, in the board UI. An edit is read to its own end, depth-aware, and lexed on its own, so a substitution argument (a heredoc body included) and an edit inside `$(…)` or backticks are read; one the hook still cannot read whole gets the hand line when its text names a milestone flag (`namesMilestone`) or when it named no readable issue at all (`xargs`). The post-hook sets a 70-second deadline (`IRACEDECK_POST_BASH_BUDGET_MS` in tests) under the 90-second PostToolUse timeout and memoizes the Status field for its run, so a large edit names the issues it had no time for instead of being killed with its notes lost. After a worktree start the card is already In progress, so the milestone set then reports `setBoardStatus`'s "not moving it to Planned" line; that is expected, not a failure. An edit, repository or issue the hook cannot read gets the `node -e … setBoardStatus(<n>,'Planned',…)` line to run by hand. Each skip reports one line.

**Raw board edits are refused (#1574).** The rules said "a raw `gh project item-edit` is refused" while nothing refused it, so the never-backwards table in `BOARD_MOVES` could be bypassed by hand. The pre-hook now denies `gh project item-edit` at command position; any `gh api` at command position in a command whose raw text carries the item field-value, field-clear or item-position mutation anywhere, since reading only the call's own arguments let a query through a substitution, a variable, a PowerShell here-string or `--input -` (the second read on #1574); and a REST write to a Projects v2 item (`projectsV2/…/items` with a method other than GET, or fields / `--input`, which make `gh api` POST). Deny on doubt: a command that names a mutation and runs an unrelated `gh api` is refused too. The helpers spawn `gh` directly, not through the Bash tool, so they are unaffected. Not covered, as for every anchored rule: a query read from a file (`-F query=@q.graphql`), a REST item path built from a variable (`gh api "$P" -X PATCH`) and a command inside a shell string (`bash -c "…"`).

## The integration tree and deck-linked trees (#1520, #1526)

**The worktree name.** `ir-integration` is the one non-issue name the worktree-add rule accepts, compared exactly against the resolved path's last segment, so `ir-integrations` or `ir-Integration` is still refused. It must still be a true sibling and come from a fresh `origin/master`; it skips the spec gate, since it names no issue, and the post-hook moves no card for it.

**The `integration` branch is never pushed.** Every `git push` in a chain is judged on its own (`chainCommands` in `shell-lexer.mjs`), in the tree it runs in: the session cwd moved by the `cd`s chained ahead of it, then by each of its own `git -C`s in order. It is denied when a refspec names `integration` on either side (`+`, `refs/heads/` and `heads/` allowed, and a source with a revision suffix — `integration~0`, `^0`, `@{0}` — counts as the branch), when a glob refspec could match it (`refs/heads/*`), on `--all`, `--mirror` or `--branches` (refs are shared by every worktree, so these carry it from any tree), and when it pushes the current branch (no refspec, or `HEAD` / `@`, with or without a revision suffix) while that branch is `integration` or the tree's top level is named `ir-integration`. `--dry-run` passes.

**Nothing restarts or relinks a deck host without Niklas's go.** An ask, judged per command of the chain. A build, install or clean passes in every tree, a linked one included: since #1258 a running host does not fail the build, and #1526 dropped the linked-tree build ask #1520 shipped with. A script is found whichever runner starts it (`RUNNERS` in `script-runs.mjs`): pnpm, `npm run`, `node --run`, turbo's tasks — bare, or through `pnpm turbo`, `pnpm exec` / `dlx`, `npx` or `npm exec` — `rollup`, and `node` on the root script a pnpm script wraps. Always: a `restart:*`, `watch:*`, `link:*`, `relink:*`, `unlink:*`, `start:*`, `stop:*`, `switch-test-env`, `switch-test-env:*`, `build:with-restart` or `build:stream-deck` (which restarts), the `streamdeck` CLI's `restart`, `stop`, `link` and `unlink` (with a `.cmd` / `.exe` / `.ps1` suffix or a path, and behind `pnpm`, `pnpm exec` / `dlx`, `npx` or `npm exec`), a `taskkill`, `start`, `Start-Process` or `Stop-Process` naming a host app (`StreamDeck`, `StreamDock`, `UlanziDeck`, …), and `node` on `build-with-restart.mjs`, a `link-` / `unlink-` script, `host-app.mjs start|stop` or `integration-build.mjs --restart` (its default run merges and builds without touching a host and names the linked hosts that need a restart to load the build, so it passes). Only in a linked tree: `dev:voices` and `node` on `dev-voices.mjs`, which relink the hosts linked to their tree, judged in both the cwd and the script's own tree.

**A script is judged by what it runs.** The names above are the floor, for when nothing can be read. How the hook reads what a pnpm, npm, `node --run`, turbo, `node` or rollup run, or a shell wrapper, would execute is the package-script interpreter in `script-runs.mjs` (`deckFindings`), described in `@.claude/rules/hook-script-runs.md`, which loads with that module.

**Which tree is linked.** The tree is the command's directory — the cwd moved by every chained `cd` and by the runner's own `-C` / `--dir` (pnpm), `--prefix` / `-C` (npm) or `--cwd` (turbo), never by a `git -C` — taken to its git top level, and it is linked when a host's `linkTargets()` target is inside it; a host's packaged install (no link) never matches. `test`, `typecheck`, `lint` and `format` pass under any runner: they reach no host.

**Directories, and the PowerShell tool.** Every directory a rule resolves — a `cd`, a `git -C`, a runner's `-C`, a worktree path, a pathspec — goes through `shell-lexer.mjs`'s `resolveDir`. On Windows a Git Bash `/c/…` or `/cygdrive/c/…` is the drive `C:\…`, which `path.resolve` reads as a folder `c` at the root of the current drive: `cd /c/…/master && pnpm build` was judged in a `C:\c\…` no link points into, and passed. The PowerShell tool's commands reach the same hook, marked `ctx.shell`. `checkBash` in `rules-bash.mjs` reads them through the lexer's `powershellAsBash`, which rewrites PowerShell's backtick escapes and its literal `\` at the same length so the bash lexer finds PowerShell's words and boundaries (`"C:\x\"` ends at its quote there); a `Set-Location`, `sl`, `chdir` or `cd`, any case, with an optional `-Path` / `-LiteralPath`, moves the base; `/c/…` is left to `path.resolve`, which is PowerShell's own reading; and the rules marked `bashOnly` are skipped. The post-hook is wired for both tools too, and reads a PowerShell command through the same `powershellAsBash`. The `git merge` the integration script runs is not a `git commit`, so the spec-on-a-branch guard never sees it, and a Node child process is invisible to the hooks anyway.

**Board positions.** `moveBoardItemAfter(issue, after, cwd)` in `lib.mjs` calls `updateProjectV2ItemPosition`. GitHub keeps one item order per project and a lane shows its cards in it, so `after = null` is the top of the card's lane; the anchor must be in the same lane. Cards in Testing, Done or Dropped are never moved, and `IRACEDECK_HOOKS_DRY_RUN=1` reports the move without the mutation.
