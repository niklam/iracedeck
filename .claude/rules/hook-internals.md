# Claude Code hooks — internals

How the hook guards decide, for whoever edits `scripts/claude-hooks/`. The policy — which guards exist and why — is `@.claude/rules/hooks.md`, which every session loads; this file holds the mechanics that only matter when changing them (moved out of it in #1465 to keep the always-loaded set inside its budget).

The merge gate (`gh pr merge`) has its own rule, `@.claude/rules/hook-merge-gate.md`, which loads with its modules (moved out of this file in #1659).

## The Elgato manifest `Debug` guard

`git commit` is denied, naming `pnpm debug:plugin off`, when it would record the Elgato `manifest.json` with a `Debug` key in its `Nodejs` block (#1338). The manifest is read from the staged copy for a plain commit, from the working copy for `-a`, a pathspec or a chained `git add` that selects it, and from both when the selection is only decided at run time; a manifest dirty with the key but left out of the commit passes. `pack:plugin` and `manifest-no-debug.test.mjs` are the other two guards.

## What a commit records (#1594)

Both commit rules judge each `git commit` at command position on its own, in the tree its own `cd`s and `-C` land in, and read the files it records from that commit's words, located in the trusted mask and taken raw at the same index (`commitSelection`, `manifestSources`). Those words run to where the command ends (`commandEnd`), so the `)` or backtick closing the subshell or substitution it runs in is no part of its last word, while a `$( … )` among its own arguments stays inside it; and each `git add` chained ahead of it is read in its own directory (`addsAhead`), so `cd docs && git add superpowers/specs/x.md && cd .. && git commit` still sees the spec. A mention never decides the selection: until #1594 the spec rule took its arguments from the first `commit` anywhere in the text, so `echo "commit -- notes.md" && git commit -m x` read as a pathspec commit of `notes.md`, and a quoted `-a` or `git add` counted. Operands, with or without `--`, are a pathspec commit from the working copy (`-i` adds the plain selection); a parsed `-a` / `--all` takes the modified files too; otherwise the staged files plus those a `git add` chained ahead of the commit selects. A redirection is the shell's whatever its target expands to (`2>$null`), and an abbreviated long option is the one git takes it for (`--mess` is `--message`, against the option lists in `COMMIT_OPTIONS` / `ADD_OPTIONS`). A substitution or `--pathspec-from-file` on the commit or on such an add, a long option git would refuse as unknown or ambiguous, or a commit whose words cannot be lexed (a `-F - <<EOF` commit inside `$( … )`) leaves the selection unreadable, and every staged, added, modified and untracked spec is then judged from both the index and the working copy.

## Control bytes in a spec (#1466)

A push to `master` that changes only spec Markdown starts no CI run, so `scripts/no-control-bytes.test.mjs` would not see a spec until the next code push, where it would fail a change that never touched it. Two checks stand in for it at the commit. The spec-commit rule in `rules-bash.mjs` is the early message, in a Claude Code session only: it sees the Bash and PowerShell tools and nothing else, and it fails open on text it cannot read. Unlike the section check it is not forward-only, so an amendment is checked too, and one deny names the byte and any missing sections together. The guard every committer meets is `scripts/check-staged-spec-bytes.mjs`, the first step of `.husky/pre-commit`. It reads the index the commit records, so it also covers the PowerShell tool, a terminal and `git commit --only`. All three readers share `scripts/lib/control-bytes.mjs`.

## Which checkout's data a rule reads

Hooks run the scripts of the session's `CLAUDE_PROJECT_DIR`. The `pnpm --filter <pkg> <script>` rule is the one exception about *data*: it reads the package manifests of the checkout holding the session's cwd rather than always the main one (#1021). It does not follow a `cd` inside the command, so a `master` session running `cd ../ir-<n> && pnpm --filter …` is still judged by `master`'s manifests.

## Deny beats ask (#1193, #1307)

`checkBash` returns the first deny at once and holds every ask until every rule has run, because one chained command can match an ask rule early in the list and a deny rule late in it — until #1193 the ask won, and confirming it ran the shape the deny exists to stop. The asks are then joined into one prompt (#1307): a chain the maintainer approves runs whole, so an ask hidden behind another would run unseen. Rule order still decides which of two denies is reported.

## The lexer's stopping rule (#1659)

**The lexer reads the forms agents type here, and refuses every other form that hands text to a shell.** Each spelling class #1606–#1646 taught it cost a reader and rounds of review findings, while a census of every Bash and PowerShell command in the local transcripts (54,199 distinct, 2026-11-24) found the printer, `eval`, stdin and decoder forms typed only by the hooks' own QA and reviewers. So `checkText` in `rules-bash.mjs` asks `refusedForms(text, shell)` first, before the respelled-program re-judge and every rule, and denies the first form listed with one message naming the form and its shape: type the commands directly, or write them to a script file. It is never an ask, and no rule's pass or ask stands in for it. Decision 4 of `docs/superpowers/specs/2026-11-24-issue-1659-merge-gate-module-and-lexer-stopping-rule.md`.

**Read**, each with tests:

1. The program word at the typed level in any literal spelling: a path, a suffix, case, quotes around the whole word, PowerShell's `&` and dot-source (#1606, below).
2. A wrapper that runs a program word: `time`, `command`, `exec`, `env`, `nohup`, `timeout` and `xargs` through `COMMAND_LEAD`; `coproc`, past the name of `coproc NAME { … }` / `NAME ( … )` (`coprocProgram`); `nice`, `stdbuf`, `winpty`, a `sudo` that runs a program, and `find -exec` through `fedStarts`; and inside a string, `watch -x`, which runs its words with no shell (`watchExecs`): its program is walked as a wrapper's, so `watch -x bash -c …` there is still a string inside a string, refused.
3. One level of shell string: the string of `bash` / `sh` / `zsh` / `dash` / `ksh` / `fish -c` (and fish's `-C` / `--init-command`, `extras`) and `su -c`, `pwsh` / `powershell -Command` (or the words PowerShell runs without it), `cmd /c`, and what `trap`, `watch` and `parallel` run unless their input fills it (below), with that shell's quote removal or word joining (`readLevel`, below), a string spliced from quoted pieces and outer expansions (`'…'"$RUN"'…'`) included. A shell word glued to its redirection (`bash<<<'…'`, `bash</dev/null -c '…'`) is read as the shell word (`SHELL_FED`, `PROGRAM_WORD`). A file a shell runs (`bash x.sh`) is no string, and the hook reads no file; a stream it names is refused (below).
4. A program word that expands or globs, judged by stand-ins as `gh`, as `git` and as a wrapper (#1606, below).
5. A directory change with a literal target: `cd`, `Set-Location`, `pushd` / `popd`, `git -C`, a runner's `-C` / `--dir`; one it cannot follow leaves the directory unknown (below).
6. A substitution's body, as the typed level is read: `$( … )`, backticks and bash 5.3's `${ …; }` / `${| …; }`, at any depth, unquoted or inside double quotes, and in an unquoted heredoc body in a string, only where the substitution runs (`liveSubs` over the masked text: never in a comment, a single-quoted string or a quoted heredoc body). A word in one is a program word even inside double quotes (`literalQuoted`), and `pipedCommands` reads each body as a command list of its own, piped when the command holding it is. #1659's own quoted-mention check once skipped `"$(eval …)"` and `"$(bash -c …)"`.

**Refused** (`REFUSED` in `shell-lexer.mjs`; `fedStarts` finds them, and `view()` collects them over every round, since a later round can reveal one an earlier round could not):

- a printer (`echo`, `printf`) or any other command piped into a shell that has no string or file of its own: a pipe into that command, or into a group, subshell, loop, `if` or `case` holding it (`pipedCommands`), never one into another command beside it (`{ printf x | wc -c; bash; }`); a shell a `coproc` runs, or one in an output process substitution (`tee >(bash)`), reads that pipe too, and a process substitution's `)` is no closing word;
- a shell, `source` or `.` reading its script from a stream (`scriptStream`): stdin named by a path (`/dev/stdin`, `/dev/fd/0`, `/proc/<pid>/fd/0`, read with `.` and `..` resolved; `streamOf`) or by PowerShell's bare `-` or `-File -`, a here-string, a heredoc, a process substitution (`bash <(…)`, `bash < <(…)`, `source <(…)`), or another descriptor (`bash <&3`, `bash /dev/fd/3`); the last input redirection decides its stdin (`stdinFrom`), its own or, for a shell reading stdin, one on the closing word of a group, subshell, loop, `if` or `case` around it (`{ bash; } <<< …`, `done < <(…)`) or an earlier `exec` with no program (`exec 0<<<…; bash`; `stdinAround`), unless a later `exec` at a command's start, one that surely runs in the same shell (nothing but `;`, newlines and plain commands between the two, never `&&`, `||`, a pipe or a `&`; `UNSURE_CHAIN`), sets it to `/dev/null` written out literally (`isDevNull`) — any other file may fail to open, which in bash's default mode leaves the earlier stdin in place, so it resets nothing; a script word or startup file that expands may name stdin, so it is refused when stdin is redirected or a pipe feeds that shell (`… | bash "$F"`), an expanding startup file beside a `-c` string too;
- a startup file read from such a stream, whatever the shell then runs: `--rcfile` or `--init-file` (attached or not) before the script word — after it only redirections are read, so `bash x.sh --rcfile /dev/stdin` passes it to the script — or `BASH_ENV` or `ENV` assigned one where bash makes the assignment, in a command's prefix or as an argument of `env`, `export`, `declare`, `typeset`, `local` or `readonly` (`assignsAt`), in any quoting (`export "BASH_ENV=…"`), a value that expands included (`startupFiles`);
- PowerShell's `-EncodedCommand`, a script the hook would have to decode;
- `eval`; PowerShell's `Invoke-Expression` / `iex` where PowerShell runs it: at a program position of a PowerShell-tool command, in a PowerShell string, or as a statement of a script block or subexpression (`ls | % { iex $_ }`, `$s = { iex x }; & $s`, `Invoke-Command { iex x }`; `powershellStatementEvals`), never in a string another shell runs (`bash -c 'iex -S mix'` passes);
- a `sudo` that runs a shell: `-s`, `-i`, `--shell`, `--login`, or a shell word as its program (`sudoShell`);
- a string that is not one plain level: an ANSI-C `$'…'` or locale `$"…"` piece in it (`stringForm`);
- a string inside a string: a shell word in a level-1 string that runs text it is handed (`feedsText`), `watch -x` there excepted (Read item 2);
- in a level-1 string, a command substitution in a program word, and a program word that is not its plain name after quote removal: an expansion, an escape, or a quote that splits its last path segment (quotes around the whole name, `bash -c '"gh" pr merge 7'`, are plain, and that merge reaches the merge gate), or a word ending in a path separator (`wordForm`; PowerShell splicing `"& \""` and `"C:\…\gh.exe\""` hands bash one, #1787 item 3);
- a shell string `xargs`, `parallel` or `find -exec` / `-execdir` fills from its input: one holding the replace string (`-I{}`, `-i`, `--replace`, BSD's `-J`, find's `{}`; `replaceString`), one whose string switch is left empty (`xargs bash -c`), or a joining shell's words xargs appends to (`xargs pwsh -Command …`); the deny names the safe spelling (`FILLED_ADVICE`);
- `parallel` running its input as commands: no command, one starting at `:::` or `::::`, or a program word that is a replacement string (`parallelRunsInput`).

Each is refused in a level-1 string too (`inLevel`). An escaped separator (`\(`, `\;`, `\&`, a line continuation) starts no command, so a jq `\(.name)` in a string is no program word. Every reader of a shell's words stops at an unescaped `#` that starts a word (`commandWordEnd`), so a trailing comment is neither the shell's script file nor an option: `… | bash # install` is refused, and `bash -s </dev/null # <<< x` keeps `/dev/null`. A word reader blind to comments once passed the first and refused the second.

One exception: a program word spliced from the outer string's quoted pieces (`bash -c 'g'"h"' pr merge 7'`) keeps #1646's spliced-program deny (`spliced`, below), which the replay showed already denying real commands. A glob in a string's program word is not refused; it gets the stand-ins, as at the typed level. The xargs fill is the one refusal that changes real verdicts, 3 commands in the census (worktree inspections, `find … | xargs -I{} sh -c '…{}…'`), and it is not re-opened: xargs substitutes the input before the shell parses the string, so an input line can carry a whole command and no reading is sound, while passing the input as data costs one word and stays read, `xargs -I{} sh -c 'cat "$1"' _ {}` or `find … -exec sh -c '…' _ {} \;`, the spelling the deny names (PO, 2026-11-24).

**Re-opening, one form at a time.** A refused form is read again only when the census or a session shows a real, non-probe command of it refused that the agent cannot reasonably type another way; it then joins the read list here, with tests and a census count in its PR. A spelling only a probe or a review found is answered with a refusal, never a reader. The splice in item 3 is the one re-opened so far: the replay found seven real commands spliced so (wait loops and CI waits under `timeout N bash -c` splicing a variable into a single-quoted string, and a PowerShell script whose `''` escapes bash reads as splices), four of which the refusal would have turned from pass to deny.

**The census and the equivalence proof** are `scripts/claude-hooks/replay-corpus.mjs`, a developer tool no test runs over real data. It reads every Bash and PowerShell command in the `*.jsonl` transcripts under the folder it is given (records split at LF only, since JSON allows a literal U+2028/U+2029 that `readline` would split on), judges each with `checkBash` of a base revision (`--base`, default `origin/master`, its `scripts/` copied out of git into a temp folder removed at the end) and of a checkout, under one fixed context for both sides (nothing staged, no linked host, every git and gh read failing, the cwd and package manifests of the head checkout, `--head-dir` or this one; any field `pre-bash.mjs` does not set throws), and prints each changed verdict by its kind alone (`PASS`, `ASK`, `DENY`, a stopping-rule deny with its form; the full text only with `--show-commands`, since a deny can quote a command's arguments), with the probe patterns its command matched (or `real`, the count split by the two), and a census of program positions by kind and of `view()` flags, real commands apart from probes (`PROBE_PATTERNS`); its `refused` flag comes from `refusedForms` with the command's shell, as the hook refuses (`commandCensus`). While it judges, `forbidSideEffects` makes any process spawn and any file write through the patched `fs` and `child_process` exports throw. It is a check, not a sandbox: both sides' modules are imported before it is installed, and a `FileHandle` opened earlier keeps its methods, so `--base` and `--head-dir` must name trusted code. Run it before and after any lexer or rule change. It exits 2 on a usage error, 3 when a side, the transcripts or a package manifest cannot be read, and 4 when a comparison judged no command at all (a `--match` that selects nothing proves no equivalence). Otherwise a comparison exits 1 when a verdict changed; else 3 when a tool-use line did not parse, so part of the corpus went unjudged (a transcript appended to during the run can end in a partial line: rerun); else 5 when some pair threw alike on both sides (counted apart, since a shared throw is no completed verdict); else 0, every pair having produced the same completed verdict:

```bash
node scripts/claude-hooks/replay-corpus.mjs --transcripts ~/.claude/projects --match iRaceDeck
```

The transcripts are private to the machine. The tool writes nothing into the repository and prints a command's text, or a verdict's full text, only with `--show-commands`; nothing read from them is committed or pasted into an issue, a test or a fixture, and a PR body carries counts only.

## A shape trap fires at command position, not on a mention

`cmd()` in `shell-lexer.mjs` anchors each trap to the start of the string or of a line (after any indent), or to what follows a `|`, `;`, `&` (not a redirect's own, as in `2>&1`), `(`, `)` or a backtick, with a `COMMAND_LEAD` allowed in between: assignments, the shell keywords that open a command list (`if`, `then`, `do`, `else`, `elif`, `while`, `until`, `!`, `{`), the wrappers `time`, `command`, `exec`, `env`, `nohup`, `timeout` and `xargs` with their own options, and a redirection ahead of the program (#1307: `if …; then gh pr merge …` used to pass every trap unchecked). The rule's own shape is kept as `inner`, which `matchesAt`, `has` and `chainCommands` also test at every other program position the view recorded — the first word of each command of a string a shell is handed, and the word a wrapper runs (#1634, below) — where no anchor reaches.

A boundary counts only where the shell sees one (#1321): `maskInert` is one recursive lexer that blanks the inert text — single-quoted and `$'…'` text, double-quoted text and unquoted heredoc bodies except their substitutions, quoted-delimiter heredoc bodies, and `#` comments — at the same length, so a `|` in a grep pattern or a line of a commit message is no boundary, and a rule that reads its arguments finds the command in the masked text and reads them from the raw text at the same index (`matchAt`). A command a shell reads only once it removes a string's quoting or joins its words (`cmd /c "gh pr" merge 7`, `pwsh -Command gh "pr merge" 7`) is found too, its shape tested in the text that shell reads (`found`), and the match carries `decoded`, that command as its shell reads it; its raw groups are mis-sliced, so a rule that passes or asks on one it did not excuse (`excuseDecodedHit`, only once the rule has judged that command: the tag-push, integration-push and piped-pnpm rules read `decoded`, the last with `sep`, the separator that ends it there, excused only by a `pipefail` of the shell that owns the pipe (live in its own text ahead of the pnpm, or its own `-o pipefail`), never an ancestor's, and so does the deck-host ask for the Stream Deck CLI, a host stop and a runner in a string no wrapper reader takes (`su`, `trap`, `watch`), while it reads wrapper strings whole) is refused (`takeDecodedHits`, `judge`), since an ask raised over another command would run it unnamed; a deny stands. A command a string runs is judged where the `cd`s that string runs ahead of it move (`levelLead`, `dirAfter`, the `base` of `chainCommands`): each `cd`, `pushd` or `Set-Location` at a segment's start in that string, starting from where the typed command's own `cd`s leave the word handing it over, so `su -c 'cd ../ir-x && …'` and `bash -c 'cd ../ir-x; …'` are judged in `../ir-x`; the typed command's own chain is read the same way (`cdSteps`, `dirThrough`, `typedDirAt`, behind `chainCommands` and `cwdAt`), except that a `cd` inside a string a child shell runs moves only that child (`bash -c 'true; cd ../x; true'; pnpm …` runs where it was typed). A `cd` in a pipeline stage before the last moves nothing after the pipeline, and one in parentheses closed in its segment moves nothing; one in the final stage leaves the directory unknown, since whether bash runs that stage itself (`lastpipe`, no job control) may be set in a profile or `BASH_ENV` the hook cannot see, and a `shopt` in the command may come after the pipeline, so no exception is made; one after `&&` or `||` leaves it unknown for what follows unless only `&&` leads from it to the command (`false && cd x; pnpm …` is unknown, `true && cd x && pnpm …` runs in `x`); a plain `cd` is read by the outcome that reaches the command within its and-or list (`cdOutcome`): after success through `&&`, after failure through `||` (`cd x || pnpm …` runs where it was), unknown where either can (`cd x && a || pnpm …`), and as having run past the list's end; one it cannot follow (`cd "$X"`, `cd -`, a bare `pushd`, a `popd`, or one inside a compound command whose extent the segment does not show, `{ cd x; …`, `then cd x`) does too. Such a command is `lost` (`cwdAt` gives `undefined`, `gitPlace` sets `lost` with `movesRepo` and `movesTree`): a decoded runner leaves its hit standing, refused; the deck-host ask refuses a `dev:voices` while a host is linked, since it relinks only there (a `lost` finding, kept a refusal through a script that runs itself), while a runner the tree decides nothing for, or any with no host linked, is still judged; a `git commit` is refused before its branch or index is read; an integration push counts as moved; a `git worktree remove` of a relative target is refused while a host is linked; and the post-hook leaves a merge that names no PR (even with a named repository, which never picks the branch), or only a bare number, to a check by hand, since the checkout decides which PR it merged; a PR URL, or a number with a named repository (`-R`, `GH_REPO`), is still read back. Reading every rule's arguments from the quote-removed level-1 text, as its shell does, is #1783.

**The mask is trusted only when it is sure.** The lexer reports itself unsure whenever a construct runs off the end of the string or a `)` closes nothing — states bash refuses, so reaching one means a misread — and then the whole command is read raw, as before #1321. The mask is also set aside where live text hands a string or stdin to a shell (`bash -c`, `sh`, `eval`, `bash <<'EOF'`, `sudo`, `watch`, `trap`, `pwsh -Command`, `cmd /c` …), the forms the stopping rule refuses included, since a form must be found to be refused; since #1607 only over the top-level list element that does it (`fedSpans`). The lexer knows where every substitution, backtick, `${ … }`, `$(( … ))`, paren group, quote, escape and heredoc body is, so it hands over a `top` text with all of them blanked, and the elements are read off that alone: they end at a newline, `;`, `&&`, `||` or lone `&` at the top level and outside every compound command (`if` … `fi`, `while`/`until`/`for`/`select` … `done`, `{` … `}`, `[[` … `]]`, counted at command position, where a newline is a boundary too, so a group opened on a later line or after `time -p` counts). A pipe ends none, nor does a newline the list goes on over (after `|`, `|&`, `&&` or `||`, past blanks, comments and heredoc bodies), so `echo '…' | bash`, a `|` with `bash` on the next line, `… | { cd x && bash; }`, `… | while …; do bash; done` and `[[ … && … ]] | bash` are one element each, and a shell inside a substitution sets aside the whole top-level element holding that substitution (`x=$(a; … | sh)`) and no more. The body of every heredoc whose `<<` is in the element goes with it; a newline that ends an element reaches over the heredoc bodies it read. `timeout` and `xargs` set nothing aside: they run a program, never shell text, and `COMMAND_LEAD` steps to the program word after them in the masked text. One `timeout` anywhere in a chain used to make the whole command raw, so a quoted `gh pr merge` in a `sed` or `grep` pattern elsewhere read as a merge, and the post-hook moved #1559's card for a PR nobody merged. One exception widens the span back to the whole command: a shell interpreter (any of those words but a `sudo` without `-s`, `-i`, `--shell` or `--login`, which runs a program; with one it hands its argument to a shell, `sudo -s "$X"`) whose own element holds it for a later element to feed — a function definition, an `exec` with a redirection or a `coproc` (`f() { bash; }; echo … | f`, `exec > >(bash); echo …`) — or that may run text another element stored — its own element expands a variable, or an element the mask stands over exports one (`export`, `declare`, `typeset`, `set -a`), defines an alias or a function, opens a descriptor with `exec`, runs `tee` or writes a file other than `/dev/null` (`x='…'; eval "$x"`, `echo '…' > f; bash f`, `f() { echo '…'; }; f | bash`, `exec 3< <(…); bash <&3`). A plain assignment is no such store, since another shell sees an unexported variable only through an expansion, which the first test catches. `view()` reports the spans as `fed` and keeps `trusted` for "the whole command is masked"; a consumer that reads one command's words (`mergeSegments`, `issueEdits`, `argTokens`) asks `trustedIn(command, a, b)` for its own range and reads raw words only where that range meets a span. One notion of command position serves both hooks (#1634). Before it, the first word of a shell-fed string (`bash -c 'gh pr merge 7'`, `pwsh -Command "…"`) and the program a `sudo` runs were at command position for no pre-hook rule, so those merges passed the gate while only the post-hook's `firstMerge` read them. Now `view()` builds the program positions in rounds. `fedStarts` reads forward from every program word that is a shell word or a wrapper: `commandOf` steps over its options as `OPTION_SPECS` describes them for that word — a value option takes its value (`bash -o pipefail -c '…'`, `su - me -c '…'`, `watch -n 5 '…'`, `sudo -u me gh`; so `sudo -u gh pr merge 7` runs `pr` as the user `gh` and is no merge), a string option (`-c` alone or in a cluster, `--command`, pwsh's `-Command` in any unambiguous prefix, cmd's `/c` and Git Bash's `//c`) makes the first later word that is no option the string — or the rest of its own word where that program parses it so: cmd's `/c"…"` and `/cgh …`, getopt's `su -c'…'` and `fish -c'…'`, and a quote glued to pwsh's `-c` (`-c"…"`), read as the string since what pwsh makes of it is not certain and the gate errs to deny; bash's `-cx` stays the flags `c` and `x` — a redirection takes its target, `--` ends the options, and past the program the words are still read for a string option, 64 at most, so an option the specs lack costs a false program word, never a missed string; `-File` and `-EncodedCommand` end the reading, since neither can be read (`-File -` and `-EncodedCommand` are refused, a file is not read). Since #1659 `commandOf` takes a command or process substitution as part of its word (`commandWordEnd`), so `bash --rcfile $(x) -c '…'` reaches its string. It then records the word a `nice`, `stdbuf` or `winpty` runs, and the one a `sudo` that runs no shell runs (whole, quoted or not: `sudo "gh" pr merge 7`), the word after each `-exec` of a `find`, and the first word of each command inside a shell's string past a `COMMAND_LEAD`, read as that shell reads the string (below; never the quoted string whole, so `bash -c 'x'` keeps its quotes) — each at its raw word's start, which a rewritten word's pad hides from the position read, so the set is the same whichever round reads it. `normalisePrograms` treats each as a program word — rewritten, so `bash -c 'gh.exe …'` and `nice gh.exe …` read `gh`. **The program word is read in any spelling (#1606).** `gh.exe pr merge`, `/usr/bin/gh …`, `"gh" …`, `g"h" …` and `& "C:\…\gh.exe" …` once reached no rule, since every trap named the bare word. So `view()` rewrites each program word at command position, in the masked and flat text alike and at the same length, to the name the shell runs. The word is decoded as bash reads it, cut to its last `/` or `\` segment, stripped of `.exe`, `.cmd`, `.bat`, `.com` or `.ps1` in any case, and lowercased unless bash finds the name only by its exact spelling (a builtin or keyword). The name is **right-aligned** in the word's own span with a space pad before it, so the anchor's `\s*` and `COMMAND_LEAD`'s `\s+` absorb the pad, a `cmd()` match covers the whole raw word and the arguments keep their indices. Only the literal directory part is blanked: a command substitution in it stays live (`$(git push …)/x.sh` reads as `$(git push …)  x.sh`), because blanking it once hid the command inside from every rule. A rule that finds a program by an unanchored regex and slices the raw text at that index takes the word's start from `programStart` instead, as the merge gate's prefix and the post-hook's merge read do. The pass repeats, so `/usr/bin/env /usr/bin/gh` is read through the wrapper. It runs before the shell-feed test, so `"bash" -c '…'` sets the mask aside over its element as bare `bash` already does. A word is an assignment only where bash takes one, an unquoted valid name with an optional index before `=` or `+=`, in the rewrite and in `COMMAND_LEAD` alike, so `"/c/a=b/gh.exe"` is a program. A word starting with `-` after a wrapper is that wrapper's option, never a program, and keeps its case. A quoted `NAME=VALUE` after `env` is the assignment env makes, written as `NAME=___` so the lead steps over it and the merge gate's prefix check still sees the name. An expanding `env` argument is judged four ways: as `gh`, as `git`, as `GH_REPO=<word>` and as `GIT_DIR=<word>`. `COMMAND_LEAD` also steps over a redirection ahead of the program (`2>/dev/null gh …`, `</dev/null gh …`). A redirect's own `&` (`2>&1`, `&>log`) is neither a command boundary nor a chain separator. The merge prefix accepts a plain redirection, though not one whose target runs a command. `$"…"` is decoded as bash's locale string. Whether env's arguments are assignments is decided by the lead's own token parse (`leadToken`, which also builds `COMMAND_LEAD`), so an option's value spelled like a wrapper (`env -u time …`) never counts as one. Every program position is read past its lead by `leadStep` in code, with the one word reader every level uses (`pieceEnd`, `wordEnd`): a value ends where bash ends it, whatever it nests (`X="a b;c" gh`, `X="$(echo "a b")" gh`, `X=a$(a $(b $(c)))b gh`), where `=\S*` once stopped at the first blank (#1646). `COMMAND_LEAD`, the regex each `cmd()` anchor holds, is only its fast path, reading values in `WORD_PIECE`s with substitutions one level deep; where it stops short, every rule still tests its shape at the program position `leadStep` found (`matchesAt`), and the merge gate, which reads segments by the regex, refuses one it cannot isolate. The regex sits in every `cmd()` rule, so its size is paid on every command each rule reads: keep it short, and build a rule's flagged copies once (`compiled`). Where the mask is set aside the raw text is rewritten too, but only one word at a time, and only a word that stands on its own: no newline, `;`, `&`, `|`, paren or backtick in it, and every quote it opens closed within it. Anything else stays exactly as the raw text has it. A word read from inside a quoted string once swallowed the closing quote and the real commands after it, and the rewrite blanked them. A property test checks that every boundary and quote keeps its index, and that every trapped shape the raw text shows is still there. `powershellAsBash` blanks a statement-leading `&` (the call operator, not a background job) and a statement-leading `.` followed by a blank (dot-source, which runs the command the same way). It also lowercases each program word, since PowerShell resolves commands in any case. The one-merge backstop counts whichever is larger: raw mentions of `pr merge` after the program in any of these spellings (only the program's case is folded, so an upper-case mention in a body is not counted), or merges in the rewritten text. **A program word the hook cannot read**, one whose last segment expands or globs (`$GH`, `$(which gh)`, `g?`) at the typed level, or globs in a shell-fed string (listed, never rewritten; one that expands or substitutes there is refused by the stopping rule), is judged again as `gh`, as `git`, and blanked out as a wrapper that runs the words after it (`$W gh pr merge` with `W=command`) (`unreadablePrograms`, `checkBash`). Any verdict the substitution adds becomes a deny naming the word. An ask that another command of the chain raises anyway stays an ask. An unquoted expansion can split into several words, which no one-word stand-in models: `$(echo gh -R x/y) pr merge 5` once read this repository's PR through its `gh` stand-in. So when the word itself names `gh` or `git`, or the word after it is a subcommand a guard reads (`$CMD pr merge 5`), it is refused outright. Such a word may also split into a wrapper and an assignment, so it is judged as `GH_REPO=<word>` and `GIT_DIR=<word>` too, within its own command only, since an assignment reaches no later command. `$EDITOR notes.md` and `$PAGER git log` still pass.

**A string a shell runs is read as that shell reads it, one level deep (#1646, #1659).** A fed span's raw text is one quoting level short of what the inner shell reads: `bash -c "X=\"a b\" gh pr merge 7"` hands bash `X="a b" gh …`, and a splice `'…'"$V"'…'` joins pieces. Read raw, a lead ended inside such a value, and a quoted `;` ended a wrapper's command, so the merge after it passed the gate. `fedStarts` reads each string a shell is handed in a level of its own (`readLevel`): its word with the typed command's quote removal (`decodeWord`), or every word to its command's end joined by a blank for `pwsh -Command`, `cmd /c`, `watch` and `parallel` (`JOINING_SHELLS`), each character but a letter, digit, `_`, `-`, `$` and `=` backslash-escaped for `watch -x`, which keeps each word one; each character keeps the view index it is read from. A shell word inside a level is never read as a second level: one that runs text it is handed is refused, and any other is judged as the program word it is. Every command of a level, after each separator that level holds, is read past its lead to where it ends at that level, and a wrapper inside a string is read in the string's level. A recorded word spans what its level makes one word, a whole word of a joined level its own quotes too (`pwsh -Command "gh" pr merge 7`; `levelWord`, read by `normalisePrograms`), so a rewrite never erases an escape. It is recorded where its raw text starts, an escape's backslash included, and once rewritten where the rewritten word starts, the first round's reading standing (`view()` keeps it), so every round records the same position: a `\ls` once alternated and never settled. A word whose raw text does not spell what its shell reads is never rewritten (`rewritable`, `respelledIn`): one that globs is listed unreadable; one escaped in its string as a whole (`bash -c "\"gh\" pr merge 7"`, pwsh's `& \"C:\…\gh.exe\"`) is respelled, and `checkBash` judges the command with the name its shell runs in its place and again with the name its raw text spells, the stricter verdict standing; one spliced from the string's quoted pieces (`'g'"h"`) is `spliced`, and refused, as no name can stand in its place. Each match is one occurrence (`occurrenceOf`: its view index, and for one read in a string its level and the index there), so a decoded hit and its excuse are keyed by occurrence. A merge read as a later command of such a string is named so (`carriedMerge`, `shell`). A level is read from the command itself, each word a fed reading rewrote laid over it, so a raw-text anchor's misread erases no escape, and a raw-read word a level word starts inside is no program. A `#` starting a word, at the line's start or after an unescaped blank or operator (`a\ #b` is one word), comments out the rest of its line, and a heredoc's body runs to its delimiter's line: neither holds a command, nor a quote that closes nothing. A lead that stops at a word opening a quote it never closes, or a heredoc with no delimiter, cannot be read past: `view()` reports `unclosedLead` and `checkBash` refuses the command whole, as it refuses an `unsettled` one; the inner shell would refuse it too. cmd.exe has no `'` quoting, so a string it runs sets no `unclosedLead`: that exception only suppresses the refusal, and `level()` still reads a `'` inside a cmd.exe string with bash's word reader. A `$'` is ANSI-C only where no backslash escapes its `$` (`ansiOpen`).

The post-hook's triggers read the same trusted text, unanchored, so `xargs sed -i` and `nice gh pr merge` still get their follow-up; the merge trigger counts a `gh pr merge` only where `gh` is the program, as above. A rule that must fire on ANY occurrence stays unanchored and reads the raw text: `updateProjectV2Field`, the doubled-backslash heredoc and `/code-review … --fix` are the three, because there the damage is in the text the command carries rather than in the command being run. They are marked `occurrence`, and a command re-judged with a respelled program in its place is read by them first as it is, since the re-judge reads a rebuilt text (CodeRabbit on PR #1788).

## A `git -C <dir>` belongs to one command in a chain

**Git's global options are one fragment (#1606).** Every git trap is `git${GIT_GLOBALS}<verb>`, where `GIT_GLOBALS` in `shell-lexer.mjs` holds each option git takes before the verb: `-C`, `-c`, `--git-dir`, `--work-tree`, `--namespace`, `--config-env`, `--exec-path`, `--super-prefix`, `--attr-source` and `--list-cmds`, with their values, and `--no-pager`, `-p`, `--paginate`, `-P`, `--bare` and the pathspec, lock, advice and lazy-fetch switches without one. Each rule once hand-rolled `git\s+(-C\s+\S+\s+)?<verb>`, so `git -c user.name=x commit` passed the spec-commit deny outright, and only the worktree-remove rule took `-c`. A test in `shell-lexer.test.mjs` scans the hook modules for a git regex that skips the fragment. Every `-C` is read in order, each resolved against the one before as git does, with a quoted or escaped value taken whole (`gitPlaceAt`, `gitGlobals`). The options are read off the git program word that the lexer found at the command's own depth. A lead's option value spelled `git` (`exec -a git git -C …`) once had its options read in place of the real command's. `--git-dir`, or a `GIT_DIR` or `GIT_COMMON_DIR` that reaches the command, moves the repository away from the directory the hook judges. For a commit, `--work-tree`, `GIT_WORK_TREE`, `-c core.worktree=…` and `--config-env=core.worktree=…` (the key read in any case, as git reads it) do too: the commit then takes its files from that tree while its branch and index stay the cwd's. So does `GIT_INDEX_FILE`, which records from another index than the one `ctx.staged` reads. So does `core.worktree` reached through the environment: any `GIT_CONFIG_PARAMETERS`, or a `GIT_CONFIG_KEY_<n>` that names it or cannot be read. The key, there and in a `-c` or `--config-env`, is decoded as bash reads it (`c'ore.worktree'`), and one that expands counts, a command substitution included. An option's value takes a `$( … )` or backtick substitution whole, so `git -c x=$(echo a b) commit` is still read as a commit. None of these refuse a push, which reads neither. A reaching variable is any of these in live text ahead of the git word, in any case:

- a bash assignment with `=` or `+=`, `export`, or an `env` prefix;
- PowerShell's `$env:` or `${env:}`;
- `Set-Item`, `si`, `New-Item` or `ni` on `Env:`;
- `[Environment]::SetEnvironmentVariable`.

A `git add` ahead of the commit that moves any of these makes the commit refuse with the same message, naming the add. A `-C` that expands (`"$TARGET"`, `~/x`) counts as moving the repository too. The hook cannot resolve it, and its git reads in the literal path fail open. A rule that reads that repository's branch, index or files then denies and asks for `git -C <dir>` with the directory written out. Those rules are the commit rules, worktree add, and an integration push of the current branch; a push with a named refspec does not read the branch. Worktree remove reads only its target path, and the tag-push ask and the `diff master..` trap read only text, so they are unaffected.

`gitCwd(command, cwd, re)` in `shell-lexer.mjs` reads the `-C` off the segment (split at `&&`, `||`, `;`, `|`, newline in the trusted-masked text) that the rule's own regex matched, and finds each `cd` and `-C` in the masked text before reading its directory raw — so a `git -C ../master` quoted in a commit message moves nothing. Reading the first `-C` anywhere is how `git worktree add ../ir-N … && git -C ../ir-N log` resolved the new tree against itself, failed the repo-root lookup in a directory that did not exist yet, and was denied as "inside the repo". The `mainRoot` fallback in `pre-bash.mjs` is the second half of that fix: a dir git cannot answer for falls back to the session's repo root, never to the dir itself.

The post-hook's worktree trigger reads its target through the rule's own `worktreeAddTarget`, so the card that moves is the tree the rule judged, and a command that merely mentions the shape moves none. The rule's naming check, its spec gate and the trigger all read the issue number through `issueFromWorktreePath`, off the resolved path's last segment — the directory the add creates (#1358). An `ir-<n>` higher up is not the new tree, and reading the first one moved its card instead. The rule also requires a true sibling of the main checkout rather than only a path outside it, since `mainRoot` is the main checkout even when the add runs inside another `ir-*` worktree.

**The post-hook's board moves are for `iracedeck/iracedeck` only (#1527).** A card is found by issue number alone, so before this an issue filed in another repository (lint-staged/lint-staged#1865, from #1402) was added to the board and the iRaceDeck card with its number moved back to Backlog. Each trigger now settles the repository first, with `HOME_REPO` and the helpers in `rules-post.mjs`. `gh issue create` reads it off the URL gh printed — only a line that is an issue URL and nothing else, so a chain's `gh issue comment` (`…/issues/5#issuecomment-…`) or `gh issue view` output is not taken for the new issue, as the first URL anywhere once was. Each iRaceDeck issue it names must also be one GitHub created in the last ten minutes, however many creates the command ran — `gh issue edit` and `gh issue view --jq .url` print a bare URL too, while a `--web` or failed create prints none — and any whose age cannot be read is named for a hand move. An iRaceDeck URL is filed, and when none is the "add it by hand" reminder goes out, only if some create may have been home; one is not when every create was in another repository: the one its `-R` / `--repo` or a reaching `GH_REPO` names, else the checkout's (`gh repo view` in the directory it ran in, asked only then), so a foreign `--web` create is never sent to this board and a home one is never lost behind a foreign URL. `gh pr merge` takes it in gh's own order — a PR URL, then `--repo` / `-R` (`parseMerge`'s `repo`), then a `GH_REPO` that reaches the merge (its own prefix, or an `export` / `$env:` earlier in the chain; never another command's prefix or an unexported assignment) — and stops before any gh read when that names another repository or cannot be read (a bare `$VAR` included). An empty value reads nothing; `--remove-milestone` reads nothing and prints one line saying the card stays and the move back is Niklas's, in the board UI. An edit is read to its own end, depth-aware, and lexed on its own, so a substitution argument (a heredoc body included) and an edit inside `$(…)` or backticks are read; one the hook still cannot read whole gets the hand line when its text names a milestone flag (`namesMilestone`) or when it named no readable issue at all (`xargs`). The post-hook sets a 70-second deadline (`IRACEDECK_POST_BASH_BUDGET_MS` in tests) under the 90-second PostToolUse timeout and memoizes the Status field for its run, so a large edit names the issues it had no time for instead of being killed with its notes lost. After a worktree start the card is already In progress, so the milestone set then reports `setBoardStatus`'s "not moving it to Planned" line; that is expected, not a failure. An edit, repository or issue the hook cannot read gets the `node -e … setBoardStatus(<n>,'Planned',…)` line to run by hand. Each skip reports one line. A create or edit naming a former home (`FORMER_HOME_REPOS` in `rules-post.mjs`: `niklam/iracedeck`, until the move to the organization, #1799) is not dismissed as another repository's (`mayBeHome`): GitHub redirects it here, so it is read back like home and the URL gh prints or returns decides; a create naming one asks gh what the name resolves to (`gh repo view <name>`), which answers home while the redirect stands and the old name once a repository has taken it, and the `--remove-milestone` line, which reads nothing back, names home only. **Raw board edits are refused (#1574).** The rules said "a raw `gh project item-edit` is refused" while nothing refused it, so the never-backwards table in `BOARD_MOVES` could be bypassed by hand. Not covered: a query read from a file (`-F query=@q.graphql`) and a REST item path built from a variable (`gh api "$P" -X PATCH`).

## The integration tree and deck-linked trees (#1520, #1526)

**The worktree name.** `ir-integration` is the one non-issue name the worktree-add rule accepts, compared exactly against the resolved path's last segment, so `ir-integrations` or `ir-Integration` is still refused. It must still be a true sibling and come from a fresh `origin/master`; it skips the spec gate, since it names no issue, and the post-hook moves no card for it.

**The `integration` branch is never pushed.** Every `git push` in a chain is judged on its own (`chainCommands` in `shell-lexer.mjs`), in the tree it runs in: the session cwd moved by the `cd`s chained ahead of it, then by each of its own `git -C`s in order. It is denied when a refspec names `integration` on either side (`+`, `refs/heads/` and `heads/` allowed, and a source with a revision suffix — `integration~0`, `^0`, `@{0}` — counts as the branch), when a glob refspec could match it (`refs/heads/*`), on `--all`, `--mirror` or `--branches` (refs are shared by every worktree, so these carry it from any tree), and when it pushes the current branch (no refspec, or `HEAD` / `@`, with or without a revision suffix) while that branch is `integration` or the tree's top level is named `ir-integration`. `--dry-run` passes.

**Nothing relinks a deck host without Niklas's go.** An ask, judged per command of the chain. A build, install or clean passes in every tree, a linked one included: since #1258 a running host does not fail the build, and #1526 dropped the linked-tree build ask #1520 shipped with. Since #1737 a restart, stop or start passes too: the hook cannot see his go in the conversation, so its ask only made him click a second time after saying it. The rule stands as prose the agent keeps — no session restarts, stops or starts a host without his go in that conversation, and an issue lead never does (the `po` and `issue-lead` skills) — and the scripts are allowed in `.claude/settings.json`, so no permission prompt follows outside auto mode either. Every finding of `deckFindings` carries a kind, and the rule asks when any is not a restart. A script is found whichever runner starts it (`RUNNERS` in `script-runs.mjs`): pnpm, `npm run`, `node --run`, turbo's tasks — bare, or through `pnpm turbo`, `pnpm exec` / `dlx`, `npx` or `npm exec` — `rollup`, and `node` on the root script a pnpm script wraps. Asks always: a `link:*`, `relink:*`, `unlink:*`, `switch-test-env` or `switch-test-env:*`, a `watch:*`, the `streamdeck` CLI's `link` and `unlink` (with a `.cmd` / `.exe` / `.ps1` suffix or a path, and behind `pnpm`, `pnpm exec` / `dlx`, `npx` or `npm exec`), `node` on a `link-` / `unlink-` script, an unreadable pnpm script selector, and a restart run over and over: anything a rollup watch hook runs — the Stream Deck plugin's `watch` runs `streamdeck restart` on every rebuild, so `pnpm -r watch` or `turbo run watch` asks although the command inside is a restart — a `turbo watch` task, a command `watch` reruns (its whole quoted string, whatever its first command), and one inside a bash `while` / `until` / `select` / C-style `for ((…))` loop or a PowerShell `while` / `do` / `for (…)` loop (a labelled `while` or `for` too; a labelled `do` is read by the lexer as bash's `:` builtin and its block as arguments, which hides any command in it, a relink included, since before #1737: #1739); a quoted `done` or brace does not end the loop. A `for` or `foreach` over a list is bounded and its restart passes. Deliberately out (#1737 second read, upheld by its judge under the module header's rule that the reader grows when a real command slips past): cmd.exe's step-0 `for /l`, and `xargs` / `parallel` fed by an endless producer such as `yes`. Asks only in a linked tree: `dev:voices` and `node` on `dev-voices.mjs`, which relink the hosts linked to their tree, judged in both the cwd and the script's own tree. Passes as a restart: a `restart:*`, `start:*`, `stop:*`, `build:with-restart` or `build:stream-deck`, the `streamdeck` CLI's `restart` and `stop`, a `taskkill`, `start`, `Start-Process` or `Stop-Process` naming a host app (`StreamDeck`, `StreamDock`, `UlanziDeck`, …), and `node` on `build-with-restart.mjs`, `host-app.mjs start|stop` or `integration-build.mjs --restart`. A restart's name no longer ends the judgement: the script is still read for what it runs, so a `restart:x` whose body relinks asks, and so does one whose body the depth bound leaves unread. When a chain asks, the prompt names its restarts too, since confirming runs the whole chain.

**A script is judged by what it runs.** The names above are the floor, for when nothing can be read. How the hook reads what a pnpm, npm, `node --run`, turbo, `node` or rollup run, or a shell wrapper, would execute is the package-script interpreter in `script-runs.mjs` (`deckFindings`), described in `@.claude/rules/hook-script-runs.md`, which loads with that module.

**Which tree is linked.** The tree is the command's directory — the cwd moved by every chained `cd` and by the runner's own `-C` / `--dir` (pnpm), `--prefix` / `-C` (npm) or `--cwd` (turbo), never by a `git -C` — taken to its git top level, and it is linked when a host's `linkTargets()` target is inside it; a host's packaged install (no link) never matches. `test`, `typecheck`, `lint` and `format` pass under any runner: they reach no host.

**Directories, and the PowerShell tool.** Every directory a rule resolves — a `cd`, a `git -C`, a runner's `-C`, a worktree path, a pathspec — goes through `shell-lexer.mjs`'s `resolveDir`. On Windows a Git Bash `/c/…` or `/cygdrive/c/…` is the drive `C:\…`, which `path.resolve` reads as a folder `c` at the root of the current drive: `cd /c/…/master && pnpm build` was judged in a `C:\c\…` no link points into, and passed. The PowerShell tool's commands reach the same hook, marked `ctx.shell`. `checkBash` in `rules-bash.mjs` reads them through the lexer's `powershellAsBash`, which rewrites PowerShell's backtick escapes and its literal `\` at the same length so the bash lexer finds PowerShell's words and boundaries (`"C:\x\"` ends at its quote there); a `Set-Location`, `sl`, `chdir` or `cd`, any case, with an optional `-Path` / `-LiteralPath`, moves the base; `/c/…` is left to `path.resolve`, which is PowerShell's own reading; and the rules marked `bashOnly` are skipped. The post-hook is wired for both tools too, and reads a PowerShell command through the same `powershellAsBash`. The `git merge` the integration script runs is not a `git commit`, so the spec-on-a-branch guard never sees it, and a Node child process is invisible to the hooks anyway.

**Board positions.** `moveBoardItemAfter(issue, after, cwd)` in `lib.mjs` calls `updateProjectV2ItemPosition`. GitHub keeps one item order per project and a lane shows its cards in it, so `after = null` is the top of the card's lane; the anchor must be in the same lane. Cards in Testing, Done or Dropped are never moved, and `IRACEDECK_HOOKS_DRY_RUN=1` reports the move without the mutation.
