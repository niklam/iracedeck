# Claude Code hooks — the merge gate (`gh pr merge`)

How the merge guard decides, for whoever edits it. Its policy row is in `@.claude/rules/hooks.md`; the lexer it reads the command through is `@.claude/rules/hook-internals.md`. Moved out of that file with its code in #1659.

`mergeGateVerdict` in `merge-gate.mjs`, which the rule's entry in `rules-bash.mjs` calls from its place in the rule order, denies more than one merge per command, judged on its own words, and otherwise denies unless all of these hold: the PR is OPEN; the method is `--squash` (or `--merge` for a `release/*` head); `reviewDecision` is APPROVED; every rollup entry is green (it fails closed on unknown node types); the merge state is not BLOCKED or DIRTY; and CodeRabbit has reviewed the current head. `--admin` skips the review checks (approval, CodeRabbit's review at the head, the summary and rebase paths), and is then judged as below.

**A merge under `--admin` (#1648).** Skipping the review checks would merge a head CodeRabbit never saw: an approval survives a push here, and an unapproved PR reads `UNKNOWN` while GitHub computes its mergeability, so keying on BLOCKED alone let both through unread. So every `--admin` merge whose other checks pass goes to `adminVerdict`, whatever its `mergeStateStatus`. It refuses `CHANGES_REQUESTED` first, qualifying or not and in any merge state, since no prompt stands in for answering a review; then it decides whether the PR is one the bypass is for (`adminQualifies`):

- **Prose, or Dependabot's whole.** Every file it changes is on the list in `no-review-paths.mjs` (Markdown under `.claude/rules/`, `.claude/skills/` and `.claude/agents/`, and `.claude/CLAUDE.md`, `packages/*/CLAUDE.md`, `scripts/CLAUDE.md` — never a `CLAUDE.md` at any depth, since one under the website's content folder is published), which `no-review-paths.test.mjs` holds to the list in `code-review.md`, and no skill's or agent's frontmatter changed: under `.claude/skills/` and `.claude/agents/` it is configuration (`tools`, `allowed-tools`, `hooks`, a permission mode), so the file qualifies only when its frontmatter block (`frontmatterBlock`: from the first byte through the closing `---` line when the text, past a BOM and leading whitespace, opens with `---`; the whole text when unterminated; empty when there is none) is byte-identical at the merge-base and the head, and an added or deleted one never does. A rule's `paths` frontmatter only scopes loading and is not checked. Or gh's `author` is Dependabot (`is_bot: true`, login `app/dependabot`, as `gh pr view` reports a GitHub App) and every commit from the merge-base to the head carries Dependabot's author line `DEPENDABOT_COMMIT_AUTHOR` (`dependabot[bot] <49699333+dependabot[bot]@users.noreply.github.com>`) and GitHub's committer line `GITHUB_COMMITTER` (`GitHub <noreply@github.com>`): a local amend or rebase keeps the author but replaces the committer, so an edit folded into Dependabot's own commit is caught too. A Dependabot PR with anyone else's commit is judged on its files; both lines can be written by anyone, so this stops an accidental edit, not a forged one. A release back-merge never qualifies (the bypass keeps `--squash`) and is not read. The `no-coderabbit` label is never read: it is free to add, and only decides whether CodeRabbit spends a review.
- **The read** is `merge-gate-reads.mjs`'s `prChangedFiles`: `git diff-tree -r --no-renames --ignore-submodules=none --name-status -z`, `git rev-list --no-commit-header --format=%an%x00%ae%x00%cn%x00%ce` (the raw author and committer lines, which no mailmap or signature setting changes) and, for each skill or agent file on the list, `git cat-file blob` of both sides read as latin1 (none for the side an added or deleted file lacks) from the one merge-base of `baseRefOid` and `headRefOid` to the head, at the repository root with replace refs and grafts ignored, fetching a missing commit from `origin` by sha — the helpers it shares with `replayRebase`. `--no-renames` lists both sides of a rename, so a script moved into `.claude/rules/` shows the deleted script; GraphQL's `files` would show the new path only, and caps at 100 a page. A failed fetch, criss-cross history, a failed diff, commit list or blob read, or an empty list counts as not qualifying, so it can reach a prompt or a refusal, never a pass.

**A qualifying PR** must be pinned with the full `--match-head-commit <head>`, the head the files were read at, so a push between the read and the merge cannot slip a file in; and must show every status check its base branch's rules require, present in the rollup and green, read by `merge-gate-reads.mjs`'s `requiredStatusChecks` from `repos/<repo>/rules/branches/<base>` (one page of 100, every ruleset that applies; GH_REPO the confirmed repository), because BLOCKED, which it may pass when the only reason is `REVIEW_REQUIRED`, also stands for a required check that never reported. An unreadable rule set refuses; one requiring no check (a `release/*` base today) passes, unless the PR is BLOCKED, where an empty set contradicts the block and refuses. A check matches by its rollup name (`name`, or a status's `context`).

**Any other `--admin` merge** keeps the checks above with BLOCKED refusing (one BLOCKED only by `REVIEW_REQUIRED` is read first, and its refusal names the files off the list or the failed read); where it would pass, it **asks** instead, naming the same, so it runs only when Niklas confirms the prompt. DIRTY, a red or pending check, an empty rollup, the method and the repository checks refuse either way, on the PR view (`ctx.prView`, which is read first) and before the `--admin` qualification reads: the changed files and their blobs, the commits and the required checks. Spec: `docs/superpowers/specs/2026-11-07-issue-1648-no-coderabbit-admin-merge.md`.

**The repository comes first (#1393, #1534).** The gate can judge only an `iracedeck/iracedeck` PR, and reading this repository's PR of the same number is how a merge aimed elsewhere once passed on checks nobody ran there. The gate reads before the command runs, so it fails closed on anything that could change what gh resolves the merge to after that read:

- **A flag between `gh` and `merge`** is refused: `--repo` / `-R` is a flag of `gh pr` itself, which cobra takes ahead of the subcommand and even ahead of `pr`, where the merge shape never matched and the merge ran ungated.
- **Nothing may come ahead of the merge but a plain `cd <dir>`** (`cdsAhead` in `shell-lexer.mjs`, which also gives the directory the read runs in, from those `cd`s alone), **and nothing may run beside it**: a pipe or a background `&` anywhere in the command is refused, since a pipeline runs each command in its own subshell (`cd x | gh pr merge` never moves gh) and a concurrent `git checkout` or `git remote set-url` can win the race against gh's own reads. An enumerating parser cannot keep up with every way a command reaches gh's environment or checkout — an exported variable assigned again, `export A=1 GH_REPO=…`, `declare -gx`, `set -a`, PowerShell's `${env:…}`, `Set-Item Env:` or `SetEnvironmentVariable`, a `pushd`, a subshell `cd`, a branch switch, `gh repo set-default` — so a merge runs as its own command.
- **The merge's own prefix is an allow-list** (`plainMergePrefix`): the wrappers `!`, `command`, `env`, `exec`, `nohup` and `time` without options of their own, `timeout <duration>`, and assignments of any variable but gh's and git's (`GH_*`, `GIT_*`, compared in any case because Windows hands gh its environment case-blind), `GH_REPO=<owner/repo>` aside. So `GH_HOST` (which moves a bare `owner/repo` to another host), `GIT_DIR`, `env -C<dir>` in any spelling, and `env -i` / `env -u GH_REPO`, which drop a `GH_REPO` the gate's own read still sees, are refused.
- **A merge handed to a shell or run under any other wrapper** (`bash -c "gh pr merge 7"`, `bash -c 'ls; gh pr merge 7'`, `nice gh …`) is refused (#1634, `carriedMerge`): the gate cannot read what that shell does around it, so the merge is typed as its own command. A merge piped into a shell, run by `eval` or in a here-string never reaches the gate: the lexer's stopping rule refuses those forms first (#1659).

Then, before any gh read, it takes the repository in gh's own order with the post-hook's helpers (`mergeRepo`, `assignedGhRepo` in `rules-post.mjs`): a PR URL, then `--repo` / `-R` (separate, `=`, attached, or combined with other short flags as pflag reads them, `-dR owner/repo`), then the prefix's `GH_REPO`; an empty value is none, as gh reads it. Another repository is refused, and so is a value it cannot read (a `$VAR`, a substitution, a flag with no value). It reads the PR in the directory the merge runs in, with a named repository passed as `GH_REPO`, and refuses unless the URL gh returns is `iracedeck/iracedeck`, which covers a followed `cd` into another repository's checkout and a `GH_REPO` or `GH_HOST` the hook process inherited. The summary comment and the base timeline are then read of that confirmed repository, passed as `GH_REPO`, never of whatever the session's checkout resolves `{owner}/{repo}` to: another repository's PR of the same number with no base events once read as "base unmoved". Not covered: a variable exported by the Bash tool's shell profile but absent from the hook's own environment, which the hook cannot see; a `gh alias` for `pr merge`; and a merge through `gh api`, which no rule reads.

**A head without a review object of its own.** Thread replies, which GitHub files as empty COMMENTED reviews, are not reviews. For such a head a back-merge is refused, and the merge must be pinned with the full `--match-head-commit <head>` before anything is read; then one of two things stands in for the review.

**CodeRabbit's summary comment** (#1386), which a clean incremental review edits instead of filing a review object, counts as the head's review when:

- exactly one summary exists, authored and last edited by the Bot `coderabbitai`, and every edit in its history (`userContentEdits`: at most 100, complete, newest first, the newest being the body read) was made by that Bot;
- it is not minimized, the PR has at most 100 comments, and there is no other auto-generated block (a `rate limited` one refuses);
- each statement is read only from its own block: one recent-review block whose one range line ends at the head and says no actionable comments, and exactly one `change_assessment_commit` and one `final_review_risk_coverage` (`kind: reviewed`, `sourceCommitId` equal to `coveredCommitId`) marker naming that same commit;
- the range's **start** is shown reviewed too: the newest review object's commit, a clean pure-rebase replay of it, or the range end of an earlier version of the same comment, walked back through its edit history at most 10 steps.

A base retargeted or force-pushed since the newest review object refuses before the summary is used.

**Otherwise a pure rebase** (#1307) of the commit CodeRabbit last saw — a passing summary's commit when the comment was written after the newest review object, else that object's; a summary that fails any condition, a rate-limited one included, is never a replay start. The reviewed change replayed onto the head's base must give the head's exact tree, and every file the replay reports as conflicted gets a line check that at best earns an **ask**. A follow-up push, a base retargeted or force-pushed since the newest review object, and criss-cross history are refused on that path.

A refusal names the condition that failed, so "rate limited, wait" reads differently from "not reviewed, ask `@coderabbitai review`".

Where the code lives (#1659): the pure `merge-gate.mjs` holds the verdicts (`mergeGateVerdict`, `unreviewedHeadVerdict`, `adminVerdict`, `adminQualifies`, `classifyCheck`) and the gate's own reading of the merge command (`mergeSegments`, `parseMerge`, `firstMerge`, which `post-bash.mjs` imports as its trigger); the impure `merge-gate-reads.mjs` holds the git and gh reads, `replayRebase` (the replay, with `git merge-tree -X no-renames`), `prChangedFiles`, `requiredStatusChecks`, `baseChangedSince` and `prComments`, built on `lib.mjs`'s runners and wired into `ctx` by `pre-bash.mjs`, so the verdicts' tests (`merge-gate.test.mjs`) hand in a fake context. The pure leaves are `change-signature.mjs` for conflicted files, `coderabbit-summary.mjs` (`readSummary`, tested against verbatim bodies in `__fixtures__/coderabbit-summary/`) and `no-review-paths.mjs`. Imports run one way, `rules-bash.mjs` → `merge-gate.mjs` → the leaves and `shell-lexer.mjs`. `scripts/CLAUDE.md` has the module map.

**The replay writes objects.** It is the one path `IRACEDECK_HOOKS_DRY_RUN=1` does not make read-only: it writes the replay's trees, and any reviewed commit the checkout lacks, fetched from `origin` by sha without automatic maintenance, to the shared object store — never a ref or `FETCH_HEAD`.
