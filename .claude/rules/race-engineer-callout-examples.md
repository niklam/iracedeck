# Race Engineer Callout — Reference Implementations

Worked precedents for the how-to in `@.claude/rules/race-engineer-callouts.md`. Each entry names the pattern a past callout established and the reusable lesson — consult one when a new callout needs a variation the checklist doesn't cover (continuous-distance triggers, multi-class projection, replay gating, cause classification, …). The full rationale for any entry also lives in its linked issue/PR.

- **Track Conditions / Wetness change** — issue #526. End-to-end example covering a brand-new family with a new bus enum, directional predicate, single per-callout opt-in covering multiple subjects.
- **Flag callouts** — issue #467. Per-subject opt-in (one boolean per flag colour); scope-aware predicate (`yellow.scope`); session-type branching (green/white/checkered).
- **Pit-service status** — issue #479. Per-target opt-in across eight subjects; sentinel suppression (* → None).
- **Damage** — issue #489. Single-subject family; debounced rising-edge detection in the diff.
- **Pit readback** — issues #476 / #481. Compositional scenarios (multiple pools per fire) and snapshot-at-fire-time pattern.
- **Session start ("car entry")** — issue #542. Single-subject family on the existing `driver.firstOnTrack` event; snapshot-at-fire-time conditions (`getSessionStartConditions()`) composed with the PI driver-name pick in each plugin; dynamic clips resolved via `engine.defineVar` (`registerSessionStartVars`) rather than enumerated `if` branches; a conditional clause (pit speed) gated on a curated value set. Establishes the **snapshot-driven builder-export shape** (issue #558): exports `buildSessionStartScenario(getSnapshot)` + `registerSessionStartVars(...)` rather than a static `*_ALERTS` array, because the scenario's `where:` / `if` steps close over a runtime resolver and must be materialized at wiring time — a future snapshot-driven family copies this precedent.
- **UI-side acknowledgment (Race Engineer toggle)** — issue #554. Not a sim-event-driven callout — the scenario engine isn't involved. The Pit Crew action's `toggleRaceEngineer()` plays "going silent" / "resuming" directly via `playVoiceSequence(...)` on `AudioChannel.Voice`, gated by a per-callout opt-in (`calloutEnabledToggleRaceEngineer`). Reuses the same `in-flight` bypass shape as the PI Voice Test (`raceEngineerToggleInFlight` ↔ `raceEngineerTestInFlight`) so `applyRaceEngineerAudio` leaves Voice audible after the master gate flips off, until the ack clip finishes. Reach for this pattern when a Stream Deck button itself needs to speak a confirmation; reach for the scenario-engine pattern when telemetry should drive the speech.
- **SDK-connection ack (Telemetry-connect radio check)** — issue #554 follow-up. Triggered by a real-time signal that isn't on the event-bus catalog: the SDK controller's connection state (false→true transition). Each Pit Crew instance subscribes to `sdkController` with its own id (`pitCrewRadioCheck:<contextId>`); a module-scope `lastTelemetryConnected: boolean | null` dedups so the ack fires once per real transition no matter how many Pit Crew buttons happen to be mounted. Disconnect flips the tracker back so reconnects re-fire. Composes the active driver-name clip + a new `toggle/radio-check-01` clip via `playVoiceSequence(...)`. No in-flight bypass needed (master gate is on by definition when this fires; gate-off short-circuits before playback). Use this pattern when a non-event-bus signal (connection state, app monitor, settings change) should drive a one-shot callout, with care to dedup across action instances at module scope.
- **Lap time (best lap)** — issue #555. Single-subject family on a new `lap.completed` bus event with a rich payload (`{ lap, lapTime, isBest, isFirstValid, bestLapTime?, previousBestLapTime?, lapsRemaining?, timeRemaining?, sessionType? }`). Time readout composed from `lap-time-intro` + `lap-time-minute` + `lap-time-second` + `lap-time-decimal` clips via `engine.defineVar` (`registerLapTimeVars`); a conditional `{ if }` step skips the minute clip for sub-1-minute laps; `where:` filters on `isBest && lapTimeIsSpeakable(lapTime)` so off-range laps stay silent rather than producing a partial readout. The snapshot resolver is **plugin-owned** (a `lap.completed` subscription that caches the latest payload) rather than translator-owned, because the data is frozen in the event itself rather than read from live telemetry. Triggered by `LapLastLapTime` changing (the field iRacing refreshes when a lap completes) rather than `LapCompleted` incrementing — the counter races the time-field refresh and produces stale duplicate emissions. Establishes the **snapshot-driven builder-export shape** (issue #558): exports `buildLapTimeScenario(getSnapshot, getRaceFinishedFired?)` + `registerLapTimeVars(...)` rather than a static `*_ALERTS` array, because the scenario's `where:` / `if` steps close over a runtime resolver and must be materialized at wiring time — a future snapshot-driven family copies this precedent.
- **Race start** — issue #568. Single-subject family that **replaces** session-start in race sessions: the existing session-start scenario's `where:` returns false when `sessionType === "race"`, and race entries are spoken exclusively by the new race-start scenario fired off `session.changed` (~3 s after the transition lands, before the driver even has to leave the garage). Reuses an existing bus event rather than introducing a new one — the trigger is `session.changed` filtered by `classifySessionType(getSessionType()) === "race"`, anchored on the per-session reset hook (`resetPerSessionState`) from #564. Demonstrates **clip-group reuse across families** — the conditions brief (track temp / air temp / wetness intros, integer temp clips, wetness state clips, degrees-unit clips) re-points at the existing `session-start`, `session-start-temp-numbers`, and `position-number` groups so the new clips ship as only 3 entries (`time-to-race-01`, `starting-from-pole-01`, `qualifying-put-us-to-01`). Position clause uses a **two-branch conditional** — P1 picks a pre-recorded "Starting from pole. Well done." single clip; P2..POSITION_MAX composes "Qualifying put us to," + `position-number/<n>`; out-of-range or missing positions skip the clause entirely so the greeting + conditions still play. Snapshot is **plugin-composed** (telemetry-derived `RaceStartConditions` + PI driver-name pick), translator exposes `getRaceStartConditions()` without the pit speed limit (race start doesn't speak it). Family `race-start` (distinct from `session-start`) reserves the namespace for future race-only openers (wet-race brief, formation-lap brief) so a future addition can preempt this scenario without affecting practice / qualifying.
- **Race status + race end** — issue #569. Two families on the same trigger model: race-status (`lap.completed` `where:` filters on `sessionType === "race" && lapsSincePositionChange > 0 && lapsSincePositionChange % 3 === 0 && !getRaceFinishedFired()`) plus race-end (`race.finished`, a once-per-session latched event the translator emits on the first lap.completed after the checkered raises in a race). Demonstrates **payload extension as cadence anchor** — `lap.completed.lapsSincePositionChange` is computed in `diffLaps` from `state.lastPositionChangeLap`, anchored on the driver's first valid lap (no change yet) so a hold-position-from-start driver still hears every-3 status updates; the same field acts as both the cadence counter (race-status) and the change-detection signal (position-change). Race-end uses a **latch-once event** rather than a transient — the diff emits race.finished only on a successful position read so a missing-position lap defers the latch and the next lap.completed retries. Cross-scenario coordination via a **state-field resolver** (`isRaceFinished()`) lets race-status's `where:` suppress on the final lap without inter-scenario coupling — the diff publishes race.finished first into the pending queue, so by the time lap.completed's where: runs the latch reads true. Two new bus events (`position.changed` is added as plumbing for future per-change race callouts but has no consumer this issue; `race.finished` is consumed by race-end). Reach for this pattern when a single bus event needs to drive multiple families with different cadence/gating rules, and when one family's fire needs to suppress another's same-tick fire.
- **Overtake gained / lost** — issue #574. Two-event family with mirrored gain/loss semantics. **Bus event extension instead of a new shape** — `overtake.completed` was extended with position context (`position`, `previousPosition`, `gapBehindMeters`, `isLeader`, plus the class-position fields) rather than introducing a separate `overtake.gained` event, because the gain side already existed; the new `overtake.lost` parallels it for the loss direction. **Physical-gap gating in the translator** — on top of the existing `OVERTAKE_HOLD_MS = 3000` sustainment + `OVERTAKE_MAX_JUMP = 3` sim-glitch filter, a 10 m (`OVERTAKE_MIN_GAP_M`) distance check between the player and the relevant neighbour (whoever's now immediately behind for a gain; immediately ahead for a loss) postpones emission rather than dropping it — pending state is held until the gap opens up. Computed from `CarIdxLapDistPct` × parsed track length (cached on `TranslatorState.trackLengthMeters` keyed by `(TrackID, SessionNum)` so a track change invalidates the cache). When track length isn't parsed yet, the gate is treated as unknown and emission proceeds — don't punish missing data. **Driver-name composition from a dedicated per-name clip group** — the loss line's "Come on, &lt;name&gt;." slot is a full per-name clip from the `position-overtake-come-on` group (one entry per driver name + a `driver` fallback), resolved via `resolveActiveDriverName(driverNames, "driver")` so the line stays complete even when the user's name isn't recorded. Originally (#542/#574) this slot reused the `session-start-greeting/<driverName>.mp3` pool, but those clips carry an "Ok, &lt;name&gt;," greeting prefix, so the spliced line played "Come on, Ok, Niklas. Don't give up..." — #591 replaced the splice with purpose-recorded "Come on, &lt;name&gt;." clips and dropped the generic `come-on-01` from the sequence. **Two scenarios under a shared `family: "overtake"`** so a fast sequence of swaps doesn't stack stale callouts — the engine preempts the in-flight family-mate when a fresher fire arrives. Reach for this pattern when extending an existing event with new payload fields (vs. introducing a parallel event), when a gate needs to *postpone* rather than *drop* a pending fire while waiting for an external condition, and when a callout needs to compose with a per-user dynamic clip that already has a pool. The shared "We're currently P[n]" readout (live position at speak-time + cross-trigger cooldown) lives in `position-readout.ts` and is reused by overtake, lap-completed (#566), and race-status (#569) — see the `POSITION_CURRENTLY_CLIP` constant + `tryClaimPositionAnnouncement` cooldown.
- **Multi-class overtake detection** — issue #588. Demonstrates **keying change-detection on the position that's actually spoken**. The overtake diff originally detected on OVERALL position (`calculateRacePositions[playerCarIdx]`), but in a multi-class race the overall rank churns as other-class cars pass / pit / lap even while the driver holds station in class — so a steady class-leader heard an endless stream of "we lost a position / we're currently P[class]" (the readout already speaks CLASS position in multi-class via `selectLivePosition`). Fix: `diffOvertakes` computes `useClass = isMultiClass === true && rawClassPos > 0` and runs all change-detection / sustainment on `currentPos = useClass ? classPos : overallPos` against a `lastEffective` baseline; single-class is byte-identical (still overall). The payload keeps overall `position`/`previousPosition` and class `classPosition`/`previousClassPosition` (consumers read class in multi-class); `isLeader` stays overall ("leading the race" ≠ class P1). The physical-gap gate is skipped in multi-class — the class neighbour can't be found from the overall `positions` array, and a class change sustained for the hold window is already a real overtake. Reach for this pattern when a callout's *detection* signal and its *spoken* value must be the same projection of multi-dimensional telemetry (overall vs class), and when a gap/neighbour gate doesn't translate to the new projection (skip it rather than mis-compute).
- **Overtake round-trip suppression** — issue #597. Demonstrates **gating an emission on the last *announced* value, not just the per-tick baseline**. The overtake baseline (`lastPosition`/`lastClassPosition`) advances every tick, so a momentary unannounced excursion (P10 → P9 → P10, where the P9 leg never sustained the hold window) moved the baseline to 9 and the settle back to P10 confirmed as a *loss* (9→10) — the driver heard only the down-leg of a flicker. Fix: `state.lastCalledPosition` tracks the position last actually announced by a callout; at each confirmed gain/loss (after the sustainment + gap gates) the emission is skipped when `currentPos === state.lastCalledPosition` (net no-op since the last callout), and `lastCalledPosition` is updated *only* when a callout actually fires. Seeded on the first eligible tick, rolled silently under caution, reset in `resetOvertakeState`, and compared in the same effective space the detection uses (#588). A *sustained, announced* gain then a real loss back still fires both (the gain updated `lastCalledPosition`); only unannounced round-trips are suppressed. **Race-start grid seeding (#568 follow-up):** at a race start the first-tick seed anchors *both* `lastPosition` and `lastCalledPosition` to the player's announced starting grid slot — the translator passes `resolveStartingGridPosition(sessionInfo)` (the same overall qualifying position the race-start callout speaks) into `diffOvertakes` as an optional trailing `startingGridPosition` param (trailing + optional so the diff's ~50 call sites stay untouched). So early-race gain/loss is measured from the grid and an opening-lap round-trip back to it is silent. (Originally single-class only because the grid value was overall; #599 made `resolveStartingGridPosition` return the EFFECTIVE grid slot — class in multi-class — and the diff now seeds the matching detection space, so multi-class anchors to the class grid slot too.) Reach for this pattern when a transient that never produced output can still move a baseline and make the *return* to the last-spoken state look like a new event — track the last-emitted value and short-circuit equal returns; and when a baseline should start from a *semantically meaningful* anchor (the grid) rather than the first value the diff happens to observe.
- **Pit-box count-in** — issue #600. Demonstrates **a callout driven by a derived continuous distance rather than a sim enum/state diff**. The translator resolves the player's box from `SessionInfo.DriverInfo.DriverPitTrkPct` (`resolvePitBoxTrkPct`) and `diffPitBoxCountdown` computes the forward gap from `LapDistPct` to the box, folded around the lap, times the cached `state.trackLengthMeters` (reused from #574). The matching mark is the **band** the remaining distance falls into — the smallest threshold (120/100/80/60/40/20 m) still ≥ the gap, with a `1e-6` epsilon so a `pct × length` value a hair above an exact boundary still lands in the intended band — so a normal approach fires `five`→`pit-now` once each, and once the box is passed the gap folds to ~a full lap so no band matches and the count stops. **Threshold-crossing via entry-seeding (issue #601 review):** on the first valid tick of a pit-road visit the diff seeds every already-passed threshold into `state.pitBoxMarksSpoken` (gated by `state.pitBoxEntrySeeded`), so a mark only fires on a genuine downward crossing — joining pit road mid-band (e.g. at 70 m) never speaks a just-passed number ("three"); the count picks up at the next mark ahead. Both the set and the seeded flag are **cleared whenever the car is off pit road**, so a second stop counts down again; there's no connect-time seeding concern since the diff keys on live distance, not a transition. Gated on `OnPitRoad` and **suppressed in the stall** (`PlayerCarInPitStall`) so an arrived/connecting-in-box car gets no spurious "pit now". The audio side is **six per-mark scenarios → one `count-in` opt-in** (the track-conditions multi-scenario/single-subject shape), `family: "pit-box"` for preempt, and **no radio-open/close frame** (terse countdown). New bus event `pitBox.countdown` with a `{ mark: PitBoxMark }` payload; the box position is known up front so the count-in works on the **first** stop of a session — no learn-once needed. Reach for this pattern when the trigger is a continuous measurement (distance, time-to-X) rather than a discrete state change: band-select on the live value, dedup per-episode in a Set keyed to the activity window, and reset on the window's exit edge.
- **Invalid-lap prefix on the position callout** — issue #572. Demonstrates **extending an existing callout with a contextual prefix derived from a new payload field, without adding a new opt-in**. Adds `lapIsValid?: boolean` to the `lap.completed` payload — derived in `diffLaps` from `resolveLapIsValid(telemetry)` which `every`s the four `LapDeltaTo*_OK` flags (`LapDeltaToBestLap_OK`, `LapDeltaToSessionBestLap_OK`, `LapDeltaToSessionOptimalLap_OK`, `LapDeltaToSessionLastlLap_OK` — preserving iRacing's "Lastl" typo) and returns `undefined` when no flag is present so consumers fall through to the existing path on a missing signal. The position scenario wraps its existing `if/then/else` (pole vs intro+number) in a new outer `if/then/else` keyed on `sessionType === "qualifying" && lapIsValid === false`; the invalid branch is composed from static clip steps — a local `POSITION_DIDNT_COUNT_CLIP` ("That lap didn't count.") followed by the shared `POSITION_CURRENTLY_CLIP` (#574's "We're currently") and the existing `position.number` var, beating the pole / "better" branches unconditionally. **Gated to qualifying** so the #574 race path (live position at speak-time + shared cooldown) is untouched — "that lap didn't count" has no meaning in a race where every lap counts; the frozen-snapshot `position.number` resolver returns the qualifying number. No new opt-in key — rides on `calloutEnabledPositionChange` because the invalid prefix is conceptually the same callout with a contextual modifier; if user feedback later wants it independently silenceable, add `calloutEnabledPositionInvalidLap` as a separate subject. Reach for this pattern when the new behavior is a *modifier* of an existing callout (rather than a parallel subject) and the trigger is already on the bus payload.
- **Class focus in multi-class: starting grid + leader** — issue #599. Demonstrates **making the LAST overall-only references consistent with the class-aware detection (#588) and readout**. Two strands. (1) **Starting grid position.** `resolveStartingGridPosition(sessionInfo)` returns the EFFECTIVE grid slot — the player's CLASS slot in multi-class, overall otherwise. The class slot isn't a direct YAML field, so it's computed: build a `CarIdx → CarClassID` map from `DriverInfo.Drivers`, then count same-class `QualifyResultsInfo.Results` entries with a better (lower) overall `Position` and `+1` (falls back to the overall slot when the player's class can't be resolved). One function feeds BOTH consumers — the race-start callout (`getRaceStartConditions().playerCarPosition`, so "Qualifying put us to P3" / "Starting from pole" now mean the class slot) and the overtake baseline seed — so they stay aligned by construction. `diffOvertakes` now applies the grid seed in the **matching detection space**: the class baseline in multi-class (where detection runs on class position, #588), the overall baseline in single-class. The transient multi-class tick before `PlayerCarClassPosition` populates (`rawClassPos === 0`, so `useClass` is false) detects in overall space while the grid value is a class slot — a space mismatch, so it falls back to the live seed rather than mis-anchor. (2) **Leader wording.** The overtake payload's `isLeader` field stays OVERALL-only (`position === 1`), but the *spoken* leader is now the EFFECTIVE leader via `isOvertakeEffectiveLeader(data)` (= class P1 in multi-class, overall P1 otherwise) — shared from `position-readout.ts` (the lower-level module, so `overtake.ts` imports it without a cycle) by both the overtake reaction (picks the "leading our class" clip vs the "leading the race" clip on `isMultiClass`) and the gained position readout (suppresses the follow-up when effective-leader, since the reaction states the position). The race-status "still leading" line was already triggering on class P1 in multi-class (it keys on `selectLivePosition`), so #599 only fixed its **wording** — its `stillLeading` var picks `still-leading-class-01` when the live position is multi-class. Two new clips (`position-overtake/nice-pass-leader-class-01`, `race-status/still-leading-class-01`) in `default.voice.json`; no new opt-in (the leader wording rides on the existing overtake/race-status callouts) and no bus-payload change (consumers derive effective-leader from the existing `position`/`classPosition`/`isMultiClass` fields). Reach for this pattern when a family is *mostly* class-aware and the remaining overall references are an inconsistency: derive the projection (class vs overall) at the consumer from fields already on the payload rather than adding parallel events, and place a shared helper in the dependency sink to avoid an import cycle.
- **Replay-only session gate — suppress callouts while the user is watching a replay, without regressing the #568 live-transition path** — issue #604. Demonstrates **picking the right discriminator from session YAML when a transient telemetry flag isn't safe to gate on**. Two emissions in `translator.ts` (`handleTick`) are deliberately published BEFORE the main replay guard at ~L841 so they survive the brief `IsReplayPlaying: true` tick that a live qualifying → race transition passes through: the SessionNum-delta `session.changed` (~L811) and the fresh-connect synthetic `session.changed { from: -1, to: N }` (~L754). Both fire `session.changed`, which is the trigger for race-start (`packages/audio-scenarios/src/catalog/pit-crew/race-start.ts`). Bug surface: a saved-replay scrub across a session boundary, or a plugin connect while the Replays UI is open, would synthesize a race-start brief for a race the driver isn't in. **Cannot gate on `IsReplayPlaying`** — that's the exact transient signal #568 was placed pre-guard to bypass. **Heuristic-based detection doesn't work either:** a layered "never-live + sustained-replay-ticks" approach needs threshold tuning the live-transition window doesn't permit, and `ResultsPositions`/`LapsComplete` presence in the current session can't distinguish "live race just-loaded" from "replay jumped to start of race" (in both, the current session reads zero laps; only later sessions' data differs, and during a live qualifying → race transition the FROZEN qualifying session ALSO has populated `LapsComplete`). **Validated against a real telemetry snapshot (`local/telemetry-snapshot-20260528-203804.json`):** iRacing exposes `WeekendInfo.SimMode` — `"full"` while live, `"replay"` while in the Replays UI — and crucially, SimMode does NOT flip during the live qual → race transition's `IsReplayPlaying` flicker; it stays `"full"` the whole time. `isReplayOnlySession(sessionInfo)` is a one-line read on this field. Gates **both** pre-guard emissions on `!isReplayOnlySession`. **Freezing `lastObservedSessionNum` during replay-only is load-bearing**: if the tracker advanced through a replay scrub, exiting back to live with a different SessionNum would emit a phantom `session.changed` measured against the scrubbed value. With the tracker frozen at the last live-observed SessionNum, exit-to-live either matches (no emit) or detects a genuine intervening session change. The fresh-connect synthesis is also gated **without latching** `freshConnectFireChecked`, so a user who closes the replay UI and starts a real session still gets the synthesis on the first live-SimMode tick. Reach for this pattern when a callout-driving signal must remain pre-guard but the SAME signal will mis-fire under a parallel use case, and look in session YAML for a self-reported discriminator before designing a tick-counter or persistence heuristic — iRacing often exposes the distinction directly (here: `SimMode`).
- **Self-managed running order — freeze blipped / teleported / retired cars, quiet retirement gains, tune reaction frequency** — issue #603. Demonstrates **owning the running-order state instead of re-deriving it from raw telemetry every tick**, classifying a callout by the cause of the position change, and gating audio behaviour on the cause without a new bus event or opt-in. (1) **The root issue is the same shape across three symptoms.** iRacing snaps a car's `CarIdxLapCompleted` / `CarIdxLapDistPct` / `CarIdxTrackSurface` to `-1` / `NotInWorld` the moment the car is gone (proven from dump-file analysis: a car a lap ahead went `lc6 dp0.142 ts3` → `lc-1 dp-1 ts-1` in one 60 Hz tick during a connection blip), and a tow teleports `CarIdxLapDistPct` to the pit. `calculateRacePositions` (pure, `@iracedeck/iracing-sdk`) ranks only cars with `lc >= 0 && dp >= 0`, so re-deriving order from raw telemetry every tick reshuffles the player on every blink / tow / vanish — manifesting as a string of phantom "Nice pass" gains (finishers leaving), single-tick rank churn (mid-race blinks of cars a lap ahead), and the "tow looks like a pass" case. Anchoring on iRacing's official `CarIdxPosition` is not an option — it only refreshes at S/F. (2) **One mechanism replaces the per-symptom patches.** `updatePositionTracking` (`diff/race-finish.ts`) maintains `state.positionLastKnownScores[carIdx]` (the last in-world `lc + dp`) and `state.positionFrozen: Set<number>` per car. A car's **effective score** is its live `lc + dp` while it's moving normally on track, **frozen at its last-known good value** whenever its telemetry is invalid (`NotInWorld`) or has drifted from the anchor by more than `TELEPORT_THRESHOLD` (0.05 lap — well above the ~0.0003 lap/tick of racing motion and the ~0.002 score-jump on a natural S/F crossing, well below any plausible tow). A car unfreezes automatically when its live score returns to within the threshold of the anchor (racing nearby again — covers a 1-tick blip cleanly). `calculateFrozenRacePositions` is the stateful wrapper around the pure SDK helper, sorting everyone by their effective score with the identical comparator. **Same rule, all four symptoms:** blink → frozen for one tick, unfreezes on return; disconnect → frozen at last → player passes it only by *advancing past its anchor*; finisher into the garage → frozen at the finishing score → can't be passed without finishing; tow → live score jumps far from anchor → frozen at the pre-tow on-track score → stays where it was. **Subsumes** an earlier checkered-detection design (`updateFinishedCars`, `USE_PER_CAR_CHECKERED`, `finishedCarScores`) AND a separate `−isTowed` patch — the unified model is more accurate and has fewer moving parts than either. (3) **Layering.** The wrapper lives in `sim-events-iracing` (it needs `TranslatorState`) while the SDK function stays pure (threading translator state into `iracing-sdk` would invert layering). Both `diffOvertakes` (detection) and `getLivePosition` (the spoken overall readout) consume it; `diffOvertakes` takes the frozen vector as a trailing optional `frozenPositions` param so existing call sites / tests that just want raw active positions stay unchanged. (4) **Retirement classification keys off the FROZEN ordering, not the raw active one** (CodeRabbit #605 review). When the player's effective rank improves, `isRetirementGain(state.lastFrozenPositions, playerCarIdx, state.positionFrozen)` returns true iff at least one car ranked ahead of the player in the PREVIOUS tick's frozen positions is currently in `positionFrozen`. Critically — the moment of detection is the tick the player CROSSES a frozen car's anchor (which is when the rank actually changes in the frozen path), NOT the tick the car vanished. An earlier draft keyed off the raw active ordering and missed pure frozen-anchor gains, because by the time the player crossed the anchor the raw order had long since dropped the vanished car. Latched across the hold window so a real pass deepened by a same-window retirement ahead is caught (the latch re-evaluates every held tick). Emitted as the new optional `overtake.completed.fromRetirement`; the reaction `where:` returns false on `fromRetirement` (readout only, no "Nice pass"). Single-class only — multi-class detects on `PlayerCarClassPosition`, which iRacing recomputes correctly when a car leaves. (5) **Sparser reactions + podium.** `shouldReactToOvertake(effectivePosition)` replaces the old 20 s `tryClaimReaction` cooldown: P1/P2/P3 always react (each with a dedicated line — P2/P3 added alongside the existing P1 leader line, single + "…in class" variants), everything else rolls `REACTION_CHANCE` (~1/3, via an injectable `reactionRandom` test seam). Podium gains suppress the follow-up position readout (their line states the position). (6) **Bare/full intro.** `shouldSpeakIntro` drops the "We're currently" intro for a bare "P[n]" when it was spoken within `INTRO_COOLDOWN_MS` (30 s) AND the move is ≤1 position; a >1 jump always restores the full intro. Tracked in module state (`lastIntroAt` / `lastSpokenPosition`) and scoped to the overtake position readout (the shared `readoutSequence`); race-status / position-change keep their own always-full intro, since the existing 20 s cross-trigger position cooldown already prevents their double-announce. Reach for this self-managed-state pattern whenever a pure helper's output is missing cross-tick memory that several symptoms all want (don't add per-symptom patches — own the state once); and for the cause-classification pattern when the *same* position change should produce different audio depending on whether it was earned (a pass) or inherited (a retirement / frozen-anchor cross). Key on the PREVIOUS-tick effective ordering, not the raw one — the gain is detected on the anchor-crossing tick, and the raw order no longer remembers the frozen car was ever ahead.
