# Race Engineer Callout — Reference Implementations

Worked precedents for the how-to in `@.claude/rules/race-engineer-callouts.md`. Each entry names the pattern a past callout established and the reusable lesson — consult one when a new callout needs a variation the checklist doesn't cover (continuous-distance triggers, multi-class projection, replay gating, cause classification, …). The full rationale for any entry also lives in its linked issue/PR.

- **Track Conditions / Wetness change** — issue #526. End-to-end example covering a brand-new family with a new bus enum, directional predicate, single per-callout opt-in covering multiple subjects.
- **Flag callouts** — issue #467. Per-subject opt-in (one boolean per flag colour); scope-aware predicate (`yellow.scope`); session-type branching (green/white/checkered).
- **Pit-service status** — issue #479. Per-target opt-in across eight subjects; sentinel suppression (* → None).
- **Damage** — issue #489. Single-subject family; debounced rising-edge detection in the diff.
- **Pit readback** — issues #476 / #481. Compositional scenarios (multiple pools per fire) and snapshot-at-fire-time pattern.
- **Session start** — issue #542. Single-subject family on the existing `session.changed` event (practice/qualifying sessions only); snapshot-at-fire-time conditions (`getSessionStartConditions()`) composed with the PI driver-name pick in each plugin; dynamic clips resolved via `engine.defineVar` (`registerSessionStartVars`) rather than enumerated `if` branches; a conditional clause (pit speed) gated on a curated value set. Established the **snapshot-driven builder-export shape** (issue #558): at the time `buildSessionStartScenario(getSnapshot)` + `registerSessionStartVars(...)` rather than a static `*_ALERTS` array, because the scenario's `where:` / `if` steps closed over a runtime resolver and had to be materialized at wiring time. The shape survived #1065 with the body moved into the script — today it is `buildSessionStartContract(getSnapshot)` + `registerSessionStartVocabulary(engine, getSnapshot)` in `session-start.ts`, and a future snapshot-driven family copies THAT (see the #1065 entry). **#668 moved the trigger** from `driver.firstOnTrack` to `session.changed` (~3 s after the session begins, before the driver leaves the garage) with a scenario-level `triggerDelay` providing the pause; the translator's fresh-connect synthesis was extended to cover practice/qualifying sessions (previously only covered race-start on connect). The #568 race-start scenario's `where:` already restricts itself to race sessions, so session-start's `where:` only needed to keep rejecting race — the two scenarios ride the same event without double-greeting.
- **UI-side acknowledgment (Race Engineer toggle)** — issue #554. Not a sim-event-driven callout — the scenario engine isn't involved. The Pit Crew action's `toggleRaceEngineer()` plays "going silent" / "resuming" directly via `playVoiceSequence(...)` on `AudioChannel.Voice`, gated by a per-callout opt-in (`calloutEnabledToggleRaceEngineer`). Reuses the same `in-flight` bypass shape as the PI Voice Test (`raceEngineerToggleInFlight` ↔ `raceEngineerTestInFlight`) so `applyRaceEngineerAudio` leaves Voice audible after the master gate flips off, until the ack clip finishes. Reach for this pattern when a Stream Deck button itself needs to speak a confirmation; reach for the scenario-engine pattern when telemetry should drive the speech.
- **SDK-connection ack (Telemetry-connect radio check)** — issue #554 follow-up. Triggered by a real-time signal that isn't on the event-bus catalog: the SDK controller's connection state (false→true transition). Each Pit Crew instance subscribes to `sdkController` with its own id (`pitCrewRadioCheck:<contextId>`); a module-scope `lastTelemetryConnected: boolean | null` dedups so the ack fires once per real transition no matter how many Pit Crew buttons happen to be mounted. Disconnect flips the tracker back so reconnects re-fire. Composes the active driver-name clip + a new `toggle/radio-check-01` clip via `playVoiceSequence(...)`. No in-flight bypass needed (master gate is on by definition when this fires; gate-off short-circuits before playback). Use this pattern when a non-event-bus signal (connection state, app monitor, settings change) should drive a one-shot callout, with care to dedup across action instances at module scope.
- **Lap time (best lap)** — issue #555. Single-subject family on a new `lap.completed` bus event with a rich payload (`{ lap, lapTime, isBest, isFirstValid, bestLapTime?, previousBestLapTime?, lapsRemaining?, timeRemaining?, sessionType? }`). Time readout composed from `lap-time-intro` + `lap-time-minute` + `lap-time-second` + `lap-time-decimal` clips via `engine.defineVar` (`registerLapTimeVars`); a conditional `{ if }` step skips the minute clip for sub-1-minute laps; `where:` filters on `isBest && lapTimeIsSpeakable(lapTime)` so off-range laps stay silent rather than producing a partial readout. The snapshot resolver is **plugin-owned** (a `lap.completed` subscription that caches the latest payload) rather than translator-owned, because the data is frozen in the event itself rather than read from live telemetry. Triggered by `LapLastLapTime` changing (the field iRacing refreshes when a lap completes) rather than `LapCompleted` incrementing — the counter races the time-field refresh and produces stale duplicate emissions. Established the **snapshot-driven builder-export shape** (issue #558) alongside session-start: at the time `buildLapTimeScenario(getSnapshot, getRaceFinishedFired?)` + `registerLapTimeVars(...)` rather than a static `*_ALERTS` array, because the scenario's `where:` / `if` steps closed over a runtime resolver and had to be materialized at wiring time. Today (#1065) it is `buildLapTimeContract(getRaceFinishedFired)` + `registerLapTimeVocabulary(engine, getSnapshot)` in `lap-time.ts`, the minute clip's `if` a named condition the script branches on — the current pointer for a future snapshot-driven family.
- **Race start** — issue #568. Single-subject family that **replaces** session-start in race sessions: the existing session-start scenario's `where:` returns false when `sessionType === "race"`, and race entries are spoken exclusively by the new race-start scenario fired off `session.changed` (~3 s after the transition lands, before the driver even has to leave the garage). Reuses an existing bus event rather than introducing a new one — the trigger is `session.changed` filtered by `classifySessionType(getSessionType()) === "race"`, anchored on the per-session reset hook (`resetPerSessionState`) from #564. Demonstrates **clip-group reuse across families** — the conditions brief (track temp / air temp / wetness intros, integer temp clips, wetness state clips, degrees-unit clips) re-points at the existing `session-start`, `session-start-temp-numbers`, and `position-number` groups so the new clips ship as only 3 entries (`time-to-race-01`, `starting-from-pole-01`, `qualifying-put-us-to-01`). Position clause uses a **two-branch conditional** — P1 picks a pre-recorded "Starting from pole. Well done." single clip; P2..POSITION_MAX composes "Qualifying put us to," + `position-number/<n>`; out-of-range or missing positions skip the clause entirely so the greeting + conditions still play. Snapshot is **plugin-composed** (telemetry-derived `RaceStartConditions` + PI driver-name pick), translator exposes `getRaceStartConditions()` without the pit speed limit (race start doesn't speak it). Family `race-start` (distinct from `session-start`) reserves the namespace for future race-only openers (wet-race brief, formation-lap brief) so a future addition can preempt this scenario without affecting practice / qualifying.
- **Race status + race end** — issue #569. Two families on the same trigger model: race-status (`lap.completed` `where:` filters on `sessionType === "race" && lapsSincePositionChange > 0 && lapsSincePositionChange % 3 === 0 && !getRaceFinishedFired()`) plus race-end (`race.finished`, a once-per-session latched event the translator emits on the first lap.completed after the checkered raises in a race). Demonstrates **payload extension as cadence anchor** — `lap.completed.lapsSincePositionChange` is computed in `diffLaps` from `state.lastPositionChangeLap`, anchored on the driver's first valid lap (no change yet) so a hold-position-from-start driver still hears every-3 status updates; the same field acts as both the cadence counter (race-status) and the change-detection signal (position-change). Race-end uses a **latch-once event** rather than a transient — the diff emits race.finished only on a successful position read so a missing-position lap defers the latch and the next lap.completed retries. Cross-scenario coordination via a **state-field resolver** (`isRaceFinished()`) lets race-status's `where:` suppress on the final lap without inter-scenario coupling — the diff publishes race.finished first into the pending queue, so by the time lap.completed's where: runs the latch reads true. Two new bus events (`position.changed` is added as plumbing for future per-change race callouts but has no consumer this issue; `race.finished` is consumed by race-end). Reach for this pattern when a single bus event needs to drive multiple families with different cadence/gating rules, and when one family's fire needs to suppress another's same-tick fire.
- **Overtake gained / lost** — issue #574. Two-event family with mirrored gain/loss semantics. **Bus event extension instead of a new shape** — `overtake.completed` was extended with position context (`position`, `previousPosition`, `gapBehindMeters`, `isLeader`, plus the class-position fields) rather than introducing a separate `overtake.gained` event, because the gain side already existed; the new `overtake.lost` parallels it for the loss direction. **Physical-gap gating in the translator** — on top of the existing `OVERTAKE_HOLD_MS = 3000` sustainment + `OVERTAKE_MAX_JUMP = 3` sim-glitch filter, a 10 m (`OVERTAKE_MIN_GAP_M`) distance check between the player and the relevant neighbour (whoever's now immediately behind for a gain; immediately ahead for a loss) postpones emission rather than dropping it — pending state is held until the gap opens up. Computed from `CarIdxLapDistPct` × parsed track length (cached on `TranslatorState.trackLengthMeters` keyed by `(TrackID, SessionNum)` so a track change invalidates the cache). When track length isn't parsed yet, the gate is treated as unknown and emission proceeds — don't punish missing data. **Driver-name composition from a dedicated per-name clip group** — the loss line's "Come on, &lt;name&gt;." slot is a full per-name clip from the `position-overtake-come-on` group (one entry per driver name + a `driver` fallback), resolved via `resolveActiveDriverName(driverNames, "driver")` so the line stays complete even when the user's name isn't recorded. Originally (#542/#574) this slot reused the `session-start-greeting/<driverName>.mp3` pool, but those clips carry an "Ok, &lt;name&gt;," greeting prefix, so the spliced line played "Come on, Ok, Niklas. Don't give up..." — #591 replaced the splice with purpose-recorded "Come on, &lt;name&gt;." clips and dropped the generic `come-on-01` from the sequence. **Two scenarios under a shared `family: "overtake"`** so a fast sequence of swaps doesn't stack stale callouts — the engine preempts the in-flight family-mate when a fresher fire arrives. Reach for this pattern when extending an existing event with new payload fields (vs. introducing a parallel event), when a gate needs to *postpone* rather than *drop* a pending fire while waiting for an external condition, and when a callout needs to compose with a per-user dynamic clip that already has a pool. The shared "We're currently P[n]" readout (live position at speak-time + cross-trigger cooldown) lives in `position-readout.ts` and is reused by overtake, lap-completed (#566), and race-status (#569) — the `tryClaimPositionAnnouncement` cooldown, plus a `POSITION_CURRENTLY_CLIP` constant until #1065, when the "We're currently" line moved into the script as `pool:position-intro-worse/currently`.
- **Multi-class overtake detection** — issue #588. Demonstrates **keying change-detection on the position that's actually spoken**. The overtake diff originally detected on OVERALL position (`calculateRacePositions[playerCarIdx]`), but in a multi-class race the overall rank churns as other-class cars pass / pit / lap even while the driver holds station in class — so a steady class-leader heard an endless stream of "we lost a position / we're currently P[class]" (the readout already speaks CLASS position in multi-class via `selectLivePosition`). Fix: `diffOvertakes` computes `useClass = isMultiClass === true && rawClassPos > 0` and runs all change-detection / sustainment on `currentPos = useClass ? classPos : overallPos` against a `lastEffective` baseline; single-class is byte-identical (still overall). The payload keeps overall `position`/`previousPosition` and class `classPosition`/`previousClassPosition` (consumers read class in multi-class); `isLeader` stays overall ("leading the race" ≠ class P1). The physical-gap gate is skipped in multi-class — the class neighbour can't be found from the overall `positions` array, and a class change sustained for the hold window is already a real overtake. Reach for this pattern when a callout's *detection* signal and its *spoken* value must be the same projection of multi-dimensional telemetry (overall vs class), and when a gap/neighbour gate doesn't translate to the new projection (skip it rather than mis-compute).
- **Overtake round-trip suppression** — issue #597. Demonstrates **gating an emission on the last *announced* value, not just the per-tick baseline**. The overtake baseline (`lastPosition`/`lastClassPosition`) advances every tick, so a momentary unannounced excursion (P10 → P9 → P10, where the P9 leg never sustained the hold window) moved the baseline to 9 and the settle back to P10 confirmed as a *loss* (9→10) — the driver heard only the down-leg of a flicker. Fix: `state.lastCalledPosition` tracks the position last actually announced by a callout; at each confirmed gain/loss (after the sustainment + gap gates) the emission is skipped when `currentPos === state.lastCalledPosition` (net no-op since the last callout), and `lastCalledPosition` is updated *only* when a callout actually fires. Seeded on the first eligible tick, rolled silently under caution, reset in `resetOvertakeState`, and compared in the same effective space the detection uses (#588). A *sustained, announced* gain then a real loss back still fires both (the gain updated `lastCalledPosition`); only unannounced round-trips are suppressed. **Race-start grid seeding (#568 follow-up):** at a race start the first-tick seed anchors *both* `lastPosition` and `lastCalledPosition` to the player's announced starting grid slot — the translator passes `resolveStartingGridPosition(sessionInfo)` (the same overall qualifying position the race-start callout speaks) into `diffOvertakes` as an optional trailing `startingGridPosition` param (trailing + optional so the diff's ~50 call sites stay untouched). So early-race gain/loss is measured from the grid and an opening-lap round-trip back to it is silent. (Originally single-class only because the grid value was overall; #599 made `resolveStartingGridPosition` return the EFFECTIVE grid slot — class in multi-class — and the diff now seeds the matching detection space, so multi-class anchors to the class grid slot too.) Reach for this pattern when a transient that never produced output can still move a baseline and make the *return* to the last-spoken state look like a new event — track the last-emitted value and short-circuit equal returns; and when a baseline should start from a *semantically meaningful* anchor (the grid) rather than the first value the diff happens to observe.
- **Pit-box count-in** — issue #600. Demonstrates **a callout driven by a derived continuous distance rather than a sim enum/state diff**. The translator resolves the player's box from `SessionInfo.DriverInfo.DriverPitTrkPct` (`resolvePitBoxTrkPct`) and `diffPitBoxCountdown` computes the forward gap from `LapDistPct` to the box, folded around the lap, times the cached `state.trackLengthMeters` (reused from #574). The matching mark is the **band** the remaining distance falls into — the smallest threshold (120/100/80/60/40/20 m) still ≥ the gap, with a `1e-6` epsilon so a `pct × length` value a hair above an exact boundary still lands in the intended band — so a normal approach fires `five`→`pit-now` once each, and once the box is passed the gap folds to ~a full lap so no band matches and the count stops. **Threshold-crossing via entry-seeding (issue #601 review):** on the first valid tick of a pit-road visit the diff seeds every already-passed threshold into `state.pitBoxMarksSpoken` (gated by `state.pitBoxEntrySeeded`), so a mark only fires on a genuine downward crossing — joining pit road mid-band (e.g. at 70 m) never speaks a just-passed number ("three"); the count picks up at the next mark ahead. Both the set and the seeded flag are **cleared whenever the car is off pit road**, so a second stop counts down again; there's no connect-time seeding concern since the diff keys on live distance, not a transition. Gated on `OnPitRoad` and **suppressed in the stall** (`PlayerCarInPitStall`) so an arrived/connecting-in-box car gets no spurious "pit now". The audio side is **six per-mark scenarios → one `count-in` opt-in** (the track-conditions multi-scenario/single-subject shape), `family: "pit-box"` for preempt, and **no radio-open/close frame** (terse countdown). New bus event `pitBox.countdown` with a `{ mark: PitBoxMark }` payload; the box position is known up front so the count-in works on the **first** stop of a session — no learn-once needed. Reach for this pattern when the trigger is a continuous measurement (distance, time-to-X) rather than a discrete state change: band-select on the live value, dedup per-episode in a Set keyed to the activity window, and reset on the window's exit edge.
- **Invalid-lap prefix on the position callout** — issue #572. Demonstrates **extending an existing callout with a contextual prefix derived from a new payload field, without adding a new opt-in**. Adds `lapIsValid?: boolean` to the `lap.completed` payload — derived in `diffLaps` from `resolveLapIsValid(telemetry)` which `every`s the four `LapDeltaTo*_OK` flags (`LapDeltaToBestLap_OK`, `LapDeltaToSessionBestLap_OK`, `LapDeltaToSessionOptimalLap_OK`, `LapDeltaToSessionLastlLap_OK` — preserving iRacing's "Lastl" typo) and returns `undefined` when no flag is present so consumers fall through to the existing path on a missing signal. The position scenario wraps its existing `if/then/else` (pole vs intro+number) in a new outer `if/then/else` keyed on `sessionType === "qualifying" && lapIsValid === false`; the invalid branch was composed from static clip steps — a local `POSITION_DIDNT_COUNT_CLIP` ("That lap didn't count.") followed by the shared `POSITION_CURRENTLY_CLIP` (#574's "We're currently") and the existing `position.number` var, beating the pole / "better" branches unconditionally — until #1065, when the shape moved into the script: the two clips are now the `invalid-lap` branch of the `position.readoutShape` case in `callouts.json` (`pool:position-invalid-lap/that-lap-didnt-count`, `pool:position-intro-worse/currently`), and the precedence lives in the case resolver. **Gated to qualifying** so the #574 race path (live position at speak-time + shared cooldown) is untouched — "that lap didn't count" has no meaning in a race where every lap counts; the frozen-snapshot `position.number` resolver returns the qualifying number. No new opt-in key — rides on `calloutEnabledPositionChange` because the invalid prefix is conceptually the same callout with a contextual modifier; if user feedback later wants it independently silenceable, add `calloutEnabledPositionInvalidLap` as a separate subject. Reach for this pattern when the new behavior is a *modifier* of an existing callout (rather than a parallel subject) and the trigger is already on the bus payload.
- **Class focus in multi-class: starting grid + leader** — issue #599. Demonstrates **making the LAST overall-only references consistent with the class-aware detection (#588) and readout**. Two strands. (1) **Starting grid position.** `resolveStartingGridPosition(sessionInfo)` returns the EFFECTIVE grid slot — the player's CLASS slot in multi-class, overall otherwise. The class slot isn't a direct YAML field, so it's computed: build a `CarIdx → CarClassID` map from `DriverInfo.Drivers`, then count same-class `QualifyResultsInfo.Results` entries with a better (lower) overall `Position` and `+1` (falls back to the overall slot when the player's class can't be resolved). One function feeds BOTH consumers — the race-start callout (`getRaceStartConditions().playerCarPosition`, so "Qualifying put us to P3" / "Starting from pole" now mean the class slot) and the overtake baseline seed — so they stay aligned by construction. `diffOvertakes` now applies the grid seed in the **matching detection space**: the class baseline in multi-class (where detection runs on class position, #588), the overall baseline in single-class. The transient multi-class tick before `PlayerCarClassPosition` populates (`rawClassPos === 0`, so `useClass` is false) detects in overall space while the grid value is a class slot — a space mismatch, so it falls back to the live seed rather than mis-anchor. (2) **Leader wording.** The overtake payload's `isLeader` field stays OVERALL-only (`position === 1`), but the *spoken* leader is now the EFFECTIVE leader via `isOvertakeEffectiveLeader(data)` (= class P1 in multi-class, overall P1 otherwise) — shared from `position-readout.ts` (the lower-level module, so `overtake.ts` imports it without a cycle) by both the overtake reaction (picks the "leading our class" clip vs the "leading the race" clip on `isMultiClass`) and the gained position readout (suppresses the follow-up when effective-leader, since the reaction states the position). The race-status "still leading" line was already triggering on class P1 in multi-class (it keys on `selectLivePosition`), so #599 only fixed its **wording** — its `stillLeading` var picks `still-leading-class-01` when the live position is multi-class. Two new clips (`position-overtake/nice-pass-leader-class-01`, `race-status/still-leading-class-01`) in `default.voice.json`; no new opt-in (the leader wording rides on the existing overtake/race-status callouts) and no bus-payload change (consumers derive effective-leader from the existing `position`/`classPosition`/`isMultiClass` fields). Reach for this pattern when a family is *mostly* class-aware and the remaining overall references are an inconsistency: derive the projection (class vs overall) at the consumer from fields already on the payload rather than adding parallel events, and place a shared helper in the dependency sink to avoid an import cycle.
- **Replay-only session gate — suppress callouts while the user is watching a replay, without regressing the #568 live-transition path** — issue #604. Demonstrates **picking the right discriminator from session YAML when a transient telemetry flag isn't safe to gate on**. Two emissions in `translator.ts` (`handleTick`) are deliberately published BEFORE the main replay guard at ~L841 so they survive the brief `IsReplayPlaying: true` tick that a live qualifying → race transition passes through: the SessionNum-delta `session.changed` (~L811) and the fresh-connect synthetic `session.changed { from: -1, to: N }` (~L754). Both fire `session.changed`, which is the trigger for race-start (`packages/audio-scenarios/src/catalog/pit-crew/race-start.ts`). Bug surface: a saved-replay scrub across a session boundary, or a plugin connect while the Replays UI is open, would synthesize a race-start brief for a race the driver isn't in. **Cannot gate on `IsReplayPlaying`** — that's the exact transient signal #568 was placed pre-guard to bypass. **Heuristic-based detection doesn't work either:** a layered "never-live + sustained-replay-ticks" approach needs threshold tuning the live-transition window doesn't permit, and `ResultsPositions`/`LapsComplete` presence in the current session can't distinguish "live race just-loaded" from "replay jumped to start of race" (in both, the current session reads zero laps; only later sessions' data differs, and during a live qualifying → race transition the FROZEN qualifying session ALSO has populated `LapsComplete`). **Validated against a real telemetry snapshot (`local/telemetry-snapshot-20260528-203804.json`):** iRacing exposes `WeekendInfo.SimMode` — `"full"` while live, `"replay"` while in the Replays UI — and crucially, SimMode does NOT flip during the live qual → race transition's `IsReplayPlaying` flicker; it stays `"full"` the whole time. `isReplayOnlySession(sessionInfo)` is a one-line read on this field. Gates **both** pre-guard emissions on `!isReplayOnlySession`. **Freezing `lastObservedSessionNum` during replay-only is load-bearing**: if the tracker advanced through a replay scrub, exiting back to live with a different SessionNum would emit a phantom `session.changed` measured against the scrubbed value. With the tracker frozen at the last live-observed SessionNum, exit-to-live either matches (no emit) or detects a genuine intervening session change. The fresh-connect synthesis is also gated **without latching** `freshConnectFireChecked`, so a user who closes the replay UI and starts a real session still gets the synthesis on the first live-SimMode tick. Reach for this pattern when a callout-driving signal must remain pre-guard but the SAME signal will mis-fire under a parallel use case, and look in session YAML for a self-reported discriminator before designing a tick-counter or persistence heuristic — iRacing often exposes the distinction directly (here: `SimMode`).
- **Self-managed running order — freeze blipped / teleported / retired cars, quiet retirement gains, tune reaction frequency** — issue #603. Demonstrates **owning the running-order state instead of re-deriving it from raw telemetry every tick**, classifying a callout by the cause of the position change, and gating audio behaviour on the cause without a new bus event or opt-in. (1) **The root issue is the same shape across three symptoms.** iRacing snaps a car's `CarIdxLapCompleted` / `CarIdxLapDistPct` / `CarIdxTrackSurface` to `-1` / `NotInWorld` the moment the car is gone (proven from dump-file analysis: a car a lap ahead went `lc6 dp0.142 ts3` → `lc-1 dp-1 ts-1` in one 60 Hz tick during a connection blip), and a tow teleports `CarIdxLapDistPct` to the pit. `calculateRacePositions` (pure, `@iracedeck/iracing-sdk`) ranks only cars with `lc >= 0 && dp >= 0`, so re-deriving order from raw telemetry every tick reshuffles the player on every blink / tow / vanish — manifesting as a string of phantom "Nice pass" gains (finishers leaving), single-tick rank churn (mid-race blinks of cars a lap ahead), and the "tow looks like a pass" case. Anchoring on iRacing's official `CarIdxPosition` is not an option — it only refreshes at S/F. (2) **One mechanism replaces the per-symptom patches.** `updatePositionTracking` (`diff/race-finish.ts`) maintains `state.positionLastKnownScores[carIdx]` (the last in-world `lc + dp`) and `state.positionFrozen: Set<number>` per car. A car's **effective score** is its live `lc + dp` while it's moving normally on track, **frozen at its last-known good value** whenever its telemetry is invalid (`NotInWorld`) or its `lc + dp` jumps discontinuously from the previous tick by more than `TELEPORT_THRESHOLD` (0.05 lap — well above the ~0.0003 lap/tick of racing motion and the ~0.002 score-jump on a natural S/F crossing, well below any plausible tow). A car unfreezes when it resumes continuous forward motion (issue #697 refined this — the original "live score returns to within the threshold of the anchor" rule pinned a towed car at its stale anchor for the rest of the race; see the #697 entry below). `calculateFrozenRacePositions` is the stateful wrapper around the pure SDK helper, sorting everyone by their effective score with the identical comparator. **Same rule, all four symptoms:** blink → frozen for one tick, unfreezes on return; disconnect → frozen at last → player passes it only by *advancing past its anchor*; finisher into the garage → frozen at the finishing score → can't be passed without finishing; tow → live score jumps far from anchor → frozen at the pre-tow on-track score → held until it drives off again (#697). **Subsumes** an earlier checkered-detection design (`updateFinishedCars`, `USE_PER_CAR_CHECKERED`, `finishedCarScores`) AND a separate `−isTowed` patch — the unified model is more accurate and has fewer moving parts than either. (3) **Layering.** The wrapper lives in `sim-events-iracing` (it needs `TranslatorState`) while the SDK function stays pure (threading translator state into `iracing-sdk` would invert layering). Both `diffOvertakes` (detection) and `getLivePosition` (the spoken overall readout) consume it; `diffOvertakes` takes the frozen vector as a trailing optional `frozenPositions` param so existing call sites / tests that just want raw active positions stay unchanged. (4) **Retirement classification keys off the FROZEN ordering, not the raw active one** (CodeRabbit #605 review). When the player's effective rank improves, `isRetirementGain(state.lastFrozenPositions, playerCarIdx, state.positionFrozen, state.positionJustReleased)` returns true iff at least one car ranked ahead of the player in the PREVIOUS tick's frozen positions is currently in `positionFrozen` (or was just released from it this tick — `positionJustReleased`, #697 — so a tow-released rival dropping back doesn't read as a real pass). Critically — the moment of detection is the tick the player CROSSES a frozen car's anchor (which is when the rank actually changes in the frozen path), NOT the tick the car vanished. An earlier draft keyed off the raw active ordering and missed pure frozen-anchor gains, because by the time the player crossed the anchor the raw order had long since dropped the vanished car. Latched across the hold window so a real pass deepened by a same-window retirement ahead is caught (the latch re-evaluates every held tick). Emitted as the new optional `overtake.completed.fromRetirement`; the reaction `where:` returns false on `fromRetirement` (readout only, no "Nice pass"). - **Countdown outranks the readback + resume-from-interruption + inter-mark pending hold** — issue #758 (reverses #646). Demonstrates **flipping a scheduling pairing when field experience contradicts the original design**, and two new engine capabilities: **`resumable`** (an interrupt-cut queueable fire continues from the interrupted clip at idle-replay instead of re-firing from the top) and **`pendingHoldMs`** (a finishing fire holds the bus's pending drain so a train of related fires doesn't let the displaced line stutter back into its gaps). (2) **`resumable` (engine, opt-in per scenario).** When an `interrupt` cuts a queueable fire whose scenario declares `resumable: true`, `stashRunningIfQueueable` stashes the fire's FULL original expansion + the index of the op in flight (mapped through the `ActiveFire` source fields so a resumed fire cut AGAIN still stashes an absolute position). At idle-replay the engine RE-EXPANDS the sequence first: an unchanged expansion resumes at the interrupted clip — re-keying the walkie frame with the open tick when one was opened before the cut — while a changed expansion (the snapshot moved on while stashed) falls back to a full fresh replay, preserving the #481 freshness guarantee (the readback.test.ts interrupt-stash freshness test still passes untouched). The resume skips the cooldown re-check (a continuation, not a new fire). Opt-in matters: a blanket resume would break #669's furled speak-time `if:` validity gate, which relies on full re-expansion at replay — so `resumable` requires `queueable: true` (load-time validation) and is only for deterministic sequences with side-effect-free `if:` predicates; pool draws may differ between expansions and simply force the full-replay path. The knob lives on the INTERRUPTING scenario (the train knows more of itself is coming), not on the displaced one — a one-shot interrupter (meatball) still lets the readback resume immediately at idle. Reach for this trio when a time-critical countdown must win a band-mate: explicit between-band weight + `interrupt` on the countdown, `resumable` on the long line it displaces, and `pendingHoldMs` on the train's members so the resume waits for the train to finish.

- **Repeat an uncorrected state until the driver fixes it — pit-box positioning nags** — issue #951 (extends #479). Demonstrates **turning a latched sim state into a repeating callout without a cooldown**, and **why a repeat must NOT share its transition sibling's family**. iRacing reports a pit-box positioning error once and then leaves `PlayerCarPitSvStatus` latched, so a driver who overshoots, backs up, and stops still short of the box sits unserved in silence — iRacing's own spotter is equally single-shot, and a transition-only diff has no edge left to fire on. (1) **A dedicated event, not a flag on the existing one.** `pitService.positioningRepeat { status }` was added alongside `pitService.statusChanged` rather than extending the latter with `repeat?: boolean`: a repeat is not a transition, and a shared payload would force all five existing positioning scenarios to grow a `repeat !== true` guard — an ISP violation and a trap for every future consumer. The new event costs one catalog entry and one `event-names.ts` line; the eight transition scenarios are untouched. (2) **Cadence + movement hold, diff-side.** `diffPitStatus` takes `now` (the `diffPitLane` threading precedent) and re-emits every `PIT_STATUS_REPEAT_INTERVAL_MS` (2 s) while one of the five positioning statuses stays latched — deliberately **no cooldown**, since repeating IS the feature. The repeat is HELD while the car moves, gated on an **asymmetric** debounce: a single `Speed` sample above `PIT_STATUS_MOVEMENT_SPEED_MPS` (0.05 m/s ≈ 2 in/s, because box corrections happen at a crawl over inches) clears the rest clock instantly, while counting as at rest again needs `PIT_STATUS_REST_SETTLE_MS` (500 ms) continuously below it. The asymmetry is the design: noise costs at most a delayed nag, whereas the failure that matters — talking over a driver mid-correction — demands sustained evidence of stillness. Missing `Speed` reads as at rest (don't punish missing data). A transition re-arms the clock from the transition instant (its own full call speaks through the existing path), and a fired repeat re-arms **from `now`, not from the missed due time**, so a nag held back through a 10 s correction can't drain its backlog as a burst the moment the car settles. (3) **LEVEL-armed, not edge-armed — the review catch that mattered most.** The first implementation armed the cycle ONLY on a status transition while the seed / off-track branch disarmed it, so anything that RE-SEEDED the diff mid-stop left a latched error with no edge to arm on and went permanently silent — the exact failure the issue exists to remove. `pitStatusInitialized` resets on a plugin restart (a deck-host auto-update, #870), an SDK reconnect, a one-tick `IsOnTrack: false` blip, and the replay-flip `wipeStateForReplay` (which does NOT preserve it), so it is reachable in ordinary play, not a corner case. The fire path now arms from the LEVEL — a latched positioning error with `pitStatusRepeatDueAt === 0` starts a fresh interval — which is the shape the spotter's still-there loop already used, and is why that loop never had the equivalent hole. General rule: a REPEATING callout must be driven by current state; only a one-shot may be edge-driven. (4) **Bounded to pit road.** The repeat is gated on `telemetry.OnPitRoad !== false` (missing data counts as on pit road). Without it, a status still latched after the driver gives up and drives out would nag forever wherever the car next came to rest — a spin, a red flag, an off-track recovery — an unbounded exposure that level-arming makes strictly more reachable. The gate is deliberately NOT `PlayerCarInPitStall`: an overshot car may well read `false` there, which is exactly the repro case. (5) **Speak-time validity gate.** `queueable: false` does NOT guarantee a nag is dropped when it can't play — the engine sets it as the bus's PENDING fire whenever it outranks the in-flight line without interrupting (`weight > runningWeight && interrupt !== true`, `interpreter.ts`), and a pending fire replays WITHOUT re-running `where:`. A nag queued behind the long CHATTER-weight readback could therefore speak after the driver had already parked correctly. The whole sequence is wrapped in an `if:` (the #669 furled precedent — `if:` expands at speak time, deferred replays included) re-checking the live `PlayerCarPitSvStatus`; unknown telemetry plays (#574), which also keeps every nag auditionable from the scenario harness. Read `queueable: false` as "never replayed after losing to an equal-or-higher-weight line" — it says nothing about the lower-weight case. (6) **The repeat needs its OWN family.** The issue specified sharing `family: "pit-status"`, but same-family preemption replaces the in-flight family-mate BEFORE any weight comparison, so the first nag at t+2 s would chop the ~2.5 s initial call mid-sentence. The nags therefore carry `family: "pit-status-repeat"` plus an explicit `PIT_STATUS_REPEAT_WEIGHT = 40` (between `CHATTER` and `NORMAL`, the #655/#758 between-band precedent), `interrupt: false`, `queueable: false` — which produces the intended behavior through WEIGHT instead: a nag arriving mid-call is dropped and retries on the next cadence tick (the diff already advanced its clock, so the cadence is unaffected), a fresh error at `NORMAL` outranks a playing nag and speaks in full the moment it ends, and nags still replace each other within their own family. Strictly-below is load-bearing — at equal weight the fresh error would be the one dropped. Terse delivery (no radio frame, the #600 pit-box precedent) because beeps at a 2 s cadence drown the words. (7) **No new opt-in** — the five repeat scenario ids map onto the existing `PitStatusCalloutId`s in `SCENARIO_ID_TO_PIT_STATUS_ID` (the #772 two-stage white-flag shape), so one checkbox governs both stages and there is no schema / PI / plugin / `registerPitCrew` change. Within audio-scenarios the positioning-subject list is single-sourced in `pit-status.ts` and feeds both arrays, but note it is still **forked across packages**: the translator keeps its own `POSITIONING_ERRORS` set in `diff/pit-status.ts`. Both must gain a status together — a diff-only addition emits a dead event every 2 s, an audio-only addition is dead code, and nothing cross-checks them. **Known unverified:** a live capture (#951 manual test) showed the same positioning status re-firing 6 s and 13 s apart, which means the status is not always latched — it can flick through `None` and back. The repeat handles that correctly (the `→ None` transition disarms, the return re-arms and speaks the full call), but the duty cycle was never measured; if a flicker faster than the 2 s cadence ever shows up, the repeat would be starved and look like this bug again. Reach for this pattern when a sim reports a correctable error as a latched state with no repeat edge: own the cadence in the diff with a `now`-threaded due-time, arm it from the LEVEL so a re-seed can't silence it, gate it on an asymmetric activity debounce so the engineer yields while the user is already acting, bound it to the context where the error is actionable, re-arm from the fire instant to avoid backlog bursts, add a speak-time `if:` because a lower-weight loss still queues — and give the repeat its own family with a strictly-lower weight, never the transition's family, so preemption can't invert into the repeat cutting the call it repeats.

  **(2) Pool members are matched with an exactly-two-digit variant suffix** (`<base>(?:-\d{2})?.mp3`). These clips shipped three-digit (`pit-limiter-001`) — the only such group in the repo — so every pool built EMPTY, and an empty pool skips its step at fire time. The callouts would have fired, played the radio-open/close ticks, and been silent between them: registered, enabled, unit-tested and mute, because tests build pools against a mocked manifest. Count the digits when a new family's clips predate the convention.
  **(3) A pool is every clip sharing a base**, so two scenarios cannot split one base. Moving a clip between families is a RENAME onto a new base, not a variant reassignment — and `generate.manifest.json` is keyed by clip path with a content hash, so a rename that skips it re-bills generation.
  **(4) Capability fields are read by PRESENCE, and the harness could not express absence.** The mock telemetry omitted `dcPitSpeedLimiterToggle` entirely, so one family could never fire and the other always would; and because the telemetry patch spread-merges and JSON has no `undefined`, no request could make a field absent. Fixed generally with an explicit `null` that DELETES a key, which makes `hasVisor` and `hasWipers` auditionable too.
  Two smaller reusable calls: a spoken value that another callout already speaks belongs folded into an existing line rather than given its own scenario (the pit limit is already in the session-start brief, so a standalone one would duplicate it and collide on the same trigger), and a family needing a runtime value should reuse an existing snapshot resolver rather than add a positional parameter — `registerPitCrew` is past the arity where positional works, and every addition is another slot an insertion can silently misalign.
- **Callout scripts move into the voice pack — the contract/script split, `case` for a multi-way choice, the frame as a contract field** — issue #1064 (the flags family migrated as proof; #1065 migrates the rest, #1066 documents the format). Demonstrates **splitting one object along the axis its two halves change on**, **a mapping that belongs to the pack rather than to code**, and **presentation applied by the engine rather than spelled in every sequence**. A `Scenario` welded together the telemetry logic that decides WHETHER and WHEN the engineer speaks (`when`/`where`, weight, family, interrupt, queueable, cooldown) and the wording that decides WHAT — and wording is the whole substance of a voice pack, which until now could only re-record lines we had written. The split pairs two artifacts by id: the **contract** (`ScenarioContract`, `flagContract(id)` in `flag-alerts.ts`, registered with `engine.defineContract`) keeps everything scheduling-shaped plus the default `frame`, and registers every var, condition and case a script may name (`registerFlagVocabulary`); the **script** (`scenarios["pit-crew.flag-red"]` in the voice's `callouts.json`, authored in `configs/default.voice.json` and extracted by `pnpm generate:callout-scripts`) carries `sequence`, `comment`, `test`, an optional `skip` and an optional `frame` override. **Scheduling, pacing and triggers are withheld from packs deliberately**: a pack that demotes a safety flag below chatter or zeroes a cooldown produces behaviour that reads as a plugin bug, and letting packs bind triggers would need a predicate language over telemetry, a public bus contract and a sandbox — five times the work, aimed at the half that does not vary by voice. **The grammar is the closure DSL serialised, with one line drawn hard: the only operator is `!`.** No `and`, `or`, comparisons, field access or arithmetic — a script needing `a && b` gets a named condition registered for it. That is what stops the format sliding into a predicate language one convenience at a time, and it is what makes the vocabulary the public API (names and one-sentence descriptions, read back through `engine.vocabulary()`) with the JSON only how it is spelled. **`case` earns its place by removing nesting, not adding power.** Green, white and checkered branch on `{ "case": "session.type", "of": { practice, qualifying, race, default } }` — the key comes from the resolver, the mapping stays in the script, and the key set is DECLARED with the registration (`defineCase(name, resolver, keys, description)`) so a pack author can write the branch without reading the resolver and the compiler can refuse a typo'd key. Use `if` for a binary choice and `case` for a multi-way one.
  **Two rules for writing a script, both found by writing the two hardest callouts out in full, and neither applicable by a codemod.** *A lookup is a var; a condition is a choice*: translating pit readback literally produces eighteen near-identical `if` blocks for the tire slot alone — that table is a lookup over a closed set, not a script decision, and as a `case` with a declared key set the whole callout is sixteen readable lines. And `case` rather than a var returning the clip, because the mapping is the pack's business: with `case` a pack can collapse the four three-corner keys onto one line or map a key to `[]` and stay silent, where a var returning `tires-all.mp3` would force fifteen separate recordings — the difference between a plausible first pack and none. *A fragment may not be optional; a clause may*: `{ optional }` swallows a step that resolves to nothing, and whether that is correct depends on what is left behind — drop the number from "you're now P4" and the speech is broken or false, drop readback's tire clause and it is shorter and still true. So the tire slot can carry `"default": []` and a position readout cannot. **The lap-time minute is the instructive boundary, and the mistake is the useful part:** the first reading was that dropping the minute always yields a false statement ("one thirty-two four" degrading to "thirty-two four"); Niklas corrected it — dropping the minute is a real racing convention, Crew Chief reads times that way, and it only breaks where the assumed minute is not 1 (an 8:32 Nordschleife lap). A rule about correctness was being applied to a matter of register, so the decision was handed to the pack (a terse pack writes `{ "optional": ["{{lapTime.minute}}"] }`, a careful one keeps the hard `if`) rather than settled in the grammar.
  **The frame became a contract field, and an empty body gets no frame.** `@pit-crew.radio-open` / `-close` sat in 35 sequences and were presentation, not content — and not merely a beep: `radio-open` is the tick PLUS `ambient: start` / `seek`, the only thing that ever ran the pit-lane ambience bed. The contract names the default (`DEFAULT_FRAME` = `radio`; `frame: NO_FRAME` on the four opt-outs whose cadence would drown the words — pit-box count-in, pit-status nags, corner names, spotter — each beside the rationale comment it always had), the pack defines what a frame MEANS under `frames`, the engine wraps at fire time, and no sequence spells it. The wrapper applies only when the body expanded to at least one `play` op, which is what preserves the furled pair: its speak-time predicate sat INSIDE the frame precisely so a stale fire produced no beeps, and now no callout can play bare ticks around nothing. Two settings fell out of it — Radio beeps and Pit ambience, applied by POSITION inside the frame rather than by clip path — because `backgroundVolume` governing both was the real complaint under "put the beeps behind an option"; the wrapper landed for every family in the same change so one mechanism honours the settings one way, rather than two mechanisms two ways for a release. `radio-frame.ts` was deleted; a sequence still carrying the includes would be framed twice. The position rule reached the whole engine in the review fix wave: frame ops are TAGGED with their side, frame clips ride the SFX channel whatever they are, the switches drop frame STEPS before expansion (a switched-off step cannot abort), the frame expands before the body (a frame abort commits no body side effect), and the resume re-key replays the tagged open — nowhere does the engine still recognise the frame by the built-in tick's path except for a legacy sequence that spells the tick inline, gone with #1065.
  **Skip semantics: a pack is never punished for what it does not say — and ours is.** Absent means skipped (individual ids at debug, an aggregate per voice at debug), `skip: true` is the same behaviour made deliberate, an unknown pool / var / condition / case key / include / frame is ONE warn per (voice, scenario) and that callout skipped for that voice, a malformed file drops the voice from its pack (never the whole pack; the unit is the voice because the script is per voice), no file at all is a valid clips-only voice, and a `setWarning` banner marks an active voice with no loadable script. Silence is the right failure for a third-party pack and the wrong one for ours, so the bundled voice gets `bundled-scripts.test.ts`: every contract the real `registerPitCrew` registers has an entry (read off a pass-through spy on `defineContract`, so the set widens as #1065 migrates), no entry names an undeclared id, every entry carries `comment` and `test` — required because they are the source text of the published reference, not decoration — and every referenced name exists. It is the safety net JSON otherwise costs: deleting a TypeScript array entry broke a test, deleting a JSON key would not have. **Rejected on purpose:** inheriting the default script when a pack omits a callout (an omitting pack must not silently speak in our voice) and a sibling `<id>.scenarios.json` (honest about lifecycles, but two files per pack; the extraction step gives the same separation without splitting what an author edits).
  **Two findings from the migration worth carrying forward.** *Making a predicate public exposes its inconsistencies*: the green/white/checkered branch had tested `=== "Practice"` exactly, while `isRaceSession` beside it (and the translator's own classifier) treat "Lone Practice" and "Offline Testing" as practice via `includes` — so `session.type` would have called those sessions a race while the `raceOnly` gate in the same file did not. Now one `classifySessionType` in `race-start.ts` is the package's session rule for the vocabulary AND every `where:` gate, with one documented asymmetry: a gate never suppresses on missing data (`isRaceSession("")` stays `true`, the #574 precedent) while the vocabulary reports `""` honestly as `null` and leaves it to the script's `default` branch — which is why the three session-typed scripts carry `"default": ["pool:flag-<x>-race"]`, the old code's implicit "not practice, not qualifying → race" made an explicit pack choice. *A name has to carry a decision*: the migration first gave every flag a named pool (`flag-blue` → `flags`/`blue`, thirty of them) on the spec's argument that the name is the indirection protecting packs from our file layout — and the maintainer's question, why name a pool when every callout is one and most have a single take, exposed that none of the thirty decided anything: each restated its path, and the indirection protected against a reorganisation of `flags/` that would break every pack's clip folder regardless. So the script addresses its clips directly as `pool:flags/<base>` (the same `pickFromPoolRef` path a var resolver's reference takes, same members, same no-repeat tracker), `pools` became an alias facility — a name only where it decides something the path does not, an alias onto another group or a separate no-repeat tracker, with the reason in its `comment` — and `FLAG_POOL_NAMES` became `FLAG_CLIP_SOURCES`, a literal list of the published `(group, base)` pairs. A pool the script does name is still looked up before `POOL_REGISTRY`, so the two coexist until #1065 empties the registry applying the same test per family. Reach for this entry when a family migrates (#1065 does them one at a time, each conditional step on its own terms), when a script wants an operator (register a condition instead), when a branch has more than two arms (`case` with declared keys), or when a step might resolve to nothing (ask whether what remains is a sentence).
- **Migrate the whole callout catalog to pack scripts — one shape, one procedure, the within-pack coverage check** — issue #1065 (finishes what #1064 started; #1066 documents the format). Demonstrates **finishing a half-migration rather than living with two idioms**, **applying the two script rules at scale, by judgement**, and **replacing a check whose premise the new format invalidates**. A half-migrated catalog was worse than either end state: a contributor had to know which idiom a family used, the rules documented both, the generated reference could not be built from a catalog where half the scripts were closures, and a pack could not meaningfully override "everything except the eleven families still in code". So the remaining 125 callouts moved across — readback first and alone, as the spec's stress test (the fifteen-way tire table became one `readback.tirePattern` case with declared keys, and the body shared by its entry and exit readbacks became the first pack-defined fragment); then three workers in parallel over the pit, race-flow and opponent groups; then the close: `POOL_REGISTRY` deleted with `pools.ts` (no family kept a name — even `pit-action-acknowledgment`, the one alias the #1064 spec expected to survive for its separate no-repeat tracker, turned out to be a different `(group, base)` from the generic acknowledgment and needed none; the bundled `pools` is `{}`), `bundled-scripts.test.ts` widened to the whole catalog with a two-sided floor (at least `CATALOG_FLOOR` = 149 contracts, and exactly zero `defineScenario` calls, so a family re-added in the legacy shape cannot speak from code past the script checks), and `Scenario` / `defineScenario` re-documented as engine primitives the interpreter's tests use rather than a catalog shape. **Two engine prerequisites landed first.** Every vocabulary resolver now receives the fire's `ScenarioContext` (`VocabularyResolver<T>` in `dsl.ts`; a zero-parameter resolver stays assignable), because readback's opener branches on the EVENT's `reason` and several families read `ctx.data` inside their old `if` closures — without the context there was no honest way to register those as named conditions. And a script may define `fragments`, included as `"@<name>"` and resolved ONLY within the same script: the compiler inlines them at compile time (no runtime include for a script; cycles refused naming the chain), which is what let the last code-registered fragment go and kept fragments to genuine sharing between scenarios — `readback-body` and `gap-readout` are the two, and neither hides complexity inside one callout. **The family procedure** (plan, 2026-09-05) is the reusable part: every `Scenario` literal becomes a `ScenarioContract` with every scheduling field verbatim; every closure conditional migrates on its own terms — a closed-set table to a `case` with every key declared and described, a binary predicate to ONE named condition (compound predicates get one name, `readback.fastRepairSkipped`, never two a script would have to `&&`), a value to a var returning `pool:<group>/<base>`; the script entry carries `comment`, `test` (a harness route with real button labels) and the sequence, with `{ optional }` kept only where the remainder is still a true sentence and the judgement written into the `comment`; the family test fires through the real artifact narrowed to its own ids and fragments (a scripted contract is SILENT without `setScripts`, so every fire-through test needs a vacuity floor). **Migrating each conditional as a judgement found a silent regression.** #603 designed the position readout's "We're currently" intro to resolve to nothing inside its 30 s cooldown window, leaving the bare "P four"; #835 later made a null REQUIRED var abort the whole callout and did not touch that file, so from that release the bare-number path produced silence — the readout claimed the shared cooldown and played nothing. The script writes the intro as `{ optional: ["{{positionReadout.intro}}"] }`, which is exactly the rule's test (a number is a complete statement without its lead-in), and the bare number speaks again. A codemod would have translated the closure `if` faithfully and kept the bug. **`voice-parity.test.ts` was replaced, and the replacement is stronger.** It refused a non-default voice any `<group>/<base>` the default lacked, reasoning that such a base was referenced by no pool — true only while pools came from a code registry; once a voice ships its own script, its own base is referenced by its own sequence, and enforcing parity would forbid the central thing the format exists to allow. `script-coverage.test.ts` (audio-assets) is per voice: every clip authored in a group the script addresses must be referenced (orphans), everything referenced must be authored and every pool name defined (dangling), with a floor for the bundled voice. Two things it cannot see are declared beside it: a group NO step addresses is var-driven and skipped whole (the vocabulary lives in audio-scenarios, which depends on audio-assets), and a MIXED group — addressed by steps for some bases while a resolver produces the rest (`session-start`, `incidents`, `pit-limiter`) — is covered by a small pattern list naming each resolver, guarded against going stale; declaring source groups per var so the check can read them is #1066's `lint:pack`. Its first run over the bundled voice did what the old test never could: it named `pit-readback/windshield-off` (authored, deliberately never spoken — the readback never says the negative because open-wheel cars have no windshield and telemetry cannot tell; parked in `DELIBERATELY_UNSPOKEN` with that reason) and `position-overtake/come-on` (the generic "Come on," take that #591 dropped from the sequence and nobody deleted). Reach for this entry when adding a callout to any family (the procedure is the checklist), when a resolver needs the event that fired the callout (read `ctx`), when a body is shared between two entries (a fragment — and only then), when a var can resolve to nothing (ask whether the remainder is a sentence, and remember #835 makes the wrong answer silent rather than wrong), and when a voice's clip goes unreferenced (the coverage check is the instrument, and its allowlists are for reasons, not for findings).
- **Document the voice-pack format — a reference generated from the catalog, the prose written once, the harness as the audition path, `lint:pack`** — issue #1066 (closes the #1064 → #1065 → #1066 sequence). Demonstrates **generating the half of the documentation that would drift and hand-writing only the half that decides**, **making a type carry the prose it lacked rather than keeping it in a document**, and **cutting a feature to the audience it actually has**. The website's Voice Packs section (`packages/website/src/content/docs/docs/voice-packs/`, sidebar group **Voice Packs**) is two kinds of page. Three are written by hand and describe decisions: the concept (`/docs/voice-packs/` — what a pack can change and cannot, why a correct script can be silent), the format (`/docs/voice-packs/format/` — the grammar, every rule the schema enforces, what a problem line looks like, what compiling does) and the tutorial (`/docs/voice-packs/first-pack/` — three callouts, three clips, a `voice-pack.json`, a three-entry `callouts.json`, heard in the harness). Three are generated and describe the catalog: `reference/callouts`, `reference/vocabulary` and `reference/recording-script` render ONE committed artifact, `packages/website/src/data/pack-reference.json`, which `pnpm generate:pack-reference` builds from `engine.contracts()`, `engine.vocabulary()`, the bundled `callouts.json`, `configs/default.voice.json` and the manifest — `scripts/generate-pack-reference.test.mjs` names the command on drift, and the site mirrors the artifact's shape by hand (`src/pack-reference-types.ts`, a path-naming parser) rather than importing the engine. **The reference needed prose no contract carried: when a callout fires.** An entry's `comment` says what is said and its `test` how to hear it; nothing said WHEN, because that lived in a `where:` predicate a pack author cannot read. So `ScenarioContract` gained `description` — one sentence in the sim's terms, US spelling, required for every catalog contract by `bundled-scripts.test.ts` (non-empty, ends with a full stop, at most 200 characters, does not open with its own id) — and the engine gained `contracts()` beside `vocabulary()`: a `ContractReport` per registered contract with every value EFFECTIVE (`frame` and `weight` carry the defaults, `event` is `null` for a `fire()`-only contract, `family` `null` when it has none), so no consumer re-derives what the scheduler already applies. Writing 149 sentences by hand found what a codemod could not: gates the sentences had to name (the podium exclusion on the position-gained callout, the 20 s cooldown four siblings share, the pit-road exclusion) and four stale script comments. **The spec's pool list became a recording script.** Named pools are an alias facility and the bundled `pools` is `{}` (#1064/#1065), so a page of pool names would have listed nothing; what a full pack must record is every `(group, base)` of the bundled voice with the text of every take — 46 groups, 1465 lines, 1544 takes — each line saying which entries address it directly (`usedBy`) and which var draws from its group (`viaVar`). That last attribution is a heuristic by design: a resolver is a closure, so a var draws from a group only if its DESCRIPTION names it (`descriptionNamesGroup` — `incidents/points-2`, or "the session-start clip group"; a plain word is deliberately not enough), which makes naming the group in a var's description a rule rather than a nicety, and the reference and the linter share the one function so they never disagree. Two rulings from the review are worth keeping: a recording line carries EVERY take's text (the 38 multi-take lines are alternate wordings, not repeats), and `usedBy` is direct consumers only, with a var's callouts on the vocabulary page instead of repeated across the 1169 lines only a var draws from. Callouts with no `family` (the meatball, the opponent flag and pit callouts) render last under "No family"; the six groups nothing draws from (`acknowledgment`, `names`, `openers`, `toggle`, `units`, `welcome`) stay in the artifact, the page marks them, and its prose names `toggle/`, `names/` and `welcome/` as played by plugin code outside the script (the linter exempts the three the same way — `PLUGIN_PLAYED_GROUPS` in `scripts/lib/lint-pack-run.mjs`, the runner's knowledge rather than the pure linter's, since neither a description nor a script can see a code path). The third was found by the final review, not the ruling: the ruling that surfaced the groups as possibly dead was made from the script and the vocabulary alone, and `welcome/greeting-01` is what the settings window's Race Engineer **Test** button plays after the driver's name (`packages/iracing-actions/src/audio/voice-test.ts`) — a consumer outside every task's file list, so the branch had documented and linted a clip the first press after installing a pack plays as dead. A by-path consumer has to be looked for in the plugin, not inferred from the catalog. So the tutorial ends in the scenario harness (`IRACEDECK_VOICE_PACKS_PATH` naming the packs folder lists a sideloaded voice beside the bundled one, and every callout's harness button is already named by its `test`), documented with its limit: a snapshot-driven callout fired with no matching state resolves to nothing and aborts, which is exactly what the `test` field is for. The check an author runs is `pnpm lint:pack <packDir>` (`lintPack` in `audio-scenarios/src/reference/lint-pack.ts`, the CLI in `scripts/lint-pack.mjs` + `lib/lint-pack-run.mjs`; exit 1 on any problem, 2 when it could not run): what the plugin would only skip quietly, said loudly — grammar problems, a script over the scanner's 1 MiB cap, every compile skip the pack did not mean with the compiler's reason, failed frames and fragments, dangling references, orphaned clips, and `<voice>: N of M callouts scripted` per voice, over the clip FILES a pack ships, in the scanner's own order. **The coverage rules moved to the leaf.** The plan put the shared script-vs-clips rules in `audio-assets/src/generate/`, which is `tsx`-run and never built, so a `tsc`-built linter cannot import it — and the reverse direction is a package cycle. `@iracedeck/callout-script` is the one package both consumers already hold, so `coverage.ts` (`coverageOf` / `orphansOf` / `danglingOf` / `checkCoverage`) lives there, `audio-assets`' `script-coverage.ts` became the config → rules adapter its test imports, and the bundled voice's facts (`VAR_DRIVEN_BASES`, `DELIBERATELY_UNSPOKEN`) stayed in the test as facts rather than rules — which is why a lint of the bundled tree is not expected to be clean.
