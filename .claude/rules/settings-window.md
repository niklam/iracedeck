# Settings Window (#992)

The dedicated, full-size settings window that owns the plugin-global settings. It is **not a Property Inspector**: it is a page the plugin process serves over loopback and opens as a chromeless browser app window — but it reuses the PI framework verbatim (`sdpi-components.js`, `pi-components.js`, the `global-*.ejs` partials, every `ird-*` component), so a control that works in a PI works in the window unchanged. Website docs: `docs/features/settings-window.md`.

Since #993 the server starts from the plugin's **store-ready startup block** (`ensureStarted()`, or the first `open()` if something gets there first) and runs for the process's lifetime, with its port + token — `_settingsChannel`, never persisted in the plugin's own store — mirrored to the deck host once per start (since phase 2) so Property Inspectors can bootstrap from it (the guarded full-cache mirror; see `global-settings.md`); on the fail-closed unreadable-file path that block never runs, so nothing is started and no channel is published. Every write the window makes lands in the plugin-owned settings file, now the single source of truth — and since phase 2 **every action PI talks to this same server** through its own bridge, so window ↔ PI ↔ PI edits all land in that one file and each surface sees the others' changes live (a PI whose bootstrap can't complete falls back to the deck host's copy — see `global-settings.md`).

## Architecture (where each piece lives)

| Request guard  | `deck-core/src/settings-window-guard.ts`                                                      | Pure. **Token first, then Origin, then cookie** (#993 phase 2): a valid launch token authorizes whatever the `Origin` — PIs are `file://` (Origin `null`) or host-served pages — while a token-less request must still match the loopback origin exactly (when it sends an `Origin` at all) before its `SameSite=Strict` cookie is even looked at, which is what keeps the DNS-rebinding mitigation on the cookie path. | Server         | `deck-core/src/settings-window-server.ts`                                                     | `node:http` + `ws`. Loopback only, **ephemeral port bound at plugin startup** (#993 — the lifetime changed, not the auth model), released on `close()`. Exposes `token` standalone for the `_settingsChannel` publisher. **Never throws out of a request or upgrade listener** — a malformed request target or percent-escape is a 400/404, the request handler is wrapped, and every accepted socket gets an `error` handler: an exception on any of those paths would end the plugin process. | Controller     | `deck-core/src/settings-window.ts`                                                            | One server per plugin, started by `ensureStarted()` at plugin startup or by the first `open()` — whichever comes first, idempotent and race-safe (concurrent first-callers share ONE in-flight start, and `close()` awaits a start already in flight so it can never orphan the server that start produces) — and **reused across opens** (a re-click never binds a second port). `ensureStarted()` resolves `{ port, token }`; the `onStarted` hook fires once per actual start with the same channel — the plugins bind it to `createSettingsChannelPublisher(...).publish` so a server that comes up late (after a failed startup bind) is still published and mirrored. Debug-logs the origin only, never the tokenised URL. A throwing hook is logged and swallowed.                                                                                                     |
| Settings store | `deck-core/src/settings-store.ts`                                                             | The plugin-owned settings file (#993) every window write ultimately lands in, via the injected host → `updateGlobalSettings`. | Failure banner | `deck-core/src/settings-window-warning.ts` + `settings-window-warning-reporter.ts`          | The controller's `onStatus` turned into the `_warnings` PI banner (#1005): a pure evaluator plus a thin reporter the plugins wire as `onStatus`, mirroring the elevation-mismatch pair. Two ids, because **placement is keyed by id**: `settings-window-server` (`error`) is page-wide and stays in the PI's top strip, `settings-window-open` (`warning`) renders directly above the Open Settings button (`open-settings.ejs`). They are NOT alternatives: a failed START raises BOTH — the error explains the page, and a third, short message marks the button unusable (it points at the error rather than repeating it, since both are on screen at once). The evaluator therefore returns a LIST, and the reporter reconciles it against `settingsWindowWarningScope`: a server report speaks for both records, an open report only for its own, so one press can never clear the page-wide error. **The button note cannot be raised by the press itself** — with no service there is no loopback channel, so the only thing that reaches a PI is the once-per-start host mirror (`publishUnavailable`), and anything raised after it has no route to the page. ## Rules

1. **The window is the only home for plugin-global settings** (#1003). New global settings go in a `global-*.ejs` partial (or one of the split group partials below) and are included by `settings-window.ejs`. Never author a global control in an action Property Inspector: the one exception is `key-bindings-section.ejs`, which shows an action's OWN bindings because they are contextual to the action being configured — and even those also appear, in full, on the window's Key Bindings tab.
2. **`accordion.ejs` has two modes.** Pass `settingsWindow: true` at a top-level include and it renders a flat `.ird-sw-card` instead of `<details>`; EJS copies include data into nested includes, so the `global-*.ejs` partials forward it without changes. **Exception:** an `include()` written INSIDE the object literal of another include (`include('accordion', { content: include('global-common-diagnostics'), … })`) is evaluated in the page's own scope and gets nothing from the outer call — pass `{ settingsWindow: true }` to that nested include explicitly, or its `locals.settingsWindow` guards silently render nothing (the Diagnostics card's Open folder button, #993). `locals.foo` inside a partial reads include parameters (the compile plugin no longer shadows EJS's `locals`).
3. **The Common Settings groups are partials**: `global-common-{window-focus,simhub,dual-press,replay,chat,updates,diagnostics}.ejs` (items only), placed on tabs by the window. Same for the Race Engineer block: `race-engineer-settings.ejs`, `race-engineer-callouts.ejs` (owns its list computation), `setup-warning-patterns.ejs`, rendered as cards. Both sets had a second home in a PI until #1003 — the `global-common-settings.ejs` assembler (deleted) and `pit-crew.ejs`'s three accordions (removed). Tests render the REAL partials and pin every setting key.
   **Scripts follow the same split**: behaviour for these controls lives in `settings-window-scripts.ejs`, included by the window only. `head-common.ejs` keeps what BOTH surfaces need. Adding a global-control handler to `head-common.ejs` ships dead script to all 35 PIs — a test guards both directions.
4. **Write only what changed — an optimisation now, not a correctness guard.** sdpi saves its _whole_ global object on every change; the fake host diffs it against the current cache with deck-core's `sameValue` (string forms equal parsed values) and forwards only the differing keys, sparing a re-parse and a listener fan-out on every keystroke. Under #993's single writer a full-object write would also be correct — before it, this diff was load-bearing: a full write marked every key pending and let the #896 overlay misread a PI edit restoring a previous value as a stale echo (a window value rolling back a PI edit on hardware). Keep the diff; don't rely on it for correctness.
5. **Things a PI can't do the same way in the window** — each has a window-mode path keyed on `window.__irdSettingsWindow`:
   - SimHub reachability/roles: a direct fetch is cross-origin (no CORS) → `simhub-probe.ts` uses `GET /simhub/roles`, answered from the plugin's own SimHub service. `key-binding-input.ts` goes through the probe (a structural test forbids a private fetch).
   - Test buttons: no action context → `ird-audio-test` with a `preview="radar|voice|background"` attribute sends `sendToPlugin {event:"audioPreview", kind}`; the plugin runs `runAudioPreview` (`iracing-actions/src/audio/audio-previews.ts`). Since #1003 this is the ONLY preview path — the old route (a hidden `_test*` timestamp setting the Pit Crew action watched) went with the controls it served, and `ird-audio-test`'s `target` attribute was removed with it.
   - Profiles: no device → `ird-deck-device-select` (populated from the `_deckDevices` passthrough global the Elgato plugin publishes, like `_audioDeviceList`) + `ird-profile-switch device-from="<select id>"`; no choice → no send. The plugin routes it through `ElgatoPlatformAdapter.switchToBundledProfile` — the SAME dispatch the PI's accordion buttons use (suffix per #753, history per #762). Elgato build only (`profiles` flag), gated at compile time.
   - Bounds: the bridge reports a **settled** position (unchanged for one 1 s tick) plus a final report on `pagehide`, so a drag is one global-settings write, not one per second. A window that opens **fully off-screen** (bounds saved on a monitor since unplugged — Chromium replays `--window-position` unclamped) is pulled onto its nearest display with `moveTo` and a size-only report is persisted, so the next open gets default placement even if the move was refused.
   - Storage (#993): `global-common-diagnostics.ejs` shows the settings file's path on **both** surfaces (a disabled `sdpi-textfield` bound to `_settingsStorePath`); the **Open folder** button (`ird-open-folder` → `sendToPlugin {event:"openSettingsFolder"}`) renders only in the window (`locals.settingsWindow`), since that command is handled by `createSettingsWindowCommandHandler` — a PI's `sendToPlugin` goes to its action instead.
6. **Passthrough keys the window introduces**: `_settingsWindowBounds` (validated, sanity-bounded), `_deckDevices`, and — from #993 — `_settingsStorePath`. All plugin-written; not user settings; they live in the plugin's store and reach the deck host's copy once per start through the guarded mirror write (`hostMirrorPayload`). `_settingsChannel` (`{ port, token }`) is the exception: per-process, so it is NOT persisted in the store (a stale copy from an older build is removed) and exists only in that host mirror — which is what lets a PI bootstrap the channel before it can talk to the plugin.
7. **Ulanzi normaliser trap:** `ulanzi-client.ts` `normalizeFrame` **drops** any `sendToPlugin` whose payload isn't a known marker. A new PI→plugin command on Ulanzi needs a marker added there (`openSettings` was), not just an adapter listener. It applies to commands sent from a **PI over the host socket** only: `openSettingsFolder` (and every other window command) arrives through the loopback fake host, which never passes through the Ulanzi normaliser, so it needs no marker. Global settings never needed one either — they are not `sendToPlugin` frames — and since phase 2 a bootstrapped PI sends them straight to the loopback fake host, so only global-settings frames on the bootstrap read and the fallback path still cross `translate.ts` at all (non-global frames always translate, bootstrapped or not).
8. **Shared browser helpers, never a private copy.** `window.__irdSettingsWindow` is read ONLY through `pi-components/src/components/settings-window-context.ts` (`SETTINGS_WINDOW_FLAG`, `inSettingsWindow()`); the bridge keeps its own copy of the name (separate bundle) and `build/settings-window-constants.test.ts` pins them equal. Components that send `sendToPlugin` frames go through `components/sdpi-client.ts` (`sendToPlugin`, `getStreamDeckClient`) — never a private client lookup.
9. Brand: accent `#ce2128`, the header shows `iracedeck-logo.png` (committed in `pi-components/browser/` beside the vendored sdpi file — that `.gitignore` is `browser/*` with negations, since git can't re-include a file under an ignored _directory_).
10. **One bridge per page** — `pi-settings-bridge.js` on Elgato/Mirabox action PIs, `ulanzi-pi-bridge.js` on Ulanzi action PIs, `settings-window-bridge.js` on `settings-window.html` only. Two bridges on one page double-patch `WebSocket`. The build enforces it: `assertBridgeInjectionPlugin` runs in `closeBundle` on all three plugins and throws — naming the file — unless every generated page that loads sdpi carries its expected bridge exactly once, immediately before `<script src="sdpi-components.js">`, with no other known bridge present.

## Verifying a change

`pnpm build` then check the built `ui/` per plugin: the expected bridge script present exactly once and before `sdpi-components.js` in every PI page and in `settings-window.html`, the other bridges absent (the build asserts this, so a green build is the check), and the expected controls present (e.g. `grep -c '<ird-key-binding'` = 236 — one per unique setting; the two FFB force bindings that `key-bindings.json` lists under two categories are deduped). For a partial split, snapshot the compiled PI HTML before and prove it is byte-identical modulo whitespace after. Then the manual round-trip on hardware, with debug logging on: change a setting in the settings window → a PI showing that setting updates live, the log shows the update and `Settings saved: <path>`, and the settings file's **content** changes (not just its mtime — the load-time re-save refreshes mtime on every start); change a setting in a PI → the window updates live and the file changes again; a second PI open on the same setting follows both; restart the deck software → every value is still there, from the file. A PI that fell back to the host path logs `iRaceDeck: …` in its own DevTools console — that is the signal to check, not a silent wrong value.
