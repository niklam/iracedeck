# @iracedeck/audio-native

Native Node.js addon (C++/N-API) around the miniaudio single-header library. Provides a 5-channel mixer with per-channel volume, looping, completion callbacks, and device selection.

## Cross-platform architecture

The package detects the platform at module load and behaves accordingly:

- **Windows (`win32`)**: loads the native `.node` addon via `createRequire()`. If the load throws (the file is missing or quarantined, a runtime DLL is missing, a fresh clone skipped `pnpm build:native`), it falls back to the silent mock and reports the failure (#1373): unlike `iracing-native`, nothing changes in behaviour, because the mock's silence misleads no further than the silence itself, which the plugin's banner now explains.
- **Other platforms**: skips native addon loading entirely and uses `AudioNativeMock`.
- **Force mock**: setting `IRACEDECK_MOCK=1` in the environment or creating a `.mock` file in the process cwd (the sdPlugin folder) forces the mock even on Windows.
- **The test suite already sets it (#1084).** `vitest.config.ts` sets `test.env.IRACEDECK_MOCK`, so test **workers** — and any child process they spawn — never load this package's `.node`. The main Vitest process is not covered; see `iracing-native/CLAUDE.md` for why that matters. Outside its own tests, the package is loaded only by `plugin-runtime`'s recorded mocks (which import the real module, under the forced mock, and stub its functions); every other test import is type-only. The lever covers both native packages. Use `IRACEDECK_REAL_NATIVE=1` to opt back in.

The `AudioNative` class delegates every method call to either `addon` (native) or `AudioNativeMock`. Callers use the class the same way either way; only `plugin-runtime` asks which is active, through `getNativeLoadStatus()`, to report a failed load.

**The load status (#1373).** `getNativeLoadStatus()` reports how the module loaded, once, at import — the same `NativeLoadStatus` union `iracing-native` declares (`native`, `mock` with `platform` or `forced`, `load-failed` with the thrown message), declared again here rather than shared. `plugin-runtime` logs an error and raises the `native-addon-audio` banner on a failed load. The decision is the pure `loadNativeAddon({ platform, forceMock, load })` (`@internal`), tested with a fake loader. See `iracing-native/CLAUDE.md` for the rest.

### Build behavior

`scripts/build.mjs` is platform-aware:
- On Windows: runs `node-gyp rebuild` then `tsc`
- On macOS/Linux: runs `tsc` only (skips native compilation)

A running deck host has `build/Release/audio_native.node` loaded, and Windows refuses to delete a loaded image, which node-gyp's clean step needs. So before `node-gyp rebuild` (and `node-gyp clean`, in `scripts/clean.mjs`) the script deletes the binary itself, and when that fails with `EPERM`/`EBUSY`/`EACCES` it **moves** it into the package's gitignored `.locked-native/` folder — Windows allows moving a loaded image on the same volume, and the host keeps running the old code from the moved file until it restarts. The rebuild then always produces a fresh binary; there is no catch around it, so any build failure is a real one. Keeping the old binary instead would let turbo cache the stale `.node` under the new sources' hash (#1258). Each native build or clean sweeps the moved copies a host has since released; a cache-hit build runs no script, so they can sit there until then. The step is the shared `scripts/lib/native-addon-build.mjs`, used by `iracing-native` too and named as a turbo input of both packages' `build`; spec `docs/superpowers/specs/2026-10-03-issue-1258-native-build-locked-addon.md`.

The `install` script in `package.json` is a no-op `echo`, so `pnpm install` never triggers node-gyp — building the addon is explicit-only via `pnpm build`.

### Mock implementation

`AudioNativeMock` (in `src/mock-impl.ts`) produces no audio and returns success for most methods, with two deliberate exceptions:

- `isChannelPlaying()` always returns `false` (nothing ever actually plays).
- `setAudioDeviceById()` returns `true` only for the synthetic id `mock-device-0` — the id of the single `Mock Audio Device` entry returned by `getAudioDevices()`. Any other id returns `false`, mirroring the unknown-device case on real hardware; tests rely on this distinction.

`setSessionIdentity()` also records its arguments on the mock's public `sessionIdentity` field (`null` until called, and again after an empty display name or `destroyAudioEngine()`, as natively), so tests can assert what reached the native layer. `setDeviceReroutedCallback()` records its callback on the public `deviceReroutedCallback` field (`null` until registered, after a `null` clear, and after `destroyAudioEngine()`), so a test fires a reroute by calling it.

### When adding new native methods

1. Update `addon.cc` — C++ implementation + register in `Init()`
2. Update `src/index.ts` — add corresponding TypeScript method to `AudioNative` class
3. Update `src/mock-impl.ts` — add matching no-op in `AudioNativeMock`
4. Update `src/mock-impl.test.ts`
5. `@iracedeck/audio-service` consumes the `AudioNative` class directly by type (`initializeAudio(logger, native, …)` in `packages/audio-service/src/audio-service.ts`), so a new method is visible there automatically — add the `AudioService` usage there if the method is meant to be consumed by the audio service

## Audio engine functions

The addon embeds miniaudio for multi-channel mixing. 5 independent channels (`IRD_MAX_CHANNELS`, one per `AudioChannel` entry) with per-channel volume, looping, and completion callbacks via `ThreadSafeFunction`.

`stopChannel`, `isChannelPlaying`, `stopAllChannels`, and `destroyAudioEngine` do exactly what their names say (see `src/index.ts`); the functions below have behavior worth documenting.

### `initAudioEngine(): boolean`
Creates the shared `ma_context` (device enumeration) and, on WASAPI, starts the namer thread (#1414; see the rule about abandoned audio clients below). **No `ma_engine` and no OS audio device exist after init** (issue #849): Windows holds a sleep-blocking SYSTEM power request ("An audio stream is currently in use") for a WASAPI stream that merely exists — even initialized-but-stopped — so the engine is created lazily (`startAudioEngine`/`playOnChannel`) and torn down entirely when idle (`stopAudioEngine`). Returns `true` when the context is usable.

### `startAudioEngine(): boolean` / `stopAudioEngine(): boolean`
The device lifecycle pair (issue #849). `startAudioEngine` lazily creates the engine on the remembered device selection (system-default fallback if it vanished — the selection is kept so a replug self-heals) and starts it; `stopAudioEngine` tears the whole engine down, releasing the OS stream and any loaded sounds. Both idempotent. Consumed by `@iracedeck/audio-service`, which starts at the playback-start chokepoint and releases after all channels have been idle for `IDLE_STOP_DELAY_MS` — so sounds are never cut. While the service holds the device (`hold(reason)`, taken for the length of an iRacing session, #1347) it starts the engine at once and skips that release, so the sleep-blocking stream then lives for as long as iRacing runs. While holding it also calls `startAudioEngine` again at every sound, relying on both halves of this contract: a running device reports success, and a device that cannot be started (a selected headset that powered off; only a default-device change is rerouted) tears the engine down, so the next start falls back to the system default. That fallback is silent and a live engine is never moved back, so the service checks the enumeration at each open under a hold and does not hold a default that is standing in for a missing selected device: it releases it after the burst, and the next open tries the selection again. `playOnChannel` also recreates the engine on demand (the device starts moments later via `startAudioEngine`, and a stopped device just holds the sound at its start).

**Every teardown unregisters miniaudio's notification client first (#1411).** `teardownEngine` calls `detachDeviceNotifications` before `ma_engine_uninit`, and no engine is uninitialised any other way. miniaudio follows a default-device change on Windows' notification thread — stop, reroute, start, waiting each time for the audio worker — while `ma_device_uninit` ends that worker first and unregisters its `IMMNotificationClient` last. An uninit landing inside one of those waits left the notification thread waiting for a worker that was gone, and the JS thread waiting in `UnregisterEndpointNotificationCallback` for the lock that thread held: a freeze for good, which the probe's `--cycle` reproduced within a few device changes. Unregistering first returns only when no notification is running, with the device and its worker still whole, and none can start afterwards; miniaudio's own unregister then finds nothing registered and ignores that. The wait is for a reroute to finish, which never waits for the JS thread. It reads `device->wasapi.pDeviceEnumerator` and `notificationClient`, which are miniaudio internals: recheck both on a miniaudio upgrade.

**The audio client miniaudio abandons at a reroute is released by the namer thread (#1414, spec `docs/superpowers/specs/2026-10-11-issue-1414-rerouted-stream-release.md`).** At a reroute miniaudio 0.11.25 reinitialises its device and sets `pAudioClientPlayback` to NULL without releasing the old `IAudioClient`; its own comment in `ma_device_reinit__wasapi` calls it a known leak, because releasing inside Windows' notification callback deadlocks. One default change is several reroutes (four on the machine measured), so clients are abandoned on the endpoint the stream moves to as well as the one it left. Measured on 2026-10-11: about nine handles per reroute (274 to 3910 over 100 default changes), and after a reroute onto a SteelSeries Sonar device the audio power request for the headset Sonar plays through stayed until the process exited, which undoes #849. **The vendored `miniaudio.h` therefore carries one local change**, marked `iRaceDeck (#1414)`: right before that NULL it hands the pointer to `MA_IRD_ON_ABANDONED_AUDIO_CLIENT`, which `addon.cc` defines as `irdOnAbandonedAudioClient`. That function runs on the notification thread, so it only queues the pointer under the namer's mutex. The namer releases each client 1 s after it was abandoned: twice the rename's delay, so the rename for the same reroute goes first, and a due time per client, so a default that keeps changing cannot hold the older ones back. Nothing is released on the JS thread or inside the callback, and nothing is queued while no namer runs, which is why the namer starts in `initAudioEngine` on WASAPI and not only when an identity is set. `destroyAudioEngine` has the namer release what is still queued; the env cleanup hook drops it instead, because a reroute may be in flight there and the process is ending. **On a miniaudio upgrade** the new header has no hook and `addon.cc` stops compiling (it checks `MA_IRD_ABANDONED_AUDIO_CLIENT_HOOK_PRESENT`): re-read `ma_device_reinit__wasapi`, and put the hook back only if it still drops the client without releasing it. If it releases the client itself, delete the hook and `irdOnAbandonedAudioClient`, or ours becomes a second release of freed memory.

### `playOnChannel(channel: number, filePath: string, loop?: boolean, volume?: number): boolean`
Plays a file on a specific channel (an `AudioChannel` value, 0–4). Stops any existing sound on that channel first. Supports WAV, MP3, FLAC.

### `setChannelVolume(channel: number, volume: number): void`
Sets per-channel volume (0.0–1.0). Only works on an existing `ma_sound`.

### `setChannelEndCallback(channel: number, callback: () => void): void`
Registers a JS callback via TSFN that fires when a sound finishes playing.

### `seekChannelRandom(channel: number): void`
Seeks to a random position in the current sound (used for ambient loop variation).

### `getAudioDevices(): AudioDeviceInfo[]`
Enumerates available audio playback devices. `id` is a hex-encoded `ma_device_id` — the platform-stable identifier (WASAPI endpoint ID on Windows, CoreAudio UID on macOS, etc.) suitable for persisting selection across sessions. `index` is the volatile enumeration position retained for backward compatibility. `AudioDeviceInfo` (`{ index, name, id, isDefault }`) is an exported type — it is the persistence contract consumed by the `ird-audio-device-select` PI component, which persists selection by stable `id`, never by `index`.

### `setAudioDevice(deviceIndex: number): boolean`
Selects the output device by enumeration index (-1 for system default): validates, remembers the selection, and tears down any live engine — the next play recreates it on the new device (issue #849; recreating eagerly would hold the sleep-blocking power request while idle; `@iracedeck/audio-service` starts it again at once only while it holds the device, #1347). Selection identity is compared on stable `ma_device_id` bytes (never the volatile index), so re-selecting the already-active physical device is a no-op. Prefer `setAudioDeviceById` for persisted selections.

### `setSessionIdentity(displayName: string, iconPath?: string): boolean`
Names our audio session in the Windows Volume Mixer, which otherwise shows the host executable's name — "Node" (issue #1253 for the name and the icon, spec `docs/superpowers/specs/2026-09-26-issue-1253-audio-session-name.md`; issue #1411 for how it is applied, spec `docs/superpowers/specs/2026-10-10-issue-1411-audio-session-rename-deadlock.md`). Stores UTF-16 copies of the name and the icon path (icon only when given; it must be an absolute `.ico` path) and, on the first non-empty name, starts the **namer thread**, which does all the naming.

**Nothing of ours calls a COM object miniaudio owns.** The stream miniaudio opens passes no session GUID, so it is in our process's default session on its endpoint, and the namer reaches that session through objects of its own: `CoInitializeEx` (multithreaded) once on its thread, then per request an `IMMDeviceEnumerator`, the endpoint's `IMMDevice` (`GetDefaultAudioEndpoint(eRender, eConsole)`, or `GetDevice(<id>)` for a selected device), `Activate(IAudioSessionManager)`, `GetAudioSessionControl(NULL, 0)`, `SetDisplayName` / `SetIconPath`, and everything released. Until #1411 the name went through the playback `IAudioClient`'s `GetService` on the JS thread, and a default-device change while the stream was open froze the plugin for good: the JS thread held the audio client's lock and waited for the device enumerator's notification lock (creating a session control always registers an endpoint notification callback); Windows' notification thread held that lock for the whole of `OnDefaultDeviceChanged`, in which miniaudio's `ma_device_stop` waited for the audio worker; and the worker, in `GetBuffer`, waited for the audio client's lock. Creating the control still waits while a notification callback runs, but the namer holds nothing the worker, miniaudio or the JS thread needs while it does, so the callback finishes and the wait ends; the cost is a session that shows the host's name a little longer. Never reintroduce a call on miniaudio's `IAudioClient`, or any use of `device->wasapi.*` beyond the one in `detachDeviceNotifications` (the teardown rule under `startAudioEngine` / `stopAudioEngine`). The audio clients the namer releases are not an exception: miniaudio has abandoned them, and hands them over itself (#1414).

**Requests.** One mutex with a condition variable (`g_namerMutex`, `g_namerWake`) guards the identity strings, the one pending request, the queue of abandoned audio clients (#1414) and the stop flag; it is never held across a COM call, a miniaudio call or the join, which is what makes it safe to take on Windows' notification thread. A request carries its endpoint — an empty id for the default render endpoint, or a copy of the selected device's id taken on the JS thread, so the namer never reads miniaudio state or the selection — and requests coalesce to the latest. `ensureEngineCreated` posts one after either init path succeeds (the selected device when the first `ma_engine_init` opened it, the default endpoint with no selection or after the fallback), served at once. `maNotificationCallback` posts one for the default endpoint on `ma_device_notification_type_rerouted` — miniaudio only reroutes an engine it opened on the default — served 500 ms after the **last** reroute request arrived, because Windows reports one default change once per role and miniaudio reroutes on each. That callback runs on the notification thread inside miniaudio's reroute, so it locks, notifies and does nothing else. A request is dropped while no identity is set, and `teardownEngine` cancels one still pending.

**Lifetime.** `destroyAudioEngine` stops and joins the namer (after the engine is gone, so no notification callback of ours can be what the namer waits for) and removes its env cleanup hook; the hook does the same join when Node tears the environment down first. The thread is held on the heap (`g_namerThread`), never in a static `std::thread`: a deck host often ends the process with no cleanup, and the destructor of a joinable `std::thread` calls `std::terminate`. After a destroy the next `initAudioEngine` or `setSessionIdentity` starts a new thread.

**Contract.** An empty `displayName` clears the identity, icon included, for engines created afterwards (Windows keeps a name already applied to the process's session while that session lives — measured: set, play, clear, replay still shows the name; set, clear, play shows the default); `destroyAudioEngine` clears it too, and `@iracedeck/audio-service` sets it again from `init()`, before any engine can exist. Returns `false` while an engine exists — the live session was named at creation and would keep the old name — and the TypeScript wrapper also returns `false` when the loaded binary predates the method (the TypeScript and the binary are built by separate steps, and before #1258 a host-locked binary survived every rebuild), so a stale binary degrades the feature instead of aborting startup. Every HRESULT failure is silent and leaves the Windows default; engine creation never fails or waits because of it. A no-op on any backend other than WASAPI.

### `setDeviceReroutedCallback(callback: (() => void) | null): void`
Registers a JS callback that fires, with no arguments, each time miniaudio follows a default-device change onto a new endpoint (issue #1330, spec `docs/superpowers/specs/2026-10-04-issue-1330-main-thread-watchdog.md`); `@iracedeck/audio-service` turns it into `INFO Audio device rerouted`. miniaudio's notification callback posts through an `Unref`'d `ThreadSafeFunction` (`g_rerouteTSFN`, mutex-guarded like the channel end TSFNs) whose JS-thread handler (`OnDeviceRerouted`) calls the callback and does nothing else: since #1411 the session is renamed by the namer thread, so the line is the record of a reroute and no longer the last thing before a COM call. The TSFN exists while a callback is registered — registering creates it, clearing releases it, `destroyAudioEngine` always releases it, and an env cleanup hook disarms it if Node tears the environment down first — and no longer because an identity is set; the callback and the identity work with or without each other. A callback that throws is swallowed (`NAPI_DISABLE_CPP_EXCEPTIONS`: the pending exception is cleared), so it cannot surface as an uncaught exception from a TSFN call. The reference is heap-held (`g_deviceReroutedCallback`) so no static destructor calls Node-API at process exit; `null`/`undefined` clears it, registering again replaces it, `destroyAudioEngine` clears it (the audio service registers it again from `init()`, as it does the identity), and the env cleanup hook forgets it without deleting the reference Node-API frees with the environment. The TypeScript wrapper does nothing when the loaded binary predates the method, the same tolerance as `setSessionIdentity`. A no-op off Windows. The reroute path itself is exercised only by hand, with the probe under *Checking the session identity and the reroute by hand* below.

### `setAudioDeviceById(deviceId: string): boolean`
Same as `setAudioDevice` but looks the device up by its stable `id` from `getAudioDevices`. Returns `false` if the id is malformed or not found in the current enumeration (e.g. unplugged device). Should the selected device vanish before the next play, the lazy engine creation falls back to the system default so the mixer remains usable. Use this for any selection that needs to survive replug or driver reset.

## Checking the session identity and the reroute by hand

No unit test can reach the session-identity and reroute code: it is COM on a live device, and the suite runs against the mock. `scripts/reroute-probe.mjs` is the repeatable check, to run after a miniaudio upgrade or any change to that code (#1411). It loads the real addon (and refuses the mock), sets a session identity, opens the device and keeps it open — silent unless `--clip` is given — and prints a heartbeat once a second, `REROUTED` for each reroute, and a loud `STALLED <ms>` when the event loop was blocked for more than 1.5 s, from a second thread as well, so a loop that never comes back still says so. After ten seconds of that the second thread ends the process, which Ctrl+C cannot do while the main thread is stuck, and a run that stalled exits 1 even when the loop came back.

```bash
pnpm --filter @iracedeck/audio-native build
node packages/audio-native/scripts/reroute-probe.mjs --list    # the output devices and their ids
node packages/audio-native/scripts/reroute-probe.mjs --name "iRaceDeck probe" --busy 15 [--cycle 150] [--icon <absolute .ico>] [--device <id>] [--clip <file> --volume 0.05] [--seconds 30] [--no-destroy] [--release-after <s>] [--on-stall <command>]
pwsh -File packages/audio-native/scripts/list-audio-sessions.ps1 [-ProcessId <pid>]
```

**Always pass `--busy`.** It keeps the main thread unavailable for that many milliseconds at a time, in sleeps, the way a plugin's is in a race. The #1411 freeze needed the reroute to reach JavaScript a few milliseconds late, inside the next of the two or three rounds Windows sends for one change, and an idle event loop is never late: without the option the addon that froze the plugin survived 21 changes in a row, and with `--busy 15` it stalled on the first.

**Then run it again with `--cycle 150` as well**, which closes the device and opens it again that often, as the plugin does around its sounds. A close landing inside a reroute was the second way to lock up (see the teardown rule under `startAudioEngine` / `stopAudioEngine`), and before that fix the probe stalled within a few changes. `--on-stall <command>` runs a shell command, with `{pid}` replaced by the probe's, once a stall is for good and before the probe ends itself: the moment for a stack walker or a dump.

**Checking that a reroute leaves nothing behind (#1414).** Two measurements, both against the process while it is alive. Handles: with the device held open (`--busy 15`, no `--cycle`), the probe's handle count is the same before and after a hundred default changes; before #1414 it grew by about nine per reroute. The power request: `--release-after <s>` releases the device after that many seconds and keeps the process alive, and `powercfg /requests`, from an elevated terminal, must then show no audio request for a device nothing else is playing on. Windows lists the request under the device's driver, not the process, so start on an output nothing else uses (a monitor's) and switch the default to a SteelSeries Sonar device before the release: that is the case that held the headset's request until the process exited.

While the probe runs, change the Windows default output device several times, slowly and as fast as the picker allows: each change prints `REROUTED` and never `STALLED`, and `scripts/list-audio-sessions.ps1` — read-only, every render session on every active endpoint with its pid, state, display name and icon path — shows the probe's session under its name on the new default about half a second later. With `--device` the session is named on that device, and a default change does not reroute it. `--no-destroy` leaves with `process.exit(0)` and no `destroyAudioEngine`, the way a deck host ends a plugin: it must exit 0 with no abort message.

## Channel enum

```ts
export enum AudioChannel {
  Ambient = 0, // pit lane background noise (loops)
  SFX = 1, // walkie-talkie open/close ticks
  Voice = 2, // engineer voice messages, reminders, toggles
  Radar = 3, // directional radar ticks (independent)
  Feedback = 4, // control feedback, the volume step tick (#1455); no bus
}
```

The same enum is duplicated in `@iracedeck/audio-service` (`packages/audio-service/src/audio-service.ts`) — keep the two in sync when channels change; a type-level check in that package's tests fails when they differ. A new channel is an entry in both enums plus a bump of `IRD_MAX_CHANNELS` in `addon.cc`, which sizes every per-channel table there (`g_channels`, `g_completionTSFN`, `g_tsfnRegistered`); the service sizes its own per-channel state from its enum. Every native entry point refuses a channel at or above `IRD_MAX_CHANNELS`, so a `.node` built before a bump refuses the new channel: its play returns false and the channel is silent rather than a crash. `pnpm build:ts` builds no binary, so a channel change needs a full native build (`pnpm --filter @iracedeck/audio-native build`) before a manual test.
