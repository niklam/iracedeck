# @iracedeck/iracing-actions

The platform-agnostic iRaceDeck action classes — one folder per action under `src/actions/`. Actions contain no platform-specific code — they import from `@iracedeck/deck-core`, and the iRacing side (`SimIRacingAction`, `getCommands()`, the fuel, unit and hotkey helpers) from `@iracedeck/deck-iracing` (#1351), and shared constants and their pure helpers (today the Mouse to Sim target resolver) from `@iracedeck/app-constants` (#1364); Replay Markers and Replay Control reach the per-session replay store through `@iracedeck/replay-store`, and Telemetry Control reaches `@iracedeck/diagnostics` for two modes: Capture Profile uses the CPU profile capture (#1367), and Take Snapshot collects the plugin's own state through `collectStateSections()` (#1387). The telemetry it writes beside that state is the tick the state was computed from, chosen by `selectSnapshotTelemetry` between the translator's latest tick (`getLatestTelemetry()` from `@iracedeck/sim-events-iracing`) and a fresh `getCurrentTelemetry()`. A fresh read can be one frame ahead of that state, and then the translator's tick is written. A fresh read of the same `SessionTick` is preferred, because the controller dispatches a tick once and iRacing goes on changing fields under a frozen one (the camera target in a paused replay), so the translator's copy can be as old as the pause. With no tick in the translator the fresh read is used. Nothing is awaited between the read and the collection, so no tick lands in between. They are registered for all three plugins (`iracing-plugin-stream-deck`, `iracing-plugin-mirabox`, and `iracing-plugin-ulanzi`) through `@iracedeck/plugin-runtime`'s shared action list (`src/actions.ts`, #1349).

`src/shared/` holds cross-action utilities:

- `adjust-styles.ts` — paired +/− key styles: style catalog, shared settings fields + fresh-key seeding, value-source gating over VIEW_DEFS, and the SVG renderer (spec: docs/superpowers/specs/2026-07-07-paired-adjust-key-styles-design.md)
- `black-box.ts` — canonical black-box id↔global-key map (`BLACK_BOX_GLOBAL_KEYS`, also consumed by `comms-catalog.ts`) plus `showBlackBox()` / `resolvePrimeKey()`: press a different box first, then the target, because a black-box hotkey toggles and telemetry never reports the shown box (#818). The prime matches the target's binding kind first (keyboard target → keyboard prime, SimHub target → SimHub prime); both keys keyboard-bound → one atomic key sequence (no flash), a SimHub role involved → a serialized tap-then-tap that presses the target only if the prime went out (#962)
- `car-cycle-bindings.ts` — the one home of iRacing's Next Car / Previous Car binding keys (`CAR_CYCLE_BINDING_KEYS`: `replayControlNextCar` / `replayControlPrevCar`, V / Shift+V), dependency-free because two actions tap them: Replay Control's Next Car / Previous Car modes and Camera Controls' Cycle by Track Order on the keypad and the dial (#1277). One sim control, one setting — `key-bindings.json` lists the pair under both `replayControl` and `cameraControls`; `CAR_CYCLE_BINDING_DEFAULTS` (`V` / `Shift+V`, literals rather than a JSON import so the plugin bundle does not carry `key-bindings.json`; a test cross-checks them against both sections) is what every plugin hands `@iracedeck/settings`' `seedBindingDefaultsIfAbsent` at startup, so an upgraded user who never opened a Replay Control Next / Previous Car panel does not get the #612 warning on CAR AHEAD / CAR BEHIND
- `car-select-intent.ts` — per-device intent deciding what a selector car-key press means (admin target vs camera focus, #790)
- `dial-box.ts` — the dial "dash box" dispatcher + `dialAppearanceFields` settings fragment: `renderDialBox(canvas, args)` takes the context's `DialCanvasProfile` and dispatches by `canvas.id` (an exhaustive switch — a new profile id stops compiling until it gets a drawing) to `renderStripBox` or `renderKnobBox` (#1013). Fourteen surfaces render through it — the seven Setup dials, Camera Editor Adjustments, Cockpit Misc, Force Feedback, Replay Control, Replay Markers, Splits & Reference and View Adjustment — resolving their per-setting accent plus user color overrides with `resolveDialBoxColors` (#811). Besides the label, value and `pending` slot, `DialBoxArgs` carries `sideMarker` (`"left"` / `"right"` for one lit side, #953, or `{ left, right }` for each side on its own), an optional `caption` line under the value, and `dimmed` to fade the whole box (#1230); all are additive, so a surface that passes none draws exactly as before. Fuel Service, Audio Controls, Camera Controls and Black Box Selector draw their own strip/knob pairs over the same colours.
- `dial-strip-box.ts` — `renderStripBox`, the Stream Deck+ 200×100 drawing, byte-pinned to its pre-#1013 output by `__fixtures__/dial-strip-box.json`. Identity-only labels are baseline-centered (`+0.36em`) so they sit truly centered rather than above center (#804)
- `dial-knob-box.ts` — `renderKnobBox`, the Stream Dock knob drawing at 176×112 (#1013): designed for that screen rather than scaled from the strip, with the same vocabulary (label, value, pending bar, binding warning). Its `KNOB_BOX_WIDTH` / `KNOB_BOX_HEIGHT` are the one knob size: the self-drawn knob renderers (Fuel Service, Audio Controls, Black Box Selector) import them rather than repeating 176×112
- `dial-fit.ts` — `fitValueFontSize`, the value-fitting both dash-box renderers share. A pure primitive with no dial dependency, so a keypad icon that draws a value in a fixed frame uses it too: Camera Controls' Switch by Car Number / Switch by Position keys, through `camera-controls/switch-target-value.ts` (#1352)
- `dial-side-markers.ts` — the dash box's two side triangles (`renderSideMarkers`, `resolveSideMarks`, the `DialSideMarker` / `DialSideMarks` types): one drawing both renderers call, each side lit or dimmed on its own (#953 lit one; #1230 any combination)
- `dial-preview.ts` — `renderPendingBar`, the one #1120 hold-preview mark every renderer draws
- `dial-release.ts` — `classifyDialReleaseForHost`, the one release rule every dial surface calls: deck-core's `classifyDialRelease` where `__FEATURE_DIAL_EXTENDED_GESTURES__` is on; never `long` where it is off (`"push-turn"` after a pressed rotation, `"short"` otherwise) (#1013)
- `dial-context.ts` — `hasDialInputContext`, the one gate in front of every dial surface's input events (#1329): a `rotate` / `down` / `touchTap` acts only on a context `willAppear` / `didReceiveSettings` created, and one arriving after `willDisappear` is dropped with a single debug line (`Dial <event> dropped: no context for <id> (it has disappeared)`) before any side effect. Each surface calls it from its private `inputContext`, which hands an existing context to `ensureContext` so it is refreshed exactly as before (rule 11 in `.claude/rules/encoders-and-touchscreen.md`)
- `dial-name-icon.ts` — plain two-line action-name image for dial contexts (#775); push it with `pushDialNameIcon`, which sends it only on the `sd-plus-strip` profile — on a Stream Dock knob `setImage` IS the live screen (#1013). The `shared/dial-*` modules import deck-core and zod only; `dial-sim-agnostic.test.ts` keeps them free of `@iracedeck/iracing-sdk` / `@iracedeck/sim-events-iracing`
- `profile-entries.ts` — shared `_deviceProfiles` PI-dropdown entry building + echo-loop change guard (#790)
- `repeat-controller.ts` — long-press hold-to-repeat timing controller
- `replay-busy-indicator.ts` — what the pressed replay key or dial shows while its press is worked on (#1437): working, waiting or not done, read only from the gate's state seam (`subscribeReplayGate`, `getReplayGateView`) and sending nothing. A key or dial registers its context id as the token (`registerReplayBusySurface`, with `drawsWorking` false for a mode whose own command is not a jump or search), draws from `getReplayBusyLook`, and the action reports a press it ignored itself (`reportReplayPressIgnored`). One interval for the plugin, every `REPLAY_BUSY_FRAME_MS` (125), alive only while a registered surface shows working; each tick re-reads the gate's view, and a five-minute ceiling stops a spinner the gate never ends. No start delay. Spec: `docs/superpowers/specs/2026-10-13-issue-1437-replay-key-busy-look.md`.
- `replay-command-gate.ts` — the replay command gate (#1430): the one module that sends a replay command. Never call `getCommands().replay` anywhere else; `replay-command-gate.single-sender.test.ts` refuses it. A surface says what it wants sent and the gate decides when, and whether, by the table in its header: while a position jump is under way only another absolute jump (or go to start / go to end) goes out, a frame step becomes an absolute jump one frame from the target, a pause is not sent, and a speed or a search waits in the gate's one waiting slot (newest wins) for the target's read-back; behind a search that may be on its way every press waits for the landing, and a second press takes over at once (a pause if the replay is moving, an absolute jump to the frame beside the reading, then the press's command). `pressReplayCommand` is a one-shot press from a key or a dial and takes the replay cursor first, as every command did before; `sendOwnedReplayCommand` is a claim holder's own send (the jump sequence's pause and playback step, the fastest-lap walk's probes), and `openReplayJump` / `sendReplayJumpSeek` / `replayJumpLanding` / `closeReplayJump` carry the jump sequence. It also exports the waits #1426 and #801 build on (`waitForReplaySettled`, `waitForReplayJumpsToSettle`, `waitForReplaySearchLanding`, `settleReplayByJump`, `replaySearchCouldRunMs`) and the state seam (`subscribeReplayGate`, `getReplayGateView`, per origin token), which reports what is under way or waiting and changes nothing that is sent. Every wait ends on what telemetry reads back; each clock only gives up. Tests drive it over `replay-command-gate.test-support.ts`'s `fakeReplay`
- `replay-cursor.ts` — single, process-wide owner of iRacing's one replay cursor (#1203): a long-running driver claims it for as long as it runs — the fastest-lap walk, and every jump through `replay-jump-playback.ts` while it waits for its landing: Jump to Fastest Lap's record jump, a Jump to Race Start press (#1354, which runs the walk too when it has to search) and, since #1276, a Replay Markers Previous / Next jump, which until then was a one-shot cancel — and any one-shot replay command in any action takes it before it is sent (since #1430 inside the gate's `pressReplayCommand`) — the hidden legacy Replay Navigation, Replay Speed and Replay Transport included, every mode and dial path, owner `<action>-<mode>` (Replay Speed's dial press is `replay-speed-reset`) (#1334); their tests share `replay-cursor.test-support.ts`. Camera switches outside Replay Control (Camera Controls, Race Admin) deliberately do not: a walk lasts about 0.1 s, too short for a second key to land inside it (Niklas, 2026-10-10). It also holds the pending jump speed (#1276); where the replay is headed is not kept here but in `replay-position-state.ts`, which a cursor take leaves standing (#1430, which replaced the pending landing of the last marker jump the Replay Markers surfaces shared since #1230). The pending jump speed is the speed the replay had before a jump still under way, or the speed a finished jump left it at until telemetry shows it. A jump pauses a moving replay before it seeks, so a second jump pressed meanwhile would otherwise read "paused" and remember that; a jump that takes the cursor from another jump inherits the speed that one captured, and any other replay command clears it, since a speed the driver sets mid-jump is theirs. When it still stands is `replay-jump-playback.ts`'s rule. Whether a replay is on screen is not kept here: since #1324 that is `SDKController`'s debounced replay state (`getReplayState()`, `@iracedeck/iracing-sdk`), stepped on every poll that reads telemetry — before the `SessionTick` dedupe, since in a paused replay the flag's return after a seek can arrive on a repeated tick. iRacing reports `IsReplayPlaying` false for ~300 ms after every `setPlayPosition`, so leaving a replay counts only after `REPLAY_EXIT_GRACE_MS` (1 s) of false, and a saved replay is always a replay. Replay Markers' `readReplayContext`, Replay Control's two Jump to Fastest Lap "from the car" checks and the Race Engineer translator all read that one state. A `goToEnd` that was sent (Replay Control's Jump to Live, Replay Navigation's Jump to End) calls `sdkController.noteReplayLeftForLive()`, which ends the grace at once outside a saved replay, so an Add pressed straight after it files at the live edge; in a saved replay the same command only seeks to the end of the file, and the SDK leaves the grace standing
- `replay-frame-move.ts` — `planFrameMove`, what a move of the replay by frames sends (#1317, moved out of `replay-control-frame-jog.ts` for #1430): one frame step on a replay at rest, otherwise one absolute jump to the frame the move is heading for, never a jump relative to the cursor. A Frame Forward or Frame Backward key, its long-press repeat and a Frame Jog detent are one code path through the gate, with one end-of-tape margin (`JUMP_END_MARGIN_FRAMES`); `frameBeside` is the frame the gate's takeover jumps to
- `replay-jump-playback.ts` — the one jump sequence behind Replay Control's Jump to Fastest Lap and Jump to Race Start (#1354) and Replay Markers' Previous / Next Marker, and what the replay does after it (#1276). `beginReplayJump` is called at the press, before any command: it captures the speed to restore (a speed waiting in the gate's slot, else the speed the replay had when a search still on its way went out, else the cursor's pending jump speed while one stands, else telemetry; unreadable counts as paused), claims the cursor and records the frame it is going to, when the press knows it, as the pending target, before its pause (#1430). `runReplayJump` then pauses a replay that is moving — one whose captured speed is not zero, or that does not read paused, since right after another jump applied a speed telemetry still reads paused — and waits for the pause to show. A jump that took the cursor from one still under way (`ReplayJump.tookOver`) skips the pause when the replay has been paused for the jump under way (`isReplayPausedForJump`, the gate's judgement) and sends its seek at once: only an absolute jump may arrive while a seek is under way, since it retargets the seek where any other replay command, a pause included, ends it where it stands (measured 2026-10-12). It then seeks through the gate (`sendReplayJumpSeek`) and waits for the gate's read-back of its target (`replayJumpLanding`), the one judgement of "landed" a speed held behind the jump also waits on, for as long as iRacing shows a seek under way, runs the caller's `afterLanding` step (Jump to Fastest Lap's camera switch, which would cut the seek short if sent earlier) and ends in `applyReplayJumpPlayback`: one `setPlaySpeed`, sent only when the speed the **Replay jump playback** global setting asks for (`readReplayJumpPlayback` — `remember` the captured speed, `play` 1x, `stopped` paused) differs from the one the landing reads, so a paused `remember` press sends the seek and nothing else. Every command it sends goes through the gate as the claim holder's own (`sendOwnedReplayCommand`). The fastest-lap walk keeps its own probes and uses only the two ends, `beginReplayJump` and `applyReplayJumpPlayback`. A cancelled claim, a refused command or a wait that gives up — the pause after `readReplayJumpTimeoutMs`, the landing once iRacing has shown no seek for that long — sends nothing more, which leaves the replay paused where it stopped whatever the setting says. It never throws for those and has no logger: the outcome (`landed`, `cancelled`, or `stopped` with a reason) says what happened, `describeReplayJump` is the one wording of it both actions log — a warning only when something went wrong, the details for the debug line always — and the caller calls `jump.end()` in its `finally`
- `replay-jump-speed.ts` — the **Replay jump playback** setting (`readReplayJumpPlayback`) and the speed it resolves to (`resolveReplayJumpSpeed`, `isSameSpeed`, `PAUSED`, `NORMAL_SPEED`): its own module so the jump sequence and the gate, which applies the same step after a search that waited behind a jump, read one rule without importing each other (#1430)
- `replay-position-state.ts` — where the replay stands or is headed: the one pending target (#1317, moved here from `actions/replay-control/` for #1430). Every position jump of every surface records it — the dial's frame moves, the jump sequence's seeks (Replay Markers, Jump to Fastest Lap, Jump to Race Start) and the keys' frame steps — and only the gate writes it. A move is measured from it while it stands (`ReplayPosition.seeking`), and Replay Markers anchors its next jump on it (`resolveMarkerJumpAnchor`). It ends when its frame reads back conclusively (`settleReplayTarget`) or is given up by `replayTargetGiveUpMs` (the larger of `REPLAY_TARGET_GIVE_UP_MS`, 3 s, and twice the jump's length at 2048 frames a sim update, not running while the jump that recorded it holds the cursor); a cursor take does not clear it. Its header holds the measurements of 2026-10-12 and 2026-10-13
- `replay-seek.ts` — the waits a replay jump is made of (#1275), and `replaySeekWaitMs`, how long an absolute jump of a given length is waited for (twice its time at iRacing's 2048 frames a sim update, never under the caller's floor, #1354; the lap search's own jumps, its Next Session searches and its way back use it, and the gate builds a target's give-up, `replayTargetGiveUpMs`, and how long a search could still be running on it, #1430): iRacing covers a long jump in steps of at most `maxFramesToSearchPerUpdate` frames, and a command arriving mid-search cuts it short, so nothing may follow a jump until it lands. `seekReplayFrame` sends an absolute jump and waits until `ReplayFrameNum` reads the frame sent, resolving `refused` without waiting when the send was refused; `waitForReplay` is the same poll for any condition, with `isLandedOn` and `isPaused` as the two it is asked for; each reports `cancelled` at its next poll once the caller's cursor claim is taken. `timeoutMs` is a plain wait unless the caller passes `seeking`, a predicate for what a seek still under way reads: the timeout then does not run while a read shows one, so the wait gives up on a replay that has stopped short and not on one that is slow, and `maxWaitMs` caps it however long the seek shows. The one in use is `isSeeking`, `IsReplayPlaying` false with nobody on track. A seek never shows as a moving frame: a long jump forwards, and any jump sent less than about half a second after another, reads like a replay that was left (frame a flat 0, `SessionNum` -1) until it lands, half a second for 60,000 frames on a fast machine and longer with the distance (measured 2026-10-12). The raw sample cannot tell that from a replay left for the garage, which is what `maxWaitMs` is for. `requireReplay` refuses a landing from a sample with `IsReplayPlaying` false, so a jump to frame 0 does not land on the 0 a seek reads. The fastest-lap walk's probes call `seekReplayFrame` with the plain timeout; the jump sequence (`replay-jump-playback.ts`), and through it the record jump and the marker jumps, calls `waitForReplay` for its pause and, since #1430, takes its landing from the gate's read-back of the target, using `isSeeking` to keep that wait going while the seek shows
- `replay-timing.ts` — the one home of the numbers the replay waits are timed from, most of them derived from the `fastestLapSearchDelayMs` global setting; moved out of `replay-control.ts` in #1276 so the walk and the shared jump sequence read the same ones. `readFastestLapSearchDelayMs` (clamped to 50–1000 ms, 400 on anything non-numeric), `STABILIZATION_TIMEOUT_MULTIPLIER` (the walk's `delay × 4` settle cap), `STABILIZATION_POLL_INTERVAL_MS` (the walk's 50 ms poll), `RECORD_JUMP_MIN_TIMEOUT_MS` (3 s, #1275) and the jump sequence's three: `REPLAY_JUMP_POLL_MS` (20 ms, shorter than the walk's because a jump on a playing replay holds the picture still for both waits), `readReplayJumpTimeoutMs` — how long a jump waits for its pause to show, and how long its landing wait goes on once iRacing shows no seek, not a cap on the wait: `delay × 4`, never under 3 s — and `REPLAY_JUMP_MAX_WAIT_MS` (120 s), the longest a landing is waited for while iRacing is still seeking, and what ends the wait of a jump whose replay was left meanwhile
- `setup-view.ts` — registry, formatters, and render helper for the setup actions' "View …" sub-modes (#541)
- `spotter-bindings.ts` — canonical AI Spotter control↔global-key map (`SPOTTER_GLOBAL_KEYS`, also consumed by `comms-catalog.ts`): the spotter has no SDK surface, and two actions dispatch its bindings — AI Spotter Controls (every control, keypad) and the Audio Controls dial's Spotter mode (louder/quieter on rotation, silence on press as Skip Spotter Call, #809/#1015)
- `unavailable-look.ts` — `unavailableLook(colors, border)`, the look of a key whose press would do nothing right now: every colour slot but the background and the border's colour in grey, plus `assembleIcon`'s `dimmed`, spread into the `assembleIcon` call in place of the resolved colours and border. Replay Markers' Next / Previous with no marker that way (#1162) and Replay Control's Jump to Race Start in a replay with no race session (#1354) draw it; a new "this key cannot act now" state uses it too, so the look stays one.
- `test-support/replay-state.ts` — test-only: `steppedReplayState` / `withSteppedReplayState` give a mocked controller `getReplayState` / `noteReplayLeftForLive` over the SDK's own `ReplayStateTracker`, stepped from the mock's current telemetry at every read — a mock has no poll, so stepping on read stands in for the real controller's per-poll stepping (#1324). Never imported by production code.

The former `icon-update-throttle.ts` (per-context 10 Hz throttle + trailing-edge coalescer for telemetry-driven `setKeyImage` bursts, #493) moved to `@iracedeck/deck-core` in #899 — import `IconUpdateThrottle` from there.

The top-level `icons/` directory holds one 144x144 runtime template per dynamic-icon action (content rendered from live telemetry) — see the directory for the current set and `.claude/rules/icons.md` for the template format.

## Action Pattern

See `.claude/rules/stream-deck-actions.md` for the full requirements (UUID constant, `ConnectionStateAwareAction`, `CommonSettings`, icon assembly, super calls, settings handlers). An action that reads iRacing directly through `this.sdkController` (telemetry, session info, the template context, its own telemetry subscription) extends `@iracedeck/deck-iracing`'s `SimIRacingAction` instead, which adds the typed controller; one that only calls `getCommands()` does not need it. `deck-core`'s `ConnectionStateAwareAction` has no `sdkController`.

## Dial surfaces

A dial-capable action routes its dial events to a `*-dial-surface.ts` module beside it; `fuel-service/fuel-dial-surface.ts` is the reference and `.claude/rules/encoders-and-touchscreen.md` holds the rules. Two shapes every surface shares: the per-context state is created only by the lifecycle events (`willAppear`, `didReceiveSettings`, through `ensureContext`) while the input events go through `inputContext` and never create one (#1329); and where `__FEATURE_DIAL_EXTENDED_GESTURES__` is off the hold preview is deck-core's one `NOOP_HOLD_PREVIEW`, never a local copy (#1329). A test that drives dial input makes the dial appear first, since input on a context that never appeared is dropped. One surface keeps its rotation in a registry of modes: Replay Control's `ReplayControlDialSurface` hands a turn, the box's label and what the box reads to the `ReplayDialMode` that `dial.mode` picks from `DIAL_MODES` (`replay-control/replay-control-dial-mode.ts`, #1316) — Speed Control (`replay-control-speed-mode.ts`) or Frame Jog (`replay-control-frame-jog.ts`, #1317) — and keeps the per-context state, the in-replay guard, the gestures (one `GESTURES` table: dial-hint label, run, hold-preview text) and the hold preview itself, so a new rotation mode there is one module plus one registry row, plus its `dial.mode` value, PI option and comms entry.

Dial PIs switch between keypad and dial views through `@iracedeck/pi-components`' `dial-controller` partial; never a local `resolveController` / `applyDialView` (#1329).

## Comms Catalog (#612)

`src/actions/comms-catalog.ts` (in this package) is the authoritative record of how every (action, mode) talks to iRacing — API, key binding, or chat. Editing it in a Claude Code session regenerates `data/action-comms.json` through the post-edit hook; run `pnpm generate:action-comms` from the repo root otherwise. A freshness test (`comms-catalog.test.ts`) fails when the committed JSON drifts from the catalog, and a cross-check verifies every keybind key exists in `key-bindings.json`. The full wiring (PI status line, icon overlay) is in `.claude/rules/stream-deck-actions.md` §"Per-Mode Communication Method & Binding Status".

## Build

This package has **no build step**. It exports raw TypeScript source. Consumer packages (e.g., `iracing-plugin-stream-deck`) bundle it via their shared Rollup config (`@iracedeck/plugin-build`) with `@rollup/plugin-typescript`.

The shared factory (`createPluginRollupConfig` in `packages/plugin-build/src/plugin-rollup.mjs`, which all three plugins' `rollup.config.mjs` call) includes:
- `resolve-actions-ts` plugin — resolves `.js` → `.ts` for relative imports within this package and `@iracedeck/plugin-runtime`, the two raw-TypeScript packages
- `typescript({ include: ["src/**/*.ts", "../iracing-actions/src/**/*.ts", "../plugin-runtime/src/**/*.ts"] })` — compiles the plugin's, the actions' and the runtime's TypeScript (the globs are relative to the plugin package the build runs in)
- `svg` plugin — resolves `@iracedeck/icons/` and relative SVG imports (such as `../../icons/`) to their file and imports the SVG as a string

The full step order and options are in `packages/plugin-build/CLAUDE.md`.
