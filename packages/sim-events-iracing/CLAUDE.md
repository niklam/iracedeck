# @iracedeck/sim-events-iracing

The iRacing translator (`initializeSimEventsIracing`, `src/translator.ts`): it diffs `sdkController` ticks and publishes semantic events on `@iracedeck/event-bus`, one diff module per family under `src/diff/`. The `replay.*` events come from a second subscriber beside it, the replay recorder (below).

## Place in the architecture

- It is the bus's only source of sim events. A future sim adapter is a parallel sibling emitting the same catalog. The one exception is `telemetryReadout.requested`, which the deck layer publishes, not a translator.
- It is not the only reader of `@iracedeck/iracing-sdk` telemetry: actions read the SDK controller directly through `deck-iracing`'s `SimIRacingAction`, and part of the `audio-scenarios` catalog reads raw telemetry — through the `getLatestTelemetry` dependency `race-engineer-wiring` fills from this package's getter by way of `SimRuntime`, never by importing it (#1378). `TelemetryData` is re-exported as a type so those consumers name the tick's shape without importing `iracing-sdk`. The measured leaks are listed under the Architecture page's "Seams & where the abstraction leaks" (#1351).

## What it owns besides the events

- **The canonical live order** — `getLiveRacePositions` / `getLivePosition` (`race-order.ts`). Every position consumer must use it; see `.claude/rules/race-positions.md`.
- **The pace lineup, that rule's one carve-out** — who a driver lines up behind under a caution or in a rolling-start formation: `getPaceLineup()` (`diff/pace-lineup.ts`), whose `anchor` says which of the two frames the rows were counted in (#1127 / #1167); the formation as a state, `getRollingStartFormation()` (#1167); and the caution catch-up reading, `getCautionGap()` — measured in `diff/caution-gap.ts`, decided by `diffCatchUp` in `diff/caution.ts` (#1168).
- **The track-order gaps** Session Info's Gaps shows outside a race: `getTrackGaps()` (`diff/track-gaps.ts`, #1515), the nearest cars ahead and behind on track in practice, warmup, testing and open qualifying (Lone Qualify and Lone Practice excluded), measured by the race gaps' crossing time over per-car odometer traces. Mutually exclusive with `getLiveGaps()`, which answers only in a race past the green. Deliberately not on `SimRuntime`, so the Race Engineer's gap callouts stay race-only.
- **The last-stop tire temperature reading** Session Info shows (`getLastStopTireTemps`, #254).
- **The fastest lap of the race** in the player's class (`diff/fastest-lap.ts`, #1571): a record in `TranslatorState`'s `fastestLap` slice (`fastestLap.record`) that survives the replay wipe while its per-car `CarIdxBestLapTime` baselines do not, behind `fastestLap.set` and `lap.completed`'s `isClassFastestLapOfRace`. The player's lap reaches it only through the judge `handleTick` hands `diffLaps`, which asks it only of a lap iRacing took as a new best (#1582), and `laps.ts` imports nothing from it; `diffFastestLap` publishes or clears the judge's claim on every live tick. While the player has crossed the line and that lap is not judged yet (`LapCompleted` ahead of the count `diffLaps` last emitted for), the scan of the other cars holds, for at most `FASTEST_LAP_HOLD_MAX_MS`, so a rival is never announced against a record the player has already beaten.
- **The pit-lap rule** (`diff/pit-lap.ts`, #1163): what an out-lap and an in-lap are, read by the fuel tracker (`fuel-laps.ts`, which leaves such laps out of its averages) and the lap diff (`laps.ts`, which publishes them on `lap.completed` as `isOutLap` / `isInLap`). Each keeps its own latch at its own lap boundary; the rule is the one thing shared, so a change to it is made there.
- **When a timed race ends** (`leader-finish.ts`, #1405): the leader's crossing model — the white at their first crossing at or after expiry, the chequered one lap later — shared by the gap horizon (`timeSideCrossings` in `translator.ts`, #1311) and the fuel race-coverage estimate (`diff/fuel-laps-left.ts`). Only the model is shared: each consumer keeps its own fallback for an unreadable leader, because their safe directions are opposite (the gap horizon takes an unknown lap fraction as `0`; `predictLeaderChequeredS` answers `null` and the fuel side keeps its cautious `SessionTimeRemain + 2 × leaderLap` bound). A change to the model is made there.
- **The session kind** the Stream Deck plugin switches profiles by: `getSessionKind()`, from `classifySessionKind()` in `session-kind.ts` (#1111), which reaches the plugin through `plugin-runtime`'s `HostSim` (#1500), never by import. Deliberately separate from the three-bucket `classifySession` below, which the Race Engineer depends on; see `.claude/rules/profiles-and-devices.md`.
- **The classified session** the Race Engineer reads: `getSessionClass()`, from `classifySession()` in `session-type.ts` (#1587) — practice / qualifying / race (testing is practice, anything unrecognised is race) and `soloQualifying` (iRacing's "Lone Qualify" only), `null` while the session type is unknown. Its types, `SessionClass` and `SessionCategory`, are `@iracedeck/event-bus`'s, the sim-neutral home of the buckets the bus payloads already carry, so a second sim's translator answers the same shape. The one classifier for those buckets: the translator's own `classifySessionType` (an unknown type read as race) and `classifyLapSessionType` (only a type naming "Race" counts as a race) are thin readings of it, and the catalog reaches it only through `SimRuntime.getSessionClass`, so it holds no iRacing session strings. `session-type.test.ts` pins every session type the translator meets to its bucket. The translator's own exact `=== "Race"` reads (the canonical order, the pace lineup, the replay greens) and the track gaps' Lone checks are deliberately not routed through it, since a Heat Race classifies as race here but is not `"Race"` there.
- **The after-tick hook** — `onTranslatorTick(listener)` (#1500), returning the unsubscribe. Its listeners run at the end of the translator's own `sdkController` callback, on every one — a connected tick, a connected callback without telemetry, a disconnect — from a `finally`, so after the translator has handled it and even when its frame threw (that throw still reaches the controller after them). A read inside (`getSessionKind`, `getSessionType`, `getLatestTelemetry`) sees that callback's state: that ordering is the contract, which a second controller subscriber would only have had by insertion order. A listener is never called on registration. Each is called through the step boundary (below) under one id, `translator:onTranslatorTick`, so one that throws is reported like a step and skipped while the next still runs; under `"rethrow"` its throw leaves the callback once every listener has run (#1559). The registry is module level, so a listener registered before `initializeSimEventsIracing` is kept, and `_resetSimEventsIracing` clears it. It publishes nothing, so `TICK_ORDER` does not list it. Its consumer is `plugin-runtime`'s `HostSim.onTick`.

## Recording for `@iracedeck/replay-store`

The replay recorder (`startReplayRecorder`, `src/replay-recorder.ts`, #1468) is a second SDK-controller subscriber, started by `initializeSimEventsIracing` right after the translator subscribes. Its four recorder diffs share one eligibility module (`diff/replay-record-gate.ts`) and publish what the replay store writes:

- every car's lap crossings — `replay-laps`, `replay.lapStarted` / `replay.lapTimed` (#1203);
- the race start and caution restarts — `replay-greens`, `replay.greenFlag` (#1354);
- each session's start and every incident — `replay-sessions`, `replay.sessionStarted`, and `replay-incidents`, `replay.incident` (#1426).

The session starts are also recorded out of the car at the live edge of a live session, through the gate module's second resolver.

- **No replay guard.** A recorder must see the ticks it cannot record, to mark itself unseeded on them and re-seed silently on the first eligible tick after; each diff's gate is the only one. Its "in a replay" answer is the controller's debounced replay state, read in its own callback.
- **Its own state**, `ReplayRecorderState` (`replay-recorder-state.ts`); it reads nothing of `TranslatorState`, and the translator's per-session and replay wipes never reach it. `readSimState()` reports it under `raw.replayRecorder`.
- **Its own reset points**, listed in the header of `replay-recorder.ts`: the lap, green and incident baselines at a session change (before the diffs run), on entering and on leaving a replay view (after them); everything at a disconnect. The session record (`replay-sessions`' run and published list) survives every reset but the disconnect.
- **Pinned across the move.** `replay-recorder.equivalence.test.ts` compares the `replay.*` stream of the real init with a golden recorded while the recorders still ran inside the translator; a deliberate behaviour change regenerates it (`REPLAY_GOLDEN_UPDATE=1`) and reviews the diff. One change the golden cannot see: inside the translator, the first subscriber, the recorders got the first connected tick twice at startup (the controller's connect notification, then the subscribe callback), so the session record published that session's start during init, before replay-store subscribed, and lost it; subscribed second, the recorder gets it once and publishes on the first poll. `replay-recorder.startup.test.ts` pins that over the real `SDKController`.

## Session identity (#1509)

`session-identity.ts` states once which tick starts a different session: a new `(SubSessionID, SessionNum)`, never inside a saved replay, read on every tick, the baseline reset only at a disconnect. The translator (per-session wipe, `session.changed`) and the replay recorder (baseline reset) each read it from a baseline of their own (`readSessionIdentity`, then `advanceSessionIdentity`), so both change on the same ticks. A change to the rule is made there, never in one subscriber.

## The tick order (#1499, #1468)

`src/tick-order.ts` lists every stage that can publish, in the order its publishes reach the bus, in three tables. `TICK_ORDER` is the translator's `handleTick`: the direct publishes first (the session-change sites, the pre-guard diffs, the replay-entry teardown; a pre-guard diff's reach the bus when its step returns, #1559), then the `pending` batch the live diffs fill, flushed in call order from a `finally`. `REPLAY_RECORDER_ORDER` is the replay recorder's tick, its four diffs publishing directly, each when its step returns. The controller notifies in subscription order, so a tick's `replay.*` events reach the bus after all of the translator's; `CONTROLLER_TICK_ORDER` is the two end to end, the table an `endsOn` check reads. `findEndsOnOrderViolations` reads it to prove an `endsOn` contract's trigger is never published after its end on one tick (#1407); `race-engineer-wiring`'s `ends-on-order.test.ts` applies it to every registered contract. `tick-order.test.ts` proves the tables are the code by spying on the real diff calls, the publishes and the subscriber boundaries. Keeping them true:

- **A diff module that emits declares what.** It exports `<NAME>_EVENTS` (`as const satisfies readonly SimEventName[]`) and types its emitter `EmitFn<(typeof <NAME>_EVENTS)[number]>`. `EmitFn` has no default, so an emit the list does not name is a compile error; a module with two emitting functions declares one list each (`START_COUNTDOWN_EVENTS`, `START_LIGHTS_EVENTS`).
- **A new emitting diff, or one that starts emitting,** gets its row at its call position in the table of the subscriber that calls it — `TICK_ORDER` (`via: "pending"` for a live diff, `"direct"` for a pre-guard one) or `REPLAY_RECORDER_ORDER` (`"direct"`), never both — whose `events` is the module's list itself rather than a copy, and a `vi.mock` spy line in `tick-order.test.ts` naming the index of its emitter argument. The completeness test fails on a declared list with no row, and the call-order test on a stage it never recorded. A diff that publishes nothing gets no row.
- **Reordering any diff call in either subscriber** means moving its row too; the call-order test fails until it does. If an `endsOn` pair then fails in the wiring test, the reorder broke that contract: put the trigger's stage back ahead of its end's.
- **A new publish site in `translator.ts` itself** gets a `source: "translator.ts"` row and a real tick that publishes from it in the translator-sites test; the completeness test fails on an event those sites name that no such row lists. `replay-recorder.ts` publishes from one site, `publish`, and the same test fails on a second.

## The step boundary (#1559)

A throw in one step of a tick costs that step and no other. `TickSteps` (`src/tick-steps.ts`) runs every call of the translator's tick (`handleTick` and its live half, `handleLiveSteps` and `handleOrderSteps`) and of the replay recorder's through one #1558 `createErrorBoundary` from `@iracedeck/logger`, built per instance in `initializeSimEventsIracing` with a reporter table of its own, apart from the controller's, and handed to `startReplayRecorder`. A step that throws publishes nothing that tick — `live` truncates `pending` back to its mark, `direct` buffers and publishes when the step returns, `run` is for a step that emits nothing — is reported once per throw site as `translator:<function>` or `replay-recorder:<function>`, and is called again on the next tick, while every later step still runs. The translator does not restore a failed step's state; keeping it consistent is the step's job. The frame (the tick's reads, the session identity and its reset, the replay guard's teardown and wipes) is not split: a throw there reaches the controller's subscriber boundary, and the `pending` flush runs in a `finally`, so what completed is still published in call order. The policy and clock are `initializeSimEventsIracing` options, `onStepError` (#1558's `ErrorPolicy`, default `"report"`, what every plugin runs) and `errorClock`; under `"rethrow"` every step still runs and `steps.finish()` throws the first error at the end of the callback. The decision record is `docs/superpowers/specs/2026-10-31-issue-1559-translator-diff-isolation.md`.

- **A new call in a tick goes through the boundary under its function's name** — `steps.live`, `.direct` or `.run` for a step, a value call for a value — with the name a string literal and the argument expressions computed inside the closure, so a throw while computing one costs that step only. `tick-steps.source.test.ts` parses both ticks with the TypeScript compiler and fails on any call outside a step that the tick's frame allow-list does not name; a frame call is added there deliberately, never to let a bare diff pass.
- **A value a step hands on gets its fallback stated in the same change.** `steps.value(name, self.lastValues, absent, …)` falls back to its last good answer this session (the store is cleared at a session change and a disconnect, kept through the replay wipe), else to `absent`, the resolver's answer for absent session info; `steps.fallbackValue` always to one fixed answer, for a value whose last answer would be wrong (`resolvePlayerResultsSnapshot` → `null`, `resolvePlayerIsLeader` → `false`); `steps.requiredValue` has none, so its consumers are skipped that tick and listed where it is read — the canonical order's six in `handleOrderSteps`, `diffTireWear` behind `stallVisit`. A value read by one step only, from telemetry, is part of that step.
- **A diff that loops over independent cars runs each car as a unit.** It takes a `UnitRunner` parameter defaulting to `runUnitsDirectly`, which catches nothing so the diff's own tests stay loud, and the tick hands it `steps.runUnit`: a car whose unit throws drops that car's events only, reported under the step's id, and the other cars commit. That car's baseline is written last inside the unit, so a throw retries the car on the next tick. `diffReplayLaps`, `diffReplayIncidents`, `diffOpponentPit` and `diffOpponentFlags` do this; field-wide work after the loop stays in the step.
- **A diff writes its baseline last**, after the work that can throw, so a throw is retried on the next tick rather than lost: its events are dropped with it, and nothing restores its state.
- **No step reads its own events from `pending`.** Truncating on a throw is safe only because the readers (`diffPitReadback`, `updateStallVisit`, `diffTireWear`) look for other steps' events.
- **A same-tick flag one step hands another is a returned value, not a state field**, so a throw in the writer cannot leave the previous tick's answer behind: `diffToggles` returns whether the fuel plan changed and `handleLiveSteps` hands it to `diffPitReadback`, `false` when `diffToggles` threw.
- **A new id grows `TRANSLATOR_REPORTER_MAX_KEYS`.** The shared boundary's global cap is four throw sites (`TICK_STEP_KEYS_PER_ID`, #1558's per-id cap) for every id it reports — each step and value of both ticks, plus `translator:onTranslatorTick` — so it is never what hides one step's first error. The source check counts the ids and fails until the constant matches.
- **Translator-level tests pass `onStepError: "rethrow"`**, so a diff that starts throwing fails the suite instead of being reported and passing; every suite that drives ticks through `initializeSimEventsIracing` does, the scenario harness's included. A diff's own tests call it directly and need neither.

## Translator state slices (#1588)

`TranslatorState` (`src/state.ts`) holds each cluster of state as one nested member, a *slice*, rather than as flat family-prefixed fields, so a diff's signature says what it touches and the wipes and the snapshot have a unit to act on. The decision record is `docs/superpowers/specs/2026-11-02-issue-1588-translator-state-slices.md`.

- **When.** Every new cluster is a slice: a new family's fields, or a new concern inside an existing family. An existing flat cluster becomes one when its family next changes in substance, never in a sweep. Which clusters are still flat, and what each one's move must settle first, is the guard's pin `LEGACY_FLAT_MEMBERS` in `src/state-slices.test.ts` (one entry per `state.ts` heading, the note as a comment on it); a move deletes its entry in the same change.
- **Shape.** One member `<family>: <Family>State`, its key camelCase and its fields without the family prefix (`fastestLap.record`, not `fastestLap.fastestLapRecord`). The type and a `create<Family>State()` setting every field (no `?:` field) are declared in `state.ts` beside the member, the cluster's documentation on the type and each field documented inside it, and `createInitialState` builds the member with a no-argument call. Not in the diff module: a diff imports `state.ts`, so a factory there closes a `state.ts` → `diff/x.ts` → `state.ts` cycle as soon as the diff imports a value from `state.ts`, and the plugin builds fail on a cycle among our sources.
- **What a diff receives.** A diff that owns a slice takes it as its first parameter, never `TranslatorState` whole, `Readonly` or narrowed with `Pick<>`. Another family's fact arrives as a value `handleTick` reads at the call, typed with `null` for its unknown case, its JSDoc naming the fact and its writer: `diffFastestLap`'s `lapsJudgedThrough` is `lastLapCompletedCounter` once `lapCompletedInitialized`, else `null`. A write into another family's slice goes only through a closure `handleTick` builds over that slice. The fastest-lap judge, `createFastestLapJudge(self.state.fastestLap, …)` handed to `diffLaps`, writing `record` and `claim`, is the one sanctioned cross-step writer of `fastestLap`, which therefore has two writers; a new one needs the same justification and its own line here.
- **Mutate in place.** A diff that clears its slice writes `Object.assign(slice, create<Family>State())`, never a new object through the parent, so a reference taken earlier in the tick (the judge's) is still the object later steps read. `diffTrackGaps` and `diffLaps`' `lapCrossing` reset do this.
- **Lifecycles.** A disconnect and a session change recreate the whole state, so a slice resets at both with no code; one that must outlive a session change goes in `resetPerSessionState`'s `preservedAcrossSessions`. At the replay wipe (`wipeStateForReplay`) the slice's owner picks one of three: wiped whole (`trackGaps`; nothing to write), kept whole (its key in `preservedAcrossReplay`), or kept in part by a `reset<Family>…(slice): <Family>State` beside the factory in `state.ts` that returns the slice to keep, called from `preservedAcrossReplay` and documenting which fields survive and why — `resetFastestLapBaselines`, which carries `record` (by reference) and `raceSeeded` and returns the rest fresh.
- **The Telemetry Snapshot needs no code.** `readSimState` hands the whole state over as `raw.state`, so a slice shows as `raw.state.<family>.<field>` (`raw.state.fastestLap.record`); `raw` promises no stability.
- **The guard** is `src/state-slices.test.ts`, over the TypeScript-compiler scanner in `src/state-slices.test-support.ts`, whose header says exactly what each rule matches. Every rule has planted positive controls and the scan asserts minimum counts, so an empty read cannot pass.
  - A: a `TranslatorState` member the pin does not name must be a slice — a reference to an object type alias in `state.ts` ending in `State`, with no `?:` field, whose `create<Type>` in `state.ts` `createInitialState` calls with no arguments.
  - B: the pin only shrinks and matches the file — a pinned name that is no longer a member, sits under another heading or is pinned twice fails, as does an empty entry or one whose heading `state.ts` no longer has.
  - C: a `diff/` module importing `TranslatorState` names no slice type and reads no slice key off a binding annotated `TranslatorState`, destructuring included; an exception goes in `SLICE_READS_ALLOWED` with its reason (`laps.ts:lapCrossing` until the laps cluster moves), and an entry no read matches fails.
  - D: no assignment in a `diff/` module targets `<x>.<sliceKey>`; a slice is cleared in place.

## Rules

- A new bus event needs an entry in the scenario harness's `src/event-names.ts`, and a new callout a shortcut button there (`packages/scenario-harness/CLAUDE.md`).
- Captured telemetry fixtures for the diff tests live in `src/diff/__fixtures__/` (see its `README.md`). Another package's test reads one through the `./testing` entry, `captureFixturePath("<name>.json")` from `@iracedeck/sim-events-iracing/testing` (#1375; `audio-scenarios`' `caution.test.ts`), never by a relative path into `src/`. It resolves `../src/diff/__fixtures__/` against its own module, the same folder from `src/` (the vitest alias) and from `dist/`, and refuses a name that is not a bare `.json` file name or that the folder does not hold. Renaming or removing a capture another package reads breaks that test.
