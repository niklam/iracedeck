# @iracedeck/sim-events-iracing

The iRacing translator (`initializeSimEventsIracing`, `src/translator.ts`): it diffs `sdkController` ticks and publishes semantic events on `@iracedeck/event-bus`, one diff module per family under `src/diff/`. The `replay.*` events come from a second subscriber beside it, the replay recorder (below).

## Place in the architecture

- It is the bus's only source of sim events. A future sim adapter is a parallel sibling emitting the same catalog. The one exception is `telemetryReadout.requested`, which the deck layer publishes, not a translator.
- It is not the only reader of `@iracedeck/iracing-sdk` telemetry: actions read the SDK controller directly through `deck-iracing`'s `SimIRacingAction`, and part of the `audio-scenarios` catalog reads raw telemetry — through the `getLatestTelemetry` dependency `race-engineer-wiring` fills from this package's getter by way of `SimRuntime`, never by importing it (#1378). `TelemetryData` is re-exported as a type so those consumers name the tick's shape without importing `iracing-sdk`. The measured leaks are listed under the Architecture page's "Seams & where the abstraction leaks" (#1351).

## What it owns besides the events

- **The canonical live order** — `getLiveRacePositions` / `getLivePosition` (`translator.ts`, memoised once per tick on `canonicalOrderMemo`; `race-order.ts` holds only the choice between its three sources: the qualifying grid before a race's green, a replay frame's line-corrected progress, and the live lap-progress order with its freeze). Every position consumer must use it; see `.claude/rules/race-positions.md`.
- **The replay order's progress** (`diff/replay-progress.ts`, #1682): a replay frame never reaches the live freeze, so ranked raw a car whose lap counter and lap fraction disagree for a tick at the start/finish line blinked a lap ahead. The replay guard in `handleTick` runs `stepReplayProgress` on every tick it swallows (in-session replay, the seek grace, a saved replay), whether or not anyone reads the order: it reads every car through the same line-progress core as the live step, under `REPLAY_CAR_PROGRESS_POLICY`, against the `replayProgress` slice (per-car last progress, confirmed flag and continuing run, and the last `SessionTime`; wiped whole at both replay edges). The readings themselves are paired with their telemetry object on the instance (`replayReadings`, never in `TranslatorState`, so no telemetry lands in a Telemetry Snapshot), cleared before the step and written once it returns; the step then clears `canonicalOrderMemo`, and `resolveCanonicalOrder` hands the readings to `calculateCanonicalRacePositions` only for that very telemetry. It is the translator's step, not the replay recorder's (#1468), because it feeds the canonical order. Evidence: `diff/__fixtures__/replay-order-line-20261110.json`.
- **The pace lineup, that rule's one carve-out** — who a driver lines up behind under a caution or in a rolling-start formation: `getPaceLineup()` (`diff/pace-lineup.ts`), whose `anchor` says which of the two frames the rows were counted in (#1127 / #1167); the formation as a state, `getRollingStartFormation()` (#1167); and the caution catch-up reading, `getCautionGap()` — measured in `diff/caution-gap.ts`, decided by `diffCatchUp` in `diff/caution.ts` (#1168).
- **The track-order gaps** Session Info's Gaps shows outside a race: `getTrackGaps()` (`diff/track-gaps.ts`, #1515), the nearest cars ahead and behind on track in practice, warmup, testing and open qualifying (Lone Qualify and Lone Practice excluded), measured by the race gaps' crossing time over per-car odometer traces. Mutually exclusive with `getLiveGaps()`, which answers only in a race past the green. Deliberately not on `SimRuntime`, so the Race Engineer's gap callouts stay race-only.
- **The last-stop tire temperature reading** Session Info shows (`getLastStopTireTemps`, #254).
- **The track's sectors** (#1573): resolved in every session type from `iracing-sdk`'s `extractSectorStarts` into the `trackSectors` slice, and handed by `handleTick` as a value to each diff that reads them (the sector-start calls, and #1572's sector timer) — the one place any feature reads them. There is deliberately no exported getter: a reader outside the translator gets a sim-neutral `SimRuntime` member instead. Like the track length, the corner markers and the pit speed limit, it is cached per `trackSessionKey(sessionInfo, telemetry)`, the one builder of the `TrackID|SessionNum` key all four share. The sector-start diff sweeps the same lead point as the corner names through `diff/lead-point-sweep.ts`, so the two calls cannot drift apart.
- **When race progress is read** (`diff/car-progress.ts`, #1572): `stepCarProgress` runs once per live tick in `handleOrderSteps`, right before `diffGaps`, and is the one place the gate on race progress lives — a race, both `CarIdx` progress arrays, a finite `SessionTime`, a player index, a canonical order, past the green, the player racing. It appends each car's reading to its trace in the `carProgress` slice (the crossing-time traces #933's gap model reads, moved out of the flat gaps cluster) and returns a `CarProgressTick` — `sessionTime`, `previousSessionTime`, per-car `progress` and `traceReset`, and the live `traces` — or `null` on a refused gate, which `diffGaps` (it blanks its live snapshots) and the sector timer both take, so neither re-derives the gate. A car's reading is `readCarLineProgress` (validity, then `readCarProgress` against the confirmed last progress, then `confirmsCarProgress`), the one per-car reading every progress step applies, and `readCarProgress` the one statement of what progress is at the start/finish line: `CarIdxLapCompleted` can step a tick before or after `CarIdxLapDistPct` wraps (8 of 24 crossings in a 2026-11-10 replay capture), so a sum more than half a lap from the car's confirmed last progress (`confirmedLastProgress`: a reading that itself continued the one before it, where that one was confirmed or this one was read clear of the line guard band; so a first reading after none is taken as it stands, a seed that lands on a disagreeing tick is replaced by the next reading rather than locked in, and any run that began inside the band — after a blink, a gate flicker or a span past 0.5 s — stays unconfirmed and uncorrected until it leaves it, since a disagreement of two ticks gives two wrong readings that agree) takes its lap count from that progress instead, when the last read is at most `CAR_PROGRESS_LINE_MAX_SPAN_S` (0.5 s) old (`withinCorrectionSpan`, which `liveGapBetween` applies too; after a longer gap a car near the line may have driven a whole lap, so the reading stands as it is and counts as a first reading, confirming nothing), but only when the corrected lap count is exactly one off the counter's (a counter several laps off is rewound), the fraction is within `CAR_PROGRESS_LINE_GUARD_PCT` of the line and the corrected step within `CAR_PROGRESS_LINE_MAX_TICK_STEP` (one tick's travel, 0.01 lap, not the trace's 0.05 between samples, so a hop across the line stays a reset); anything else stays the discontinuity it is. `liveGapBetween` (behind `getLiveGapBetween` and the opponent-flag range) applies the same correction against `confirmedLastProgress`, so every live reader sees one scale. The replay step is the one exception, and only by policy (`CarProgressPolicy`), never by a rule of its own: it corrects across `|since| <= 0.5 s` (a replay rewinds as often as it plays), also confirms by a run of `CAR_PROGRESS_CONFIRM_RUN` (3) continuing readings, each at a distinct `SessionTime` and each a different progress (a car on pit road at pit speed sits inside the band for hundreds of ticks before its crossing, so band exit alone never confirms it; a repeated reading adds nothing, whether a paused saved replay repeats its `SessionTime` or an in-session replay paused at its live edge runs the clock on), and reads the lap fraction through `readLapFraction` (a hair below zero is the line). The live step keeps `LIVE_CAR_PROGRESS_POLICY`; whether it adopts any of the three is #1742's call. The continuity rule is on `CarProgressTick`: a consumer that keeps a reading from one tick to measure against the next bridges only when the tick's `previousSessionTime` equals the `sessionTime` it last consumed. The step clears `lastReadSessionTime` on entry and writes it once every car is read, so a refused gate, a throw and the first tick all read as "no previous tick", and every car's continuity breaks across such a tick, whatever `traceReset` says: a reset proves a break, its absence proves nothing. A tick the step is not called on at all (the canonical order threw, so `handleOrderSteps` was skipped) clears nothing and is bridged like a telemetry tick that never arrived: a wider tick pair, which the sector timer bounds with `SECTOR_MAX_TICK_SPAN_S`.
- **The sector timer** (`diff/sector-times.ts`, #1572): every car's sector times, which iRacing does not report, measured by interpolating each car's crossing of every sector start between two consecutive progress ticks, and the cars the player is compared with. `diffSectorTimes` runs right after `diffGaps` as a `steps.run` (it publishes nothing, so no `TICK_ORDER` row), each car a `runUnit` unit, and takes the progress tick, the track's sectors (the `trackSectors` value `handleLiveSteps` resolves ahead of the order steps), `CarIdxTrackSurface`, whether a caution is out (after `diffCaution`) and the class neighbours `diffGaps` returned. It bridges a car's two readings only under the continuity rule above, at most `SECTOR_MAX_TICK_SPAN_S` apart, with no trace reset and a reading on both ticks; anything else drops the lap in progress, so a lap can go missing but never get a wrong time. A lap opens only at a measured start/finish crossing and is recorded only when every crossing was measured. Its state is the `sectorTimes` slice: per car the previous reading, the lap in progress and the last `SECTOR_HISTORY_LAPS` completed laps (`{ lap, sectorTimes, clean }`, `lap` being the count `lap.completed` carries, the opening lap 1), plus the three targets and the sector count it measured with on its last tick (`sectorCount`, `null` on a tick it recorded nothing). `clean` is one rule for every car: `OnTrack` on every tick, no full-course caution on any tick, not lap 1, every sector time positive; the player's `lapIsValid` is deliberately not used, since no other car has one. It holds facts only — the reference lap, the thresholds and the cadence are the catalog's (`sector-comparison.ts` in `audio-scenarios`). Two readers: `getCarSectorTimes(carIdx)`, any car's recorded laps, and `getSectorComparison()`, the sector count (the slice's, so it is the count the laps were measured against) and, for the player, the class leader, the car ahead and the car behind, each car's index, number, live gap to the player (`liveGapBetween`), completed-lap count (`lapsCompleted`, from `CarIdxLapCompleted`, `null` for a car out of the world, so the catalog can bound its window by completed laps and skip a retired leader) and recorded laps — facts only, with the leader `null` only when the player leads the class or no leader is known, and `null` whole outside a race, with no player index or with no sectors; the latter reaches the catalog as `SimRuntime.getSectorComparison`.
- **The pit-lane landmark edges** (`diff/pit-lane-landmarks.ts`, #1112): `approachStart`, `pitRoadStart`, `pitRoadEnd` and `blendEnd`, learned from every car but the pace car and published as `pitLane.landmarkLearned` when accepted. This package keeps only iRacing's half: `resolvePitLaneTrackIdentity` (from `WeekendInfo`, with `sim: IRACING_SIM_ID` — `"iracing"`, exported from the barrel and persisted as the track store's folder name, so it never changes), the per-car edge detector and its slice, the translator wiring (`seedPitLaneLandmarkLearner`, which logs what track-data's load did) and the accessor. The learner itself — loading, the fold (`learnPitLaneLandmarks`, all or nothing per car), the track key and the per-landmark view — is `@iracedeck/track-data`'s (`pit-lane-learner.ts`); never reimplement it, its median or its wrap math here. `getPitLaneLandmarks()` reads them, `null` until a live tick has loaded the track, and a consumer that finds no landmark stays silent (spec decision 5). The translator does no file IO: the plugin hands in `loadPitLaneLandmarks` (an `initializeSimEventsIracing` option, not a setting, typed by track-data's `PitLaneLandmarksLoader`), called once per track identity and again after a session change or a disconnect empties the learner, and on track-data's back-off (by the tick's wall clock, `now`) while it answers `PIT_LANE_SECTION_UNAVAILABLE` — warned on the first such answer per identity, debug on the retries, learning meanwhile. The learner sits on the instance, like `fuelLaps`, so a garage visit keeps it; the per-car baselines are the `pitLaneLandmarks` slice, wiped at the replay wipe. The edges must hold whether `CarIdxOnPitRoad` is right or wrong: captures read it true for cars on the racing surface, and in one online practice session (Spa, 2026-11-09) the player's read true throughout while remote cars' disagreed with their surface (a race is not captured yet). So the player's car reads the player's `OnPitRoad` (other cars, and the player when `PlayerCarIdx` or `OnPitRoad` is missing, read `CarIdxOnPitRoad`), a pit-road edge needs `AproachingPits` on its pit side as well as the flip, and the "came from the pit lane" mark that `blendEnd` needs is armed by a stall exit (`InPitStall → AproachingPits`) as well as by pit road ending, and cleared on any `OnTrack` tick; a pit-road flip that teaches nothing logs its reason at debug to the `PitLaneLandmarks` scope. Acceptance (road state, plausible distance per `SessionTime`, the two ticks at most `PIT_LANE_MAX_EDGE_SPAN_S` apart so a car not read for longer is re-seeded rather than learned from, the settle time) is in the module header. Live in-car only: replay ticks never reach it (spec amendment 5). `pit-lane-landmarks.types.test.ts` pins event-bus's inline payload types to track-data's, both ways.
- **The approaching-traffic arrival model and its two detectors** (#1113; spec `docs/superpowers/specs/2026-09-04-issue-1113-approaching-traffic-warnings.md`). `diff/traffic-arrival.ts` answers when each car reaches a lap position P: its OWN class's reference time at P minus its `CarIdxEstTime`, wrapped round the lap when the car is ahead of P by position (never by the sign of the difference), from one of three sources in the caller's order — a landmark's per-class `estTime` (pit exit only), the class's learned curve, the player's class reference scaled by the `CarClassEstLapTime` ratio; a car no source can time is reported untimed with its reason, and each detector decides what that means. Candidates are every other car on the racing surface (`OnTrack` / `OffTrack`, the pace car included) but one measured standing still that has a lap position this tick: each car's progress along the lap is measured on `SessionTime` over at least half a second (the slice's `motion`), and a car under `TRAFFIC_CRAWL_MPS` (the 3 m/s both detectors share) is left out, since at reference pace it would read as arriving now and hide every car really coming; one with no usable rate (first readings, a gap, a tow, no track length) counts as moving, and so does one measured standing that has since gone forward faster than the crawl speed allows inside its next window (it pulled away), without waiting for that window to complete. `CarIdxOnPitRoad` is never read. The module is split on purpose, and stays split: iRacing's half is `resolveTrafficClassInfo`, `resolveCarClassId` and the two per-car array walks (`updateTrafficReferenceCurves`, `computeTrafficArrivals`); the sim-neutral half is the curve fold and lookup (`referenceTimeAt`), `curveLapEnd`, `resolveClassLapTime`, `crossesLineBefore`, `arrivalSeconds` and the reference-source tiers — what lets it move to `@iracedeck/track-data` at the second-sim spike (#714). The detectors are `diffTrafficRejoin` (`diff/traffic-rejoin.ts`, `traffic.rejoin`; it runs only when `initializeSimEventsIracing`'s `trafficRejoin` option is on — the development flag of the same name, off in every release build and by default, since the rejoin warnings do not ship (the spec's fourth amendment, 2026-11-21) — and otherwise its step is skipped whole, so neither of its events is ever published: stopped or crawling on the circuit, a running episode ending at once when the car is taken off the track — out of the world or in the pit stall (a tow or a reset), out of the car, the garage — which publishes `traffic.rejoinTowed`, the end the Race Engineer's rejoin lines name in `endsOn` so a line in flight is cut (amended 2026-11-20; nothing else is published on that tick, the order `ends-on-order.test.ts` in `race-engineer-wiring` exempts by citing the detector's test), and on any other gate only once it has failed for `TRAFFIC_REJOIN_GATE_GRACE_MS`, silently, so a one-tick blip never repeats the first call; a payload keyed on `verdict`, the fixed band of the nearest arrival — `rightBehind` under 2 s, `near` under 10 s carrying its whole `seconds` and `first`, and nothing at all from 10 s or with no car (amended 2026-11-20: no reassuring line) — the edges `@iracedeck/event-bus`'s constants beside the payload (`TRAFFIC_REJOIN_RIGHT_BEHIND_S`, `_OVER_TEN_S`), because the lines name them and the catalog's contracts read the same ones; it speaks the first band under 10 s, a closer band and a `near` count down by 3, and once the close car has gone by (its arrival rising past `TRAFFIC_REJOIN_PASSED_RISE_S`, reaching the detector's own `TRAFFIC_REJOIN_GONE_S`, 15 s, or untimed or standing still) the call is forgotten, so the next car under 10 s is a new first call; an untimed car is left out and withholds nothing; a pack is one call (amended 2026-11-18): the nearest timed car under 10 s with another chained behind it within `TRAFFIC_REJOIN_PACK_GAP_S` (2 s) of the car before is `pack` in place of the band, ranked closer than `rightBehind`, so it is also said over a lone car already announced; its cars, kept in the slice's `packCars`, are followed one by one with the close car's rule, a car arriving within the gap behind the last still coming joins it and a car of it gone by never joins again, nothing is said until every one has gone by, and then the call is forgotten, as for a lone car) and `diffTrafficPitExit` (`diff/traffic-pit-exit.ts`, `traffic.pitExit`: from the stall departure to `blendEnd`, the verdict settled silently from the stall on — the first at once, a different one only once it holds for `TRAFFIC_PIT_EXIT_FLIP_CONFIRM_EVALUATIONS` evaluations in a row, since both lines cut in and a car at a window edge wobbles across it — and spoken only at the call point (amended twice on 2026-11-20, superseding the call at the stall and then the call at the end of pit road): `TRAFFIC_PIT_EXIT_CALL_LEAD_S` (3 s) short of `pitRoadEnd` at the pit speed limit, measured by the ETA's own pit-road term (`secondsToPitRoadEnd`, never a second estimate), so a stall closer than that is called on the departure and a track whose `pitRoadEnd` is at `blendEnd` gets its call 3 s before the merge; or past `pitRoadEnd` already (the ETA's blend-phase test, `OnPitRoad` false or the position at or past it), the fallback for landmarks arriving mid-exit and the call point outright with no track length or pit speed limit. The test is written once (`reachedCallPoint`) and latched (`callPointReached`), so a rollback or a wobble never speaks twice; the first tick at it evaluates there and then even between the scheduled one-second evaluations, counted toward no flip's hold, and says whatever has settled by then, and after it each settled flip up to `blendEnd`; a flip first seen at the call point is held like any other. In the exit lane, past `pitRoadEnd` and short of `blendEnd`, it publishes `traffic.pitExitMerge` once per episode, whatever the call said, and then publishes no further `traffic.pitExit` that episode (a flip settling after it is logged, not said: no verdict follows "Watch for cars."), when the nearest crossing of a TIMED car lies within `trafficPitExitMergeWarnSeconds` of the player's ETA either side (`|arrival − eta| ≤ threshold`; an untimed car never triggers it, since "truly close" is a number); the first tick past `pitRoadEnd` evaluates off the schedule for it too, until an evaluation there has timed the cars (`mergeChecked`), so a short exit lane is not crossed unchecked, and every tick between two evaluations reads the landmarks until the episode ends, the call made and the merge checked or not, so one that finds the player at or past `blendEnd` ends the episode as a scheduled evaluation would; every end of an episode publishes `traffic.pitExitEnded`, and so does the translator's teardown for a running exit a wipe ends, which the Race Engineer's pit-exit gate reads to drop a line about that exit still waiting; with no position on the departure tick the episode starts from the stall's last read position, `lastStallPct`). Each car an evaluation times is a unit of the step's runner, so a car whose reading throws is untimed and the rest timed, and the curve walk reads each car's progress before its sample, so a throwing estTime never keeps a stale standing rate; a curve's lap end is extrapolated only over a baseline at least as long as its reach to the line. Three slices, one owner each: `trafficArrival`, the per-class reference curves and each car's progress, fed on every live tick from the racing surface only, its curves kept and its progress dropped at the replay wipe (`resetTrafficArrivalMotion`: a curve is a function of track and class and only live ticks feed it, while a car's progress is a run of live readings the glance broke) and recreated whole at a session change or a disconnect; `trafficRejoin`, owned by `diffTrafficRejoin`, and `trafficPitExit`, owned by `diffTrafficPitExit`, each wiped whole at the replay wipe, since an episode is a run of live facts a garage visit or a replay glance breaks. The pit-exit detector reads #1112's learner on the instance through `resolvePitLaneLandmarks(self.pitLaneLearner)`, handed in by `handleLiveSteps` — the learner's second reader, not through `getPitLaneLandmarks()` — and stays silent while `pitRoadEnd` or `blendEnd` is unlearned, or is still the one kept from before a track rebuild (`source: "previous"`), learned on the old geometry, where neither the landmark slack nor the ETA holds, or while the pair is out of driving order (`pitRoadEnd` past `blendEnd` beyond the slack that makes them one point: read forward, a `blendEnd` more than half a lap on from `pitRoadEnd`), a mislearned pair that would put every position short of the blend past the end of pit road and make the call at the departure. Its window tests every crossing of each car a class lap apart (`seconds + k × classLap − eta`, from `k = −1` up to the first past the after side), because the arrival model answers only the next one: `k = −1` is the before side looking back, and the later ones catch a car whose crossing a lap on lands in the window when the ETA is longer than its class lap. The pit-exit window's two sides (`trafficPitExitBeforeSeconds`, `trafficPitExitAfterSeconds`) and the merge threshold (`trafficPitExitMergeWarnSeconds`, 0–5 s, default 1.5) are injected as live-read options, sanitized by `diff/traffic-settings.ts`'s exported sanitizers, the gap settings' pattern; rejoin reads no setting, and the call lead is a constant.
- **The fastest lap of the race** in the player's class (`diff/fastest-lap.ts`, #1571): a record in `TranslatorState`'s `fastestLap` slice (`fastestLap.record`) that survives the replay wipe while its per-car `CarIdxBestLapTime` baselines do not, behind `fastestLap.set` and `lap.completed`'s `isClassFastestLapOfRace`. The player's lap reaches it only through the judge `handleTick` hands `diffLaps`, which asks it only of a lap iRacing took as a new best (#1582), and `laps.ts` imports nothing from it; `diffFastestLap` publishes or clears the judge's claim on every live tick. While the player has crossed the line and that lap is not judged yet (`LapCompleted` ahead of the count `diffLaps` last emitted for), the scan of the other cars holds, for at most `FASTEST_LAP_HOLD_MAX_MS`, so a rival is never announced against a record the player has already beaten.
- **The pit-lap rule** (`diff/pit-lap.ts`, #1163): what an out-lap and an in-lap are, read by the fuel tracker (`fuel-laps.ts`, which leaves such laps out of its averages) and the lap diff (`laps.ts`, which publishes them on `lap.completed` as `isOutLap` / `isInLap`). Each keeps its own latch at its own lap boundary; the rule is the one thing shared, so a change to it is made there.
- **The standing of a car against the player** (`diff/standings.ts`, #950): the class screen (a readable class that differs from the player's never counts, in any session; in multi-class an unreadable one does not either), the class-space-or-overall projection of the canonical order, the player's own standing and the same-lap test, with a named miss for each check that fails. Opponent-pit and opponent-flags share the whole check (`resolveStanding`), each keeping its own relation window on top; fastest-lap takes only the projection (`standingPosition`), with no class screen or same-lap test. A change to the class screen, the projection or the same-lap span is made there.
- **When a timed race ends** (`leader-finish.ts`, #1405): the leader's crossing model — the white at their first crossing at or after expiry, the chequered one lap later — shared by the gap horizon (`timeSideCrossings` in `translator.ts`, #1311) and the fuel race-coverage estimate (`diff/fuel-laps-left.ts`). Only the model is shared: each consumer keeps its own fallback for an unreadable leader, because their safe directions are opposite (the gap horizon takes an unknown lap fraction as `0`; `predictLeaderChequered` answers `null`, and the fuel side then keeps its cautious `SessionTimeRemain + 2 × leaderLap` bound while the clock runs and leaves the timed side unknown, which keeps announcing, once it reads expired). The fuel side trusts an expired clock only after `CLOCK_EXPIRY_CONFIRM_TICKS` (60, about a second) consecutive ticks (`countClockExpiredTicks` into `state.fuelCallout.clockExpiredTicks`), against the #666 blip of a tick or two; `leader-white.ts` keeps its own two-tick confirmation. It also trusts the post-expiry crossing marker only when the clock bears it out (`leaderCrossedSinceExpiry`: `f · L < secondsSinceExpiry − 0.03 · L`), since a lead change while expired sets the marker too; otherwise the leader is taken to be one lap further from the flag. For fuel, `resolveLeaderFinish` hands over the prediction in seconds and in the leader's crossings to the flag, plus the player's distance from the leader (`readLeaderGap`, from `CarIdxLapCompleted` and `CarIdxLapDistPct`, unknown when either car is within `LAP_LINE_GUARD_PCT` of the line). A player within a lap of the leader now and projected to still be at the chequered (`g + T · (1/L − 1/P) < 1`) counts the leader's crossings exactly, with no tolerance, at the lap-count pace `min(L, P)` (`lapCountChequered`: the leader's raw lap time capped at the player's validated average, used for the crossings, the chequered time and the projection alike), because an inflated raw lap — caution, pit, spin — would count too few crossings there; the time path keeps the raw lap time, where an inflated one only adds laps. One a lap or more away now or at the flag (a slower car the leader will lap first), or with unreadable lap data or an unknown leader lap time, counts by time with the near-tie tolerance. The `-1` clock before the start reads as expired and is harmless only for the pre-green reasons documented in `leader-finish.ts`. The gap horizon converts the leader's crossings into the player's distance to their own flag (`resolveGapLapsRemaining`, #1380): through the same lap-count test and count (`staysWithinLapAtChequered`, `lapCountCrossings`), but at the leader's faster known pace (the smaller of their last and best lap) and with no tolerance, its time path capped at `C_L + 1` and a leader inside `LAP_LINE_GUARD_PCT` past the line counted one crossing short there, since for the gap horizon a count too high is the unsafe direction. The player's own finish is read at the crossing through `tookChequeredAt` (`diff/laps.ts`), not from `raceFinish`, which lands only after the lap-time and standings waits. A change to the model is made there.
- **The session kind** the Stream Deck plugin switches profiles by: `getSessionKind()`, from `classifySessionKind()` in `session-kind.ts` (#1111), which reaches the plugin through `plugin-runtime`'s `HostSim` (#1500), never by import. Deliberately separate from the three-bucket `classifySession` below, which the Race Engineer depends on; see `.claude/rules/profiles-and-devices.md`.
- **The classified session** the Race Engineer reads: `getSessionClass()`, from `classifySession()` in `session-type.ts` (#1587) — practice / qualifying / race (testing is practice, anything unrecognised is race), `soloQualifying` (iRacing's "Lone Qualify" only) and `testing` (a type naming "Testing", i.e. "Offline Testing": still practice by category, told apart for the fuel countdown's Test toggle, #1702), `null` while the session type is unknown. Its types, `SessionClass` and `SessionCategory`, are `@iracedeck/event-bus`'s, the sim-neutral home of the buckets the bus payloads already carry, so a second sim's translator answers the same shape. The one classifier for those buckets: the translator's own `classifySessionType` (an unknown type read as race) and `classifyLapSessionType` (only a type naming "Race" counts as a race) are thin readings of it, and the catalog reaches it only through `SimRuntime.getSessionClass`, so it holds no iRacing session strings. `session-type.test.ts` pins every session type the translator meets to its bucket. The translator's own exact `=== "Race"` reads (the canonical order, the pace lineup, the replay greens, `diffFuelLapsLeft`'s race branch, which a heat race or warmup therefore does not take, #1702) and the track gaps' Lone checks are deliberately not routed through it, since a Heat Race classifies as race here but is not `"Race"` there.
- **Whether the player's final lap has started**, which the Race Engineer's fuel contracts ask at speak time: `isPlayerFinalLapStarted()` (#1702), the fuel countdown's emit-time silence applied to the latest tick — `isPlayerFinalLapReached` (the chequered flag out, or `resolveFuelFinalLapStarted`'s answer: the sticky `playerFinalLapStarted` marker in a race, the White bit elsewhere) over `handleTick`'s session branch. It holds no state of its own, so it cannot disagree with the diff; `null` with no translator, before the first tick, and while the session type cannot be read unless the chequered flag is out (Checkered or CoolDown answers `true` even then). It reaches the catalog only through `SimRuntime.isPlayerFinalLapStarted`.
- **The after-tick hook** — `onTranslatorTick(listener)` (#1500), returning the unsubscribe. Its listeners run at the end of the translator's own `sdkController` callback, on every one — a connected tick, a connected callback without telemetry, a disconnect — from a `finally`, so after the translator has handled it and even when its frame threw (that throw still reaches the controller after them). A read inside (`getSessionKind`, `getSessionType`, `getLatestTelemetry`) sees that callback's state: that ordering is the contract, which a second controller subscriber would only have had by insertion order. A listener is never called on registration. Each is called through the step boundary (below) under one id, `translator:onTranslatorTick`, so one that throws is reported like a step and skipped while the next still runs; under `"rethrow"` its throw leaves the callback once every listener has run (#1559). The registry is module level, so a listener registered before `initializeSimEventsIracing` is kept, and `_resetSimEventsIracing` clears it. It publishes nothing, so `TICK_ORDER` does not list it. Its consumer is `plugin-runtime`'s `HostSim.onTick`.

## Recording for `@iracedeck/replay-store`

The replay recorder (`startReplayRecorder`, `src/replay-recorder.ts`, #1468) is a second SDK-controller subscriber, started by `initializeSimEventsIracing` right after the translator subscribes. Its four recorder diffs share one eligibility module (`diff/replay-record-gate.ts`) and publish what the replay store writes:

- every car's lap crossings — `replay-laps`, `replay.lapStarted` / `replay.lapTimed` (#1203);
- the race start and caution restarts — `replay-greens`, `replay.greenFlag` (#1354);
- each session's start and every incident — `replay-sessions`, `replay.sessionStarted`, and `replay-incidents`, `replay.incident` (#1426).

The session starts are also recorded out of the car at the live edge of a live session, through the gate module's second resolver.

- **No replay guard.** A recorder must see the ticks it cannot record, to mark itself unseeded on them and re-seed silently on the first eligible tick after; each diff's gate is the only one. Its "in a replay" answer is the controller's debounced replay state, read in its own callback.
- **Its own state**, `ReplayRecorderState` (`replay-recorder-state.ts`); it reads nothing of `TranslatorState`, and the translator's per-session and replay wipes never reach it. `readSimState()` reports it under `raw.replayRecorder`.
- **Its own reset points**, listed in the header of `replay-recorder.ts`: the lap, green and incident baselines at a session change (before the diffs run), on entering and on leaving a replay view (after them); everything at a disconnect. The session record (`replay-sessions`' run and published list) survives every reset but the disconnect.
- **Pinned across the move.** `replay-recorder.equivalence.test.ts` compares the `replay.*` stream of the real init with a golden recorded while the recorders still ran inside the translator; a deliberate behaviour change regenerates it (`REPLAY_GOLDEN_UPDATE=1`) and reviews the diff. One change the golden cannot see: inside the translator, the first subscriber, the recorders got the first connected tick twice at startup (the controller's connect notification, then the subscribe callback), so the session record published that session's start during init, before replay-store subscribed, and lost it; subscribed second, the recorder gets it once and publishes on the first poll. `replay-recorder.startup.test.ts` pins that over the real `SDKController`.

## Session identity (#1509)

`session-identity.ts` states once which tick starts a different session: a new `(SubSessionID, SessionNum)`, never inside a saved replay, read on every tick, the baseline reset only at a disconnect. The translator (per-session wipe, `session.changed`) and the replay recorder (baseline reset) each read it from a baseline of their own (`readSessionIdentity`, then `advanceSessionIdentity`), so both change on the same ticks. A change to the rule is made there, never in one subscriber.

## The tick order (#1499, #1468)

`src/tick-order.ts` lists every stage that can publish, in the order its publishes reach the bus, in three tables. `TICK_ORDER` is the translator's `handleTick`: the direct publishes first (the session-change sites, the pre-guard diffs, the replay-entry teardown; a pre-guard diff's reach the bus when its step returns, #1559), then the `pending` batch the live diffs fill, flushed in call order from a `finally`. `REPLAY_RECORDER_ORDER` is the replay recorder's tick, its four diffs publishing directly, each when its step returns. The controller notifies in subscription order, so a tick's `replay.*` events reach the bus after all of the translator's; `CONTROLLER_TICK_ORDER` is the two end to end, the table an `endsOn` check reads. `findEndsOnOrderViolations` reads it to prove an `endsOn` contract's trigger is never published after its end on one tick (#1407); `race-engineer-wiring`'s `ends-on-order.test.ts` applies it to every registered contract. `tick-order.test.ts` proves the tables are the code by spying on the real diff calls, the publishes and the subscriber boundaries. Keeping them true:

- **A diff module that emits declares what.** It exports `<NAME>_EVENTS` (`as const satisfies readonly SimEventName[]`) and types its emitter `EmitFn<(typeof <NAME>_EVENTS)[number]>`. `EmitFn` has no default, so an emit the list does not name is a compile error; a module with two emitting functions declares one list each (`START_COUNTDOWN_EVENTS`, `START_LIGHTS_EVENTS`).
- **A new emitting diff, or one that starts emitting,** gets its row at its call position in the table of the subscriber that calls it — `TICK_ORDER` (`via: "pending"` for a live diff, `"direct"` for a pre-guard one) or `REPLAY_RECORDER_ORDER` (`"direct"`), never both — whose `events` is the module's list itself rather than a copy, and a `vi.mock` spy line in `tick-order.test.ts` naming the index of its emitter argument. The completeness test fails on a declared list with no row, and the call-order test on a stage it never recorded. A diff that publishes nothing gets no row.
- **Reordering any diff call in either subscriber** means moving its row too; the call-order test fails until it does. If an `endsOn` pair then fails in the wiring test, the reorder broke that contract: put the trigger's stage back ahead of its end's.
- **A new publish site in `translator.ts` itself** gets a `source: "translator.ts"` row and a real tick that publishes from it in the translator-sites test; the completeness test fails on an event those sites name that no such row lists. `replay-recorder.ts` publishes from one site, `publish`, and the same test fails on a second.

## The step boundary (#1559)

A throw in one step of a tick costs that step and no other. `TickSteps` (`src/tick-steps.ts`) runs every call of the translator's tick (`handleTick` and its live half, `handleLiveSteps` and `handleOrderSteps`) and of the replay recorder's through one #1558 `createErrorBoundary` from `@iracedeck/logger`, built per instance in `initializeSimEventsIracing` with a reporter table of its own, apart from the controller's, and handed to `startReplayRecorder`. A step that throws publishes nothing that tick — `live` truncates `pending` back to its mark, `direct` buffers and publishes when the step returns, `run` is for a step that emits nothing — is reported once per throw site as `translator:<function>` or `replay-recorder:<function>`, and is called again on the next tick, while every later step still runs. The translator does not restore a failed step's state; keeping it consistent is the step's job. The frame (the tick's reads, the session identity and its reset, the replay guard's teardown and wipes) is not split: a throw there reaches the controller's subscriber boundary, and the `pending` flush runs in a `finally`, so what completed is still published in call order. The policy and clock are `initializeSimEventsIracing` options, `onStepError` (#1558's `ErrorPolicy`, default `"report"`, what every plugin runs) and `errorClock`; under `"rethrow"` every step still runs and `steps.finish()` throws the first error at the end of the callback. The decision record is `docs/superpowers/specs/2026-10-31-issue-1559-translator-diff-isolation.md`.

- **A new call in a tick goes through the boundary under its function's name** — `steps.live`, `.direct` or `.run` for a step, a value call for a value — with the name a string literal and the argument expressions computed inside the closure, so a throw while computing one costs that step only. `tick-steps.source.test.ts` parses both ticks with the TypeScript compiler and fails on any call outside a step that the tick's frame allow-list does not name; a frame call is added there deliberately, never to let a bare diff pass.
- **A value a step hands on gets its fallback stated in the same change.** `steps.value(name, self.lastValues, absent, …)` falls back to its last good answer this session (the store is cleared at a session change and a disconnect, kept through the replay wipe), else to `absent`, the resolver's answer for absent session info; `steps.fallbackValue` always to one fixed answer, for a value whose last answer would be wrong (`resolvePlayerResultsSnapshot` → `null`, `resolvePlayerIsLeader` → `false`); `steps.requiredValue` has none, so its consumers are skipped that tick and listed where it is read — the canonical order's nine in `handleOrderSteps` (eight read the order: `diffCaution`, `diffOpponentPit`, `diffFastestLap`, `diffOpponentFlags`, `diffLeaderWhite`, `diffOvertakes`, `stepCarProgress` and `diffGaps`; `diffSectorTimes` takes `diffGaps`' neighbours), `diffTireWear` behind `stallVisit`. A value read by one step only, from telemetry, is part of that step.
- **A diff that loops over independent cars runs each car as a unit.** It takes a `UnitRunner` parameter defaulting to `runUnitsDirectly`, which catches nothing so the diff's own tests stay loud, and the tick hands it `steps.runUnit`: a car whose unit throws drops that car's events only, reported under the step's id, and the other cars commit. That car's baseline is written last inside the unit, so a throw retries the car on the next tick. `diffReplayLaps`, `diffReplayIncidents`, `diffOpponentPit`, `diffOpponentFlags` and `diffSectorTimes` do this, and so do `updateTrafficReferenceCurves` and the replay order's `stepReplayProgress` (#1682), `steps.run` steps that emit nothing (their units get a no-op emit); field-wide work after the loop stays in the step. `updateTrafficReferenceCurves` is the one exception to the baseline-last order, deliberately: a car's motion reading is written before its `CarIdxEstTime` and class are read for the curve sample, so a throw there drops that tick's sample only and never rolls back the valid motion (a stale standing rate would keep a car that has pulled away out of the arrivals); a throw before the motion reading drops the car's measured rate instead.
- **A diff writes its baseline last**, after the work that can throw, so a throw is retried on the next tick rather than lost: its events are dropped with it, and nothing restores its state.
- **No step reads its own events from `pending`.** Truncating on a throw is safe only because the readers (`diffPitReadback`, `updateStallVisit`, `diffTireWear`) look for other steps' events.
- **A same-tick flag one step hands another is a returned value, not a state field**, so a throw in the writer cannot leave the previous tick's answer behind: `diffToggles` returns whether the fuel plan changed and `handleLiveSteps` hands it to `diffPitReadback`, `false` when `diffToggles` threw; `diffGaps` returns the class neighbours and leader it resolved and `handleOrderSteps` hands them to `diffSectorTimes`, `null` when `diffGaps` threw (#1572).
- **A returned value may carry a read-only view of the producing step's own slice, valid for that tick only.** `CarProgressTick.traces` is the `carProgress` slice's own trace array, typed `ReadonlyProgressTrace`, which `diffGaps` and the sector timer read during the tick and must not keep: the next tick's samples are appended to it. The producer runs under `steps.fallbackValue(…, null, …)`, so a throw hands on `null` rather than a stale view or the last tick's readings (#1572).
- **A new id grows `TRANSLATOR_REPORTER_MAX_KEYS`.** The shared boundary's global cap is four throw sites (`TICK_STEP_KEYS_PER_ID`, #1558's per-id cap) for every id it reports — each step and value of both ticks, plus `translator:onTranslatorTick` — so it is never what hides one step's first error. The source check counts the ids and fails until the constant matches.
- **Translator-level tests pass `onStepError: "rethrow"`**, so a diff that starts throwing fails the suite instead of being reported and passing; every suite that drives ticks through `initializeSimEventsIracing` does, the scenario harness's included. A diff's own tests call it directly and need neither.

## Translator state slices (#1588)

`TranslatorState` (`src/state.ts`) holds each cluster of state as one nested member, a *slice*, rather than as flat family-prefixed fields, so a diff's signature says what it touches and the wipes and the snapshot have a unit to act on. The decision record is `docs/superpowers/specs/2026-11-02-issue-1588-translator-state-slices.md`.

- **When.** Every new cluster is a slice: a new family's fields, or a new concern inside an existing family. An existing flat cluster becomes one when its family next changes in substance, never in a sweep. Which clusters are still flat, and what each one's move must settle first, is the guard's pin `LEGACY_FLAT_MEMBERS` in `src/state-slices.test.ts` (one entry per `state.ts` heading, the note as a comment on it); a move deletes its entry, and its names' lines from `FROZEN_FLAT_MEMBERS` in `src/state-slices.baseline.test-support.ts`, in the same change. A diff module that moves onto its slice leaves `WHOLE_STATE_DIFF_MODULES` and `FROZEN_WHOLE_STATE_DIFF_MODULES` the same way. Lines in that baseline file are only ever deleted.
- **Shape.** One member `<family>: <Family>State`, its key camelCase and its fields without the family prefix (`fastestLap.record`, not `fastestLap.fastestLapRecord`). The type and a `create<Family>State()` setting every field (no `?:` field) are declared in `state.ts` beside the member, the cluster's documentation on the type and each field documented inside it, and `createInitialState` builds the member with a no-argument call. Not in the diff module: a diff imports `state.ts`, so a factory there closes a `state.ts` → `diff/x.ts` → `state.ts` cycle as soon as the diff imports a value from `state.ts`, and the plugin builds fail on a cycle among our sources.
- **What a diff receives.** A diff that owns a slice takes it as its first parameter, never `TranslatorState` whole, `Readonly` or narrowed with `Pick<>`. Another family's fact arrives as a value `handleTick` reads at the call, typed with `null` for its unknown case, its JSDoc naming the fact and its writer: `diffFastestLap`'s `lapsJudgedThrough` is `lastLapCompletedCounter` once `lapCompletedInitialized`, else `null`; a fact with no unknown case is a plain value, as `diffFuelLapsLeft`'s `finalLapStarted` (in a race the flags' sticky final-lap marker, elsewhere the White bit on the tick, #1702) is a `boolean`. A write into another family's slice goes only through a closure `handleTick` builds over that slice. The fastest-lap judge, `createFastestLapJudge(self.state.fastestLap, …)` handed to `diffLaps`, writing `record` and `claim`, is the one sanctioned cross-step writer of `fastestLap`, which therefore has two writers; a new one needs the same justification and its own line here. The fuel reassurance re-arm, `createFuelReassuranceRearm(self.state.fuelCallout)` handed to `diffFlags`, is the one of `fuelCallout` (#1405): it writes `raceCoveredAnnounced` only, when a green clears the player's sticky final-lap marker, because the race was extended or restarted and the pre-extension coverage verdict no longer holds.
- **Mutate in place.** A diff that clears its slice writes `Object.assign(slice, create<Family>State())`, never a new object through the parent, so a reference taken earlier in the tick (the judge's) is still the object later steps read. `diffTrackGaps` and `diffLaps`' `lapCrossing` reset do this.
- **Lifecycles.** A disconnect and a session change recreate the whole state, so a slice resets at both with no code; one that must outlive a session change goes in `resetPerSessionState`'s `preservedAcrossSessions`. At the replay wipe (`wipeStateForReplay`) the slice's owner picks one of three: wiped whole (`trackGaps`, `carProgress`; nothing to write), kept whole (its key in `preservedAcrossReplay`), or kept in part by a `reset<Family>…(slice): <Family>State` beside the factory in `state.ts` that returns the slice to keep, called from `preservedAcrossReplay` and documenting which fields survive and why — `resetFastestLapBaselines`, which carries `record` (by reference) and `raceSeeded` and returns the rest fresh, `resetFuelCalloutBaselines`, which carries the fuel level, the announce floor and the reassurance latch, and `resetSectorTimesForReplay` (#1572), which carries the completed laps (by reference) and drops the laps in progress, the previous readings and the targets, because the wipe resets the traces their continuity was judged on.
- **The Telemetry Snapshot needs no code.** `readSimState` hands the whole state over as `raw.state`, so a slice shows as `raw.state.<family>.<field>` (`raw.state.fastestLap.record`); `raw` promises no stability.
- **The guard** is `src/state-slices.test.ts`, over the TypeScript-compiler scanner in `src/state-slices.test-support.ts`, whose header says exactly what each rule matches. Every rule has planted positive controls. The real-tree scan has floors (over 200 `TranslatorState` members; at least 40 diff modules, `laps.ts` among them; at least 12 other modules, `index.ts`, `race-order.ts`, `sim-state.ts` and `translator.ts` among them, and no `state.ts`, diff module or test), and its importers must equal `WHOLE_STATE_DIFF_MODULES` exactly (rule E), so an empty read fails, as does one that misses a pinned importer or any of those named modules. A read that skips some other diff module or source module, while the counts still hold, is not caught.
  - A: a `TranslatorState` member the pin does not name must be a slice — a reference to an object type alias in `state.ts` ending in `State`, with no `?:` field, whose `create<Type>` in `state.ts` `createInitialState` calls with no arguments.
  - B: the pin matches the file and only shrinks — a pinned name that is no longer a member, sits under another heading or is pinned twice fails, as does an empty entry or one whose heading `state.ts` no longer has; and every pinned name must be in the frozen baseline `FROZEN_FLAT_MEMBERS` (#1661), so a name added fails by name whatever else the change removes (a rename included), and a baseline name the pin no longer holds fails, naming the line to delete. Nothing is ever printed to copy into the baseline.
  - C: a `diff/` module importing `TranslatorState` (from `state.ts` or from any relative module that relays it, by a star re-export of such a relay too, `export type * from "../relay.js"`, resolved against the scanned sources and followed transitively, or as a qualified name ending in `TranslatorState` at any depth, `facade.model.TranslatorState`, whose leftmost name is imported from a relative module, #1661) names no slice type and reads no slice key off a binding annotated `TranslatorState`, destructuring included; an exception goes in `SLICE_READS_ALLOWED` with its reason (`laps.ts:lapCrossing` until the laps cluster moves), and an entry no read matches fails.
  - D: no assignment in a `diff/` module targets `<x>.<sliceKey>`; a slice is cleared in place.
  - E: the `diff/` modules importing `TranslatorState`, in any form rule C reads, are exactly `WHOLE_STATE_DIFF_MODULES`, those that took the whole state when it was frozen (#1661), held to the baseline `FROZEN_WHOLE_STATE_DIFF_MODULES` as the pin is to its own: a new diff module importing the state fails, since it takes its slice (*What a diff receives* above), whether or not it is added to the list, and a pinned module that no longer imports it fails until its entry and its baseline line are deleted.
  - F: no other production module under `src/` exports `TranslatorState` under another name, since E counts the state by that name: no `export type { TranslatorState as X }` (from `state.ts` or a relay, or of a local import), no exported alias, interface or `export import X =` alias that is the state (`type X = Readonly<TranslatorState>`), at the top level or inside an exported namespace at any depth (`export namespace model { export type Whole = TranslatorState }`), and no `export * as ns from "./state.js"`. Relaying it as `TranslatorState`, a type that only holds it (`SimRawState`), and a facade's `export * as ns from` a relay pass: the facade keeps the name, and C counts the qualified name a diff module reaches it by.
  - Neither E nor F sees a module that takes the whole state through a type derived without naming `TranslatorState` (`Parameters<typeof diffFlags>[0]`, `SimRawState["state"]`): the scan reads each module's syntax alone, so such a disguise is left to review.

## Rules

- A new bus event needs an entry in the scenario harness's `src/event-names.ts`, and a new callout a shortcut button there (`packages/scenario-harness/CLAUDE.md`).
- Captured telemetry fixtures for the diff tests live in `src/diff/__fixtures__/` (see its `README.md`). Another package's test reads one through the `./testing` entry, `captureFixturePath("<name>.json")` from `@iracedeck/sim-events-iracing/testing` (#1375; `audio-scenarios`' `caution.test.ts`), never by a relative path into `src/`. It resolves `../src/diff/__fixtures__/` against its own module, the same folder from `src/` (the vitest alias) and from `dist/`, and refuses a name that is not a bare `.json` file name or that the folder does not hold. Renaming or removing a capture another package reads breaks that test.
