# @iracedeck/plugin-runtime

The composition root the three deck plugins share (#1349). `startPlugin(host)` runs eleven synchronous phases; a plugin's `plugin.ts` only builds its adapter (and on Stream Deck its `PluginExtension`) and calls it. Decision record: `docs/superpowers/specs/2026-10-05-issue-1349-shared-composition-root.md`.

## Phases (`src/phases/`, called in this order by `src/start-plugin.ts`)

| # | Phase | Takes | Returns |
| --- | --- | --- | --- |
| 1 | `initCore` | `PluginHost` | `Core` |
| 2 | `initSim` | `Core` | `SimRuntime` |
| 3 | `initInput` | `Core` | `Input` |
| 4 | `initAudio` | `Core` | `Audio` |
| 5 | `initVoicePacks` | `Core`, `Audio` | `VoicePacks` |
| 6 | `initRaceEngineer` | `Core`, `SimRuntime`, `Audio`, `VoicePacks` | — |
| 7 | `initSettings` | `Core`, `Audio`, `VoicePacks` | `Settings` |
| 8 | `initReplay` | `Core` | `Replay` |
| 9 | `registerActions` | `Core`, `Input` | — |
| 10 | `startServices` | `Core`, `Input`, `Settings`, `Replay`, `VoicePacks` | — |
| 11 | `adapter.connect()` | — | — |

A data dependency is a parameter, so a phase cannot run before what it needs exists. An ordering with no data edge stays inside one phase, adjacent, with its comment. `src/start-plugin.test.ts` records every effectful startup call (init, start, listener, registration, subscription, constructor, factory) against a fake adapter and fails naming the first call that moved or ran extra — update `expectedOrder()` there only for an intended change, and its `PURE_FACTORIES` set only for a new pure factory whose product goes straight into a recorded call. Since #1387 its `EFFECTFUL` pattern also matches a bare `register…` call: until then the only registrations were the adapter's, which `adapter.` covers, so `registerStateSection` would have passed unseen. The order test now lists the four of them, adjacent, at the end of `initCore`.

## The Telemetry Snapshot's state sections (`src/state-sections.ts`, #1387)

`registerStateSections(core)` is the last call of `initCore`. It names, in one place and in the order the snapshot file lists them, the four plugin-state sections Telemetry Control's Take Snapshot collects through `@iracedeck/diagnostics`: `environment` (built here), `settings` (`@iracedeck/settings`' `readSettingsForSnapshot`), `sim` (`@iracedeck/sim-events-iracing`'s `readSimState` and `simStateHeadline`) and `raceEngineer` (`readRaceEngineerState` and `raceEngineerStateHeadline`, from the `@iracedeck/audio-scenarios/pit-crew` subpath, since that package's root barrel imports no sim package). The owning packages export their readers and import nothing from diagnostics; registering them is this package's job.

- **It needs no ordering against the later phases.** Registering stores four functions and reads nothing, and every reader answers for a subsystem that has not started (`{ initialized: false }`, or the schema defaults for the settings) instead of throwing. So the translator, the scenario engine and the settings store may come up after it, and a snapshot from a plugin whose scenario engine never started says so instead of lacking the section. That is what lets one file name every section.
- **`environment` is read at the press, never at registration**: the plugin version, the deck host (`getPluginPlatform()`), the Node version, whether the SDK is connected and iRacing is running, the elevation check's verdict, whether the settings store was ready and how it was filled, and how each native addon loaded (`nativeAddons`: the kind, and a mock's reason; never a failed load's error text, which names the `.node` path — #1373). The SDK connects and the settings load long after `initCore`, so its reader keeps `core` and asks at each press. **It carries no file path, ever**: the plugin's directories all sit under the Windows profile, so a path would put the user's account name in a file they send to someone else.
- **The `settings` section goes through `readSettingsForSnapshot`, never `getGlobalSettings`**: that reader decides what of the settings may leave the machine (`packages/settings/CLAUDE.md`).
- Call it once per run: the registry refuses a name registered twice.

## Rules

- Raw TypeScript, no build: each plugin's Rollup compiles `src/` (the `typescript` include and `.js`→`.ts` resolver of the shared config in `@iracedeck/plugin-build` name this package), and `@rollup/plugin-replace` substitutes the `__FEATURE_*__` constants here as in `iracing-actions`. `platform-features.d.ts` and `svg.d.ts` declare them for this package's own program.
- `src/actions.ts` is the only importer of `@iracedeck/iracing-actions`: the shared action list and the plugin-level hooks. A new action goes in `SHARED_ACTIONS` (or a host extension's `extraActions`) and every manifest; `src/actions.test.ts` fails until they match.
- Host differences arrive through `IDeckPlatformAdapter` (`setLogLevel`, `logLocation`, `openUrl`, `onOpenSettingsRequest`) or the optional `PluginExtension`. Test for the extension's presence, never for a host name.
- The iRacing side of the deck layer comes from `@iracedeck/deck-iracing`, never `@iracedeck/deck-core` (#1351): `initCore` calls `initializeSDK`, which also installs deck-core's sim connection before any action can appear, and hands the app monitor's `onIRacingStarted` / `onIRacingTerminated` / `isIRacingActive` to the resource monitor; `registerActions` injects `isIRacingActive` and `hasElevationMismatch` into `initWindowFocus`; `startServices` starts `initAppMonitor`, then the audio session hold (below), and the elevation-check and replay-session subscribers; `initSettings` reads `isIRacingActive` / `onIRacingTerminated` for the startup notices. A second sim's deck package would be chosen here and nowhere else.
- The audio session hold is started in `startServices`, right after `initAppMonitor` (#1347): `startAudioSessionHold` from `@iracedeck/iracing-actions` keeps the audio device open while iRacing runs and the Race Engineer or the Radar master gate is on, or press sounds are (#269), so a race opens the device once instead of once per burst of callouts. The controller imports no app monitor, audio service or settings; this phase injects `onIRacingStarted` / `onIRacingTerminated` / `isIRacingActive` from `@iracedeck/deck-iracing`, the three gate readers (`isRaceEngineerEnabled`, `isRadarEnabled`, and `isPressSoundEnabled` as `getPressSoundMode() !== "none"` from deck-core), `onGlobalSettingsChange` from `@iracedeck/settings`, and `getAudio()`, whose `hold` / `release` own the hold itself. It sits after the app monitor because it follows that monitor's edges and is seeded from its view of an already-running iRacing, and before `adapter.connect()` because a host reports an already-running iRacing as a launch event right after connecting. The order test pins the call, and a second test pins what it is handed.
- Every action is registered wrapped for press sounds (#269): `registerActions` calls deck-core's `initPressSounds` once, with `playPressSound` from `@iracedeck/iracing-actions` as its `play` delegate and a `PressSounds` logger, after the replay busy indicator's logger and before the first `registerAction`, then registers `withPressSounds(action.create(…))` for the shared list and the host's extras alike. The wrapper exposes only `IDeckActionHandler`'s members, so a test here that needs something else from a registered handler reaches it through what `create` returned, not through the adapter. The order test pins `initPressSounds` and its scope, and a second test pins that every registered handler is the wrapper.
- The voice-pack stack comes from `@iracedeck/voice-packs`, never `@iracedeck/deck-core` (#1366): `initVoicePacks` builds the scanner, storage, catalog, installer and launch step from it and injects what they need from `@iracedeck/settings` (`setWarning` / `clearWarning`, the launch step's `settled` thunk over `whenSettingsStoreSettled` and `onGlobalSettingsChange`), since `voice-packs` imports neither `settings` nor `deck-core`; `initSettings` reads the catalog URL from it, and `src/types.ts` names its service, installer and launch-step types. The pack format's names (`CalloutScript`, the manifest schema) come from `@iracedeck/callout-script` directly.
- Four more concerns come from their own packages, never `@iracedeck/deck-core` (#1367): `initCore` starts `@iracedeck/diagnostics`' watchdog and resource monitor; `initReplay` builds `@iracedeck/replay-store`'s store (#1467); `initSettings` builds `@iracedeck/app-updates`' version check and update-check service, `@iracedeck/diagnostics`' CPU profile capture, and the settings window from `@iracedeck/settings-window` (the controller, the command handler with the callbacks it injects — the capture, the voice-pack commands — the warning reporter and the channel publisher); `initVoicePacks` takes `openDirectoryInExplorer` from `settings-window`. `LogLocation` is `@iracedeck/app-constants`' (`src/log-location.ts` here holds `requireLogLocation` and `profilesDirFor`). `src/audio-session-identity.ts` — `pluginAudioSessionIdentity(binDir)` (#1253), the `{ displayName, iconPath }` `initAudio` passes to `initializeAudio` so the Windows Volume Mixer lists our session as "iRaceDeck" with the logo (`AUDIO_SESSION_DISPLAY_NAME`, `<plugin>/imgs/plugin/` + `AUDIO_SESSION_ICON_FILE`, resolved absolute from the plugin's `bin/`) — lives here since #1367, as plugin-layout knowledge with one consumer; `@iracedeck/audio-service` only defines the shape.
- The replay layer is its own phase, `initReplay` (#1467, `src/phases/replay.ts`). It configures `@iracedeck/replay-engine` once through `configureReplayEngine`: the SDK controller, `getCommands().replay` and `getCommands().camera` reached at each use, `Date.now` as the engine clock, a `ReplayEngine` logger the engine scopes its own children under, and the **Replay jump playback** and **Fastest Lap Search Delay** settings as closures read at the time of use, so a change in the Settings window needs no re-wiring. It then builds the replay store with its exit flush and its five `replay.*` bus subscriptions, and returns `Replay`, whose store `startServices` hands the replay-session subscriber. The replay busy indicator stays in `iracing-actions`, which has no registration entry point, so `registerActions` sets its logger (`setReplayBusyIndicatorLogger`) just before the actions are constructed.
- A native addon that failed to load is said once in each place it belongs (#1373). `initCore` reads `getNativeLoadStatus()` from `@iracedeck/iracing-native` and `@iracedeck/audio-native` into `Core.nativeAddons`, right after the log level is applied, and writes one `error` line per failed addon under a `NativeAddons` logger (made only when there is a line to write); the settings phase sets one `error` banner per failed addon (`native-addon-iracing`, `native-addon-audio`) on every settings arrival, straight after the missing-script banner; the snapshot's `environment` section carries the kinds. What is said is decided in `src/native-addons.ts`, which only maps statuses to log lines, banner records and the snapshot view; the phases only write them. Spec: `docs/superpowers/specs/2026-10-20-issue-1373-native-load-failure.md`.
- Never import from `src/index.ts` inside the package (a cycle fails the plugin build). Phases take their shared types from `src/types.ts`.
- `registerActions` hands the native focuser and pointer mover to deck-core's `initWindowFocus` / `initMousePointer`, whose `FocusResult` and `PointerMoveResult` are hand-kept mirrors of `@iracedeck/iracing-native`'s enums (deck-core may not import the native package). `src/phases/focus-result.test.ts` and `src/phases/pointer-move-result.test.ts` assert each mirror matches member for member; they live here because this package depends on both, and they need no mocks.
- Tests mock collaborators through `src/test-support/recorder.ts`; never initialise a real singleton (`initializeSDK`, `initializeEventBus`, …) in a test here. The `vi.mock` factory bodies live in `src/test-support/module-mocks.ts` (its header has the block to paste); each test file still names every mocked module, because `vi.mock` is hoisted per file. `src/test-support/fake-host.ts` builds the host, adapter and extension whose calls land in the same `callLog`; the adapter keeps its logger scopes in `scopes` and its event listeners to fire, and a file that builds hosts calls `cleanupTempBinDirs()` in `afterAll`. An unimplemented stub is a truthy function, so a test that depends on a settings branch implements `getGlobalSettings` — read the header of `recorder.ts` before writing an expected call list.
