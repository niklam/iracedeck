# @iracedeck/settings

The plugin's global settings, below the deck layer (#1365, spec #1351): the schema and cache, the one-shot migrations, the plugin-owned settings store, run-scoped keys, the PI warning banners, first run and the per-feature startup gates. It depends on `@iracedeck/app-constants`, `@iracedeck/callout-script` (voice-id qualification), `@iracedeck/callout-settings` (the opt-in registry the schema is built from), `@iracedeck/logger`, `zod` and `semver`. `deck-core` depends on it, never the reverse, and so do `deck-iracing`, `iracing-actions`, `plugin-runtime`, `race-engineer-wiring`, `scenario-harness`, the Stream Deck plugin, and since #1367 `replay-store` (the path helpers and `WRITE_RETRY_DELAYS_MS`) and `settings-window` directly; `deck-adapter-elgato`, `pi-components` and `voice-packs` list it only as a devDependency, for one test each.

## SettingsHost

The package cannot import `IDeckPlatformAdapter`, which is deck-core's, so it declares the host surface it actually uses (`settings-host.ts`): `onDidReceiveGlobalSettings`, `getGlobalSettings` and the optional `onHostReady?` that `global-settings.ts` reads through, and the `setGlobalSettings` that `@iracedeck/settings-window`'s settings-channel publisher writes through. `onHostReady` stays optional on purpose (#1056): its absence says the host queues a read until it can be sent, so the migration deadline `initGlobalSettings` armed is already honest. deck-core's `IDeckPlatformAdapter` extends `SettingsHost`, so every adapter satisfies it unchanged and the `onHostReady` contract has one copy. `initGlobalSettings` takes a `SettingsHost`; a test passes a plain object literal.

## Module map

- `settings-host.ts` — `SettingsHost`, above.
- `global-settings.ts` — Plugin-level global settings manager. Single writer (#993): the plugin-owned `SettingsStore` file is truth, the deck host is read once for migration and never read again; `isSettingsStoreReady()` reports when the cache reflects the store, `getSettingsStoreSource()` how it was filled (`"file" | "host" | "fresh"`), `isSettingsStoreHostDerived()` whether it holds everything the user stored (ready, not fresh, no pending countdown, not abandoned, salvage did not fail — the one gate for the host mirror, its binding consumer, and for any write keyed on a key's absence, #1277; never relax it for another caller), `getSettingsStoreHostDerivation()` the reason when it does not (`not-ready` / `not-read-yet` / `abandoned` / `unparseable`, the boolean being its `host-derived` case), and `runOnceSettingsStoreReady(action)` runs an action once at the first ready moment, done-before-action so a write inside it is not re-entered. `hostMirrorPayload({ port, token })` builds the ONE host write per start the PI bridge bootstraps from — the full cache plus `_settingsChannel`, `undefined` (skip the write) before the store is ready, when it started fresh, while the `_migrationPending` countdown is set, or once the durable `_migrationAbandoned` marker is (`MIGRATION_ABANDONED_KEY`, #1041) — a host `setGlobalSettings` replaces the whole object, so a defaults file must never be mirrored over a host copy the plugin has not read. A fresh start persists the countdown so later starts ask the host again; after `MIGRATION_RETRY_STARTS` unanswered starts the file is accepted and the countdown gives way to the durable marker, which keeps the mirror shut. That marker's VALUE is the plugin version that gave up (#1047): a store that has been given up on — the marker, or a countdown at the ceiling — issues ONE more read when the running version is semver-newer. Only a payload carrying keys clears the marker and restores mirroring; an empty, `null` or absent answer records this version's own give-up and the store stays quiet until the next upgrade. So a newer version gives an install the old build could only preserve a *chance* to recover — it does not guarantee one, and a blank running version counts as unknown rather than as differing, or the retry would repeat on every launch. Both shapes count because #1041 ships unreleased alongside #1047, so no field file carries the marker yet; a bare `true`, or no record, counts as never-given-up-under-a-stamping-build and is retried. On that retry the file is authoritative and the host only fills keys the file has never held — `mergeMigration`'s "still at its default implies never touched" premise holds for a defaults-born file, not for one that has been the store for months. The version is injected via `InitGlobalSettingsOptions.pluginVersion`, never read from `getPluginVersion()` here, which throws when `initPluginConfig()` has not run. Gate the mirror on having positively READ the host, never on a counter having run out, and keep retry decisions in the load path rather than in that gate; an unreadable file is retried with a doubling back-off (`LOAD_ATTEMPTS`, `LOAD_RETRY_DELAY_MS`). The Race Engineer callout opt-ins (#1350) are not written here: `calloutEnabledFields()` builds a `GlobalSettingsSchema` field for every `CalloutSettingKey` in the `@iracedeck/callout-settings` registry, each the shared `calloutEnabledField` shape with `.default(calloutDefault(key))`, and `isCalloutEnabled(key)` is the one typed, live lookup every gate reads (`PitCrewDeps.isCalloutEnabled`, the deck actions' toggles), with `setCalloutEnabled(key, enabled)` its typed write. `callout-settings-baseline.test.ts` holds every key's default and coercion to the frozen pre-#1350 record in `src/__fixtures__/callout-settings-baseline.json` — a dropped, renamed or re-defaulted key fails it, which is when a migration is owed; never regenerate it. Rules: `.claude/rules/global-settings.md`
- `global-settings-migrations.ts` — Global-settings migrations in three shapes: `migrateGlobalSettingsKeys` (one-shot passthrough-key renames, #953), `migrateRaceEngineerVoiceId` (idempotent voice-id qualification, no marker, #1144) and `seedBindingDefaultsIfAbsent(defaults, logger)` (#1277): once the store is ready it writes each given key's default binding when that key has NEVER been stored (`undefined` in the cache; a stored `""` stays cleared), in the exact value the PI binding field saves. Runs at every start with no marker, and only on a store that has read the deck host (`isSettingsStoreHostDerived()`) — elsewhere a later host answer merges under the file and a seeded default would override the user's binding; an abandoned store (#1041) is never seeded, and its log line says binding defaults are left to the user. It claims a seed only for keys the cache holds after the write. Both it and the renames run through `runOnceSettingsStoreReady` (`global-settings.ts`). Rules: `.claude/rules/global-settings.md`
- `settings-store.ts` — The plugin-owned settings file (#993): `SettingsStore`, `createFileSettingsStore` (atomic temp+rename write, 250 ms trailing debounce, failed writes retried on `WRITE_RETRY_DELAYS_MS` and kept pending for the shutdown flush, temp files cleaned up, UTF-8 BOM tolerated, `flush()` plus a synchronous `flushSync()` each plugin wires to `process.on("exit")` that also lands an async write still in flight, corrupt file moved aside as `global-settings.corrupt-<iso>.json` and reported through the `onRejected` option as a `SettingsFileRejection` — path, the parser's reason, a line and column from `json-error-location.ts`'s `locateJsonError`, the preserved copy — while a file that cannot be preserved fails the read instead, #1036; `decodeSettingsText` accepts a UTF-8 or UTF-16LE BOM), `createMemorySettingsStore` (tests/harness), `resolveSettingsStorePath` (`%LOCALAPPDATA%\iRaceDeck\Settings\<ecosystem>\global-settings.json`, `IRACEDECK_SETTINGS_PATH` override), `settingsStoreFolderName`
- `json-error-location.ts` — `locateJsonError`: the line and column where a rejected settings file first goes wrong (#1036), asked only after `JSON.parse` has failed, because only Node 22+ puts a line and column in its message and the Mirabox and Ulanzi hosts run the plugin on Node 20.
- `run-scoped-settings.ts` — `RUN_SCOPED_SETTING_KEYS` and `stripRunScopedKeys` (#1014): the keys that describe this run (`_warnings`, `_voicePacks`, `_voicePackStatus`, `_profileCaptureStatus`) and never reach the file.
- `pi-warnings.ts` — `setWarning`, `clearWarning`, `reconcileWarnings` over the run-scoped `_warnings` key (#610). The record they write, `PiWarning` / `PiWarningLevel`, is `@iracedeck/app-constants`' beside `PI_WARNINGS_KEY` (#1366), and this package does not re-export it. Rules: `.claude/rules/global-settings.md`
- `setup-warning.ts` + `setup-warning-constants.ts` — Setup-name mismatch warning (#625): `evaluateSetupWarning`, pattern helpers (`compileSetupWarningPattern`, `setupNameMatchesPattern`, `validateSetupWarningPatterns`), and the warning-id/setting-key constants (kept in a leaf module whose only import is the registry: `SETUP_WARNING_ENABLED_KEY` is `calloutKey(SETUP_WARNING_CALLOUTS, "warning")`, #1350)
- `settings-file-rejection-warning.ts` + `settings-file-rejection-reporter.ts` — the `settings-file-rejected` banner (#1036): the pure `evaluateSettingsFileRejectionWarning(rejection)` and `createSettingsFileRejectionReporter()`, the handler every plugin passes as the settings store's `onRejected`. Rules: `global-settings.md`
- `first-run.ts` — `resolveFirstRunDecision` and `runFirstRunCheck` (#1061): a store with no `_lastSeenVersion` is a fresh install, so the check runs before the changelog version check on the same tick; `GETTING_STARTED_PANE` names the settings-window tab it opens.
- `feature-startup-policy.ts` + `feature-startup-gates.ts` — the per-feature startup policy for the Race Engineer and Radar master gates (#1007): the pure policy values and resolver, and `applyStartupFeatureGates` / `migrateStartupPolicies`, the half that reads and writes settings. The policy module never imports `global-settings.ts`, whose schema imports it at module init.
- `callout-settings-schema.test.ts` and `callout-settings-baseline.test.ts` (over `src/__fixtures__/callout-settings-baseline.json`) test only `GlobalSettingsSchema`'s callout opt-ins.

## One import path per name

The barrel `src/index.ts` is the package's only entry, and deck-core re-exports none of it: import every name the barrel exports from `@iracedeck/settings`. A test that stubs `getGlobalSettings`, `isCalloutEnabled` or any other name here mocks `@iracedeck/settings`, never `@iracedeck/deck-core`. A mock of the barrel also cannot reach this package's internal imports: `pi-warnings.ts` writes through `global-settings.ts` by relative path, so a mocked `getGlobalSettings` does not change what `setWarning` reads. That is why `settings-window`'s `settings-window-warning-reporter.test.ts` and `voice-packs`' `voice-script-warning-reporter.test.ts` run over the real cache (`initGlobalSettings` with a memory store) and count writes from its change fan-out. For the same reason, and because this package cannot import the binding dispatcher, the positive control for `seedBindingDefaultsIfAbsent` is deck-core's `binding-defaults-seed.test.ts`, over the real dispatcher and the real cache.

## Rules

The architecture, the startup and migration paths, the store's write discipline, the callout opt-ins, the warning banners and run-scoped keys are in `.claude/rules/global-settings.md`. `.claude/rules/code-review.md` reviews `GlobalSettingsSchema`, its keys and the migrations at `xhigh`, as published contracts, and the settings store's write path at `max`, because a wrong decision there destroys settings the user cannot get back.
