# @iracedeck/voice-packs

The Race Engineer voice-pack stack (#1034, #1064, #1144), moved out of `deck-core` in #1366 (spec #1351, `docs/superpowers/specs/2026-10-07-issue-1351-deck-core-split-and-sim-seam.md`): the scanner, the voice-pack service, the catalog and its client, the downloader, archive extraction, storage, the installer, the launch step, the voice labels and the missing-callout-script banner. Packs live under `%LOCALAPPDATA%\iRaceDeck\Race Engineer\Voices` (`voice-packs-path.ts`). It depends on `@iracedeck/app-constants` (the voice-pack keys, `ENSURED_VOICE_PACK_ID`, the catalog location, the `_voicePackStatus` payload and the `_warnings` record shape), `@iracedeck/callout-script` (the pack format's rules), `@iracedeck/fetch-utils` (the catalog client's deadline and byte cap), `@iracedeck/logger`, `fflate` (archive extraction), `semver` (the catalog's version fields) and `zod`. `@iracedeck/settings` is a devDependency only, for one test (below); there is no production edge to it, and none to `deck-core`. `plugin-runtime` depends on it (its voice-pack and settings phases, and `types.ts`), and so does `scenario-harness`; `audio-assets` lists it as a devDependency for `pack-voice.test.ts`.

## What it reaches, and what reaches it

Nothing here imports the settings cache. What the stack needs from settings is injected by `plugin-runtime`'s voice-pack phase: the launch step's `settled` thunk (`whenSettingsStoreSettled`) and `onSettingsChange`, and the warning writers. The banner record the stack builds is `PiWarning` / `PiWarningLevel` from `@iracedeck/app-constants`, beside `PI_WARNINGS_KEY` (moved there from `settings`' `pi-warnings.ts` in #1366), and the writers the installer's removal banner and `voice-script-warning-reporter.ts` take are plain function types (`set(id, level, message)`, `clear(id)`) that the phase fills with `setWarning` / `clearWarning`.

Three files outside the package reach its sources by relative path rather than through the barrel: `audio-assets`' `pack-voice.test.ts` (the catalog entry schema, the filesystem port and the scanner, run over a freshly packed archive), `scripts/lib/voice-catalog-data.mjs` (the catalog schema, which the website's `generate-voice-catalog-json.mjs` and `scripts/voice-catalog-data.test.mjs` read through it) and `scripts/lib/lint-pack-scanner-parity.test.mjs` (the scanner, held to `lint:pack`'s verdicts). A rename or move of `voice-pack-catalog.ts`, `voice-pack-fs.ts` or `voice-pack-scanner.ts` breaks them.

## Module map

- The pack FORMAT's rules are not here (#1134): `voice-pack.json`'s schema, version and reader (`VoicePackManifestSchema`, `VOICE_PACK_MANIFEST_SCHEMA_VERSION` — which the installer stamps on a seeded bundled pack's manifest — `readVoicePackManifestText`, `parseVoicePackManifest`, `validateVoicePackManifest`), the identity primitives `packId` / `displayLabel` / `voiceEntry`, `isSemverVersion`, `VOICE_PACK_MANIFEST_FILE`, the usable-clip grammar `USABLE_VOICE_CLIP`, `VOICE_SCRIPT_MAX_BYTES`, `packIdMatchesFolder` and `dedupeDeclaredVoices` are `@iracedeck/callout-script`'s `voice-pack.ts`, the zod-only leaf that `lint:pack` and the packer reach too, so the three cannot disagree about what a pack is. Every module here imports them from there directly, and this barrel re-exports none of them: import `parseVoicePackManifest`, `VoicePackManifestSchema`, `CalloutScript` and the rest from `@iracedeck/callout-script` (deck-core's old re-exports of those names were dropped in #1366, not moved). The catalog schema's `version` and `minPluginVersion` still go through `semver.valid` here — this package holds the library — and `voice-pack-semver-parity.test.ts` runs the leaf's `isSemverVersion` and `semver.valid` over the same inputs (the semver.org examples plus the library's trim, leading `v`, 256-character cap and `MAX_SAFE_INTEGER` ceiling) and asserts they agree on every one; a `semver` bump that changes a verdict fails there and nowhere else, because the leaf cannot see the library.
- `voice-pack-no-window.test.ts` — the structural guard that no voice-pack module opens a window, on any outcome including failure: the install path runs while iRacing is running, so progress and failure are passive only (the `_warnings` banner and the settings window's Race Engineer card). It globs this package's `voice*` modules, so a new module of the feature must be named `voice-*` to be covered, and enrols by path the modules outside it that the feature runs: callout-script's `voice-pack.ts`, the two fetch-utils helpers on the catalog fetch path, and app-constants' voice-pack keys, catalog location and status payload.
- `voice-pack-scanner.ts` — admits packs and reads each voice's `callouts.json` beside its clips (`readVoiceScript`). A voice is addressed as `<pack id>::<voice id>` outside its pack (#1144; ours is `default::default`), so two packs may ship the same bare voice id; the scanner refuses only a voice id declared twice within ONE pack. The rules it admits by are the leaf's (above); the WORDING of every problem is the scanner's — the leaf decides, the scanner phrases — except that an issue at the manifest's `schema` reads "built for a newer version of iRaceDeck" only when `schema` is a number above 1, so a missing `schema` or a `0` is an ordinary `schema: …` line (#1134). The development voice root it scans first, and the shadowing rule for a pack id under both roots, are in `.claude/rules/platform-feature-flags.md`.
- `voice-pack-fs.ts` — the `node:fs` implementations of the scanner's `VoicePackFileSystem` port (`createVoicePackFileSystem`) and of the archive's (`createVoicePackArchiveFileSystem`), and `VOICE_PACK_MAX_DEPTH`. Every other module takes its filesystem injected, so its orderings are tested against a fake that fails at the step under test.
- `voice-pack-service.ts` — rewrites each pack's clips to `voice/<pack id>::<voice id>/…`, binds each pack's audio root to its own voices, hands the engine the composite-id → script map through the `applyScripts` dep, and exposes it as `scripts()`.
- `voice-pack-launch.ts` — no plugin bundles a voice since #1034 stage 3, so at every start this step keeps the managed pack (`ENSURED_VOICE_PACK_ID` from `@iracedeck/app-constants`, tested by `isManagedVoicePack`) at the catalog's digest and every other catalog-installed pack up to date — silently, opening no window, retrying on a schedule that tightens while the Race Engineer is on. Startup wiring: `.claude/rules/plugin-structure.md`; the development voice root that shadows it: `.claude/rules/platform-feature-flags.md`.
- `voice-pack-installer.ts` + `voice-pack-{catalog*,download,archive,provenance,storage}.ts` — catalog fetch, download, verify, install and removal, and the run-scoped `_voicePackStatus` (its payload type, phases and verdicts are `@iracedeck/app-constants`' `voice-pack-status.ts`). `voice-pack-catalog.ts` is the published catalog's shape and pure rules, `voice-pack-catalog-base.ts` where it is fetched from (`resolveVoicePackCatalogUrl` and the `_devBaseUrl` development override, #1100), `voice-pack-catalog-client.ts` the one network read (`abortAfter` and `readCappedJson` from `@iracedeck/fetch-utils`, #1101), and `voice-pack-catalog-service.ts` the TTL cache and the per-pack verdicts. `voice-pack-download.ts` streams an archive into an injected sink while hashing it, `voice-pack-archive.ts` extracts it with `fflate` treating every byte as hostile (path traversal, provenance forgery, zip bombs), `voice-pack-storage.ts` owns `.tmp/` and `.trash/` and the promote order that leaves the installed pack playable on any failure, and `voice-pack-provenance.ts` reads and writes `.install.json`, which only the installer writes and the extractor drops from an archive. `voice-pack-constants.ts` is the importless leaf the modules share (`VOICE_PACK_PROVENANCE_FILE`, the sha-256 pattern).
- `voice-script-warning{,-reporter}.ts` — the `voice-script-missing` banner (`.claude/rules/global-settings.md`): the pure `evaluateVoiceScriptWarning` and `createVoiceScriptWarningReporter({ set, clear })`.
- `voice-labels.ts` — `voiceDisplayLabels` (what the dropdown calls each voice), `isFirstPartyVoicePack` and `orderRaceEngineerVoices` (#999, spec `2026-09-27-issue-999-terse-voice-pack.md`, "Labels and order"). `isFirstPartyVoicePack` is the one place a pack's `provenance` — elsewhere only a displayed badge — becomes a decision (labelling and order, never a withheld control: the managed pack's Remove button keys off `managed`): `catalog`, `bundled-seed` and `development` are iRaceDeck's own, `sideload` never is, whatever a pack's own manifest claims about itself. A first-party pack with one voice is labelled `iRaceDeck: <pack label>`, one with several `iRaceDeck: <pack label>: <voice label>` per voice; every other pack keeps the #1034 rule (`<pack label>: <voice label>` only when the pack ships several voices or labels one differently from itself; #1147's always-prefixed rule is planned, not shipped). `orderRaceEngineerVoices` sorts the voice list the managed pack first, then other first-party voices, then everyone else, each band by the label the dropdown shows (an unlabelled voice by its title-cased voice half) — the one place the order is decided, so `ird-voice-select` (`.claude/rules/stream-deck-actions.md`) does no sorting of its own. `plugin-runtime`'s voice-pack phase orders `raceEngineerVoices` once per scan, in the voice-pack service's `onPacksChanged` (in `applyManifest` `installed()` still answers for the previous scan), and publishes that same list as `_raceEngineerVoices` — so the engine's `resolveActiveRaceEngineerVoice` fallback and the "first available" fallback `pit-crew.ts` and `audio-toggles.ts` (`@iracedeck/iracing-actions`) read from the published list agree, both picking the first iRaceDeck voice rather than an arbitrary one. A side effect of the list's order, not a change to `resolveActiveRaceEngineerVoice` itself.

## One import path per name

The barrel `src/index.ts` is the package's only entry, and deck-core re-exports none of it: import every name it exports from `@iracedeck/voice-packs`, and mock that package in a test that stubs one (`plugin-runtime`'s phase tests do, through `recordedModule`). A mock of the barrel cannot reach the package's internal imports either, which is why `voice-script-warning-reporter.test.ts` runs over the real settings cache (`initGlobalSettings` with `createMemorySettingsStore`) wired to the real `setWarning` / `clearWarning`, and counts writes from the cache's change fan-out: `settings`' `pi-warnings.ts` writes through its own `global-settings.ts` by relative path, so nothing short of the real cache shows an identical record being skipped. That test is the reason `@iracedeck/settings` is a devDependency.

## Rules
