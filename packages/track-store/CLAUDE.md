# @iracedeck/track-store

The per-track store (#1112): the pit-lane landmarks learned from live telemetry, one file per `TrackID` at `%LOCALAPPDATA%\iRaceDeck\Track Data\track_<TrackID>.json`, written debounced and atomically. It depends on `@iracedeck/track-data` (the landmark model: `foldSample`, `applyTrackLength`, `normalizePitLaneSection`, `isNewerPitLaneSection` and the types), `@iracedeck/settings` (the path helpers `resolveLocalAppData` and `nonBlank`, and the settings store's `WRITE_RETRY_DELAYS_MS` schedule) and `@iracedeck/logger`, and on nothing sim-shaped: the store knows files, never telemetry, and is in `SIM_NEUTRAL_PACKAGES` (`eslint.config.js`). The simulator a `TrackID` belongs to is a string the plugin passes in (`sim`), written to every envelope. Design: `docs/superpowers/specs/2026-09-04-issue-1112-pit-lane-landmarks.md` and its 2026-11-09 amendments.

## What reaches it, and from where

The translator (`sim-events-iracing`) folds each accepted pit-lane edge with track-data's model and publishes it as `pitLane.landmarkLearned`; the plugin hands the payload to `recordSample` (its `summary` is not read). At session start the plugin seeds the translator from `load(track)`. Consumers read the translator, never this store or the file.

## Module map

- `track-file.ts` — the file: `resolveTrackDataDirectory({ env })` (`IRACEDECK_TRACK_DATA_DIR` replaces the whole directory; there is no `platform` option, see below), `trackFileName`, `TRACK_FILE_VERSION`, the envelope (`version`, `sim`, `trackId`, `trackName`, `trackConfigName`, `trackLength`, `trackVersion`, `pitLane`, and every unknown key carried through), `parseTrackFile` / `readTrackFile` → `TrackFileRead` (`absent`, `unreadable`, `corrupt`, `newerVersion`, `newerSection`, `ok`), `trackFileMismatch` and `buildTrackFile`.
- `track-store.ts` — `createTrackStore` and the singleton trio `initializeTrackStore` / `getTrackStore` / `isTrackStoreInitialized` (`_resetTrackStore` for tests). The `TrackStoreIo` seam (`nodeTrackStoreIo` by default) and the `pid` option exist so tests can fail, count or interleave file operations and run two stores as two processes on one folder.

Never reimplement the fold, the median or the rebuild here: a sample enters a record only through `foldSample`, so the store and the translator always agree.

## One folder for every deck host, and why merging is safe

Unlike the settings and replay stores, the folder is not per ecosystem: a pit lane is a fact about a track, and per-host copies would relearn it on every switch (spec decision 3). So two plugin processes can write one file. The replay store went per ecosystem rather than merge, because its sections can be deleted from. Here nothing removes landmark data except a rebuild, and folding is idempotent — a duplicate (same key, under `PIT_LANE_DUPLICATE_WINDOW_MS` apart) is skipped and a sample older than a full window is stale — so re-folding a sample already on disk changes nothing. That is what makes merge-on-write correct.

## The store

- **`load(track)`** is synchronous and never throws. The file is read once per `TrackID` and then served from memory; the section is brought to the session's track length with `applyTrackLength` (a different `trackLength` is a rebuild: published values to `previous`, window and count reset) and this process's samples not yet written are folded in. A copy, or `null` when nothing is known. Load never moves or writes a file.
- **`recordSample`** folds into the in-memory section, remembers the sample as this process's own (the last `TRACK_STORE_OWN_SAMPLES_CAP`, twice the window, per landmark, with the track length it was learned under) and schedules the write. A changed identity (a rebuilt length, a renamed configuration) re-reads the file on next use and drops own samples of the old length.
- **Every write re-reads the file**, applies `applyTrackLength` to its section and re-folds this process's own samples into it, then writes compact JSON to `track_<id>.json.<pid>.tmp` and renames it over the file. The in-memory section becomes the merged one, so other processes' samples reach `load` too. Debounce `TRACK_STORE_WRITE_DEBOUNCE_MS` (2 s) capped by `TRACK_STORE_WRITE_MAX_WAIT_MS` (10 s) from the first unsaved sample; a failed read or write retries on `WRITE_RETRY_DELAYS_MS` and stays pending for the next sample and the shutdown flush. IO is synchronous: the file is a few kilobytes and a synchronous read-merge-rename leaves this process no await to interleave with itself.
- **The race, healed.** Another process renaming its write between this process's read and its rename drops this process's samples from the file. One debounce after every write a settle check re-reads the file and writes again only when one of this process's own samples re-folds as new (none missing: nothing written); any later write heals it too.
- **What is never written over.** A file whose `TrackID`, `trackName`, `trackConfigName` (or a non-empty `sim`) differ from the session's is another track's: treated as no data, warned about once, never written. A file whose envelope `version` or `pitLane` section version is newer than this build's is never read, written or moved aside (warned once); the samples stay in memory for this process. A corrupt file (not JSON, wrong shape, a malformed section) is moved aside by the write as `track_<id>.corrupt-<iso>.json` — a free name, never overwriting an earlier aside, with a copy fallback that skips a byte-identical aside — and one that cannot be preserved is not written over. An unreadable file (a lock, a permission) is retried, never written over.
- **`flushSync()`** writes every pending track (and runs a due settle check) synchronously, for `process.on("exit")`.
- **Stale temp files.** On create the store removes only `track_<id>.json.<pid>.tmp` files whose pid is not a running process, is this process's own (a previous process's leftover), or that are older than `TRACK_STORE_STALE_TEMP_MS` (10 min) — another live plugin process may be mid-write in the same folder. Nothing else in the folder is touched.
- **Logging.** Info when a file is created; warn on a corrupt file moved aside, a newer build's file and another track's file (each once per track per process); debug per write and per refused sample.

## Forward compatibility

Every envelope key, section key, record key and window-sample key this build does not read is carried through every write, and an entry under a landmark name this build does not know is kept as it was read (track-data's `normalizePitLaneSection` does that part). The section format is frozen (it is the later upload's payload, as a projection: see track-data's `CLAUDE.md`); what needs a `PIT_LANE_SECTION_VERSION` bump is listed there. `TRACK_FILE_VERSION` covers the envelope only; a new envelope field is additive and needs no bump.
