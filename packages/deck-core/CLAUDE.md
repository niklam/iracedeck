# @iracedeck/deck-core

Platform-agnostic core interfaces, base classes, and utilities for deck device plugins. "Platform" here means the **deck-host ecosystem** (Elgato / Mirabox / Ulanzi): this package contains no deck-host-specific code — it defines the abstraction layer that the platform adapters implement. It is not an OS-abstraction boundary: iRaceDeck is Windows-only (iRacing is), so shared Windows helpers the three plugins would otherwise triplicate live here behind injectable delegates — `settings-store.ts` (the `%LOCALAPPDATA%` path), `chromium-browser.ts` (the settings-window app-window spawn, #992), `open-folder.ts` (reveal the settings file in Explorer, #993) — while anything that needs the native addon stays injected from the plugin (`initializeKeyboard`, `initWindowFocus`, …).

## Package Contents

### Platform Abstraction (`types.ts`)

- `IDeckActionContext` — Handle to a single action instance. Wraps `id`, optional `deviceId?`/`deviceType?` (populated by adapters that expose them — Elgato; used for profile switching, #736), `setImage`, `setTitle`, `setSettings`, `isKey`, optional `showAlert?()` (flashes the host's warning indicator where supported — Elgato keys only), and (for Stream Deck+ dials) `isDial()`, `setFeedback(feedback)`, `setFeedbackLayout(layout)`, `setTriggerDescription(descriptions)` (takes a `DeckTriggerDescription`). `setFeedback`/`setFeedbackLayout`/`setTriggerDescription` no-op on platforms/controllers without a plugin-drawable touch strip (e.g. Mirabox). The dial's own screen goes through `dialCanvas()` (a `DialCanvasProfile`, or `null` on a key, an Information context, or a host with no dial screen) and `setDialCanvas(dataUri)` (one full-canvas image; a no-op when `dialCanvas()` is `null`) — #1013, see `dial-canvas.ts` below.
- `IDeckEvent<T>` and variants (`IDeckKeyDownEvent`, `IDeckWillAppearEvent`, etc.) — Platform-neutral events. Dial/touch variants: `IDeckDialRotateEvent` (carries signed `ticks` and `pressed: boolean` — whether the dial button was held during rotation, the basis of push+turn), `IDeckDialDownEvent`, `IDeckDialUpEvent`, and `IDeckTouchTapEvent` (carries `tapPos: [x, y]` and `hold: boolean`).
- `IDeckActionHandler<T>` — Interface for action lifecycle handlers (includes `onDialRotate`/`onDialDown`/`onDialUp`/`onTouchTap`).
- `IDeckPlatformAdapter` — Interface that platform adapters implement (Elgato, VSDinside, etc.). Mostly required members; `onHostReady?` is optional on purpose (#1056) — only the WebSocket adapters can report a socket opening, and Elgato declares nothing rather than stubbing it, because absence means "the deadline already armed is honest" for a transport that queues the read until it can be sent.

### Encoder Touch-Strip Feedback (`feedback-types.ts`)

- `DeckFeedbackPayload` — Platform-neutral Stream Deck+ touch-strip feedback payload passed to `IDeckActionContext.setFeedback`, keyed by layout item `key`; values are primitive shorthands or partial item overrides (`DeckFeedbackBarItem` / `DeckFeedbackTextItem` / `DeckFeedbackPixmapItem`). Details + platform caveats in `.claude/rules/encoders-and-touchscreen.md`.

### Base Classes

- `BaseAction<T>` — Abstract base with SVG image management, flag overlay, inactive state tracking, and the title-template live watcher (#899): contexts whose user-entered `titleOverrides.titleText` contains `{{` share one telemetry subscription that re-resolves the template per tick, string-compares, and re-runs the context's regenerate callback through a 10 Hz `IconUpdateThrottle` — so any action that registers `setRegenerateCallback` gets live templated titles for free. Accepts logger via constructor. Implements `IDeckActionHandler<T>`.
- `ConnectionStateAwareAction<T>` — Extends `BaseAction` with automatic iRacing connection tracking via `sdkController`. Also home of the binding-dispatch delegates: `setActiveBinding`, `tapBinding` (resolves to whether the press went out, #962), `tapBindingSequence` (atomic multi-chord sequence, #818), `holdBinding`, `releaseBinding`, `isBindingMissing` (per-context missing-binding check — prefer it over the shared `isActiveBindingMissing()`), and `isBindingKeyboardBound` (keyboard binding, not a SimHub role, #962).

### Icon Assembly (re-exported from `@iracedeck/icon-composer`)

Pure icon assembly functions (assembleIcon, extractGraphicContent, generateTitleText, resolveBorderSettings, resolveGraphicSettings, resolveIconColors, etc.) have been moved to the standalone `@iracedeck/icon-composer` package (zero dependencies). They are re-exported from `deck-core` for backward compatibility — existing imports from `@iracedeck/deck-core` continue to work.

**Exception:** `resolveTitleSettings` is no longer a pure re-export (#899) — deck-core's `title-settings.ts` wraps icon-composer's pure function and template-resolves the user-entered `titleOverrides.titleText` against the live SDK template context (`title-template.ts`). Always import it from `@iracedeck/deck-core`, never from `@iracedeck/icon-composer` directly, or titles lose template support.

deck-core adds global settings readers on top of the pure functions:

- `getGlobalTitleSettings()` — reads title defaults from global settings store
- `getGlobalBorderSettings()` — reads border defaults from global settings store
- `getGlobalGraphicSettings()` — reads graphic scale default from global settings store

### Shared Utilities

- `common-settings.ts` — `CommonSettings` Zod schema (flagsOverlay, colorOverrides, titleOverrides, borderOverrides, graphicOverrides)
- `migrate-legacy-action.ts` — `migrateLegacyActionToMode` settings-migration helper
- `global-settings-migrations.ts` — Global-settings migrations in three shapes: `migrateGlobalSettingsKeys` (one-shot passthrough-key renames, #953), `migrateRaceEngineerVoiceId` (idempotent voice-id qualification, no marker, #1144) and `seedBindingDefaultsIfAbsent(defaults, logger)` (#1277): once the store is ready it writes each given key's default binding when that key has NEVER been stored (`undefined` in the cache; a stored `""` stays cleared), in the exact value the PI binding field saves. Runs at every start with no marker, and only on a store that has read the deck host (`isSettingsStoreHostDerived()`) — elsewhere a later host answer merges under the file and a seeded default would override the user's binding; an abandoned store (#1041) is never seeded, and its log line says binding defaults are left to the user. It claims a seed only for keys the cache holds after the write. Both it and the renames run through `runOnceSettingsStoreReady` (`global-settings.ts`). Rules: `.claude/rules/global-settings.md`
- `global-settings.ts` — Plugin-level global settings manager. Single writer (#993): the plugin-owned `SettingsStore` file is truth, the deck host is read once for migration and never read again; `isSettingsStoreReady()` reports when the cache reflects the store, `getSettingsStoreSource()` how it was filled (`"file" | "host" | "fresh"`), `isSettingsStoreHostDerived()` whether it holds everything the user stored (ready, not fresh, no pending countdown, not abandoned, salvage did not fail — the one gate for the host mirror, its binding consumer, and for any write keyed on a key's absence, #1277; never relax it for another caller), `getSettingsStoreHostDerivation()` the reason when it does not (`not-ready` / `not-read-yet` / `abandoned` / `unparseable`, the boolean being its `host-derived` case), and `runOnceSettingsStoreReady(action)` runs an action once at the first ready moment, done-before-action so a write inside it is not re-entered. `hostMirrorPayload({ port, token })` builds the ONE host write per start the PI bridge bootstraps from — the full cache plus `_settingsChannel`, `undefined` (skip the write) before the store is ready, when it started fresh, while the `_migrationPending` countdown is set, or once the durable `_migrationAbandoned` marker is (`MIGRATION_ABANDONED_KEY`, #1041) — a host `setGlobalSettings` replaces the whole object, so a defaults file must never be mirrored over a host copy the plugin has not read. A fresh start persists the countdown so later starts ask the host again; after `MIGRATION_RETRY_STARTS` unanswered starts the file is accepted and the countdown gives way to the durable marker, which keeps the mirror shut. That marker's VALUE is the plugin version that gave up (#1047): a store that has been given up on — the marker, or a countdown at the ceiling — issues ONE more read when the running version is semver-newer. Only a payload carrying keys clears the marker and restores mirroring; an empty, `null` or absent answer records this version's own give-up and the store stays quiet until the next upgrade. So a newer version gives an install the old build could only preserve a *chance* to recover — it does not guarantee one, and a blank running version counts as unknown rather than as differing, or the retry would repeat on every launch. Both shapes count because #1041 ships unreleased alongside #1047, so no field file carries the marker yet; a bare `true`, or no record, counts as never-given-up-under-a-stamping-build and is retried. On that retry the file is authoritative and the host only fills keys the file has never held — `mergeMigration`'s "still at its default implies never touched" premise holds for a defaults-born file, not for one that has been the store for months. The version is injected via `InitGlobalSettingsOptions.pluginVersion`, never read from `getPluginVersion()` here, which throws when `initPluginConfig()` has not run. Gate the mirror on having positively READ the host, never on a counter having run out, and keep retry decisions in the load path rather than in that gate; an unreadable file is retried with a doubling back-off (`LOAD_ATTEMPTS`, `LOAD_RETRY_DELAY_MS`)
- `settings-channel-publisher.ts` — `createSettingsChannelPublisher({ adapter, logger }).publish(channel)` (#993 phase 2): removes a stale `_settingsChannel` (`SETTINGS_CHANNEL_KEY`) an older build persisted into the store (the channel is per-process and travels only in the host mirror) and sends the one host mirror per start; idempotent per channel, retries the mirror until it goes out, logs its own faults. Bound to the settings-window controller's `onStarted` hook and the plugins' store-ready block
- `settings-store.ts` — The plugin-owned settings file (#993): `SettingsStore`, `createFileSettingsStore` (atomic temp+rename write, 250 ms trailing debounce, failed writes retried on `WRITE_RETRY_DELAYS_MS` and kept pending for the shutdown flush, temp files cleaned up, UTF-8 BOM tolerated, `flush()` plus a synchronous `flushSync()` each plugin wires to `process.on("exit")` that also lands an async write still in flight, corrupt file moved aside as `global-settings.corrupt-<iso>.json` and reported through the `onRejected` option as a `SettingsFileRejection` — path, the parser's reason, a line and column from `json-error-location.ts`'s `locateJsonError`, the preserved copy — while a file that cannot be preserved fails the read instead, #1036; `decodeSettingsText` accepts a UTF-8 or UTF-16LE BOM), `createMemorySettingsStore` (tests/harness), `resolveSettingsStorePath` (`%LOCALAPPDATA%\iRaceDeck\Settings\<ecosystem>\global-settings.json`, `IRACEDECK_SETTINGS_PATH` override), `settingsStoreFolderName`
- `replay-session-store.ts` + `replay-session-file.ts`, `replay-markers.ts`, `replay-laps.ts`, `replay-session-subscriber.ts` — the per-session replay store (#1162, #1203), the only owner of `%LOCALAPPDATA%\iRaceDeck\Replay\<ecosystem>\session_<SubSessionID>.json` (`resolveReplayStoreDirectory({ platform, env })`, the ecosystem folder from `settingsStoreFolderName` — per ecosystem because two deck hosts run two plugin processes that would otherwise rename their copies over each other every debounce; `IRACEDECK_REPLAY_DIR` replaces the `Replay` base and the ecosystem folder is still appended). On init it removes stale `session_*.json.<pid>[.sync].tmp` files a crash left, and nothing else. Singleton trio `initializeReplaySessionStore` / `getReplaySessionStore` / `isReplaySessionStoreInitialized`; every plugin wires `process.on("exit", () => store.flushSync())` beside the settings store's. The file is an envelope (`version`, `subSessionId`, `track`, `series`, `sessionStart`, `sections`) whose sections are owned by features — `markers` and `laps` are the two this build reads, and **every other key is preserved on every write**. Same write discipline as `settings-store.ts` (atomic temp+rename; a trailing debounce `REPLAY_STORE_WRITE_DEBOUNCE_MS` 2 s capped by `REPLAY_STORE_WRITE_MAX_WAIT_MS` 10 s from the first unsaved change, so a field that never goes quiet still lands; a failed write goes back to pending — the active record itself IS the pending payload, so a retry writes whatever the record holds by then and never an older snapshot over a newer landed write, and a failed write for a session that has since changed is retried per path — on `WRITE_RETRY_DELAYS_MS` and kept for the shutdown flush; a corrupt file moved aside as `session_<id>.corrupt-<iso>.json`, the copy fallback skipping an identical aside so a locked file is preserved once and not once per open; compact JSON, because a race's record reaches megabytes and is rewritten every few seconds), with two differences: the load is SYNCHRONOUS (`setActiveSession` reads the file in the same tick the session appears, so the actions never see a loading state) and the pending write is flushed immediately on session change and disconnect. `SubSessionID` 0 (offline) is an in-memory record that is never written and is dropped on disconnect or the next session key. A session whose file could not be READ (a lock, a permission) opens in memory too, write-inhibited, and the read is retried on the same `WRITE_RETRY_DELAYS_MS` schedule (option `loadRetryDelaysMs`), then on a same-id `setActiveSession`, on the record's drop and in `flushSync`; once readable, the in-memory record is merged INTO the file — markers as a union under the dedupe rule, laps by `mergeLapsSectionInto` (the file's entry stays where both have one; a null `timeMs` is filled) — and written normally. A corrupt file that could not be preserved stays write-inhibited for the connection, because the next write would otherwise rename a near-empty record over bytes the store never saw — fail closed, as the settings store does for a corrupt file it cannot move. Forward compatibility: every envelope field and every field on a marker, lap entry, car record or laps session that this build does not read is carried through a write (index signatures on the types); a `markers` entry that is not a marker is kept aside and re-emitted after the markers on every write (`partitionMarkers`); and a `laps` section whose `version` is above `LAPS_SECTION_VERSION` (`isNewerLapsSection`) is a section this build has no reader for — carried through verbatim, `recordLapStart` / `recordLapTime` return false with one warning, and `findLapStart` misses with `newer format`. The session is fed by `createReplaySessionSubscriber({ store, getSessionInfo, logger })`, an `sdkController.subscribe` callback in the elevation-check shape that reads `WeekendInfo` and calls `setActiveSession` / `clearActiveSession`; the store itself knows files and nothing about telemetry. `markers` (`add` with the 60-frame dedupe, `deleteNearest` within 600 frames, `next` past 60 ahead, `previous` past 120 behind, `list`; the windows are the exported `MARKER_*_FRAMES` constants) and `laps` (`recordLapStart` / `recordLapTime` — a time arriving before its start is held in memory and paired when the start comes — and `findLapStart` → `LapStartLookup`, a hit with `matchedBy: "pair" | "sessionNum"` or a miss whose `reason` is the phrase the action logs: `no file` / `no session` / `no car` / `car mismatch` / `lap not recorded` / `newer format`). Which session a start joins and which one a lookup reads is the rule on `recordLapStartInSection`: a start with no pair match joins the one session with that `sessionNum` when its frame lies within the span of that session's recorded lap starts (the walk recording under a saved replay's own pair), else opens a new session (a restart's laps fall past the old span); a lookup whose pair-matched session lacks the car or the lap reads the one other session with the `sessionNum` that has both, `matchedBy: "sessionNum"`. A laps call carrying a `subSessionId` other than the active record's is ignored (`SubSessionScoped`), and every markers call takes the same scope as an optional second argument; `list()` returns a copy. `findLapStart` answers `no file` when the record was neither loaded from disk nor written to — the plugin was not running for that session — and `no session` only for a record that exists without a matching session. The pure section logic is exported for tests and the harness; `REPLAY_FILE_FRAME_LAG` (59) records the measured `.rpy` lag and is deliberately not applied. Specs: `docs/superpowers/specs/2026-09-13-issue-1162-replay-markers.md`, `2026-09-24-issue-1203-fastest-lap-from-session-record.md`.
- `audio-session-identity.ts` — `pluginAudioSessionIdentity(binDir)` (#1253): the `{ displayName, iconPath }` every plugin passes to `initializeAudio` so the Windows Volume Mixer lists our audio session as "iRaceDeck" with the logo instead of the deck host's "Node" — `AUDIO_SESSION_DISPLAY_NAME` and `<plugin>/imgs/plugin/` + `AUDIO_SESSION_ICON_FILE`, resolved absolute from the plugin's `bin/`. It lives here because it is plugin-layout knowledge the three plugins share; `@iracedeck/audio-service` only defines the shape and never learns where a plugin keeps its files
- `open-folder.ts` — `openFolderInExplorer(path)` + `explorerSelectArgs` (#993): reveals the settings file with Explorer's documented `/select,"<path>"` form, spawned detached with `windowsVerbatimArguments` so libuv can't re-quote the whole token. The second `child_process` use beside the settings-window launcher; the path always comes from the plugin's own store, never from a page, and it deliberately does not go through `openUrl` (http(s)-only on every host)
- `main-thread-watchdog.ts` — `startMainThreadWatchdog({ logger, target, heartbeatMs?, stallMs?, pauseTimeoutMs?, jsPauseLatencyMs? })` (#1330), called by all three plugins once logging is up: the main thread bumps a `SharedArrayBuffer` heartbeat every 500 ms, and an `unref`'d eval worker that sees it stand still for 5 s (on `performance.now()`; a gap of more than three heartbeats in its own samples is a suspended process and restarts the clock) pauses the main thread through the in-process inspector (`Session.connectToMainThread()`, no `--inspect`). A pause landing within 250 ms is reported as JavaScript with its call frames; a later one, or none within 2 s, as native code, with the frames where the thread resumed. Then a recovery line. Reports go straight to the host's log file (`WatchdogLogTarget`: `{ kind: "file", path }` for Elgato's `<uuid>.0.log`, `{ kind: "daily", dir }` for the Mirabox/Ulanzi `FileSink` directory, named by `watchdogDailyLogFileName`, which both adapters test against their sink). `superviseWatchdogWorker` is the main-thread side: one WARN when the worker reports the inspector unusable, and one WARN plus a stopped heartbeat when the worker errors or exits. The worker source is assembled from self-contained functions stringified with `toString()` and passed by value — `watchdogWorkerMain(watchdogStep, initialWatchdogState, watchdogDailyLogFileName)` — so none of them may use anything from module scope; `watchdogStep` is the pure reducer the unit tests drive, a guard test runs the assembled source in a real `Worker`, and another runs the terser-minified module (the plugins' own terser and options) through a real stall. Decision record: `docs/superpowers/specs/2026-10-04-issue-1330-main-thread-watchdog.md`
- `resource-monitor.ts` — `startResourceMonitor({ logger, onSessionStart?, onSessionEnd?, isSessionActive?, config?, sampler? })` (#1338), started by all three plugins beside the watchdog: every 60 s on an `unref`'d timer it samples `process.cpuUsage()` (delta, % of one core), `performance.eventLoopUtilization()` (delta) and `process.memoryUsage()`, reading each counter once per sample and diffing by hand so nothing between samples is lost. The rule is the pure reducer `resourceMonitorStep`: three consecutive samples at CPU ≥ 50 % of a core OR ELU ≥ 0.5 write ONE WARN carrying the numbers; the first sample below both writes the parameter-free INFO "Plugin CPU use back to normal" and re-arms; every sample writes a debug `Resources: …` line. At each iRacing exit `resourceSessionSummary` writes INFO "Resource summary for the iRacing session" plus a debug line (time-weighted avg and peak CPU, peak ELU, peak RSS and heap). It takes an extra PARTIAL sample at each session edge (iRacing starting and exiting) and restarts its minute there, so every interval lies wholly inside or outside a session; a partial sample is logged and counted towards the session but takes no part in the high/normal rule, and the summary follows the exit edge's sample. `isSessionActive()` only seeds the starting side. The plugins inject `onIRacingStarted`, `onIRacingTerminated` and `isIRacingActive` rather than this module importing `app-monitor` (#1176). Not gated on `debugLogging`.
- `cpu-profile-capture.ts` — `createCpuProfileCapture({ profilesDir, logger, writeSettings, durationMs?, … })` (#1338), the settings window's **Capture CPU profile**: an in-process `inspector.Session` (`session.connect()`, loaded on demand so a Node without the inspector fails one capture rather than the plugin) runs `Profiler` at a 1000 µs interval for 30 s and writes `cpu-<ISO, filename-safe>.cpuprofile` (DevTools) plus a `.txt` (wall and busy time, top 30 functions by self time with bundle positions, V8's pseudo-frames labelled) into `<log dir>/profiles`, then prunes to the newest five pairs by exact name pattern. One capture at a time; a second request is refused. Its state is the run-scoped `_profileCaptureStatus` (`PROFILE_CAPTURE_STATUS_KEY`, a JSON string `{ state: idle|capturing|saved|failed, startedAt?, durationMs?, file?, reason? }`); the key lives in the dependency-free leaf `cpu-profile-capture-constants.ts`, which the module re-exports and `run-scoped-settings.ts` imports, the same split as `pi-warnings-constants.ts`. Imports only Node built-ins, erasable types and that leaf, so its integration test runs it, transpiled, in a child Node process. Decision record: `docs/superpowers/specs/2026-10-04-issue-1338-built-in-profiling.md`
- `app-monitor.ts` — iRacing process detection (takes `IDeckPlatformAdapter`); also `isIRacingActive()` (running-flag OR live SDK connection) and the `onIRacingTerminated(listener)` subscription, whose listeners run after the running flag and SDK connection are already down (#870), with its counterpart `onIRacingStarted(listener)` (#1338): once per session, on the first of the launch event and the SDK connection coming up, re-armed by the exit notification. Exit detection is dual-path: the host terminate event, plus an SDK-disconnect fallback (`IRACING_EXIT_SDK_CONFIRM_MS`, 5 s sustained loss) for hosts that never deliver app-monitoring events — deduped per exit episode, blip-safe when a launch event affirmed the sim is running. It also keeps the current connection's verdict for `hasElevationMismatch()` (cleared on disconnect and on a probe that throws), which the window focus service reads to skip a focus that cannot succeed (#976) — never to gate an action

- `device-profiles.ts` — Canonical Stream Deck device + profile reference (#736, #753, #790): `DeviceType`, `DEVICE_SPECS`, `DEVICE_SUPPORT`, `PROFILE_NAMES` / `PROFILE_TARGET_DEVICES` / `PROFILE_NAV_ACTIONS`, `CAR_SELECTOR_PROFILE`, `shipsBundledProfiles`, lookup helpers, and the device-suffixed profile-name helpers (`PROFILE_DEVICE_SUFFIXES`, `profileDeviceSuffix`, `deviceProfileName`, `profileDisplayName`, `resolveProfileNameForDevice`); details in `.claude/rules/profiles-and-devices.md` (Elgato-only)
- `profile-switcher.ts` — Profile-switch singleton (#736): `requestProfileSwitch`, `requestProfileSwitchBack`, `notifyProfileVisible` — the layer above the adapters' `switchToProfile`; a safe no-op where unregistered (non-Elgato)

- `focus-iracing-mode.ts` — The Focus iRacing Window vocabulary (#977): `FOCUS_IRACING_MODES` (`always`, `required`, `never`), the `FocusIRacingMode` type, `DEFAULT_FOCUS_IRACING_MODE` (`always`), and `parseFocusIRacingMode`, which folds a pre-#977 boolean or its string form into a mode (`true` → `always`, `false` → `never`) and resolves anything else to the default rather than throwing, since one throwing field aborts the whole settings parse. The transform IS the migration, so there is no one-shot pass and no marker key. A leaf on purpose: `global-settings.ts` needs it for the schema and `window-focus-service.ts` needs it to read the cache, and the service already imports the schema module, so the vocabulary can live in neither.
- `window-focus-service.ts` — Window focus singleton (#930): `initWindowFocus`, `focusIRacingIfEnabled`, `focusIRacingBeforeInput`, `focusIRacingNow`, `FocusResult`, `FOCUS_TIMEOUT_COOLDOWN_MS`, `_resetWindowFocus`. Plugins inject the focuser (same DI shape as `keyboard-service`), so deck-core never imports `@iracedeck/iracing-native` — importing that package loads the native addon as a module side effect. `FocusResult` is therefore a hand-kept **mirror** of the native enum; `packages/iracing-plugin-stream-deck/src/shared/focus-result.test.ts` asserts the two stay identical. They also inject the app monitor's `isIRacingActive` as `initWindowFocus`'s third argument (the warn-vs-debug choice for `WindowNotFound`), because importing it here closed the cycle `sdk-singleton` → `window-focus-service` → `app-monitor` → `sdk-singleton` (#1176) — a cycle among workspace sources now fails the plugin builds. Previously duplicated in all three plugins' `src/shared/window-focus.ts`. Since #977 the setting is a three-value **mode** rather than a switch (`focus-iracing-mode.ts` above), and the service has two gated call sites: `focusIRacingIfEnabled()` is the adapter-level one every `plugin.ts` registers on the key/dial events, and runs under `always` only; `focusIRacingBeforeInput()` is the keystroke one and runs under `always` and `required`, called from the keyboard service immediately before every native key emit and — via the `beforeKeystrokes` hook `initializeSDK` injects into `createSDK` — from `ChatCommand.sendMessage`; the Chat action's Open Chat and Reply modes call it directly too, since the prompt they open is for the driver to type into. Both skip the native ask outright while `hasElevationMismatch()` reports a mismatch (#976), and for `FOCUS_TIMEOUT_COOLDOWN_MS` after a `FocusTimedOut`, so the doubled ask under `always` cannot double the focuser's ~1 s wait while an elevation mismatch is making every press time out. `focusIRacingNow()` (#926) is the unconditional variant for action code where focusing IS the pressed action — it skips the mode (it focuses even under `never`), the `isSettingsStoreReady()` gate, the mismatch gate and the cooldown alike, and shares the gated path's result handling.
- `mouse-pointer-service.ts` — Mouse pointer singleton (#926): `initMousePointer`, `movePointerToSim`, `PointerMoveResult`, `DEFAULT_POINTER_X_FRACTION` / `DEFAULT_POINTER_Y_FRACTION`, `_resetMousePointer`. Deliberately a SIBLING of the focus service rather than part of it — one owns the foreground, the other owns where the pointer goes, and neither needs the other. Same injected-delegate shape and the same hand-kept native mirror, guarded by `pointer-move-result.test.ts`. Composing the two (focus, then move) is feature policy and lives in `@iracedeck/iracing-actions`' `shared/mouse-to-sim.ts`. The two `DEFAULT_POINTER_*_FRACTION` constants remain the no-argument fallback; since #1029 the target callers actually pass comes from `sim-pointer-target.ts`.
- `sim-pointer-target.ts` — Pure Mouse to Sim target resolution (#1029): `POINTER_ANCHORS_X`/`_Y`, `POINTER_ANCHOR_X_FRACTIONS`/`_Y_FRACTIONS`, the `DEFAULT_POINTER_ANCHOR_*` / `DEFAULT_POINTER_OFFSET_*` defaults, `POINTER_OFFSET_LIMIT`, `SimPointerTargetConfig`, `SimPointerTarget`, `resolveSimPointerTarget`. Zero imports: it knows nothing about settings storage or the addon, so the pointer service stays the injected OS primitive and the four `mouseToSim*` global settings stay plain persistence. Total on an invalid input — an unknown anchor or a non-finite offset resolves to the default rather than a NaN the native call would turn into an arbitrary cursor position. Its defaults resolve to exactly `DEFAULT_POINTER_X_FRACTION` / `DEFAULT_POINTER_Y_FRACTION`, pinned by `sim-pointer-target.test.ts` — that equality is what keeps #1029 from moving anyone's pointer — and `sim-pointer-target.partial.test.ts` pins the settings-window control's `default=` attributes to the same constants.

### Voice packs

The Race Engineer voice-pack stack (#1034, #1064, #1144). Packs live under `%LOCALAPPDATA%\iRaceDeck\Race Engineer\Voices` (`voice-packs-path.ts`).

- The pack FORMAT's rules are not here (#1134): `voice-pack.json`'s schema, version and reader (`VoicePackManifestSchema`, `VOICE_PACK_MANIFEST_SCHEMA_VERSION` — which the installer stamps on a seeded bundled pack's manifest — `readVoicePackManifestText`, `parseVoicePackManifest`, `validateVoicePackManifest`), the identity primitives `packId` / `displayLabel` / `voiceEntry`, `isSemverVersion`, `VOICE_PACK_MANIFEST_FILE`, the usable-clip grammar `USABLE_VOICE_CLIP`, `VOICE_SCRIPT_MAX_BYTES`, `packIdMatchesFolder` and `dedupeDeclaredVoices` are `@iracedeck/callout-script`'s `voice-pack.ts`, the zod-only leaf that `lint:pack` and the packer reach too, so the three cannot disagree about what a pack is — and which `voice-pack-no-window.test.ts` enrols by path beside this package's `voice*` modules, since the scanner runs it on every scan. Every module below imports them from there directly; `index.ts` re-exports `parseVoicePackManifest`, `VoicePackManifestSchema`, `VoicePackManifest`, `VOICE_PACK_MANIFEST_FILE` and `VOICE_SCRIPT_MAX_BYTES` so deck-core's public surface did not move. The catalog schema's `version` and `minPluginVersion` still go through `semver.valid` here — this package holds the library — and `voice-pack-semver-parity.test.ts` runs the leaf's `isSemverVersion` and `semver.valid` over the same inputs (the semver.org examples plus the library's trim, leading `v`, 256-character cap and `MAX_SAFE_INTEGER` ceiling) and asserts they agree on every one; a `semver` bump that changes a verdict fails there and nowhere else, because the leaf cannot see the library.
- `voice-pack-scanner.ts` — admits packs and reads each voice's `callouts.json` beside its clips (`readVoiceScript`). A voice is addressed as `<pack id>::<voice id>` outside its pack (#1144; ours is `default::default`), so two packs may ship the same bare voice id; the scanner refuses only a voice id declared twice within ONE pack. The rules it admits by are the leaf's (above); the WORDING of every problem is the scanner's — the leaf decides, the scanner phrases — except that an issue at the manifest's `schema` reads "built for a newer version of iRaceDeck" only when `schema` is a number above 1, so a missing `schema` or a `0` is an ordinary `schema: …` line (#1134).
- `voice-pack-service.ts` — rewrites each pack's clips to `voice/<pack id>::<voice id>/…`, binds each pack's audio root to its own voices, hands the engine the composite-id → script map through the `applyScripts` dep, and exposes it as `scripts()`.
- `voice-pack-launch.ts` — no plugin bundles a voice since #1034 stage 3, so at every start this step keeps the managed pack (`ENSURED_VOICE_PACK_ID` in `voice-pack-constants.ts`, tested by `isManagedVoicePack`) at the catalog's digest and every other catalog-installed pack up to date — silently, opening no window, retrying on a schedule that tightens while the Race Engineer is on. Startup wiring: `.claude/rules/plugin-structure.md`; the development voice root that shadows it: `.claude/rules/platform-feature-flags.md`.
- `voice-pack-installer.ts` + `voice-pack-{catalog*,download,archive,provenance,storage,status}.ts` — catalog fetch, download, verify, install and removal, and the run-scoped `_voicePackStatus`.
- `voice-script-warning{,-reporter}.ts` — the `voice-script-missing` banner (`.claude/rules/global-settings.md`).
- `voice-labels.ts` — `voiceDisplayLabels` (what the dropdown calls each voice), `isFirstPartyVoicePack` and `orderRaceEngineerVoices` (#999, spec `2026-09-27-issue-999-terse-voice-pack.md`, "Labels and order"). `isFirstPartyVoicePack` is the one place a pack's `provenance` — elsewhere only a displayed badge — becomes a decision (labelling and order, never a withheld control: the managed pack's Remove button keys off `managed`): `catalog`, `bundled-seed` and `development` are iRaceDeck's own, `sideload` never is, whatever a pack's own manifest claims about itself. A first-party pack with one voice is labelled `iRaceDeck: <pack label>`, one with several `iRaceDeck: <pack label>: <voice label>` per voice; every other pack keeps the #1034 rule (`<pack label>: <voice label>` only when the pack ships several voices or labels one differently from itself; #1147's always-prefixed rule is planned, not shipped). `orderRaceEngineerVoices` sorts the voice list the managed pack first, then other first-party voices, then everyone else, each band by the label the dropdown shows (an unlabelled voice by its title-cased voice half) — the one place the order is decided, so `ird-voice-select` (`.claude/rules/stream-deck-actions.md`) does no sorting of its own. Each plugin orders its `raceEngineerVoices` once per scan, in the voice-pack service's `onPacksChanged` (in `applyManifest` `installed()` still answers for the previous scan), and publishes that same list as `_raceEngineerVoices` — so the engine's `resolveActiveRaceEngineerVoice` fallback and the "first available" fallback `pit-crew.ts` and `audio-toggles.ts` (`@iracedeck/iracing-actions`) read from the published list agree, both picking the first iRaceDeck voice rather than an arbitrary one. A side effect of the list's order, not a change to `resolveActiveRaceEngineerVoice` itself.
