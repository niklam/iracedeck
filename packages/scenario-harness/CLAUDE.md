# @iracedeck/scenario-harness

Local QA tool for auditioning Race Engineer / Pit Crew audio without launching iRacing. Boots the REAL event-bus / sim-events-iracing translator / audio-service / audio-scenarios stack against a mock SDK controller (`src/mock-sdk-controller.ts`) and a mock platform adapter, and serves a web UI for live telemetry/session mutation, presets, one-click scenario shortcuts, raw bus-event injection, and audio activity monitoring.

For the end-to-end "how to add a callout" walkthrough (which includes this package's harness steps), see `.claude/rules/race-engineer-callouts.md` — the notes below cover harness-only mechanics.

## Running

```bash
pnpm --filter @iracedeck/scenario-harness dev   # tsx watch src/main.ts
```

UI at `http://127.0.0.1:5750/` (`DEFAULT_HOST`/`DEFAULT_PORT` in `src/server.ts`). No iRacing, no deck hardware.

## Audio pipeline

Boot processes the audio-assets clips through the same radio-engineer ffmpeg filter the plugin build applies, so the harness auditions the exact clips shipped to users. The processed cache is shared with the plugin builds (`packages/audio-assets/.cache/<filter-hash>/`), so the first run after a plugin build is a fast cache-hit copy. The UI's audio refresh re-runs the processor with `wipe: false` — Windows/miniaudio holds file locks on any clip currently loaded, so overwrite-in-place instead of rmSync (`src/main.ts`). `/api/audio/wipe-cache` nukes the upstream ffmpeg cache and reprocesses everything — a last-resort diagnostic (`src/server.ts`).

## Callout scripts and voice packs (#1064)

Since #1064 a voice's callouts are data it ships — `voice/<voice-id>/callouts.json` — compiled by the engine against the contracts `registerPitCrew` declares, so the harness has to hand the engine a script or every migrated callout is silent. `src/voice-scripts.ts` does it two ways, and `src/main.ts` wires both **after** `wireRaceEngineer`, which calls `registerPitCrew` (calling `setScripts` earlier compiles every entry to "no contract" and warns once per scenario about a state the first fire would silently fix — the order the plugins keep too):

- **Every published voice's script is read from the audio-assets source tree** (`loadBundledVoiceScripts`, `audioAssetsPath` + `calloutScriptPath` for every `PUBLISHED_VOICE_IDS` entry — #1034 stage 3: the harness auditions every published voice, not just the bundled subset a plugin build ships; the function keeps the name it had when the two lists were the same) — the same committed artifact the packer ships for every published voice, and the plugin build copies for the bundled ones. **It throws, naming the file**, on a missing, non-JSON or schema-failing artifact, and that ends the boot. Deliberate: the harness is a dev tool, and a published voice with no usable script is a build that would ship a silent engineer. (The plugins go through the never-throwing scanner instead, since a plugin must never end its process over a pack.) After editing `configs/<voice>.voice.json`, make sure the artifact has been regenerated — the post-edit hook runs `pnpm generate:callout-scripts` in a Claude Code session, run it by hand otherwise, because the harness reads the generated artifact, not the config — then press **Reload audio** in the UI: `/api/audio/refresh` (and `/api/audio/wipe-cache`, which re-copies the assets too) runs the processor and then `reloadVoiceScripts` (`src/voice-scripts.ts`), which re-reads the bundled scripts (or, with a packs directory named, runs the pack service's refresh) and hands the engine the new map, so a regenerated script is auditioned without a restart. How a broken regenerated script surfaces depends on the path: without `IRACEDECK_VOICE_PACKS_PATH` the bundled loader throws and the Reload request fails loudly, naming the file; with it the Reload is the pack service's refresh, and nothing in it throws over a script. A published voice whose processed copy is missing or broken is warned about (`Bundled voice "<id>" has no usable script: …`) and keeps the last script it read cleanly (the boot copy only when no re-read has succeeded since), so the request succeeds and that OLDER script stays live; an installed pack's broken script is a logged problem and that voice is left out of the map, exactly as the plugin would. Read the harness log after a Reload on that path.
- **Installed voice packs load when `IRACEDECK_VOICE_PACKS_PATH` names a packs directory** (`loadInstalledVoiceScripts`): the plugins' own `createVoicePackService` over the real `createVoicePackFileSystem`, so a sideloaded or downloaded pack's clips AND script load as they do in a plugin — roots to the audio service, the merged manifest to the engine and the voice list, then the merged script map (published ∪ installed) to the engine, in that order. A pack's voices arrive under their composite ids (`<pack id>::<voice id>`, #1144) while the published voices keep the bare ids the authored manifest gives them, so nothing collides: a downloaded `default` under that directory is its own voice, `default::default`, listed beside the source tree's `default` and played from its own root — two copies of one voice, each auditionable on its own. Each merge rescans the voice and driver-name lists from the merged manifest with the plugins' own `scanRaceEngineerVoices` and `scanDriverNames` (`applyMergedManifest` in `src/race-engineer-wiring.ts`, into the one mutable voice state the engine's resolver and the Race Engineer wiring both read live), and the seeded `_raceEngineerVoices` / `_voiceLabels` / `_driverNames` are re-issued afterwards, so the UI's Voice and Driver Name dropdowns offer the pack's entries and a name only the pack carries is spoken. On this path the published voices' scripts are first the loud source-tree read above, at boot; then, on every voice-pack scan (boot, and each Reload / Wipe cache), the harness re-reads each published voice's `callouts.json` from the processed audio root through deck-core's `readVoiceScript` — the service itself reads no bundled voice since #1144 — and the installed packs' scripts join them under their composite ids. The voice that plays is chosen by deck-core's `resolveActiveRaceEngineerVoice`, as in a plugin: a stored bare `default` is itself in the list and plays the source-tree voice, a stored `default::default` plays the installed pack. Unset, the harness still auditions every published voice — the default, and what every shortcut assumes.

The radio frame's two opt-outs, `raceEngineerRadioBeeps` and `raceEngineerPitAmbience`, are seeded on and read live at frame expansion through `getFrameOptions` in `src/main.ts` (deck-core's `frameOptionsFromSettings`, the same rule the plugins and the Background preview use) — `POST /api/settings {"patch": {"raceEngineerRadioBeeps": false}}` is heard on the next callout, and the UI's settings grid offers both as the **Radio Beeps** / **Pit Ambience** checkboxes (`ui/app.js`, `renderSettings`).

## Mock SDK controller

`MockSDKController` implements only the structural surface the translator uses (`subscribe`/`unsubscribe`/`getSessionInfo`); it's handed over cast `as unknown as SDKController` because the real class's private fields defeat structural typing (same pattern as the translator tests). Default tick interval is 14 ms (matching the real controller's poll rate). Default telemetry is "in garage / engine off / no flags / off-track" so boot fires no spurious events.

## Seeded settings

`src/bootstrap-settings.ts` seeds the adapter's global-settings store from the audio-assets manifest: `_raceEngineerVoices` / `_driverNames` (plus the first entry of each as the picked voice / driver name), Race Engineer and Radar enabled at volume 100, and the radio frame's beeps and ambience on (#1064). So scenarios fire on a fresh boot with zero UI interaction. `initGlobalSettings` is called AFTER seeding so the listener delivers the seeded values on the first tick (`src/main.ts`).

**The Race Engineer is wired by the plugins' own code (#1349).** `src/main.ts` calls `wireHarnessRaceEngineer` (`src/race-engineer-wiring.ts`), which calls `@iracedeck/race-engineer-wiring`'s `wireRaceEngineer`, the call the three plugins make through `plugin-runtime`, with a `RaceEngineer` logger scope, `createIracingSimRuntime()` over the running translator, the harness's live voice state as `voice`, and `overrides: harnessRaceEngineerOverrides()`; `race-engineer-wiring.test.ts` calls the same function, so the test cannot drift from the boot. So every `registerPitCrew` dependency is the one a plugin gets: the bus caches, the snapshot and live-state resolvers, both master gates and the one `isCalloutEnabled` lookup every callout family gates through. The only overrides are the three snapshot stubs in `src/race-engineer-overrides.ts` (session-start, race-start, qualifying-invalidation), because the UI or a shortcut composes those snapshots whole through `/api/<name>/snapshot` (below) instead of driving the session info and telemetry the translator would build them from. `race-engineer-overrides.test.ts` pins that key set, since an override silently replaces a dependency the wiring builds; add one only for a snapshot the harness must compose itself.

**So the harness can exercise callout gates.** The gates read deck-core's `getGlobalSettings()` when a callout fires, and here that is the seeded memory store: both masters (`pitCrewRaceEngineerEnabled`, `pitCrewRadarEnabled`) are seeded `true` and no `calloutEnabled*` key is seeded, which reads as on, so every gate is open at boot. `POST /api/settings {"patch": {...}}` writes through `updateGlobalSettings`, so turning a `calloutEnabled*` key or a master off is heard on the next fire, and turning it back on restores the line. `pitCrewRadarEnabled` reaches the radar two ways, as in a plugin: through the wiring's `getRadarMasterEnabled`, and through the harness's own `applyAudioSettings` → `setRadarEnabled` path (`src/main.ts`), which stands in for the Pit Crew action the harness never mounts. `race-engineer-wiring.test.ts` checks that both masters and a sample of family gates read the seed and follow a patch. What still needs a real plugin is the settings UI writing the key; the gate that reads it is the same code here and there.

**What sharing the wiring changed.** Dependencies the harness used to leave at their `DEFAULT_DEPS` entries now come from the wiring:

- Overtake-lost lines speak the chosen driver name, resolved against the live driver-name list.
- Race-end callouts play on `race.finished`, and once the translator reports the finish every contract that reads `getRaceFinishedFired` stands down, as in a plugin: the gap callouts, the overtake gained and lost reactions and their position readouts, the lap-boundary position and race-status lines, and the lap-time line.
- Spotter track direction, the nearest-car gap and the opponent pit and flag live positions come from the real translator instead of fixed defaults; an opponent with no live position still falls back to the payload's.
- The overtake gate is real. It reads live telemetry (`Speed`, `PlayerTrackSurface`, `OnPitRoad`, `CarLeftRight`) and the time since the last incident, and it refuses on the mock's in-garage defaults. Both gap contracts read it too, so the 13 overtake and gap shortcuts in `src/scenario-shortcuts.ts` are wrapped in `atRacingSpeed`, which prepends the setup step `AT_RACING_SPEED` (on track at 40 m/s, with `tick: true`, so `/api/telemetry` ticks the translator before the publish whatever the tick rate, paused included) and declares the `sdk-connected` precondition, since a disconnected translator receives no telemetry and the gate stays shut. The step leaves `OnPitRoad` and `CarLeftRight` alone, so a car parked on pit road or with a car alongside hears the real suppression, and the car stays on track at racing speed afterwards, like any patch. Which shortcuts need the wrap is derived in `overtake-gate-shortcuts.test.ts`, by replaying every shortcut's publish at the catalog registered with a spy gate; the raw injector does no setup, so the four gated events' templates in `src/event-names.ts` carry `OVERTAKE_GATE_NOTE` instead.

Use the harness for gating and content alike: that scenarios register and fire, that a gate silences its line, and that the resolvers deliver the right *content* (a corner-name call that names no corner is a resolver reaching the wrong key, even though audio played).

## Presets

`presets/telemetry/*.json` and `presets/session/*.json`; the filename (minus `.json`) is the preset name. Applied via `/api/telemetry/preset` and `/api/session/preset`. Dropping a valid JSON file in is the whole of the registration — `loadPresets` scans the directory at boot and names the preset after the file. Malformed preset files are silently skipped at load (`src/server.ts`).

`session/race-oval.json` is `session/race.json` with an oval's `WeekendInfo` and nothing else changed — same 18-car roster, same `DriverCarIdx: 7`, same `PaceCarIdx: 0` — because the caution shortcuts' pace arrays are indexed for exactly that roster. What it unlocks is in the caution-shortcut section below. **Its `TrackID` deliberately differs from `race.json`'s**, which is not cosmetic: the translator caches resolved corner markers and track length under `${TrackID}|${SessionNum}`, so two presets sharing an id would leave a tester who switched between them holding the previous track's geometry while the harness claimed to be somewhere else. A session preset that clones another must change the id along with the name.

## Deleting a telemetry field (capability gates)

`/api/telemetry` merges **`body.patch`** into the current snapshot — `POST {"patch": {"dcPitSpeedLimiterToggle": null}}`, not the bare object, which is rejected with a 400 — and an explicit `null` there **deletes** that key rather than setting it (`mutateTelemetry`, issue #1051). An optional `"tick": true` ticks the translator once, synchronously, after the write (#1349), as `/api/readback/snapshot` always does; without it the translator sees the write on the mock's next timer tick, which the tester can slow to 5 s or pause. JSON has no `undefined`, and without the sentinel a patch could never make a field ABSENT — which is exactly what iRacing's capability fields mean: `hasPitLimiter`, `hasVisor` and `hasWipers` all read whether a `dc*` field EXISTS, not what it holds. No `TelemetryData` field takes null legitimately, so the sentinel is unambiguous.

So `{"dcPitSpeedLimiterToggle": null}` turns the mock car into one with no pit limiter, which is how the no-limiter pit-speed callouts are auditioned; the field ships present by default because most of the roster has a limiter. Before the sentinel existed, one of the two families was always unfireable and its shortcuts looked broken rather than correctly gated.

## Snapshot endpoints vs telemetry patch

Scenarios whose resolvers are harness-held (session-start, qualifying-invalidation, race-start) have dedicated `/api/<name>/snapshot` endpoints; shortcuts in `src/scenario-shortcuts.ts` may carry a snapshot inline, which the UI POSTs BEFORE publishing the trigger event so the resolver returns the intended snapshot at fire time. `/api/readback/snapshot` is different: production readback scenarios re-read live telemetry at fire time (issue #481), so it converts the composer snapshot into a telemetry PATCH via `snapshotToTelemetryPatch` (`src/pit-readback-telemetry.ts`), which mirrors the translator's `buildSnapshot()` field-for-field, then ticks once synchronously. Known limitation: `windshield.available` has no telemetry source (`buildSnapshot()` hardcodes it `true`), so the patch drops it.

The session-start composer has a second fire button, "Fire as Fresh Connect", publishing `session.changed { from: -1, to: 0 }` (the translator's mid-session connect shape) so the #871 on-track suppression is reproducible — apply a telemetry preset (`hot-lap` vs `in-garage`) before firing; the race-start equivalents are the two "Fresh connect" shortcuts in `src/scenario-shortcuts.ts`.

## Shortcuts that drive the translator (#1127)

Every shortcut used to publish one bus event, which injects **past** the translator — the whole reason a scenario is one click here. The cost is that such a button cannot audition a translator DECISION, only a callout's content: publishing `flag.yellow.cleared` speaks the line whatever the diff would have concluded. Since #1127 that event is emitted only for a yellow episode that stayed LOCAL (a full-course caution ends with a restart, which is announced already), and the thing a tester needs to hear is the SILENCE where the all-clear used to land — a question no published event can ask. The caution sequence itself moved onto its own `caution.*` events as the family grew (`caution.fieldCaught` for the pickup, `caution.oneLapToGreen`, `caution.lineup.changed`, `caution.extraLap`, `caution.restarted`) — `flag.yellow.raised {scope:"full"}` no longer speaks for the pickup and `startLight.start-go.raised` no longer speaks for a caution restart (the gantry line stands down for the whole episode so a restart is never told apart from a race start by ear), so a shortcut auditioning any of that has to drive telemetry through the real translator rather than publish an event by hand.

So `ScenarioShortcut` is a union: a `BusEventShortcut` carries `event` + `data` (plus the optional snapshots, the single `telemetryPatch`, and since #1211 an optional setup `telemetrySequence` the UI plays before publishing), and a `TelemetrySequenceShortcut` carries `telemetrySequence` — an ordered `{ patch, holdMs, tick? }` list the UI applies through `/api/telemetry`, posting each step itself as the body and holding between steps, with no `bus.publish` at all (it may carry a `qualifyingInvalidationSnapshot`, posted before the first step, since #1211). A union rather than one type with both fields optional, so a shortcut that drives NOTHING cannot be written: an event-less, sequence-less button renders fine and does nothing when pressed, which reads as a broken scenario rather than a broken shortcut. The UI disables a shortcut's button while it runs, since two overlapping sequences writing `SessionFlags` would leave neither the one described on either button. A step whose only job is to put state in front of the publish that follows sets `tick: true` rather than relying on its hold (#1349): a hold lets the timer tick only while the timer runs.

**A shortcut sets every field its behaviour depends on (#1349).** Mock state persists between presses, so a shortcut that relies on what the harness booted with is changed by whatever the previous button left. "Limiter off on pit road" is the case that made this a rule: after an overtake button left the car on track at 144 km/h, its pit-road patch became a pit-road entry at speed, and the translator added its own `limiter.missing` and a speeding episode to the line under audition. It now pins `IsOnTrack`, `PlayerTrackSurface` and `Speed` at the boot values in its own patch. `overtake-gate-shortcuts.test.ts` presses every shortcut on its own and again after an overtake button, with no session and with the `race` preset, and fails on any difference in what reaches the bus (`driver.firstOnTrack` aside, a one-shot no callout consumes). Pin the fields rather than restoring them after the publish: a delayed `where:` or re-check reads the state at fire time, which a restore would pull out from under it.

Three "Flags → Caution → …" shortcuts drive the family. `flag-caution-restart` is the reference: it replays the `SessionFlags` of a caution and restart captured at an oval (`local/telemetry-watch-20260917-191825-092.jsonl`), in order and with only the holds compressed to about 30 s: `CautionWaving`; static `Caution`; `+OneLapToGreen` (with the player's `LapDistPct` taken to 0.1 and then, one step later, to 0.4 — the one-to-green lap's 35% checkpoint, `caution.lastLapCheckpoint`, which the hot-lap preset's 0.42 would otherwise sit past for the whole run — and with per-car `CarIdxLapCompleted` / `CarIdxLapDistPct` patched in, because the position line speaks the RACE position through `getLivePosition()` and the canonical order ranks nobody without them; the last step deletes both again); `+GreenHeld`; the restart, `Green | Servicible | StartGo`, with every caution bit dropping on that same tick; `StartHidden` in place of `StartGo`; then no flag shown (`Servicible | StartHidden`). Its first step also patches `CarIdxPaceLine` / `CarIdxPaceRow` (a double-file lineup, illustrative rather than captured — the capture's own pace arrays are against a 21-car roster this harness doesn't share) and `PaceMode`, because every lineup script variable (`caution.followCarNumber`, `caution.restartPosition`, `caution.line`, …) reads the pace arrays through `getCautionLineup()`, which answers `null` outright without them — a `SessionFlags`-only replay would leave the follow-car lines nothing to say. The one caution variable that does NOT read them is `caution.racePosition`, the number the position line speaks: it reads `getLivePosition()`, which the shared wiring points at the real translator (left at its `() => null` default, the line would play silence for the wrong reason). The DRIVER ROSTER those lines resolve car numbers against comes from the race session preset, not from the sequence — its 18-car list is why the shortcut's `description` asks for that preset (or its oval twin, below) by name. With the race session and hot-lap presets applied it plays the caution-waving, follow, two-to-green, one-lap-to-green, position ("We're currently seven", at the checkpoint) and green-held lines — no green-flag line (a green that ends a caution episode is `caution.restarted`'s to announce, start bit or not — `diff/flags.ts` stands down for it), no "Go, go, go!" (the restart's own line owns that moment now), and no "Yellow cleared." `flag-caution-lineup-change` and `flag-caution-extra-lap` audition the two cases the oval capture never produced — the car ahead changing mid-caution, and a caution running past its default two laps — each with its own single-file pace lineup (simpler than the restart button's double-file one, since neither is auditioning the interleave) and the same one-to-go → checkpoint → restart tail so neither leaves the harness stuck under a flag. `scenario-shortcuts.test.ts` pins the restart shortcut's step values to the capture and the translator's events to that list, and drives the two follow-on shortcuts through the real translator too, asserting `caution.extraLap` and `caution.lineup.changed` (naming car 7) arrive where their descriptions promise. **The extra-lap button rests on a property of the hot-lap preset**: that preset carries no `CarIdxLapDistPct`, so the canonical order ranks nobody and `diff/caution.ts` counts crossings in the front of the pace lineup — line 0 row 1, index 1, the car the fixture advances. Give the telemetry preset per-car lap progress and the canonical order takes over, ranks by it, and the button's pinned test goes red until the fixture advances whichever car that order puts first. That is why the per-car lap progress every caution button patches for the position line lands at the ONE-TO-GO step and not at the throw — after one to go a crossing changes nothing — and is deleted again at the button's last step, so the next press of any caution button starts from the preset's premise; `scenario-shortcuts.test.ts` pins both halves, and asserts `getLivePosition()` ranks nobody before that step and the player 7th after it. Two things every caution sequence owes — it **ends by restoring a sane `SessionFlags`**, or the harness is left stuck under a flag and the button cannot be pressed again, and its `description` names the presets its promised lines need and says the mock SDK must be **CONNECTED**, because a disconnected translator sees no ticks and the button is then silent for the wrong reason. Hold times come off the translator's or the engine's own constants where one exists (`YELLOW_CLEARED_HOLD_MS`, `CAUTION_LINEUP_CHANGE_DELAY_MS`), so the wait stays provably past the window being listened through.

**The inside/outside lane wording needs the oval preset (`race-oval`), and only the restart button can produce it.** `resolveCautionLineup` answers a `line` only when the field is double file AND `isOvalTrack(sessionInfo)` — which reads `WeekendInfo.Category` first, as an enumeration, with a `TrackType` substring only as a fallback. Every session preset was a road course until #1127 (`race.json` is Tsukuba and carries no `Category` at all), so "take the inside line, behind..." could not be auditioned here however the pace arrays were arranged: the lineup resolved perfectly — follow car, restart position, double file — with `line: null`. `race-oval.json` is the same file with `Category: "Oval"`, `TrackType: "medium oval"`, `TrackDirection: "left"` and Homestead's name, the track the whole issue was captured at. Apply it instead of `race` and the restart button names the lane; apply `race` and every other line is identical. The other two buttons are SINGLE FILE, so they name no lane on either preset — that is not something the oval preset can change, and their descriptions say so rather than promising it. Pinned by `scenario-shortcuts.test.ts`, which drives the restart shortcut's own first step against both presets and asserts `"inside"` against one and `null` against the other, so a preset that quietly stopped reading as an oval fails rather than going quiet.

**A shortcut can refuse to run (#1127).** `ScenarioShortcutBase.requires` names preconditions (`src/shortcut-preconditions.ts`); `POST /api/shortcut/start` is the one call that means "a shortcut is starting", the UI makes it for EVERY shortcut before any setup push, sequence step or publish, and an unmet precondition comes back 409 with the rule's reason, which the UI shows in an alert and then runs nothing. The three caution shortcuts declare `player-car-index` — session info naming the player's car, mirroring `resolvePlayerCarIdx` in `diff/caution-lineup.ts`. The 13 overtake and gap shortcuts declare `sdk-connected` (#1349) through `atRacingSpeed`: the harness boots disconnected, and their gate reads telemetry a disconnected translator never receives, so a press then is refused with the reason (connect with the header's Connected toggle) rather than going silent. The rules read the live state the route hands them, `{ sessionInfo, isConnected }`, on every start. Without it the run is HALF silent: the flag-driven lines play (the caution's speak gate is flag-only) while every lineup-driven line is dropped, leaving nothing on screen and one `optional clause skipped — var {{caution.followCarNumber}} resolved to nothing` in a debug log — which teaches a tester to distrust the callouts rather than the setup. Two things it deliberately does not do: it does not apply a preset for the tester (the session state is theirs, and overwriting it is a worse surprise than a refusal), and it does not check for the oval preset (the lane is an enrichment, not a prerequisite — refusing would block the road-course case the sequence is meant to support). The check is necessary, not sufficient: `practice.json` names a player car with an empty driver list, passes, and still resolves fewer lines than the description promises. Every other shortcut declares nothing.

For any of the three to actually SPEAK, `registerPitCrew`'s `getCautionLineup`, `getCautionPhase`, `getUnderFullCourseCaution` and `getCautionEpisode` must reach the real translator's `getCautionLineup()` / `getCautionPhase()` / `isUnderFullCourseCaution()` / `getCautionEpisode()`. `@iracedeck/race-engineer-wiring`'s `buildPitCrewDeps` wires them for the plugins and, through the same `wireRaceEngineer` call, for the harness. Without them the family's `speakGate` (`getCautionPhase`, checked at speak time) never admits a single caution line, the follow / two-to-green / pace-car-off calls never find the stage they speak at, the `getCautionLineup: () => null` default leaves every follow-car variable with nothing to read, and the `getCautionEpisode: () => null` default leaves the lineup-change call nothing to judge a change against, so it never speaks (#1286); the three buttons would look wired but play nothing at all. A dependency missing from the harness's old hand-written list made a call silent for the wrong reason twice; `buildPitCrewDeps` must build every `PitCrewDeps` key (`Required<PitCrewDeps>`), so a new key now reaches the harness without an edit here.

**"Tire Wear → Stop replayed from a capture" (#1108)** is the fourth sequence and the first outside the caution family. It replays stop 1 of `local/telemetry-watch-20260919-193233-855.jsonl` — on the circuit, the approach, pit road, the stall surface on the tick the twelve `<corner>wear<L|M|R>` readings refresh, in the box, out, off pit road — because the report's decision is the translator's: a stop counts only when the car drove into its box, and the report is published behind the exit readback, 4.5 s after leaving pit road. It sets up everything it needs from the harness's boot state (no preset, no `requires`), resets the readings to 1 first so a second press refreshes them again, keeps the limiter on between the cones so the limiter family stays quiet, and holds its LAST step past the settle window so the page-wide shortcut lock covers it — another button rewriting `OnPitRoad` inside that window would cancel the report. The hold is computed from `PIT_READBACK_EXIT_DELAY_MS`, imported from `sim-events-iracing`, so it follows the translator's window; `scenario-shortcuts.test.ts` drives the real translator through the sequence and asserts the report arrives right behind the exit readback.
**"Pit Service → Autofuel takeover (replay)" is the fourth telemetry sequence (#474)**, and the one outside the caution family. It replays `local/telemetry-watch-20260919-193233-855.jsonl`: a fuel press on track with `dpFuelAutoFillActive` 0, the pit approach (`PlayerTrackSurface` 2) alone, then the takeover in one step (`PitSvFlags`, `dpFuelFill`, `dpFuelAddKg` and `PitSvFuel` to 0 and `dpFuelAutoFillActive` to 1, the values the sim wrote on one tick), and it holds `dpFuelAutoFillEnabled` at 1 throughout as the capture did. That last tick is ONE `pitService.autoFuelSwitched { on: true, refuel: false }`, the fuel flip folded in — what it auditions is the translator's reading of it, which the four "Autofuel ON / OFF …" event buttons step over: the press confirmed with an acknowledgment, the entry readback, then the bare "Auto fuel is on. We're not refueling at the next pit stop." The holds carry two constraints the tests pin: the takeover outlasts the translator's 300 ms fuel debounce with autofuel still armed (a shorter one settles the flip as a press), and the approach is held alone for a few ticks, so the readback is expanded before the fuel bit clears, as it was in the sim. The whole run also outlasts `PIT_APPROACH_COOLDOWN_MS`, so a second press replays the readback too.

**Its own bookkeeping runs inside a REPLAY-MODE bracket, and that is load-bearing rather than tidiness — a telemetry sequence that has to ARRANGE state, rather than only drive it, wants the same one.** Every run has to put the car on track off pit road with autofuel off and nothing queued, or the arming it replays is no change at all and a second press plays nothing. Each of those resets is an edge some diff announces: since #474 disarming autofuel is itself an autofuel switch ("Auto fuel is off. We're not refueling…"), and `OnPitRoad` going false from a pit-road preset is `pitLane.exited` — which sets the 4.5 s pit-action cooldown that then swallows the press confirmation, and schedules a "to confirm" recap that lands mid-run. Neither line was in the captured moment. `handleTick` suppresses every semantic event while `IsReplayPlaying` is true and calls `wipeStateForReplay` on both edges, so each diff re-seeds from the snapshot the bracket leaves behind: the first and second-to-last steps carry `IsReplayPlaying: true` and do the arranging there, and the run is live for everything between. That is also what makes the button preset-proof — the wipe rebuilds state from `createInitialState()`, so a pit-action cooldown the tester's previous button left running is cleared rather than inherited. The one thing the bracket does NOT swallow is `publishActiveStateTeardown`: entering replay closes an active radar alert or pit-speeding cue, which is the translator being right (a cue left looping would run over the run), and from the pit-road preset — parked over the limit — that is a real `pitSpeeding.ended` the test expects. `scenario-shortcuts.test.ts` drives the button through the real translator recording EVERY event in the catalog — not a chosen few, so a line the bracket let slip cannot hide — and asserts exactly four events from four different presets and twice over from one; its controls are that a teardown moved outside the bracket adds a fifth, and that the same takeover with autofuel left disarmed comes out as the driver clearing fuel.

**Three "Incidents" sequences audition the incident and damage lines waiting for a held Voice bus (#1211).** A bus-event incident button steps over what #1211 changed: the translator holding `damage.repairNeeded.raised` behind an open incident burst, and the engine parking both lines under the spotter's focus floor and draining them in order. "Collision during a spotter call" puts a car on the left (`CarLeftRight`, which `diff/radar.ts` reads, so the spotter calls it and holds its floor), then the collision-car report byte, then `PlayerCarMyIncidentCount` +4 with the repair bits on the same tick, holds the car alongside past the burst's quiet window, the damage debounce and its grace, then clears it — expect "Car left", "Clear.", the collision-car line, the damage line. "Collision during a spotter call (qualifying)" is the same telemetry with a flying-lap `qualifyingInvalidationSnapshot` posted first (`lapCompleted` 8, which no Qualifying Invalidation button uses, so their per-lap latch does not silence it; its own second press is latched and plays the incident line instead) — expect the lap-invalidation line after "Clear.", then the damage line, and no incident line. "Escalation while another line plays" replays the issue's 14:54 log: an off-track +1, the repair bits 0.1 s later, a collision-world byte and +1 four seconds after the first increment — expect the off-track line, the wall line with two points, then the damage line, which the translator publishes on the escalation's flush tick. The two race sequences post a race snapshot so a qualifying snapshot an earlier button left cannot take the burst. All three open with the autofuel button's replay-mode bracket (on track, count 0, no damage, no car alongside), so a second press starts clean: without it the first press's raised damage baseline would swallow the next rising edge. The holds read `DAMAGE_DEBOUNCE_MS` and `DAMAGE_INCIDENT_GRACE_MS` from `@iracedeck/sim-events-iracing`, and `scenario-shortcuts.test.ts` drives the real translator through the three and asserts the events, their order and (for the escalation) the damage on the same tick as the second `incident.occurred`, so a translator window outgrowing a hold turns the test red. "Damage Detected" stays a bus-event button, but the damage line's `speakGate` (#1288) now asks the translator's settled damage state (`isDamageRepairNeeded()`), so the button sets the repair bits first inside the same bracket — seeded as known damage, since set live they would be a rising edge the translator announces a second time five seconds later. A fourth, "Crash into a full-course caution" (#1185), puts the pace car in the pits and clears the flags inside its own replay-mode bracket, then drives the collision-car crash (+4, repair bits) followed within 2.5 s by caution waving with a single-file pace lineup, the car ahead changing and the pace car reaching the track (`CarIdxTrackSurface`, whose baseline the hot-lap preset lacks), and holds 20 s — it needs the race session preset (`requires: ["player-car-index"]`) and auditions the bounded pending queue ordering the caution lines against the incident and damage lines.

## API surface

HTTP for writes, WebSocket (`/ws`) for the live stream of `event` / `state` / `audio` messages. Routes (`src/server.ts`): `/api/state` (full snapshot incl. event templates, shortcuts, preset names), `/api/connection`, `/api/tick` + `/api/tick/once`, `/api/telemetry` (+`/preset`; `tick: true` ticks the translator once after the write), `/api/session` (+`/preset`), `/api/settings`, `/api/audio/device|refresh|wipe-cache`, the snapshot endpoints above, `/api/shortcut/start` (the precondition gate — 204 to proceed, 409 with the reason to refuse), and `/api/bus/publish` (raw event injection, name-checked against the catalog).

## UI

Static files in `ui/` (`index.html` / `app.js` / `styles.css`), no build step, served by `@fastify/static`.

## Maintenance hooks

- New bus event → add a template to `src/event-names.ts`; the compile-time completeness check at the bottom of that file fails `pnpm build` if the list drifts from `SimEventMap` in either direction.
- New callout → add a one-click shortcut to `src/scenario-shortcuts.ts` (per the checklist in `.claude/rules/race-engineer-callouts.md`).
