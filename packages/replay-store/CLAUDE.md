# @iracedeck/replay-store

The per-session replay store (#1162, #1203, #1354, #1426), moved out of `deck-core` in #1367 (spec #1351, `docs/superpowers/specs/2026-10-07-issue-1351-deck-core-split-and-sim-seam.md`): the replay markers, the lap record, the greens, the session starts and the incidents, one section each in one file per `SubSessionID` under `%LOCALAPPDATA%\iRaceDeck\Replay\<ecosystem>`, written debounced and atomically. It depends on `@iracedeck/settings` (the path helpers `resolveLocalAppData`, `nonBlank` and `settingsStoreFolderName`, and the settings store's `WRITE_RETRY_DELAYS_MS` schedule) and `@iracedeck/logger`, and on nothing sim-shaped: the store knows files, never telemetry, and deck-core's sim-boundary lint rule covers this package too (#1367). Four packages depend on it: `deck-iracing` (the replay-session subscriber, which takes the store and its `ReplaySessionHeader` type), `replay-engine` (#1467: Jump to Fastest Lap's and Jump to Race Start's lookups, the lap walk, which records the lap start it finds, and the record step and the incident comparison, which read the store the action hands them), `iracing-actions` (Replay Markers, Replay Control's Next / Previous Lap and Session and its incident comparison, which hand the store to the engine, and the dial's lap readout) and `plugin-runtime` (the replay phase creates and initialises it, wires its exit flush and feeds it the record events; `src/types.ts` names `ReplaySessionStore`).

## What reaches it, and from where

The store is fed from two directions. `deck-iracing`'s replay-session subscriber, which `plugin-runtime`'s `startServices` puts on the SDK controller, reads `WeekendInfo` and calls `setActiveSession` / `clearActiveSession`. What a session records comes over the bus, one recorder diff in `sim-events-iracing` per section: the replay-laps diff publishes `replay.lapStarted` / `replay.lapTimed`, the replay-greens diff `replay.greenFlag` (#1354), and the replay-sessions and replay-incidents diffs `replay.sessionStarted` and `replay.incident` (#1426), and `initReplay` subscribes to each and hands it to its section's API (`laps.recordLapStart` / `laps.recordLapTime`, `greens.record`, `sessions.record`, `incidents.record`). A further recorded section follows the same path: a pre-guard diff behind the recorders' shared gate (`diff/replay-record-gate.ts`), a `replay.*` event, one subscription, one section module here. The actions and the replay engine read the store synchronously through `getReplaySessionStore()`.

One file outside the package reaches a source by relative path rather than through the barrel: `iracing-actions`' `replay-markers-dial-surface.test.ts` loads `src/replay-markers.ts` with `vi.importActual` past its own mock of the barrel, so its fake store answers add / delete exactly as the real one does (the module has no imports); Next / Previous are the shared walk over `list()` since #1426. A rename or move of `replay-markers.ts` breaks it.

## Module map

- `replay-session-file.ts` — the file: `resolveReplayStoreDirectory({ platform, env })` (`%LOCALAPPDATA%\iRaceDeck\Replay\<ecosystem>`, the ecosystem folder from `@iracedeck/settings`' `settingsStoreFolderName` — per ecosystem because two deck hosts run two plugin processes that would otherwise rename their copies over each other every debounce; `IRACEDECK_REPLAY_DIR` replaces the `Replay` base and the ecosystem folder is still appended), `replaySessionFileName`, `parseReplaySessionFile` and the envelope type (`version`, `subSessionId`, `track`, `series`, `sessionStart`, `sections`). `REPLAY_FILE_FRAME_LAG` (59) records the measured `.rpy` lag and is deliberately not applied.
- `replay-markers.ts` — the pure marker logic: `addMarker` with the 60-frame dedupe, `deleteNearestMarker` within 600 frames, `nextMarker` past 60 ahead, `previousMarker` past 120 behind (the windows are the exported `MARKER_*_FRAMES` constants), `normalizeMarkers`, and `partitionMarkers`, which keeps a `markers` entry that is not a marker aside so it is re-emitted after the markers on every write.
- `replay-laps.ts` — the pure lap-record logic: `recordLapStartInSection` / `recordLapTimeInSection` (a time arriving before its start is held in memory and paired when the start comes), `findLapStartInSection` → `LapStartLookup`, `listLapStartsInSection` → `LapStartListing` (#1426: one car's lap starts across every session, frame-ordered and raw, each a `LapStartListEntry` `{ frame, lap, sessionNum, sessionUniqueId }` so Replay Control can tell laps that follow each other in the record from a gap — a stint in the garage — and fall back to iRacing's search there; starts within `MARKER_DEDUPE_FRAMES` of each other kept once as the earliest, with that entry's lap and session, so a lap two recorded sessions both hold is one step; a session whose record for the index carries another `carNumberRaw` contributes nothing; misses `no car` when no session holds the index, `car mismatch` when every one that does holds another car), `mergeLapsSectionInto`, `normalizeLapsSection`, `isNewerLapsSection` and `LAPS_SECTION_VERSION`. Which session a start joins and which one a lookup reads is the rule on `recordLapStartInSection`: a start with no pair match joins the one session with that `sessionNum` when its frame lies within the span of that session's recorded lap starts (the walk recording under a saved replay's own pair), else opens a new session (a restart's laps fall past the old span); a lookup whose pair-matched session lacks the car or the lap reads the one other session with the `sessionNum` that has both, `matchedBy: "sessionNum"`.
- `replay-greens.ts` — the pure green-record logic (#1354): `recordGreenInSection` (returns whether the section changed), `findGreenInSection` → `GreenLookup`, `mergeGreensSectionInto`, `normalizeGreensSection`, `isNewerGreensSection` and `GREENS_SECTION_VERSION`. A session is the exact `(sessionNum, sessionUniqueId)` pair, with no join-by-frame rule, since nothing records a green from inside a replay. Entries (`kind`, `frame`, `sessionTimeMs`) stay in frame order. A session holds one `start` and the latest replaces it (a re-grid's green is the real start); a `restart` within `MARKER_DEDUPE_FRAMES` of another restart is not added; an entry of a kind this build does not know is kept where it is, never de-duplicated against and never returned. A `start` lookup that names an instance (a `sessionUniqueId`, from a press made inside a race) is answered from that instance only: a session recorded under the pair either has a start or the lookup misses with `no green`, never another pass's start, and when no session is recorded under the pair the one other session with that `sessionNum` that has a start is taken (the lap record's rule, for a file whose unique ids did not survive the save), with several a miss, `no session`. A lookup that names none (a press from practice or qualifying) takes the session with that `sessionNum` whose start has the highest frame, the latest instance in the recording. Both fallbacks answer `matchedBy: "sessionNum"`, and a hit carries the matched session's `sessionUniqueId`, which the action logs. In the offline record (`SubSessionID` 0) the store asks for exact ids (`exactInstance`, for `findGreenInSection` and `findLapStartInSection` alike): that record lives within one sim run, so its unique ids are the ones a query carries, a session instance it does not hold is a pass of a restarted AI event whose green or lap was not seen, and a named instance is never answered from another. A record with a file behind it keeps the fallbacks, because a later sim run numbers the replay's sessions afresh.
- `replay-sessions.ts` — the pure session-start logic (#1426): `recordSessionStartInSection` (returns whether the section changed), `listSessionStartsInSection` (frame-ordered copies), `mergeSessionsSectionInto`, `normalizeSessionsSection`, `isNewerSessionsSection` and `SESSIONS_SECTION_VERSION`. The section is `{ version, sessions: [{ sessionNum, sessionUniqueId, frame }] }`: one entry per `(sessionNum, sessionUniqueId)` pair in frame order, and the first start recorded for a pair stays — a second record for it changes nothing. A restarted offline event's second instance of a `sessionNum` comes under a new unique id and is a new entry further along the tape; nothing looks a session up by its number.
- `replay-incidents.ts` — the pure incident logic (#1426): `recordIncidentInSection`, `listIncidentsInSection` (every session's entries flattened, each with its `sessionNum` / `sessionUniqueId`, frame-ordered copies), `mergeIncidentsSectionInto`, `normalizeIncidentsSection`, `isNewerIncidentsSection`, `INCIDENTS_SECTION_VERSION` and `INCIDENT_FOLD_FRAMES` (600, #1122's ten-second sequence gap). Per exact `(sessionNum, sessionUniqueId)` pair like the greens; an entry is `{ carIdx, carNumberRaw, frame, sessionTimeMs, delta, source }`, `source` being `telemetry` (the driver's own counter) or `sessionInfo` (another car's count in the session YAML), a plain string so a newer build's source is kept. A rise at most `INCIDENT_FOLD_FRAMES` after the same car's last entry in the session (same `carIdx` and `carNumberRaw`) adds its `delta` to that entry, which keeps its first frame, time and source; the window counts from the entry's frame, so one entry never spans more than ten seconds. The merge treats a source entry of the same car within the window of a target entry, either way, as the same incident and keeps the target's. Nothing reads the section for a jump yet.
- `replay-session-store.ts` — the store: `createReplaySessionStore` and the singleton trio `initializeReplaySessionStore` / `getReplaySessionStore` / `isReplaySessionStoreInitialized` (`_resetReplaySessionStore` for tests). Described below.

The pure section logic is exported for tests and the harness.

## The store

The only owner of `%LOCALAPPDATA%\iRaceDeck\Replay\<ecosystem>\session_<SubSessionID>.json`. On init it removes stale `session_*.json.<pid>[.sync].tmp` files a crash left, and nothing else. Every plugin wires `process.on("exit", () => store.flushSync())` as the settings store does (`plugin-runtime`'s `initReplay`, #1467). The file's sections are owned by features — this build reads `markers`, `laps`, `greens`, `sessions` and `incidents` (`REPLAY_MARKERS_SECTION`, `REPLAY_LAPS_SECTION`, `REPLAY_GREENS_SECTION`, `REPLAY_SESSIONS_SECTION`, `REPLAY_INCIDENTS_SECTION`), and **every other key is preserved on every write**. A section is materialised on its first write, so a file keeps exactly the sections something was recorded into. Each section's code in the store is its own and parallel to the others': a pair of `ActiveRecord` fields (the section and its newer-format flag), a branch in `recordOf`, `serialize` and `tryReload`, a once-warning, and its API object; a new section adds those beside the existing ones and changes none of them.

Same write discipline as `@iracedeck/settings`' `settings-store.ts` (atomic temp+rename; a trailing debounce `REPLAY_STORE_WRITE_DEBOUNCE_MS` 2 s capped by `REPLAY_STORE_WRITE_MAX_WAIT_MS` 10 s from the first unsaved change, so a field that never goes quiet still lands; a failed write goes back to pending — the active record itself IS the pending payload, so a retry writes whatever the record holds by then and never an older snapshot over a newer landed write, and a failed write for a session that has since changed is retried per path — on `WRITE_RETRY_DELAYS_MS` and kept for the shutdown flush; a corrupt file moved aside as `session_<id>.corrupt-<iso>.json`, the copy fallback skipping an identical aside so a locked file is preserved once and not once per open; compact JSON, because a race's record reaches megabytes and is rewritten every few seconds), with two differences: the load is SYNCHRONOUS (`setActiveSession` reads the file in the same tick the session appears, so the actions never see a loading state) and the pending write is flushed immediately on session change and disconnect.

- **Offline and unreadable sessions.** `SubSessionID` 0 (offline) is an in-memory record that is never written and is dropped on disconnect or the next session key. A session whose file could not be READ (a lock, a permission) opens in memory too, write-inhibited, and the read is retried on the same `WRITE_RETRY_DELAYS_MS` schedule (option `loadRetryDelaysMs`), then on a same-id `setActiveSession`, on the record's drop and in `flushSync`; once readable, the in-memory record is merged INTO the file — markers as a union under the dedupe rule, laps by `mergeLapsSectionInto` (the file's entry stays where both have one; a null `timeMs` is filled), greens by `mergeGreensSectionInto` (the file's `start` stays where both have one; restarts are a union under their dedupe rule), session starts and incidents by `mergeSessionsSectionInto` / `mergeIncidentsSectionInto` (the file's entry stays where both have one) — and written normally. A corrupt file that could not be preserved stays write-inhibited for the connection, because the next write would otherwise rename a near-empty record over bytes the store never saw — fail closed, as the settings store does for a corrupt file it cannot move.
- **Forward compatibility.** Every envelope field and every field on a marker, lap entry, car record, laps session, green entry, greens session, session start, incident or incidents session that this build does not read is carried through a write (index signatures on the types); a `markers` entry that is not a marker is kept aside and re-emitted (`partitionMarkers`); a green entry of an unknown `kind` is kept as it came; and a versioned section whose `version` is above this build's (`isNewerLapsSection` against `LAPS_SECTION_VERSION`, `isNewerGreensSection` against `GREENS_SECTION_VERSION`, `isNewerSessionsSection` against `SESSIONS_SECTION_VERSION`, `isNewerIncidentsSection` against `INCIDENTS_SECTION_VERSION`) is a section this build has no reader for — carried through verbatim, its record calls return false with one warning, and its lookup or list misses with `newer format`. The envelope's `REPLAY_FILE_VERSION` did not move for `laps`, `greens`, `sessions` or `incidents`: a new section is additive, and an older build carries it through like any key it does not read.
- **One API per section.** `greens` (`record`, true when the record holds that green whether stored now or already there, and scheduling a write only when something changed; `findGreen` → `GreenLookup`, a miss whose `reason` is `no file` / `no session` / `no green` / `newer format`: `no green` is a record with no `greens` section — every replay recorded before #1354 — or a session without a start, and `no file` a record that was not loaded from disk and holds neither laps nor greens). `markers` (`add`, `deleteNearest`, `next`, `previous`, `list`, under the windows above; `list()` returns a copy) and `laps` (`recordLapStart` / `recordLapTime`, and `findLapStart` → `LapStartLookup`, a hit with `matchedBy: "pair" | "sessionNum"` or a miss whose `reason` is the phrase the action logs: `no file` / `no session` / `no car` / `car mismatch` / `lap not recorded` / `newer format`; and `listLapStarts({ carIdx, carNumberRaw })` → `LapStartListing` (#1426), the car's raw lap starts, each with its lap number and session, across every session for Next / Previous Lap, whose misses are `findLapStart`'s `no file` / `no car` / `car mismatch` / `newer format` decided the same way — the caller subtracts its own approach). `sessions` (#1426: `record`, true when the record holds a start for the pair, whether stored now or already there, writing only when something changed; `list(scope?)` → `SessionStartListing`, the frame-ordered starts or a miss `no file` / `newer format`) and `incidents` (#1426: `record`, folding as above; `list(scope?)` → `IncidentListing`, likewise). For both list readers `no file` is a record that was neither loaded from disk nor recorded into by any recorder (laps, greens, session starts, incidents; a marker does not count); a record that is either but holds none of that section's entries is a hit with an empty list. `findLapStart`, `listLapStarts` and `findGreen` keep their older rules, so a record holding only a session start or only incidents still answers `no file` to them: nothing of theirs was recorded. A laps, greens, sessions or incidents call carrying a `subSessionId` other than the active record's is ignored (`SubSessionScoped`), and every markers call takes the same scope as an optional second argument. `findLapStart` answers `no file` when the record was neither loaded from disk nor written to — the plugin was not running for that session — and `no session` only for a record that exists without a matching session.

## One import path per name

The barrel `src/index.ts` is the package's only entry, and deck-core re-exports none of it: import every name it exports from `@iracedeck/replay-store`, and mock that package in a test that stubs one (the Replay Markers and Replay Control tests and the replay engine's lap-press tests do; `plugin-runtime`'s replay-phase and order tests mock it through `recordedModule`).
