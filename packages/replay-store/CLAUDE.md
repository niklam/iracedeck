# @iracedeck/replay-store

The per-session replay store (#1162, #1203, #1354), moved out of `deck-core` in #1367 (spec #1351, `docs/superpowers/specs/2026-10-07-issue-1351-deck-core-split-and-sim-seam.md`): the replay markers, the lap record and the greens, one section each in one file per `SubSessionID` under `%LOCALAPPDATA%\iRaceDeck\Replay\<ecosystem>`, written debounced and atomically. It depends on `@iracedeck/settings` (the path helpers `resolveLocalAppData`, `nonBlank` and `settingsStoreFolderName`, and the settings store's `WRITE_RETRY_DELAYS_MS` schedule) and `@iracedeck/logger`, and on nothing sim-shaped: the store knows files, never telemetry, and deck-core's sim-boundary lint rule covers this package too (#1367). Three packages depend on it: `deck-iracing` (the replay-session subscriber, which takes the store and its `ReplaySessionHeader` type), `iracing-actions` (Replay Markers, and Replay Control's Jump to Fastest Lap and Jump to Green Flag) and `plugin-runtime` (the settings phase creates and initialises it, wires its exit flush and feeds it the record events; `src/types.ts` names `ReplaySessionStore`).

## What reaches it, and from where

The store is fed from two directions. `deck-iracing`'s replay-session subscriber, which `plugin-runtime`'s `startServices` puts on the SDK controller, reads `WeekendInfo` and calls `setActiveSession` / `clearActiveSession`. What a session records comes over the bus, one recorder diff in `sim-events-iracing` per section: the replay-laps diff publishes `replay.lapStarted` / `replay.lapTimed` and the replay-greens diff publishes `replay.greenFlag` (#1354), and `initSettings` subscribes to each and hands it to its section's API (`laps.recordLapStart` / `laps.recordLapTime`, `greens.record`). A further recorded section follows the same path: a pre-guard diff behind the recorders' shared gate (`diff/replay-record-gate.ts`), a `replay.*` event, one subscription, one section module here. The actions read the store synchronously through `getReplaySessionStore()`.

One file outside the package reaches a source by relative path rather than through the barrel: `iracing-actions`' `replay-markers-dial-surface.test.ts` loads `src/replay-markers.ts` with `vi.importActual` past its own mock of the barrel, so its fake store answers next / previous / add / delete exactly as the real one does (the module has no imports). A rename or move of `replay-markers.ts` breaks it.

## Module map

- `replay-session-file.ts` — the file: `resolveReplayStoreDirectory({ platform, env })` (`%LOCALAPPDATA%\iRaceDeck\Replay\<ecosystem>`, the ecosystem folder from `@iracedeck/settings`' `settingsStoreFolderName` — per ecosystem because two deck hosts run two plugin processes that would otherwise rename their copies over each other every debounce; `IRACEDECK_REPLAY_DIR` replaces the `Replay` base and the ecosystem folder is still appended), `replaySessionFileName`, `parseReplaySessionFile` and the envelope type (`version`, `subSessionId`, `track`, `series`, `sessionStart`, `sections`). `REPLAY_FILE_FRAME_LAG` (59) records the measured `.rpy` lag and is deliberately not applied.
- `replay-markers.ts` — the pure marker logic: `addMarker` with the 60-frame dedupe, `deleteNearestMarker` within 600 frames, `nextMarker` past 60 ahead, `previousMarker` past 120 behind (the windows are the exported `MARKER_*_FRAMES` constants), `normalizeMarkers`, and `partitionMarkers`, which keeps a `markers` entry that is not a marker aside so it is re-emitted after the markers on every write.
- `replay-laps.ts` — the pure lap-record logic: `recordLapStartInSection` / `recordLapTimeInSection` (a time arriving before its start is held in memory and paired when the start comes), `findLapStartInSection` → `LapStartLookup`, `mergeLapsSectionInto`, `normalizeLapsSection`, `isNewerLapsSection` and `LAPS_SECTION_VERSION`. Which session a start joins and which one a lookup reads is the rule on `recordLapStartInSection`: a start with no pair match joins the one session with that `sessionNum` when its frame lies within the span of that session's recorded lap starts (the walk recording under a saved replay's own pair), else opens a new session (a restart's laps fall past the old span); a lookup whose pair-matched session lacks the car or the lap reads the one other session with the `sessionNum` that has both, `matchedBy: "sessionNum"`.
- `replay-greens.ts` — the pure green-record logic (#1354): `recordGreenInSection` (returns whether the section changed), `findGreenInSection` → `GreenLookup`, `mergeGreensSectionInto`, `normalizeGreensSection`, `isNewerGreensSection` and `GREENS_SECTION_VERSION`. A session is the exact `(sessionNum, sessionUniqueId)` pair, with no join-by-frame rule, since nothing records a green from inside a replay. Entries (`kind`, `frame`, `sessionTimeMs`) stay in frame order. A session holds one `start` and the latest replaces it (a re-grid's green is the real start); a `restart` within `MARKER_DEDUPE_FRAMES` of another restart is not added; an entry of a kind this build does not know is kept where it is, never de-duplicated against and never returned. A `start` lookup that names an instance (a `sessionUniqueId`, from a press made inside a race) is answered from that instance only: a session recorded under the pair either has a start or the lookup misses with `no green`, never another pass's start, and when no session is recorded under the pair the one other session with that `sessionNum` that has a start is taken (the lap record's rule, for a file whose unique ids did not survive the save), with several a miss, `no session`. A lookup that names none (a press from practice or qualifying) takes the session with that `sessionNum` whose start has the highest frame, the latest instance in the recording. Both fallbacks answer `matchedBy: "sessionNum"`, and a hit carries the matched session's `sessionUniqueId`, which the action logs. In the offline record (`SubSessionID` 0) the store asks for exact ids (`exactInstance`, for `findGreenInSection` and `findLapStartInSection` alike): that record lives within one sim run, so its unique ids are the ones a query carries, a session instance it does not hold is a pass of a restarted AI event whose green or lap was not seen, and a named instance is never answered from another. A record with a file behind it keeps the fallbacks, because a later sim run numbers the replay's sessions afresh.
- `replay-session-store.ts` — the store: `createReplaySessionStore` and the singleton trio `initializeReplaySessionStore` / `getReplaySessionStore` / `isReplaySessionStoreInitialized` (`_resetReplaySessionStore` for tests). Described below.

The pure section logic is exported for tests and the harness.

## The store

The only owner of `%LOCALAPPDATA%\iRaceDeck\Replay\<ecosystem>\session_<SubSessionID>.json`. On init it removes stale `session_*.json.<pid>[.sync].tmp` files a crash left, and nothing else. Every plugin wires `process.on("exit", () => store.flushSync())` beside the settings store's (`plugin-runtime`'s `initSettings`). The file's sections are owned by features — this build reads `markers`, `laps` and `greens` (`REPLAY_MARKERS_SECTION`, `REPLAY_LAPS_SECTION`, `REPLAY_GREENS_SECTION`), and **every other key is preserved on every write**. A section is materialised on its first write, so a file keeps exactly the sections something was recorded into. Each section's code in the store is its own and parallel to the others': a pair of `ActiveRecord` fields (the section and its newer-format flag), a branch in `recordOf`, `serialize` and `tryReload`, a once-warning, and its API object; a new section adds those beside the existing ones and changes none of them.

Same write discipline as `@iracedeck/settings`' `settings-store.ts` (atomic temp+rename; a trailing debounce `REPLAY_STORE_WRITE_DEBOUNCE_MS` 2 s capped by `REPLAY_STORE_WRITE_MAX_WAIT_MS` 10 s from the first unsaved change, so a field that never goes quiet still lands; a failed write goes back to pending — the active record itself IS the pending payload, so a retry writes whatever the record holds by then and never an older snapshot over a newer landed write, and a failed write for a session that has since changed is retried per path — on `WRITE_RETRY_DELAYS_MS` and kept for the shutdown flush; a corrupt file moved aside as `session_<id>.corrupt-<iso>.json`, the copy fallback skipping an identical aside so a locked file is preserved once and not once per open; compact JSON, because a race's record reaches megabytes and is rewritten every few seconds), with two differences: the load is SYNCHRONOUS (`setActiveSession` reads the file in the same tick the session appears, so the actions never see a loading state) and the pending write is flushed immediately on session change and disconnect.

- **Offline and unreadable sessions.** `SubSessionID` 0 (offline) is an in-memory record that is never written and is dropped on disconnect or the next session key. A session whose file could not be READ (a lock, a permission) opens in memory too, write-inhibited, and the read is retried on the same `WRITE_RETRY_DELAYS_MS` schedule (option `loadRetryDelaysMs`), then on a same-id `setActiveSession`, on the record's drop and in `flushSync`; once readable, the in-memory record is merged INTO the file — markers as a union under the dedupe rule, laps by `mergeLapsSectionInto` (the file's entry stays where both have one; a null `timeMs` is filled), greens by `mergeGreensSectionInto` (the file's `start` stays where both have one; restarts are a union under their dedupe rule) — and written normally. A corrupt file that could not be preserved stays write-inhibited for the connection, because the next write would otherwise rename a near-empty record over bytes the store never saw — fail closed, as the settings store does for a corrupt file it cannot move.
- **Forward compatibility.** Every envelope field and every field on a marker, lap entry, car record, laps session, green entry or greens session that this build does not read is carried through a write (index signatures on the types); a `markers` entry that is not a marker is kept aside and re-emitted (`partitionMarkers`); a green entry of an unknown `kind` is kept as it came; and a versioned section whose `version` is above this build's (`isNewerLapsSection` against `LAPS_SECTION_VERSION`, `isNewerGreensSection` against `GREENS_SECTION_VERSION`) is a section this build has no reader for — carried through verbatim, its record calls return false with one warning, and its lookup misses with `newer format`. The envelope's `REPLAY_FILE_VERSION` did not move for `laps` or for `greens`: a new section is additive, and an older build carries it through like any key it does not read.
- **One API per section.** `greens` (`record`, true when the record holds that green whether stored now or already there, and scheduling a write only when something changed; `findGreen` → `GreenLookup`, a miss whose `reason` is `no file` / `no session` / `no green` / `newer format`: `no green` is a record with no `greens` section — every replay recorded before #1354 — or a session without a start, and `no file` a record that was not loaded from disk and holds neither laps nor greens). `markers` (`add`, `deleteNearest`, `next`, `previous`, `list`, under the windows above; `list()` returns a copy) and `laps` (`recordLapStart` / `recordLapTime`, and `findLapStart` → `LapStartLookup`, a hit with `matchedBy: "pair" | "sessionNum"` or a miss whose `reason` is the phrase the action logs: `no file` / `no session` / `no car` / `car mismatch` / `lap not recorded` / `newer format`). A laps or greens call carrying a `subSessionId` other than the active record's is ignored (`SubSessionScoped`), and every markers call takes the same scope as an optional second argument. `findLapStart` answers `no file` when the record was neither loaded from disk nor written to — the plugin was not running for that session — and `no session` only for a record that exists without a matching session.

## One import path per name

The barrel `src/index.ts` is the package's only entry, and deck-core re-exports none of it: import every name it exports from `@iracedeck/replay-store`, and mock that package in a test that stubs one (the Replay Markers and Replay Control tests do; `plugin-runtime`'s settings-phase and order tests mock it through `recordedModule`).
