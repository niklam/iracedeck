# @iracedeck/replay-engine

The iRacing replay engine (#1467): the replay command gate, the cursor, jump playback, seek, the paced search, the speed state, the camera-switch waiter and the Jump to Fastest Lap / Jump to Race Start presses with their lap walks, moved out of `@iracedeck/iracing-actions` so Replay Control's key and dial, Replay Markers and the legacy Replay Navigation, Replay Speed and Replay Transport actions share one engine with one owner for each piece of replay state. It is iRacing-specific by name and by dependency: it depends on `@iracedeck/iracing-sdk` (types, `ReplayPosMode`, `replaySpeedFromTelemetry`, `REPLAY_EXIT_GRACE_MS`, the grid helpers), `@iracedeck/replay-store` (types, constants and the session-store singleton the presses and walks read), `@iracedeck/logger` and `@iracedeck/app-constants` (`parseReplayJumpPlayback`), and on nothing else in the workspace. Two packages import it: `iracing-actions` (the replay actions, the busy indicator's gate reads) and `plugin-runtime` (`initReplay`). Built with `tsc` to `dist/` like `replay-store`; the root `vitest.config.ts` maps both entries to `src/`. Design: `docs/superpowers/specs/2026-10-20-issue-1467-replay-engine-package.md`.

## The env, and `initReplay`

The engine has no deck concept. What the deck layer and the settings supply is injected once, by `plugin-runtime`'s `initReplay` phase (phase 8, right after `initSettings` and before `registerActions`), through `configureReplayEngine(env)` (`replay-engine-configure.ts`):

- `controller` — the SDK controller, as `ReplayEngineController` (a `Pick` of `SDKController`: telemetry, session info, `getReplayState()`, the connection, `noteReplayLeftForLive()`, subscribe / unsubscribe). The engine reads it through `engineReads()` (`readTelemetry`, `inReplay`, `connected`, `leftForLive`), each of which catches a throwing read.
- `replay()` and `camera()` — the replay broadcast surface and the camera's `switchNum`, `getCommands().replay` / `.camera` reached at each use. Only the gate calls `replay()`.
- `now()` — the engine clock.
- `logger` — the root (`ReplayEngine` in the plugin); each module takes its scope with `engineLogger(scope)`: `ReplayGate`, `ReplaySearch`, `ReplaySpeed`, `ReplayLeft`, `CameraSwitch`, and `ReplayControl` for the lap presses and walks, so their lines read as they did when the action logged them.
- `settings` — `replayJumpPlayback()` and `fastestLapSearchDelayMs()`, closures read at the time of use, so a change in the Settings window takes effect without re-wiring; each reader sanitises the raw value (`readReplayJumpPlayback`, `readFastestLapSearchDelayMs`).

Until it is configured the engine reads nothing (no telemetry, no replay on screen, connected) and refuses to send. `configureReplayEngine` sets the env (`setReplayEngineEnv`) and starts the watch for leaving the replay over the controller; a second call stops the first watch, so each departure is emitted once. It is a module of its own because the env cannot import the watch: the watch reads the engine clock and the position state, which read the env. Tests configure through `_configureReplayEngine(overrides)` (on `./testing`), which starts from the unconfigured default every time, so overrides never accumulate.

The replay busy indicator stays in `iracing-actions`; the engine never reaches it. A lap press it would have to report as ignored returns `{ kind: "ignored" }` (`LapPressResult`) and the action reports it.

## One import path

The barrel `src/index.ts` is the only production entry, and it carries what a production source outside the engine imports and no more (#1502), together with the types those functions take or return (`ReplayEngineEnv` and `ReplayEngineController` for `configureReplayEngine`, `ReplayGateView` for `getReplayGateView`), which are part of their contract whether or not a consumer names them. `@iracedeck/replay-engine/testing` (`src/testing.ts`) is for tests only: it imports `vitest`, which is why `vitest` is a devDependency of a package with no test runner of its own. Beside the shared helpers (*Tests*, below) it carries the test hooks other packages' tests call (`_configureReplayEngine`, `_resetReplayCursor`, `_resetReplaySpeedState`, `_resetCameraSwitchWaiter`, `_activeLapPress`, `_getFastestLapSessionCache`) and the engine names only tests reach (the cursor's claim and cancel, the pending target, the walk owners, among others). The env itself (`engineEnv`, `engineReads`, `engineLogger`, `setReplayEngineEnv`) is on neither entry, so only the engine's own modules reach the injected replay surface. Where a name goes follows from who imports it: a production source outside the engine puts it on the barrel; only tests in another package, on `./testing`; only the engine's own tests, on neither, imported by relative path. `index.test.ts` fails on a `_`-prefixed name on the barrel and on any production source in `packages/` that imports `./testing`; the single-sender test fails on an env internal on either entry. Never import a module by relative path from another package.

## Module map

- `replay-engine-env.ts` — the env and its types (`ReplayEngineEnv`, `ReplayEngineController`, `ReplayCommandSurface`, `ReplayCameraSurface`, `ReplayEngineSettings`, `ReplayEngineReads`), `engineEnv()`, `engineReads()`, `engineLogger(scope)`, `setReplayEngineEnv`, and the test hooks `_configureReplayEngine` / `_resetReplayEngineEnv`.
- `replay-engine-configure.ts` — `configureReplayEngine`: the env, then the leave watch over its controller (above).
- `engine-clock.ts` — `now()` (the env's clock), `sleep(ms)` on a real `setTimeout`, and `pollUntil(check, { intervalMs, timeoutMs })`, the poll a settle loop uses where its exit condition is a plain predicate.
- `replay-engine-reset.ts` — `_resetReplayEngine()`: every module's state back to nothing under way, in the order the header gives (the search queue first, since ending its run ends its jump through the gate; then the leave watch), then the env. A module that keeps state adds its reset here, and `replay-engine-reset.coverage.test.ts` enforces it (#1502): it scans every production source with the TypeScript compiler for module-level state (a top-level `let`, a `const` something writes, a `const` behind a call it cannot see into) and fails on any binding no function reached from `_resetReplayEngine` writes, unless its `EXEMPT` list names it with the reason (module wiring registered at load, and a few gate scratch values only read while something the reset clears is set); the scanner's rules are in `replay-engine-reset.coverage.test-support.ts`.
- `replay-command-gate.ts` — the replay command gate (#1430): the one module that sends a replay command. A surface says what it wants sent and the gate decides when, and whether, by the table in its header: while a position jump is under way only another absolute jump (or go to start / go to end) goes out, a frame step becomes an absolute jump one frame from the target, a pause is not sent, and a speed or a search waits in the gate's one waiting slot (newest wins) for the target's read-back; behind a search that may be on its way every press waits for the landing, and a second press takes over at once (a pause if the replay is moving, an absolute jump to the frame beside the reading, then the press's command). `pressReplayCommand` is a one-shot press from a key or a dial and takes the replay cursor first, as every command did before; `sendOwnedReplayCommand` is a claim holder's own send (the jump sequence's pause and playback step, the lap walk's probes), and `openReplayJump` / `sendReplayJumpSeek` / `replayJumpLanding` / `closeReplayJump` carry the jump sequence, and `isReplayJumpSequenceOpen()` says whether one with a frame holds the cursor, from its press until its `end()` (#1428 / #1435: the camera-switch waiter's hold; a paced search's run opens no frame). Every speed, pause or playback step it sends is recorded in the speed state (`noteReplaySpeedSent`) once the change that sent it is complete, with the press's `rememberSpeed`, and a command the slot sends later always remembers; `waitingReplaySpeed()` is the speed held in the slot. It exports the waits #1426 and #801 build on (`waitForReplaySettled`, `waitForReplayJumpsToSettle`, `waitForReplaySearchLanding`, `settleReplayByJump`, `replaySearchCouldRunMs`, `isReplayPausedForJump`), the two verdicts the paced search reads instead of keeping its own (#1450): `waitForReplaySearchLandingWithFrame`, the landing wait that also says the landing's first frame (`firstFrame`, the first reading of the leap that held: `landedFrom`, the `moved` sample `judgeSearch` landed on), and `replayTargetFate(id)`, how a target ended (`ReplayTargetFate`: read back, held or not; given up; nothing moved; cleared; replaced, by which target), kept for the last `MAX_FATES` (64), and the state seam the busy indicator reads (`subscribeReplayGate`, `getReplayGateView`, per origin token), which reports what is under way or waiting and changes nothing that is sent. On `replayLeft` it runs its own `leftReplay()` (`left`) or `disconnect()` (`disconnected`), as one change. A `goToEnd` its slot sends tells the controller the replay was left for live (`leftForLive`). Every wait ends on what telemetry reads back; each clock only gives up. Its own speed-sent record (`SPEED_SENT_HOLD_MS`, 200 ms) stays internal to its dispatch decisions. It reads the replay through `replay-reading.ts`.
- `replay-reading.ts` — the playback measures the gate judges jumps and searches by and the paced search holds a reading by (#1450): `readReplay` (the replay out of a tick, `ReplayReading`: frame, frames left, rate, speed; null when the tick is not the replay's), `rateOf` (frames a millisecond a speed plays), `playbackTolerance` and `followsPlayback` (whether a frame is where playback puts it). Its own module so both import one copy without the runner's import of the gate making a cycle; retuning one retunes both.
- `replay-cursor.ts` — the single, process-wide owner of iRacing's one replay cursor (#1203): a long-running driver claims it for as long as it runs — a lap walk, and every jump through `replay-jump-playback.ts` while it waits for its landing (Jump to Fastest Lap's record jump, Jump to Race Start's jump, a Replay Markers Previous / Next jump, the paced search's run) — and any one-shot replay command in any action takes it before it is sent, inside the gate's `pressReplayCommand`, owner `<action>-<mode>` (#1334). `cancelReplayCursorOwnerIf(owners, by)` cancels the claim only when its owner is one of `owners`; `cancelLapWalks` (`lap-walk-owners.ts`) is its one caller. `interruptReplayCursorOwnerIf(owners, by)` (#1428 / #1435) is a camera switch's way to stop a walk: it sets the claim's `interruptedBy` and takes nothing — the claim stays current so its holder can still put the replay back, the pending jump speed and the dial's pending speed are left alone, and no `onReplayCursorTaken` listener is told; a take still cancels an interrupted claim; `interruptLapWalks` is its one caller. Only a walk's search is interruptible: the walk calls `endReplayCursorInterrupts(claim)` the moment it has its answer or gives up, the claim's `interruptible` turns false, and the interrupt no longer matches it. Camera switches take no cursor, Replay Control's, Camera Controls' and Race Admin's alike (Niklas, 2026-10-10): they reach a walk only through the waiter's interrupt, which takes none. It also holds the pending jump speed (#1276): the speed the replay had before a jump still under way, or the speed a finished jump left it at until telemetry shows it, inherited by a jump that takes the cursor from another and cleared by any other replay command; when it still stands is `replay-jump-playback.ts`'s rule. Where the replay is headed is not kept here but in `replay-position-state.ts`, which a cursor take leaves standing. Whether a replay is on screen is not kept here either: that is `SDKController`'s debounced replay state (`getReplayState()`, #1324), stepped on every poll that reads telemetry, which holds "in a replay" through `REPLAY_EXIT_GRACE_MS` (1 s) of `IsReplayPlaying` false and treats a saved replay as always a replay; the engine reads it as `engineReads().inReplay()`. A `goToEnd` that was sent (Replay Control's Jump to Live, Replay Navigation's Jump to End, a slot dispatch of the gate's) calls `noteReplayLeftForLive()`, which ends the grace at once outside a saved replay. Its tests share `replay-cursor.test-support.ts`.
- `replay-position-state.ts` — where the replay stands or is headed: the one pending target (#1317, #1430). Every position jump of every surface records it — the dial's frame moves, the jump sequence's seeks, the keys' frame steps — and only the gate writes it. A move is measured from it while it stands (`ReplayPosition.seeking`), and the record walk anchors on it. It ends when its frame reads back conclusively (`settleReplayTarget`) or is given up by `replayTargetGiveUpMs` (the larger of `REPLAY_TARGET_GIVE_UP_MS`, 3 s, and twice the jump's length at 2048 frames a sim update, not running while the jump that recorded it holds the cursor); a cursor take does not clear it. Its header holds the measurements of 2026-10-12 and 2026-10-13.
- `replay-frame-move.ts` — `planFrameMove`, what a move of the replay by frames sends (#1317): one frame step on a replay at rest, otherwise one absolute jump to the frame the move is heading for, never a jump relative to the cursor. A Frame Forward or Frame Backward key, its long-press repeat and a Frame Jog detent are one code path through the gate, with one end-of-tape margin (`JUMP_END_MARGIN_FRAMES`); `frameBeside` is the frame the gate's takeover jumps to.
- `replay-seek.ts` — the waits a replay jump is made of (#1275), and `replaySeekWaitMs`, how long an absolute jump of a given length is waited for (twice its time at iRacing's 2048 frames a sim update, never under the caller's floor, #1354). `seekReplayFrame` sends an absolute jump and waits until `ReplayFrameNum` reads the frame sent, resolving `refused` at once when the send was refused; `waitForReplay` is the same poll for any condition, with `isLandedOn` and `isPaused` the two asked for; each reports `cancelled` at its next poll once the caller's claim is taken. `timeoutMs` is a plain wait unless the caller passes `seeking`, a predicate for what a seek still under way reads (`isSeeking`: `IsReplayPlaying` false with nobody on track): the timeout then does not run while a read shows one, and `maxWaitMs` caps it. A seek never shows as a moving frame — a long jump forwards, or one sent soon after another, reads like a replay that was left until it lands — and `requireReplay` refuses a landing from a sample with `IsReplayPlaying` false. The lap walk's probes call `seekReplayFrame` with the plain timeout; the jump sequence takes its landing from the gate's read-back of the target.
- `replay-jump-playback.ts` — the one jump sequence behind Jump to Fastest Lap, Jump to Race Start and Replay Markers' Previous / Next, and what the replay does after it (#1276). `beginReplayJump` is called at the press, before any command: it captures the speed to restore (a speed waiting in the gate's slot, else the speed the replay had when a search still on its way went out, else the cursor's pending jump speed, else telemetry; unreadable counts as paused), claims the cursor and records the target before its pause. `runReplayJump` pauses a moving replay (skipped by a jump that took over from one the replay is already paused for, `isReplayPausedForJump`), seeks through the gate, waits for the gate's read-back of its target while iRacing shows a seek, runs the caller's `afterLanding` step (Jump to Fastest Lap's camera switch) and ends in `applyReplayJumpPlayback`: one speed command, only when the speed the **Replay jump playback** setting asks for differs from the one the landing reads. A cancelled claim, a refused command or a wait that gives up sends nothing more, leaving the replay paused where it stopped. It never throws for those and has no logger: the outcome says what happened, `describeReplayJump` is the one wording of it, and the caller calls `jump.end()` in its `finally`.
- `replay-jump-speed.ts` — `ReplaySpeed`, `isSameSpeed`, `PAUSED`, `NORMAL_SPEED` (the one declaration; the dial files re-export it), the **Replay jump playback** setting read through the env (`readReplayJumpPlayback`) and the speed it resolves to (`resolveReplayJumpSpeed`).
- `replay-timing.ts` — the numbers the replay waits are timed from, most derived from the **Fastest Lap Search Delay** setting read through the env: `readFastestLapSearchDelayMs` (clamped to 50–1000 ms, 400 on anything non-numeric), `STABILIZATION_TIMEOUT_MULTIPLIER` (the walk's `delay × 4` settle cap), `STABILIZATION_POLL_INTERVAL_MS` (50 ms), `RECORD_JUMP_MIN_TIMEOUT_MS` (3 s), `REPLAY_JUMP_POLL_MS` (20 ms), `readReplayJumpTimeoutMs` (`delay × 4`, never under 3 s), `REPLAY_JUMP_MAX_WAIT_MS` (120 s, the longest any landing is waited for while iRacing seeks) and `HOLD_GAP_MS` (the gate's and the search queue's one hold gap).
- `replay-speed-state.ts` — the one record of the replay speed (#1316; the owner since #1467): the **pending** speed, an overlay of what was just sent until telemetry shows it or `DIAL_SPEED_HOLD_MS` (500 ms) passes, superseded by any cursor take (`clearDialPendingSpeed` on `onReplayCursorTaken`) except the dial's own (`keepDialPendingSpeed`, which keeps a send recorded inside the take); and the **remembered** speed the dial's Play resumes, which follows telemetry (`noteTelemetrySpeed`) and is written provisionally by a non-zero send made with `rememberSpeed`. The gate feeds every send through `noteReplaySpeedSent`, and every recorded send is told to `onReplaySpeedChanged`, which the keys and the dial redraw from because a paused replay may deliver no tick. `resolveLiveSpeed`, `rememberedSpeed`, `reverseRememberedSpeed`.
- `replay-speed-view.ts` — `shownReplaySpeed(telemetrySpeed, now)`, the speed every surface shows and steps from: the gate's waiting speed while one is held, else the resolved live speed. Its own module because the gate imports the speed state, so the combined read in either would be a cycle.
- `replay-speed-format.ts` — the keypad's speed setting format (`parseSpeedSetting`), how a speed reads (`formatSpeedDisplay`) and the dial's resume caption (`formatPlayCaption`, `►` / `◄`, U+25BA / U+25C4).
- `replay-search-queue.ts` — the Replay Control dial's paced search (#801): one runner per process that steps a pending count of lap, session or incident searches through iRacing's own searches, one on its way at a time, as a policy on the gate (`queueReplaySearch`, `pendingReplaySearch`, `onReplaySearchChange`, `SEARCH_QUEUE_MAX`). Its header has the run's steps and the playing path. It keeps no measure or verdict of its own (#1450): it reads the replay through `replay-reading.ts`, the frame a playing landing first read (where it jumps back to before a step against the play) from the gate's `waitForReplaySearchLandingWithFrame`, and, behind a jump of the plugin's, whether its target landed from `replayTargetFate`, following a replacement to the target that replaced it; `replay-search-queue.gate-reads.test.ts` holds the cases. On `replayLeft` a run ends as `gave-up` at its next check; its own `replayOnScreen()` read stays as a second check, since it also covers a gate target still standing.
- `replay-incident-observer.ts` — the incident comparison (#1426): after a Next / Previous Incident key's search, where the search landed against the recorded incidents, as one debug line. Sends nothing and holds no claim.
- `replay-record-walk.ts` — the one walk through a recorded list of replay frames (#1426), shared by Replay Markers and Replay Control's Next / Previous Lap and Session: `walkRecordedEntries`, `walkRecordedIndex`, `recordedIndexAt`, and the anchor (`resolveReplayWalkAnchor`, the pending target while one stands, else the cursor; Replay Markers re-exports it as `resolveMarkerJumpAnchor`; `resolveReplayWalkStart` reads the same from the debounced replay state). Next is the first entry more than `MARKER_NEXT_MIN_AHEAD_FRAMES` past the anchor, Previous the media-player rule measured from the entry's landing; a `RecordedSpanRule` keeps a walk inside the record. Its header has the rule in full.
- `replay-record-step.ts` — Next / Previous Lap and Session from the record (#1426): which list a press steps through (`RECORD_STEPS`, `listRecord`), the frame each entry lands on, and the step (`findRecordStep`, `stepRecordListing`); a miss names its reason and the caller sends iRacing's search. Pure: the caller hands in the store.
- `replay-lap-count.ts` — the laps in a session for the dial's Lap value and Session caption, `12/25` (`sessionLapCount`, `formatLapOfLaps`). Pure.
- `green-flag-target.ts` — what Jump to Race Start aims at (#1354): the race session, the landing (`GREEN_APPROACH_FRAMES`) and the car whose lap 1 stands in for an unrecorded green. Pure.
- `lap-walk-probes.ts` — `halvingProbeFrames`, the order the lap walk probes an interval in (#1354).
- `lap-walk-owners.ts` — the two lap walks' cursor owners (`FASTEST_LAP_WALK_OWNER`, `RACE_START_WALK_OWNER`, `LAP_WALK_OWNERS`), `cancelLapWalks(by)`, which cancels a walk and no other owner (leaving the replay), and `interruptLapWalks(by)`, which interrupts one and no other owner (a camera switch, #1428 / #1435). It registers the walks' `replayLeft` handling.
- `lap-press.ts` — what Jump to Fastest Lap and Jump to Race Start share: the one in-flight press slot (module state; a second press while it stands is ignored), the press's replay jump and claim (`holdLapPressSlot`, `FastestLapPressCancelled`), the two ways a walk is stopped (`throwIfWalkStopped`: a cancel throws `FastestLapPressCancelled`, an interrupt `LapWalkInterrupted`; `walkStopView`, the claim as the walk's own waits poll it), whether the press is winding down, interrupted or past its search (`isLapPressWindingDown`), the press-start hook the camera-switch waiter drops a parked switch on (`onLapPressStarted`), the wait before a camera switch of the press's own (`waitToSwitchCamera`), and the jump to a frame with its log lines (`runJumpToFrame`, which the key's record step also uses). Its lines go to the `ReplayControl` scope (`lapPressLogger`).
- `lap-walk.ts` — the lap walk (#607, #1203, #1354, #1432): the search of the replay for the start of one car's lap, run by Jump to Fastest Lap when the record has no frame for it and by Jump to Race Start for the pole car's lap 1. It reads telemetry, session info and the replay state through the env, the time through the engine clock, sends every probe through the gate as the press's claim holder, and records the frame the car's lap counter flips (#1432): from where iRacing's lap search left the cursor on the lap before (one Next Lap nudge when that is not near enough), absolute jumps bracket the flip within `LAP_CROSSING_MAX_FRAMES` (120, first `LAP_CROSSING_NEAR_FRAMES`, 16) and bisect it to adjacent frames; the first frame on the lap goes into the store and Jump to Fastest Lap's walk leaves the cursor `LAP_START_APPROACH_FRAMES` before it, where a record jump lands. No flip within the bound records nothing and leaves the cursor that far before the lap search's landing. Jump to Race Start's walk makes neither jump (`LapWalkTarget.jumpToRunUp: false`): the cursor stays where its last probe left it (the landing's `landedFrame` and `telemetry`), and the press's own jump — to the green's approach, or back where the press found the replay — is the one jump after the search. It puts the replay back (`putReplayBack`) when it gives up or a camera switch interrupts it: the frame, then the captured speed, and for a walk stopped in its opening pause before it read the frame, the speed alone (#1428 / #1435). A cancel and an interrupt are both seen at every `checkpoint` and every poll of its own waits; only the cancel ends the claim, and the walk ends its interrupts after its last crossing probe, so the jump after it (the run-up, or Jump to Race Start's own) is one a camera switch waits for. It also holds the fastest-lap session-map cache, which it drops on the engine's `replayLeft` with reason `disconnected`.
- `fastest-lap-press.ts` — one Jump to Fastest Lap press (`pressJumpToFastestLap`), from the guards to the record jump (`jumpToRecordedLapStart`) or the walk, and the lookups it rests on (`findFastestLapForCar`, `readSubSessionId`, `readUserId`, `lookupRecordedLapStart`).
- `race-start-press.ts` — one Jump to Race Start press (`pressJumpToRaceStart`, `canJumpToRaceStart`): the recorded green, else the pole car's lap 1 from the lap record, else the walk, which borrows the camera for the pole car (`env.camera()`) and puts it back.
- `camera-switch-waiter.ts` — the one camera-switch policy (`requestCameraSwitch`, below). It reads the lap press's slot (`isLapPressWindingDown`, and drops a parked switch on `onLapPressStarted`) and the gate's `isReplayJumpSequenceOpen`; nothing it reads imports it back.
- `replay-left.ts` — leaving the replay as one engine event (below): `onReplayLeft`, `startReplayLeftWatch` / `stopReplayLeftWatch`, `_resetReplayLeft`.

## Rules it keeps

- **One sender.** Only `replay-command-gate.ts` sends a replay command. Inside the engine that means only the gate calls the env's `replay()`; in `iracing-actions` nothing reaches `getCommands().replay`. `replay-command-gate.single-sender.test.ts` scans every production source of both packages for each way to reach `getCommands()`'s commands (`getCommands().replay`, a destructured `replay`, `.replay` off a bound `getCommands()`), and the engine's for a call of the injected `replay()` or a destructured `engineEnv()` — the engine's alone, since it also asserts that neither public entry exports the env (#1502) — each with a planted violation as its positive control. Camera sends are outside the rule: the waiter's sends are the caller's (a keystroke or `camera.switchNum`), and the two lap presses make their own camera moves through `env.camera()` (Jump to Fastest Lap's switch onto the lap's car and back, Jump to Race Start's borrow of the pole car and back).
- **One clock.** Every module reads the time through `engine-clock.ts`'s `now()`, never `Date.now()`, and sleeps through its one `sleep`, so a test fakes both with fake timers. The speed state takes the time as an argument and reads none.
- **One speed record.** The speed state is the only record of the current speed. The gate feeds it every speed it actually sends, whichever surface asked; every reader shows `shownReplaySpeed`, so a press the gate holds shows as the waiting speed and a press it drops never shows. The resume speed (`remembered`, written provisionally) moves only for a send made with `rememberSpeed` — the dial's own, and every speed the gate's slot dispatches later — so a key's or a legacy action's speed sent at once moves only what is shown, not what the dial's Play resumes. `noteTelemetrySpeed` is called only by Replay Control on its ticks while in a replay, so it runs only while a Replay Control context is visible. The cursor's pending jump speed (the speed to restore after a jump) and the gate's own speed-sent record are not records of the current speed.
- **One camera policy.** Every camera switch an action's key or dial makes goes through `requestCameraSwitch(send, options)`: Replay Control's (the dial's Track Order turn and Jump to My Car gesture; the keys' Jump to My Car, Next / Previous Car and Next / Previous Car Number), Camera Controls' keypad and dial (#1428 / #1435; the angle-only modes with `interruptsWalks: false`), and Race Admin's Car Selector focus press. Camera Controls' Set Camera State, flags on the camera rather than a target, is sent at once and never through the waiter. It interrupts only a lap walk's search (`interruptLapWalks`, at the request and again when the switch goes out; #1428 / #1435), never a marker jump, a record jump or the paced search: the walk keeps its claim, puts the replay back (frame, captured speed, its own camera move undone) and the switch goes out after that; a walk the second interrupt catches is waited for in turn. A walk that has its answer is no longer interruptible: the switch waits for its jump to the lap and its camera step like any jump. A Jump to Fastest Lap or Jump to Race Start press drops a switch still waiting from before it (debug line naming the switch), so an older switch never interrupts the newer walk, and ends the wait it sat behind, so a switch asked for during the walk waits on its own (its own ceiling, its own jump reads). A switch that changes only the camera's angle passes `interruptsWalks: false` and touches no walk. On a quiet replay it sends at once; behind a position jump it waits, with no claim, for the jumps to settle (`waitForReplaySettled({ jumpsOnly: true })`), as the one switch waiting for the whole plugin, a later request from any key or dial replacing it. Two holds count as under way beside the jump reads, whichever reads a caller injects: a lap press winding down (interrupted, or past its search), and a jump sequence with a frame until its `end()` (`isReplayJumpSequenceOpen`), so the switch follows a jump's own camera switch after its landing; both are reads, and the ceiling only gives up. It is dropped at the ceiling `REPLAY_JUMP_MAX_WAIT_MS` puts on any jump's wait, when the wait fails, or when `stillValid()` is false (its key or dial left the screen, or the replay was left); the drop line names the asker by `options.surface` (`the key`, `the dial`). It is not a lane in the gate, whose one slot holds a speed, search or pause.
- **One departure event.** `replay-left.ts` emits `replayLeft { reason: "left" | "disconnected" }` once per departure: `left` on the debounced replay state's edge to false, `disconnected` on the first tick without a connection or telemetry after a connected one. `left` is held through the plugin's own seek: while a gate target has not read back it waits up to that target's `replayTargetGiveUpMs`, counted from the edge or, for a target sent after it (a walk's next probe), from its send; while a seek shows with no target, up to `REPLAY_TARGET_GIVE_UP_MS` from the edge; re-judged on every tick and once by a timer; a state that reads true again first emits nothing, and a disconnect is not held. The holders register at module scope with `onReplayLeft`: the gate (`leftReplay()` / `disconnect()`), the search queue (its run ends as `gave-up`), the lap walks (`lap-walk-owners.ts` cancels the two walk owners, by `replay-left`, and the press resolves as cancelled) and the fastest-lap session-map cache (`lap-walk.ts` drops it on `disconnected` only). A record jump keeps its target and its own wait, and a Jump to Live its claim. `replayLeft` is engine-internal and never goes in the `@iracedeck/event-bus` catalog, a published contract with no consumer for it.
- **The boundary.** A `no-restricted-imports` block in `eslint.config.js` refuses `@iracedeck/deck-core`, `@iracedeck/deck-iracing`, `@iracedeck/settings`, `@iracedeck/icons` and `@iracedeck/iracing-actions` in `src/`; `scripts/replay-engine-boundary.test.mjs` lints a planted import of each so removing or narrowing the block goes red. What the engine needs from them goes through the env.
- **No import cycle among the modules.** The plugin builds fail on a cycle among our own sources. Where a read needs two modules that import each other's neighbours it gets a module of its own (`replay-speed-view.ts`, `replay-engine-configure.ts`).
- **Log text is kept when code moves.** A line that moved here kept its wording; only the logger it goes to changed.

## Tests

Each module's tests sit beside it. What both packages' tests share is exported from `@iracedeck/replay-engine/testing`, beside the test hooks and test-only names (*One import path*, above): `resetEngine(overrides)` (every module reset, then the engine configured from the default plus `overrides`, the one call a test resets through), `fakeReplay` (the replay surface the gate's tests drive), `steppedReplayState` / `withSteppedReplayState` (a mocked controller's debounced replay state over the SDK's own `ReplayStateTracker`, stepped on every read), the cursor probe, the lap-walk buffers (`singleSessionBuffer`, `multiSessionBuffer`; `lead` is how far short of the line their lap searches rest, #1432), the race weekend (`raceWeekendReplay`) and the leave watch over a stand-in controller (`replayLeftController`, `watchReplayLeft`). `replay-engine.test-support.ts`'s `configureTestEngine` (a fake controller, a spy logger per scope, the settings) is engine-local, for the lap presses' own tests.

In `iracing-actions`, `shared/replay-engine-deck.test-support.ts`'s `engineOverDeck(base)` wires the engine over a test file's `@iracedeck/deck-iracing` mocks, as `initReplay` wires it over the real ones, and gives the file its `configureEngine` / `resetEngine` pair; `replayControlScopeOn(logger)` routes the engine's `ReplayControl` scope to the action's logger, so a Replay Control test reads the press's lines where it always did. The walk's behaviour is tested here against a fake controller and clock (`fastest-lap-press.test.ts`, `race-start-press.test.ts`, `lap-walk.test.ts`); the action keeps thin tests that a press calls the engine and redraws (`replay-control.test.ts`, `replay-control-race-start.test.ts`).
