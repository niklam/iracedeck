# @iracedeck/settings-window

The dedicated settings window's plugin side (#992, #993), moved out of `deck-core` in #1367 (spec #1351, `docs/superpowers/specs/2026-10-07-issue-1351-deck-core-split-and-sim-seam.md`): the loopback server and its request guard, the controller, the app-window launcher and Chromium lookup, the `sendToPlugin` command handler, the failure banner, the settings-channel publisher, and Explorer reveal. It depends on `@iracedeck/settings` (the cache's diff and run-scoped strip, `hostMirrorPayload`, `reconcileWarnings`, the startup gates, and the `SettingsHost` the publisher writes through), `@iracedeck/app-constants` (the page name, the two warning ids, `PiWarning`, the focus modes), `@iracedeck/callout-script` (`packId`, which the command handler checks a page-supplied voice-pack id against before an install or a remove, because an id becomes a directory name), `@iracedeck/app-updates` (types only: the `UpdateStatus` its server answers `GET /updates/status` with), `@iracedeck/logger`, `ws` (the fake host's WebSocket server) and `zod`. `plugin-runtime` is its one dependent: `initSettings` builds the controller, the command handler, the warning reporter and the publisher, `initVoicePacks` takes `openDirectoryInExplorer` for the voice-pack folder, and `src/types.ts` names the controller and command-deps types. `ws` follows the package into the plugins as before: bundled into the Elgato plugin, external and installed in `bin/node_modules` on Mirabox and Ulanzi.

Windows-only by design, like the rest of the plugin (iRacing is), behind injected delegates: `chromium-browser.ts` (the app-window spawn) and `open-folder.ts` (Explorer) are the plugin's only two `child_process` uses, and each keeps the spawn to one function.

## What reaches it, and from where

`scripts/capture-settings-window.mjs` (`pnpm capture:settings`, `.claude/rules/website-screenshots.md`) imports this package's BUILT `dist/index.js` by path — `startSettingsWindowServer`, `findChromiumBrowserOnThisMachine` and `SETTINGS_WINDOW_SIZE` — and refuses to run with a message when it has not been built. Renaming one of those exports or the `dist/` entry breaks it. `pi-components`' `open-folder.ts` component and the settings page's controls are the browser half; they reach this package only over the loopback socket, never by import.

## Module map

- `settings-window-guard.ts` — `authorizeSettingsRequest`, the single, pure decision point every HTTP request and WebSocket upgrade passes through: the launch token first, then `Origin`, then the session cookie. Reviewed at `max` (`.claude/rules/code-review.md`): its failure mode is accepting a request that should have been refused.
- `settings-window-server.ts` — `startSettingsWindowServer`: `node:http` + `ws` on `127.0.0.1`, ephemeral port, started once and kept for the plugin run. Serves `ui/` (confined; traversal → 404), the fake deck host at `/ws` (the Elgato PI protocol's global-settings subset, for the window AND every PI), `GET /simhub/roles` and `GET /updates/status`. Settings I/O goes through an injected `SettingsWindowHost`, so it never touches the settings singleton or the store file. Reviewed at `max` with the guard (static-path confinement).
- `settings-window.ts` — `createSettingsWindowController`: one server per plugin process, started by the first `ensureStarted()` or `open()` and reused by every later call; `onStarted` / `onStatus` hooks; `SettingsWindowStatus` reports both stages of every attempt, since only the controller knows which one failed.
- `settings-window-launcher.ts` + `chromium-browser.ts` — `launchSettingsWindow` opens the page as a chromeless `--app=<url>` window, falling back to the host's `openUrl`; `findChromiumBrowser` / `findChromiumBrowserOnThisMachine` (App Paths registry, then well-known install paths; memoized), `appWindowArgs`, `spawnAppWindow` (detached, stdio ignored) and `SETTINGS_WINDOW_SIZE`.
- `settings-window-commands.ts` — `createSettingsWindowCommandHandler(deps)`: validates and routes the page's `sendToPlugin` payloads to injected delegates (window bounds, profile switch, audio preview, the settings, voice-pack and profiles folders, voice-pack refresh / install / remove, CPU profile capture, `enableFeature` through `enableFeatureWrites`). It never takes a path from the page, and it imports neither the voice-pack stack nor `@iracedeck/diagnostics`: `plugin-runtime` injects those callbacks. `parseSettingsWindowBounds` and `SETTINGS_WINDOW_BOUNDS_KEY` (`_settingsWindowBounds`).
- `settings-window-warning.ts` + `settings-window-warning-reporter.ts` — the failure banner (#1005, #1014): the pure `evaluateSettingsWindowWarnings` (a LIST of records — the page-wide `settings-window-server` error and the button-scoped `settings-window-open` warning — reconciled against `settingsWindowWarningScope`) and `createSettingsWindowWarningReporter`, wired as the controller's `onStatus`, the only part that touches the settings singleton.
- `settings-channel-publisher.ts` — `createSettingsChannelPublisher({ adapter, logger })` (#993 phase 2): `publish(channel)` removes a stale `_settingsChannel` (`SETTINGS_CHANNEL_KEY`) an older build persisted into the store (the channel is per-process and travels only in the host mirror) and sends the one host mirror per start; idempotent per channel, retries the mirror until it goes out, logs its own faults. `publishUnavailable()` is the same mirror for a run whose server never started (#1005). Bound to the controller's `onStarted` hook and the store-ready block in `plugin-runtime`'s `initSettings`. `adapter` is only `Pick<SettingsHost, "setGlobalSettings">`, so this package never names `IDeckPlatformAdapter`.
- `open-folder.ts` — `openFolderInExplorer(path)` + `explorerSelectArgs` (#993): reveals the settings file with Explorer's documented `/select,"<path>"` form, spawned detached with `windowsVerbatimArguments` so libuv can't re-quote the whole token; `openDirectoryInExplorer(path)` opens a folder (#1100, the voice-pack and profiles folders). The path always comes from the plugin's own store or a path the plugin names, never from a page, and it deliberately does not go through `openUrl` (http(s)-only on every host).

## One import path per name

The barrel `src/index.ts` is the package's only entry, and deck-core re-exports none of it: import every name it exports from `@iracedeck/settings-window`, and mock that package in a test that stubs one (`plugin-runtime`'s phase tests do, through `recordedModule`). A mock of `@iracedeck/settings`' barrel cannot reach that package's internal imports — its `pi-warnings.ts` writes through its own `global-settings.ts` by relative path — so `settings-window-warning-reporter.test.ts` runs over the real settings cache (`initGlobalSettings` with `createMemorySettingsStore`) and counts writes from its change fan-out.
