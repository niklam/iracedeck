# @iracedeck/diagnostics

The plugin's self-diagnostics, moved out of `deck-core` in #1367 (spec #1351, `docs/superpowers/specs/2026-10-07-issue-1351-deck-core-split-and-sim-seam.md`): the main-thread watchdog (#1330), the resource monitor (#1338) and the on-demand CPU profile capture (#1338). It depends on `@iracedeck/app-constants` (`LogLocation`, the watchdog's target type, and `PROFILE_CAPTURE_STATUS_KEY`) and `@iracedeck/logger`, and imports nothing sim-shaped: what it needs to know about iRacing is injected. `plugin-runtime` depends on it (`initCore` starts the watchdog and the resource monitor, `initSettings` creates the capture), and so does `iracing-actions` (Telemetry Control's **Capture Profile** mode reaches the capture through `getCpuProfileCapture()`). `deck-adapter-mirabox` and `deck-adapter-ulanzi` list it as a devDependency only: each adapter's `file-logger.test.ts` checks the name its `FileSink` writes against `watchdogDailyLogFileName`.

## Module map

- `main-thread-watchdog.ts` — `startMainThreadWatchdog({ logger, target, heartbeatMs?, stallMs?, pauseTimeoutMs?, jsPauseLatencyMs? })` (#1330), called by `plugin-runtime`'s `initCore` for all three plugins once logging is up: the main thread bumps a `SharedArrayBuffer` heartbeat every 500 ms, and an `unref`'d eval worker that sees it stand still for 5 s (on `performance.now()`; a gap of more than three heartbeats in its own samples is a suspended process and restarts the clock) pauses the main thread through the in-process inspector (`Session.connectToMainThread()`, no `--inspect`). A pause landing within 250 ms is reported as JavaScript with its call frames; a later one, or none within 2 s, as native code, with the frames where the thread resumed. Then a recovery line. Reports go straight to the host's log file (`WatchdogLogTarget`, which is `@iracedeck/app-constants`' `LogLocation`: `{ kind: "file", path }` for Elgato's `<uuid>.0.log`, `{ kind: "daily", dir }` for the Mirabox/Ulanzi `FileSink` directory, named by `watchdogDailyLogFileName`, which both adapters test against their sink). `superviseWatchdogWorker` is the main-thread side: one WARN when the worker reports the inspector unusable, and one WARN plus a stopped heartbeat when the worker errors or exits. The worker source is assembled from self-contained functions stringified with `toString()` and passed by value — `watchdogWorkerMain(watchdogStep, initialWatchdogState, watchdogDailyLogFileName)` — so none of them may use anything from module scope; `watchdogStep` is the pure reducer the unit tests drive, a guard test runs the assembled source in a real `Worker`, and another runs the terser-minified module through a real stall (below). Decision record: `docs/superpowers/specs/2026-10-04-issue-1330-main-thread-watchdog.md`.
- `resource-monitor.ts` — `startResourceMonitor({ logger, onSessionStart?, onSessionEnd?, isSessionActive?, config?, sampler? })` (#1338), started by `initCore` beside the watchdog: every 60 s on an `unref`'d timer it samples `process.cpuUsage()` (delta, % of one core), `performance.eventLoopUtilization()` (delta) and `process.memoryUsage()`, reading each counter once per sample and diffing by hand so nothing between samples is lost. The rule is the pure reducer `resourceMonitorStep`: three consecutive samples at CPU ≥ 50 % of a core OR ELU ≥ 0.5 write ONE WARN carrying the numbers; the first sample below both writes the parameter-free INFO "Plugin CPU use back to normal" and re-arms; every sample writes a debug `Resources: …` line. At each iRacing exit `resourceSessionSummary` writes INFO "Resource summary for the iRacing session" plus a debug line (time-weighted avg and peak CPU, peak ELU, peak RSS and heap). It takes an extra PARTIAL sample at each session edge (iRacing starting and exiting) and restarts its minute there, so every interval lies wholly inside or outside a session; a partial sample is logged and counted towards the session but takes no part in the high/normal rule, and the summary follows the exit edge's sample. `isSessionActive()` only seeds the starting side. `plugin-runtime` injects `deck-iracing`'s `onIRacingStarted`, `onIRacingTerminated` and `isIRacingActive` rather than this module importing the app monitor (#1176, #1351), since `deck-iracing` is a layer above this package. Not gated on `debugLogging`.
- `cpu-profile-capture.ts` — `createCpuProfileCapture({ profilesDir, logger, writeSettings, durationMs?, … })` (#1338), the settings window's **Capture CPU profile** and the Telemetry Control key's **Capture Profile** mode. `plugin-runtime`'s `initSettings` creates the ONE shared instance with `initializeCpuProfileCapture(...)` (its `profilesDir` is `<log dir>/profiles`, from the adapter's `logLocation`) and consumers reach it with `getCpuProfileCapture()` (the audio service's shape; `isCpuProfileCaptureInitialized`, `_resetCpuProfileCapture` for tests), so both surfaces share the one-at-a-time lock, the status key and the files; `status()` / `onStatus(listener)` give the typed state the key follows. The settings window's `captureCpuProfile` command reaches it through a callback `plugin-runtime` injects into the command handler, so `@iracedeck/settings-window` does not depend on this package. The capture: an in-process `inspector.Session` (`session.connect()`, loaded on demand so a Node without the inspector fails one capture rather than the plugin) runs `Profiler` at a 1000 µs interval for 30 s and writes `cpu-<ISO, filename-safe>.cpuprofile` (DevTools) plus a `.txt` (wall and busy time, top 30 functions by self time with bundle positions, V8's pseudo-frames labelled) into `<log dir>/profiles`, then prunes to the newest five pairs by exact name pattern. One capture at a time; a second request is refused. Its state is the run-scoped `_profileCaptureStatus` (`PROFILE_CAPTURE_STATUS_KEY`, a JSON string `{ state: idle|capturing|saved|failed, startedAt?, durationMs?, file?, reason? }`); the key lives in `@iracedeck/app-constants`, which `@iracedeck/settings`' `run-scoped-settings.ts` imports too. Decision record: `docs/superpowers/specs/2026-10-04-issue-1338-built-in-profiling.md`.

## Tests that reach outside the package

- `main-thread-watchdog.test.ts`'s minified-module test compiles the module with `typescript`, resolved through this package's own `package.json`, and minifies it with the plugins' own terser and options, resolved through `@iracedeck/plugin-build`'s `package.json` → `@rollup/plugin-terser` — the package whose shared Rollup config minifies all three plugins. Moving the terser options or the dependency out of `plugin-build` breaks it.
- `cpu-profile-capture.test.ts`'s integration test runs the capture in a child Node process, transpiled together with `@iracedeck/app-constants`' sources, which it reads by relative path (`../../app-constants/src`): the module imports only Node built-ins, erasable types and that leaf, and a child process in a temp directory cannot resolve the workspace package by name. A new import in `cpu-profile-capture.ts` breaks that test.

## One import path per name

The barrel `src/index.ts` is the package's only entry, and deck-core re-exports none of it: import every name it exports from `@iracedeck/diagnostics`, and mock that package in a test that stubs one (Telemetry Control's test does; `plugin-runtime`'s phase tests mock it through `recordedModule`).
