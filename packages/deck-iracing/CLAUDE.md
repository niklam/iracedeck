# @iracedeck/deck-iracing

iRacing's side of the deck layer's sim-connection seam (#1351). `@iracedeck/deck-core` is sim-neutral and sees a simulator only through its `SimConnection` interface; this package implements that interface over the iRacing SDK and holds everything else in the deck layer that speaks iRacing: the `SimIRacingAction` base for actions that read the SDK directly, the SDK singleton behind `getCommands()`, and the iRacing helpers actions and the plugin bootstrap share. It depends on `deck-core`, never the other way round — a lint rule on deck-core and every other package in `SIM_NEUTRAL_PACKAGES` (`eslint.config.js`) refuses any import of this package, `iracing-sdk`, `iracing-native` or `sim-events-iracing` there (`scripts/deck-core-sim-boundary.test.mjs` proves it fires).

It has the same shape `@iracedeck/sim-events-iracing` has on the bus side: a second sim is a sibling `deck-<sim>` implementing the same `SimConnection`, chosen in `@iracedeck/plugin-runtime` and nowhere else. Spec: `docs/superpowers/specs/2026-10-07-issue-1351-deck-core-split-and-sim-seam.md`.

**Naming:** a sim's deck-layer classes are named `Sim<Game>…` — `SimIRacingAction`, `SimIRacingConnection` here, and a future `deck-<sim>` would export `SimAssettoCorsaAction` / `SimLmuConnection` and so on. The prefix keeps the game in the name while stopping `IRacing…` from reading as an `I`-prefixed interface, which is how this repo names interfaces (`IDeckPlatformAdapter`, `ILogger`). The older `IRacingSDK` and `IRacingNative` predate the rule and are left as they are.

## Package Contents

### The seam

- `sim-iracing-connection.ts` — `SimIRacingConnection`, the `SimConnection` over an `SDKController`. `isConnected()` is the controller's connection status; `subscribe(id, onTick)` wraps the controller's subscription and records each tick's telemetry (null on a disconnected tick), so `activeFlags()` maps the latest tick's `SessionFlags` through `resolveAllActiveFlags` without a telemetry read of its own — the tick already did one. The recorded telemetry is connection-wide and meant to be read inside a tick; before any tick, and while disconnected, `activeFlags()` returns no flags. `resolveTitleTemplate(text)` resolves against the controller's per-tick template context and falls back to `EMPTY_TEMPLATE_CONTEXT` when there is none or it throws. `EMPTY_TEMPLATE_CONTEXT` is the frozen disconnected context — `{{variable}}` placeholders render empty and `{{= expression }}` parse errors stay visible, the rules Telemetry Display values follow — exported for any other display path that reads `getCurrentTemplateContext()` itself (Chat's key text, #1337) so it falls back the same way.
- `sim-iracing-action.ts` — `SimIRacingAction<T>`, `deck-core`'s `ConnectionStateAwareAction<T>` plus `protected get sdkController(): SDKController` (the singleton's controller). **Extend it only when the action reads iRacing directly** — `getCurrentTelemetry`, `getSessionInfo`, `getCurrentTemplateContext`, or its own `subscribe` for telemetry-driven icons; every other action stays on `ConnectionStateAwareAction`, whose disconnected look reads the sim only through `deck-core`'s presence signal (`isSimAbsent`). Calling `getCommands()` alone does not need it. The class is where an action's direct dependency on iRacing is named, so the leak the Architecture page lists under "Seams & where the abstraction leaks" is one import away from being found; porting those reads is #714's read model.
- `sdk-singleton.ts` — the iRacing SDK singleton: `initializeSDK(logger)` (once, at startup; throws on a second call, and throws before creating anything when a sim connection is already installed, so a refused call leaves the SDK uninitialised rather than half-initialised), `getSDK`, `getController`, `getCommands`, `isSDKInitialized`, `_resetSDK`. `initializeSDK` also constructs `SimIRacingConnection` over the new controller and calls `deck-core`'s `initializeSimConnection` with `absentDelayMs: IRACING_EXIT_SDK_CONFIRM_MS` (the disconnected key look's delay, #1599), so the deck layer's connection exists from the same call, and injects `deck-core`'s `focusIRacingBeforeInput` as `createSDK`'s `beforeKeystrokes` hook (the chat command types; every other command broadcasts, #977). `_resetSDK` resets the sim connection too. `getCommands()` is the iRacing-shaped command surface actions use (camera, replay, chat, pit, video capture, texture, telemetry); a sim-neutral one is #714.

### iRacing helpers

- `app-monitor.ts` — iRacing process detection: `initAppMonitor(adapter, logger)` (takes `IDeckPlatformAdapter`; requires `initializeSDK()` first), `isIRacingRunning()`, `isIRacingActive()` (running-flag OR live SDK connection) and the `onIRacingTerminated(listener)` subscription, whose listeners run after the running flag and SDK connection are already down (#870), with its counterpart `onIRacingStarted(listener)` (#1338): once per session, on the first of the launch event and the SDK connection coming up, re-armed by the exit notification. Exit detection is dual-path: the host terminate event, plus an SDK-disconnect fallback (`IRACING_EXIT_SDK_CONFIRM_MS`, 5 s sustained loss; the constant lives in the leaf `exit-confirm.ts` since #1599, because `sdk-singleton.ts` passes it too and `app-monitor.ts` already imports `sdk-singleton.ts`, so the reverse import would be a source cycle) for hosts that never deliver app-monitoring events — deduped per exit episode, blip-safe when a launch event affirmed the sim is running. Adapters that never deliver launch/terminate events declare `supportsApplicationMonitoring = false` on `IDeckPlatformAdapter` (Ulanzi); the app monitor then keeps SDK reconnect polling enabled at startup instead of pausing it until a launch event that would never come. `deck-core`'s window focus service, `@iracedeck/diagnostics`' resource monitor, `@iracedeck/app-updates`' version check and `@iracedeck/iracing-actions`' audio session hold (#1347) take these as injected delegates rather than importing them (#1176), which `plugin-runtime` wires.
- `elevation-warning.ts` + `elevation-check.ts` — Administrator/integrity mismatch detection (#610, #902): the pure `evaluateElevationWarning` (structurally typed, no native dependency) plus `createElevationCheckSubscriber`, the once-per-connection `sdkController` subscriber `plugin-runtime` wires with the native probe as `getStatus` (`native.getElevationStatus()`) — logs warn on a mismatch, info on a pass (so support logs capture the outcome at the default level), status detail at debug, and posts/clears the PI banner. The probe and its log lines run once per connection (a probe that throws is caught, logged at warn and not retried until the next connection), but the banner is latched separately (#1558): a `setWarning` / `clearWarning` that throws is left to the controller's error boundary and the banner is posted again on the next tick until a call succeeds, without re-running the probe. It also keeps the current connection's verdict for `hasElevationMismatch()` (cleared on disconnect and on a probe that throws), which `plugin-runtime` injects into `deck-core`'s `initWindowFocus` as its fourth argument (`ElevationMismatchCheck`, #1351) so the focus service skips a focus that cannot succeed (#976) — never to gate an action.
- `replay-session-subscriber.ts` — `createReplaySessionSubscriber({ store, getSessionInfo, logger })`, an `sdkController.subscribe` callback in the elevation-check shape that reads `WeekendInfo` (`replaySessionHeaderFromSessionInfo`) and calls `@iracedeck/replay-store`'s `setActiveSession` / `clearActiveSession` (#1162); the store itself knows files and nothing about telemetry.
- `camera-catalog.ts` — the camera catalog model (#1653), pure: every camera group name a session has shown (`groups`, name → first and last seen; it only grows, and a name leaves only through `removeCameraGroup`) and each track's latest list (`tracks`, keyed by `WeekendInfo.TrackID`, replaced on every observation). `recordCameraGroups(catalog, observation, now)` is the one update rule and reports whether anything changed, so an unchanged session saves nothing (a track's `lastSeen` refreshes at most once per `CAMERA_CATALOG_LAST_SEEN_REFRESH_MS`); names go through `iracing-sdk`'s `normalizeCameraGroupName`, and one longer than `CAMERA_GROUP_NAME_MAX_LENGTH` (256) or holding a control character is skipped, because the settings window's remove command (which restates the 256) could never remove it. `parseCameraCatalog` validates a loaded file (`CAMERA_CATALOG_VERSION` 1 only) and `toCameraCatalogView` builds the compact `CameraCatalogView` (`@iracedeck/app-constants`) the PIs read as `_cameraCatalog`. Every name-keyed record has a null prototype and every lookup is `Object.hasOwn`: a camera file may name a group `__proto__` or `constructor`. Spec: `docs/superpowers/specs/2026-11-08-issue-1653-custom-camera-groups.md`.
- `camera-catalog-service.ts` — `createCameraCatalogService({ path, logger, onRejected })`: `cameras.json` (`resolveCameraCatalogPath(settingsPath)`, the settings file's folder; `cameras.catalog.json` there when the settings file is itself called `cameras.json`, compared resolved and case-insensitively, since the catalog's `validate` would set the settings file aside) through `@iracedeck/settings`' `createFileSettingsStore`, unchanged, for its write discipline. A missing file is an empty catalog; an unparseable one, or valid JSON that is no camera catalog (the store's `validate`, `cameraCatalogFileProblem`: no `version`, one that is not a whole number above 1, a version-1 file of the wrong shape), is set aside by the store as `cameras.corrupt-<iso>.json`, reported through `onRejected`, and the catalog starts empty with saving on — as for a missing file, the empty catalog is written only when an observation (or a removal) changes it, so `cameras.json` stays absent until a session runs; an unreadable one (after the settings load's retries) and a newer build's file (`isNewerCameraCatalogFile`, a whole-number `version` above 1) both leave the catalog **memory-only** for the run, never saved over (`persistence()`), so a newer build's file survives a downgrade intact. Observations made before the load finishes are queued, every one in capture order with its own time (at most `CAMERA_CATALOG_QUEUE_LIMIT`, 64, dropping the oldest), and replayed after it with one save and one notification, so the result equals the same sequence made after the load. A store `save` that throws is logged and leaves the change in memory, so the load still finishes and notifies and `start()` never rejects. A finished load logs `Camera catalog loaded` at info (path and counts at debug). `observe`, `remove(name)` (exact canonical name; false before the load or for an unknown name), `subscribe`, `flush` / `flushSync`.
- `camera-catalog-publisher.ts` — `createCameraCatalogPublisher({ catalog, getSessionInfo, publish, canPublish, logger })`: `onTick`, an `sdkController.subscribe` callback that detects a new session info by reference and records one carrying a `TrackID` and a non-empty `CameraInfo.Groups` (live or in a replay, under the replay's own track) through `iracing-sdk`'s `readTrackId` / `readTrackDisplayName` / `readTrackConfigName` / `readCameraGroupNames`; and `onCatalogChange`, the service's listener. It publishes `_cameraCatalog` only at the spec's triggers (the load, a catalog change, a change of the current track or group list, `current: null` on disconnect), only when the JSON differs from the last one sent, and never before `canPublish()`; a trigger that finds settings not ready stays pending.
- `camera-catalog-warning.ts` — the `camera-catalog-rejected` banner: the pure `evaluateCameraCatalogRejectionWarning(rejection)` (`warning`, page-wide, naming the aside) and `createCameraCatalogRejectionReporter()`, the service's `onRejected`. Set-only, like the settings-file banner (`global-settings.md`).
- `fuel-telemetry.ts` — `isFuelFillOn` / `isPitstopActive` / `isAutofuelActive` / `isAutofuelEnabled`, the telemetry readers both Fuel Service surfaces (keypad + dial) share. `sim-events-iracing`'s `toggles.ts` inlines the `isAutofuelActive` rule because that package does not depend on the deck layer.
- `unit-conversion.ts` — fuel unit conversion over iRacing's `DisplayUnits` (`fuelToDisplayUnits`, `fuelFromDisplayUnits`, `getFuelUnitSuffix`, `formatFuelAmount`, …), plus `celsiusToFahrenheit` for temperature readouts.

## Testing

The tests here moved with their modules (`app-monitor`, `sdk-singleton` and `unit-conversion` came from `iracing-plugin-stream-deck/src/shared/`). The root `vitest.config.ts` aliases `@iracedeck/deck-iracing` to this package's source. In an action test, mock this package with `importOriginal` and override only the names the test drives (`getCommands`, the fuel and unit helpers), keeping the `deck-core` `ConnectionStateAwareAction` mock whose `sdkController` field shadows `SimIRacingAction`'s getter — see "Action Test Structure" in `.claude/rules/action-tests.md`. A test that replaces the barrel with a plain factory (its `SimIRacingAction` extends a deck-core class the suite does not load) yet asserts converted figures takes the real `celsiusToFahrenheit` / `fuelToDisplayUnits` from the `./testing` entry (`src/testing.ts`, `exports["./testing"]`, aliased to source in `vitest.config.ts`; #1375), never by relative path into `src/`. Nothing in the entry imports `vitest`, and no production source may import it.

## Build

```bash
pnpm build  # tsc → dist/
```

Pure TypeScript library, no Rollup needed. Outputs ESM with declarations.

## Dependencies

- `@iracedeck/deck-core` — the `SimConnection` interface and its singleton, `ConnectionStateAwareAction`, the focus hook
- `@iracedeck/replay-store` — the `ReplaySessionStore` and `ReplaySessionHeader` types the replay-session subscriber writes to (#1367)
- `@iracedeck/settings` — the PI warning banner (`setWarning`, `clearWarning`) the elevation check and the camera catalog raise, and `createFileSettingsStore` with its load back-off, which the camera catalog's file goes through (#1653)
- `@iracedeck/app-constants` — `PiWarning`, the banner record `evaluateElevationWarning` returns (#1366), and `CAMERA_CATALOG_KEY` / `CameraCatalogView`, the published catalog view (#1653)
- `@iracedeck/iracing-sdk` — `createSDK`, `SDKController`, the telemetry and session types, `resolveAllActiveFlags`, `resolveTemplate`, `PitSvFlags`, `DisplayUnits`
- `@iracedeck/logger` — For the `ILogger` interface
