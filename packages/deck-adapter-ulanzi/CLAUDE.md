# @iracedeck/deck-adapter-ulanzi

Ulanzi Deck adapter that implements `IDeckPlatformAdapter` from `@iracedeck/deck-core`. Bridges the UlanziStudio WebSocket protocol to the platform-agnostic interfaces, so every iRaceDeck action runs unchanged on Ulanzi Deck devices (D200 / D200H / Dial / D200X).

Mirrors `@iracedeck/deck-adapter-mirabox`. The key difference: VSD Craft speaks Elgato-style event names on the wire, so the Mirabox adapter barely translates; Ulanzi uses a flatter `cmd`-dispatched envelope, so the **client** does more work and the **adapter** stays a near-clone of `VSDPlatformAdapter`.

## How It Works

- **`UlanziClient`** (`ulanzi-client.ts`) — low-level WebSocket client. It NORMALIZES every raw Ulanzi frame into an Elgato-style `UlanziEvent` (`normalizeFrame`, a pure function) so the adapter layer can stay structurally identical to Mirabox. It also keeps a **per-context settings cache** (see below) and builds outbound frames. Default `onClose` is `process.exit(0)` — the plugin process terminates when the host closes the socket.
- **`UlanziPlatformAdapter`** (`adapter.ts`) — wraps the client, translating normalized events into deck-core events (`IDeckWillAppearEvent`, `IDeckKeyDownEvent`, …) via `UlanziActionContext`. Near-identical to `VSDPlatformAdapter`.
- **Every per-context event goes through deck-core's `ContextEventOrder` (#1597)** — the client dispatches each frame's one matching registration synchronously and never awaits it, so a `clear`, a `paramfromapp` or input can arrive while an action's `onWillAppear` is still awaiting. `registerAction` creates no ordering of its own: each client callback calls `order.enqueue(context, kind, task)` **before any await**, and the task builds the deck-core event and calls the handler **when it runs**, so the controller and settings it reads are those after the events ahead of it. The rules (lifecycle and the promotion step are exclusive, input waits only for them, liveness at arrival, the 10 s abandon, the log lines) live in `packages/deck-core/src/context-event-order.ts` and the spec `docs/superpowers/specs/2026-11-02-issue-1597-lifecycle-event-ordering.md`; they are not restated here. The per-context bookkeeping is inside the tasks: the appear task sets `contextControllers` then calls the handler, the disappear task reads and deletes the entry then calls the handler, so a throw still drops it and a re-add queued behind a teardown sets its entry after the delete. This replaced #1530's own machinery — `encoderPromotions`, `appearsInFlight`, `pendingPromotion`, `refreshHeldSettings` and the promotion await at the top of every handler — whose discipline ("read the promise synchronously, await it in the handler itself, never through an async wrapper") the primitive makes structural. `adapter.order-contract.test.ts` runs `CONTEXT_EVENT_ORDER_SCENARIOS` from `@iracedeck/deck-core/testing` over a harness that calls the one matching registration synchronously with a normalised frame (the `controller` of a `willAppear` payload goes into the frame, as the explicit-controller path; a second registration for the same event is refused, since the real client reaches only the first synchronously); `scripts/deck-adapter-order-contract.test.mjs` fails the package if that run disappears. Against the pre-#1597 adapter 10 of the 11 scenarios failed (only the concurrency one passed, as an unordered adapter trivially does). What only Ulanzi adds:
  - **Input with no prior `add` is dropped**, by the primitive, with its once-per-context warn (`Dropped <event> for <context>: it never appeared …`), exactly as on Elgato and Mirabox. UlanziStudio does send such input: measured on the SDK simulator (`server/clients.js`) for #1597, a main service that connects while keys are already on the deck gets no `add` replay (`connected()` only registers the socket), and every `keydown` / `dialrotate` after that reaches it with no `add` on that socket; for iRaceDeck a reconnect is a new process (`onClose` exits), so this is a plugin restart with keys on the deck. **If the real host behaves like the simulator, those keys' presses are dropped until a page switch re-adds them.** That is unmeasured on the real host (not running, no device; it probably replays `add` on connect, or nothing would draw at boot, but nothing shows it). A synthetic appear for such input — the spec's decision 3 fallback — was built and then **rejected** (PO, after the code review): an input frame carries no settings, the cache is empty in a fresh process and the protocol has no per-context settings read, so the synthetic appear always ran with `{}`, and `BaseAction.onWillAppear`'s first-appearance `setSettings({ addedWithVersion })` then replaced the key's stored configuration on the host. Losing a key's settings is worse than a dead press. Do not reintroduce it without a settings source.
  - **An `add` for a live context is a settings change.** A host re-sending the `add` of a key it has already added is enqueued as `didReceiveSettings` with the frame's settings, never a second appear (which would double-subscribe and double-render). Decided by `isLive` at arrival; the contract suite checks it on every adapter.
  - **The controller comes from the event kind, not the `add` frame (#1530).** UlanziStudio's `add` to the main service is `{cmd, uuid, key, actionid, param}` and never carries a controller — established from the SDK simulator, the host binary's message builder and its default device profiles; only the Property Inspector learns it, as the `controller` URL parameter, and the `key` names a slot per device (the Dial device's dial is `0_2`; the D200X's dial slots appear in no default profile), so it cannot be mapped either. So a context appears as `Keypad` — the controller is decided at the `add`'s arrival: an explicit `payload.controller` wins, else a context in `knownEncoderContexts` is an `Encoder`, else `Keypad` — and the first dial input (`dialDown` / `dialUp` / `dialRotate`) on a **live** context not yet known as an Encoder **promotes** it. The promotion is **one exclusive step** (`step:promoteToEncoder`), enqueued at the dial event's arrival ahead of that event, and the context goes into `knownEncoderContexts` at that moment, so a burst queues behind one step instead of starting another. When the step runs every earlier event of the context — the Keypad appear included — has settled; it reads `cachedSettings(context)` then (falling back to the dial frame's), runs the synthetic `onWillDisappear` as the previous controller, sets the controller to `Encoder`, runs the synthetic `onWillAppear` as an Encoder, each with its own copy of the settings, and logs and carries on past a handler that throws (failing the step would leave a Keypad whose every dial event re-runs the teardown). The re-appear is what makes the dial work at all: every owning action routes its dial `willAppear` / `didReceiveSettings` to the dial surface under `ev.action.isDial()`, and since #1329 a dial surface drops input for a context its `willAppear` never created (rule 11 in `.claude/rules/encoders-and-touchscreen.md`), so flipping `isDial()` alone would still drop every input. The step changes no liveness, so a real `willDisappear` arriving meanwhile queues behind it and tears the Encoder down; a re-add behind that teardown sets its own fresh entry. `knownEncoderContexts` survives `willDisappear`, so a dial that comes back after a page switch appears as an `Encoder` from its `willAppear`; a context the host declares an `Encoder` explicitly joins it at that `add`'s arrival too, so a dial event arriving while its appear still waits behind a teardown enqueues no pointless step. A first appearance leaves the key icon its Keypad appear pushed on the dial slot: no dial canvas exists here to draw over it (below). The Ulanzi manifest still declares no Encoder controllers (#786), so none of this reaches a user until Ulanzi dials are enabled. Also, `ControllerType` here is `"Keypad" | "Encoder" | "Information"` — no `"Knob"` (unlike Mirabox).
  - **Every input task reads its settings when it runs**: `UlanziClient.cachedSettings(context)`, falling back to the frame's. The client backfilled the frame from the cache at arrival, and an appear that ran while the input waited (the Keypad one finishing, the Encoder re-appear) may have written since — the cache is write-through (#1236) — so the frame's snapshot would hand the action settings it has already replaced. When nothing waited, it is the same snapshot. An appear and a `didReceiveSettings` keep the frame's own settings. A `clear` deletes the cache entry at arrival (`handleFrame`), so a task that runs after it falls back to the frame's; the disappear queued right behind tears the context down, so the staler copy is never acted on for long.
  - **Broadcasts fire at arrival, for a live context only.** `onKeyDown` / `onDialDown` / `onDialRotate` fire when the frame arrives, before the event is enqueued, and only when `order.isLive(context)` — like Elgato's SDK-wide listeners, which pass only a context in its store. The dial broadcast fires at the dial event's arrival, before the promotion step runs (until #1597 it fired after the step's re-appear).
- **No dial canvas** — `dialCanvas()` always returns `null` and `setDialCanvas` sends nothing (#1013), on every context, so a dial surface draws nothing here; enabling Ulanzi dials means choosing (or adding) a `DialCanvasProfile` for its dial screen.
- **`switchToProfile` is a no-op** — UlanziStudio has no profile system. The PI "Stream Deck Profiles" accordion is hidden on this platform via the `profiles` feature flag (`packages/iracing-plugin-ulanzi/platform-features.json`), so the method exists only to satisfy `IDeckPlatformAdapter`.
- **No app-monitoring events** — the protocol maps nothing to `applicationDidLaunch`/`applicationDidTerminate` (see `normalizeFrame`'s cmd switch), so the adapter declares `supportsApplicationMonitoring = false` (#870). The app monitor then keeps SDK reconnect polling enabled at startup — the shared-memory connection is the only "iRacing is running" signal on this host, and its sustained loss is the exit signal for the version-check deferral's SDK-disconnect fallback.
- **`openUrl(url)`** — the adapter's own method sends the `openurl` cmd best-effort (harmless if the host ignores it). PI link clicks route through here too: UlanziStudio ignores `openurl` sent on the **PI** socket, so the PI bridge relays link clicks as a `sendToPlugin` openUrl marker and the adapter constructor forwards them out the plugin socket via `client.openUrl` (#845).
- **`UlanziActionContext.setTitle` is a no-op** — Ulanzi has no native title API (labels travel as the `text` field of the icon setter). iRaceDeck bakes the title into the icon SVG and every action only ever calls `setTitle("")` to clear the native title, which Ulanzi never draws (`setImage` sends `showtext:false`).
- **`createLogger(scope)`** — `createConsoleLogger()` teed to `<plugin>/log/<YYYY.M.D>.log` (`FileSink` + `withFileSink` from `@iracedeck/logger/file-sink`, tagged `"Ulanzi"`, #1375) when a log dir is passed to the constructor (issue #609). The UlanziStudio host discards plugin stdout, same as Mirabox's Stream Dock host. Console + file share the live `logLevel` (`setLogLevel`). `logLocation` is the per-day `log` directory passed to the constructor (`{ kind: "daily", dir }`), or `undefined` without one; the shared bootstrap hands it to the main-thread watchdog and refuses to start without it. The sink's first write each run prunes log files older than `LOG_RETENTION_DAYS` (14, issue #904).
- **Broadcast callbacks** — `onKeyDown`, `onDialDown`, `onDialRotate` fire at the frame's arrival, for a live context only, before the per-action handler's task is enqueued (for window focus; see the ordering bullet above).
- **Plugin UUID** — `PLUGIN_UUID` (`com.iracedeck.sd.core`, the canonical UUID reused verbatim — see the root `CLAUDE.md`) is sent in the `connected` handshake and the global-settings frames.
- **Global-settings scope + boot bootstrap (#868, #1041)** — UlanziStudio persists global settings bucketed by the frame's `uuid` verbatim, so **writes are always plugin-scoped** (`PLUGIN_UUID`, empty key/actionid; the Ulanzi PI bridge in `@iracedeck/pi-components` writes with the same scope). **Reads need the opposite and must never copy that scope** (#1039): the host answers a `getGlobalSettings` only when `actionid` is non-empty — it routes the reply by that field — while the bucket it returns is the plugin-wide one whatever `uuid` the frame carries. Both readers are therefore the write's scope plus an address — same `PLUGIN_UUID`, same blank `key`, only `actionid` differs: the client stands in `PLUGIN_READ_ACTIONID` for the plugin's own reads (#1041), the PI bridge the PI's own `actionid` with `PI_READ_ACTIONID` when its URL has none (#1039). The two constants are deliberately different values — two sockets asking for two different reasons, and a host trace should say which — and share nothing, so there is nothing to keep in sync. The `willAppear` re-drive with the **first appearing action's context** is now a **fallback, not the mechanism**: it is guarded on no reply having arrived, so an answered connect-time read means it never fires. It stays for the one assumption the addressed read rests on — that the host keeps *echoing* an `actionid` it has never seen rather than resolving it — where a real action context is the one shape left; do not delete it, and do not describe it as how an Ulanzi read gets answered. **The read deliberately does NOT stash-and-flush** the way `setGlobalSettings` does: a read written before `open` logs (at info — the persisted `debugLogging` has not been applied that early, so a debug line would be invisible in exactly the support log that needs it) and returns, because the `open` handler issues that same plugin-scoped read unconditionally. **Both reads are load-bearing, one per ordering — do not de-duplicate them.** The settings layer's migration read (`@iracedeck/settings`' `initGlobalSettings`) fires as soon as the missing settings file resolves, which is usually *before* the socket is open, so the connect-time read is what reaches the host; in the other ordering the settings layer ignores the connect-time reply outright (`!migrationRequested`) and migration completes on its own read, sent moments later with the socket already open. Leaving both blank is what let #1041 destroy a user's pre-3.0 settings: three unanswered starts take `_migrationPending` to its ceiling and the start AFTER them used to clear the marker and let the once-per-start mirror overwrite the host copy with schema defaults. That last step is now blocked by the durable `_migrationAbandoned` marker in `@iracedeck/settings`, so such a store keeps its host copy — and since #1047 that marker names the version which gave up, so the next version asks once more and the copy is read back rather than merely preserved. Deleting the settings file still forces a migration from scratch at any point. One consequence of the deferral worth knowing: the settings layer arms `MIGRATION_TIMEOUT_MS` when it *calls*, but since #1056 the client reports the socket opening through `onHostReady` and the settings layer re-arms the deadline once from there, so the handshake no longer comes out of the budget when it completes inside it. What the budget still has to cover is the host's answer. A handshake slower than the budget itself is covered by the OTHER half of #1056, the expiry-side grace: the deadline is extended once when it expires with `onHostReady` subscribed and not yet fired, so the window is bounded at twice the budget and a connect arriving after the first one can still migrate. Only a host silent through both budgets records the give-up (the host copy untouched), and four such starts is the paragraph above. Measured on a live host, all six scope permutations: `actionid` decides whether an answer comes at all, and `key` alone does not. On `uuid`, mind the evidence boundary (#1041): every value in that sweep was an iRaceDeck uuid, which the host normalises to one plugin, so it showed only that `uuid` changes neither the answer nor the bucket *within that set*. A **foreign** uuid the host has never stored anything under gets **no reply at all** — so the field does gate answerability outside it. Still unmeasured: a registered plugin with an empty bucket, since only one plugin is installed on the dev machine, leaving "silent because unknown" and "silent because empty" indistinguishable. Also measured: a populated reply carries **no `code` field**, so the ack drop-filter below keeps it. Reply routing: plugin-scoped replies (uuid absent or `PLUGIN_UUID`) are authoritative and always forwarded; action-scoped replies are only the bootstrap fallback and are dropped once a non-empty plugin-scoped reply has been applied — a per-action bucket's stale contents must not clobber it. Ack-shaped (`code`-stamped) `didReceiveGlobalSettings` frames are exempt from the ack drop-filter only when `globalSettingsOf(frame)` has at least one key — a `code: 0` carrying an empty `settings: {}` is still dropped here. **The PI bridge's translator deliberately differs** (#1039): it drops only a frame carrying no settings field at all, and keeps an explicit empty object, because from a PI's side that is the real answer an empty store gives and dropping it would leave sdpi's `getGlobalSettings()` pending forever — a blank Property Inspector. The two rules are not meant to match; don't converge them without re-deciding both. Since #993 the plugin owns its settings in a file and reads the host store once for migration; it writes the host exactly **once per start**, the guarded mirror (`hostMirrorPayload`: the plugin's full cache plus `_settingsChannel`, since a host write replaces the whole object — skipped when the store started fresh). The adapter needs no write gate for it: the payload is always a full snapshot made after the store is ready. That mirror write can still race the client's own socket connect (observed live on the Mirabox client, whose `send()` was shown dropping a mirror sent ~3s before `open`), so `UlanziClient.setGlobalSettings()` defers until the socket is open, latest-wins — a call made before `open` is stashed and flushed right after the `connected` handshake and the `getGlobalSettings` read. Since phase 2 the Ulanzi PI bridge uses that host copy for ONE bootstrap read of `_settingsChannel` and then routes every `getGlobalSettings`/`setGlobalSettings` to the plugin's loopback settings server instead of UlanziStudio, so PI edits land in the plugin's file. That read shipped blank-scoped and was therefore **never answered**, which is what #1039 fixed — and note what the failure was NOT: the router timed out into a fallback whose replayed read carried the same unanswerable scope, so the Ulanzi PI could not read the host copy either. Every `global` control rendered empty while the settings file was perfectly intact. Do not describe the fallback as a degraded-but-working read path on this host; it is only a working path now that the read is addressable.
- **Public exports** — besides the two classes, `encodeContext` / `decodeContext` / `normalizeFrame` / `parseConnectionParams` (and `PLUGIN_UUID`) are exported from `src/index.ts` — useful for tests and PI-bridge work.

## UlanziStudio WebSocket Protocol

The plugin is the WebSocket **client**; UlanziStudio is the server. Connection params come from `process.argv`:

- `argv[2]` = address (default `127.0.0.1`)
- `argv[3]` = port (default `3906`)
- `argv[4]` = language

On open the client sends the handshake `{ code: 0, cmd: "connected", uuid }` (no separate registration payload — the host already parsed `manifest.json`). Inbound frames are dispatched on the **`cmd`** field; the context string is synthesized client-side as `uuid + "___" + key + "___" + actionid`.

### Frame normalization (`normalizeFrame`)

| Ulanzi `cmd`                                              | normalized event              | notes                                                      |
| --------------------------------------------------------- | ----------------------------- | ---------------------------------------------------------- |
| `add`                                                     | `willAppear`                  | settings in `param`                                        |
| `keydown` / `keyup`                                       | `keyDown` / `keyUp`           | no settings on the wire — backfilled from cache            |
| `dialdown` / `dialup`                                     | `dialDown` / `dialUp`         |                                                            |
| `dialrotate`                                              | `dialRotate`                  | `rotateEvent` (left/right/hold-left/hold-right) → ±1 ticks |
| `clear`                                                   | `willDisappear` (per item)    | `param` is an **array**                                    |
| `didReceiveSettings` / `paramfromapp` / `paramfromplugin` | `didReceiveSettings`          | settings in `param`                                        |
| `didReceiveGlobalSettings`                                | global event                  | settings in `settings`                                     |
| `sendToPlugin` (PI-appear marker)                         | `propertyInspectorDidAppear`  | see below                                                  |
| `sendToPlugin` (openUrl marker)                           | `openUrl` (global event)      | url in `payload.url` — see below                           |
| `sendToPlugin` (openSettings marker)                      | `openSettings` (global event) | the settings-window button (#992) — see below              |
| `run` / `setactive` / acks                                | (ignored)                     |                                                            |

Frames with `code` set and no `cmdType === "REQUEST"` are ack/responses and are dropped — except a `didReceiveGlobalSettings` that carries settings, which is a request reply the client must keep (#868).

### Per-context settings cache

Ulanzi only carries settings on `add` / `paramfromapp`; `keydown` / `keyup` / `dial*` frames omit them. The client caches the latest settings per context and **backfills** press/dial events before routing — otherwise actions would fire with empty settings. The cache is dropped on `clear`.

**The cache is write-through (#1236).** `UlanziClient.setSettings` replaces the context's entry with the written object once the frame is sent — whole, the host's write semantics — so the next press carries what the plugin last wrote. Before #1236 a plugin-side write left the cache on the pre-write object until the next `add` / `paramfromapp`, and on a freshly placed key that meant every press saw `{}`: whatever the actions wrote on first appearance was invisible, so a new Tire Service key had no `toggleMode` and no `addedWithVersion`, resolved as a pre-1.13 instance, and used *Toggle configured tires* instead of *Select configured tires*. Note that a fresh key's base `addedWithVersion` stamp is still not in the cache afterwards, on this host or any other: Tire Service and Fuel Service write `{...raw, …}` after `super.onWillAppear`, which replaces the stamp's object on the host too. That is theirs, not the cache's.

The deliberate edges:

- **The cache is isolated both ways.** It stores a `structuredClone` of every settings object it takes in (`add`, `paramfromapp`, `setSettings`) and hands each backfilled event its own clone, so neither a caller mutating the object it wrote nor a handler mutating its payload can change what later events see.
- **Only a sent write is cached.** `send` reports whether the socket was open. A dropped `setSettings` logs a warning and leaves the entry alone, so the cache never claims settings the host did not receive.
- **A write never creates an entry.** A write for a context with no entry (one landing after its `clear`) still goes to the host, logs at debug, and does not resurrect the entry.
- **An uncached context is backfilled with `{}`**, not left undefined. deck-core's event payloads require a settings object and the adapter would coerce `undefined` to `{}` anyway, so "unknown" cannot reach an action as anything else.

**Unmeasured:** whether UlanziStudio echoes a `paramfromapp` after a plugin `setSettings`. With no Ulanzi device on the dev machine no action ever appears, so no `add` has been observed. If the host does echo, the echo of an EARLIER write could land after a later write was cached and roll the entry back until the later echo arrives — on a fresh key the base's stamp and the action's own write go out back to back. The same echo would reach `onDidReceiveSettings` regardless of the cache, so the write-through does not create that exposure, but measure it before relying on the cache's ordering.

### PI markers (synthesized)

UlanziStudio has no host-generated "PI appeared" event. The Ulanzi PI bridge (in `@iracedeck/pi-components`) sends a `sendToPlugin` marker (`payload.event === "propertyInspectorDidAppear"`) on connect; the client normalizes that into the `propertyInspectorDidAppear` global event so `onPropertyInspectorDidAppear` (e.g. audio-device re-enumeration) works.

External PI links use the same relay (#845): UlanziStudio ignores `openurl` sent on the PI socket but honours it from the plugin socket, so the bridge translates sdpi's `openUrl` event into a `sendToPlugin` openUrl marker, the client normalizes it to an `openUrl` global event (string urls only — no coercion), and the adapter constructor forwards the url via `client.openUrl` after validating it parses as `http:`/`https:` (matching the PI external-link contract, #243; the debug log redacts to origin + path). The settings-window button (`ird-open-settings`, #992) uses the same relay: its `sendToPlugin { event: "openSettings" }` normalizes to an `openSettings` global event that `onOpenSettingsRequest` consumes. **Any other `sendToPlugin` payload normalizes to nothing — a new PI→plugin command on Ulanzi needs a marker added to `normalizeFrame`, not just an adapter listener.**

### Outbound icons

A single `cmd:"state"` frame with `param.statelist:[{ …, type:1, data:<data-uri>, textData:"", showtext:false }]`. Ulanzi has no `setTitle`/`setState`/`setFeedback` — labels travel via the `text`/`showtext` fields, and dial layouts are manifest-declared only. iRaceDeck passes the `data:image/svg+xml,...` URI straight through (raw passthrough; validated on Ulanzi — see the #508 note in `.claude/rules/svg-platform-compatibility.md`).
