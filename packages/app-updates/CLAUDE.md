# @iracedeck/app-updates

The plugin's own release notes and update checks, moved out of `deck-core` in #1367 (spec #1351, `docs/superpowers/specs/2026-10-07-issue-1351-deck-core-split-and-sim-seam.md`): the startup version check that opens the changelog after an upgrade (#680), and the upstream update check behind the settings window's What's New tab (#1016) — the published-changelog fetch, its parser and sanitizer, and the service that caches the verdict. It depends on `@iracedeck/app-constants` (the changelog notification policies), `@iracedeck/fetch-utils` (`abortAfter` and `readCappedJson` for the one network read), `@iracedeck/logger`, `semver` and `zod`. Two packages depend on it: `plugin-runtime` (its settings phase runs the version check and creates the update-check service) and `@iracedeck/settings-window`, for the `UpdateStatus` type its server answers `GET /updates/status` with.

## Module map

- `version-check.ts` — startup version-upgrade detection and the changelog opener (#680, #742, #870, #901): `shouldOpenChangelog`, `resolveChangelogDecision` → `ChangelogDecision`, `buildChangelogUrl`, `runVersionCheck`, `CHANGELOG_BASE_URL`, `MONTHLY_WINDOW_MS` and `VERSION_CHECK_STARTUP_GRACE_MS`. Pure except `runVersionCheck`, the orchestrator, which takes injected `persist` / `openUrl` delegates and an `isSimRunning` delegate: a due open never happens while iRacing is running — it defers, persisting nothing, and `plugin-runtime` re-runs the check on `deck-iracing`'s `onIRacingTerminated`. The `changelogNotification` policy values and their default are `@iracedeck/app-constants`' `changelog-policy.ts`. Full behaviour in `.claude/rules/global-settings.md`.
- `published-changelog.ts` — the shape of `https://iracedeck.com/changelog.json` (`parsePublishedChangelog`, `PublishedRelease`), the artifact the website build composes from `changelog.mdx` and the in-development fragments in `changelog.d/` through the same functions as the copy compiled into the build (`scripts/lib/changelog-composed.mjs`, over `changelog-data.mjs`). Fields it does not model are ignored rather than rejected, so the artifact can grow without breaking older plugins. Bullets are sanitized here, on the way in, so nothing downstream renders unsanitized remote markup. `PUBLISHED_CHANGELOG_MAX_RELEASES` / `_CATEGORIES` / `_ITEMS` cap the shape (#1101).
- `changelog-html-sanitize.ts` — `sanitizeChangelogHtml`, the allow-list sanitizer for one bullet: it re-emits the four constructs the generator produces (`<code>`, `<strong>`, `<em>`, an `<a>` with `href` / `target` / `rel`) and escapes everything else into visible text. A hand-rolled scanner, not a DOM, and linear in the bullet's length by construction (#1101) — it runs over remote text inside the plugin process.
- `changelog-feed-client.ts` — `fetchPublishedChangelog`, the one place the plugin talks to iracedeck.com for the update check and the only module here that does I/O. The URL is the constant `PUBLISHED_CHANGELOG_URL`, never taken from a page or a request. It reads the body through `readCappedJson` under `CHANGELOG_MAX_BYTES`, with a `CHANGELOG_FETCH_TIMEOUT_MS` deadline, never `response.json()` (#1101), and never throws: every failure is `undefined`, "we do not know".
- `update-check.ts` — `selectAvailableUpdates`, the product decision in one pure function: only a release with a real calendar date counts as published (the `_Unreleased_` release composed from the fragments never does — only the release fold dates it, and an unreadable date costs that one release rather than the whole artifact), and plain `semver.gt` against the running version, with no pre-release special case.
- `update-check-service.ts` — `createUpdateCheckService`: consults its injected `isEnabled()` on every call (`plugin-runtime` binds it to the `updateCheck` setting, read live) (nothing happens unless someone asks, and switching it off stops the requests without a restart), fetches at most once per TTL (`UPDATE_CHECK_SUCCESS_TTL_MS` 1 h, `UPDATE_CHECK_FAILURE_TTL_MS` 5 min, single-flight), caches the releases rather than the verdict so the running version is re-applied on every call, and never throws or rejects. Its only caller is the settings window's `GET /updates/status`.

## What reaches it, and from where

`pi-components`' `update-notice.ts` (`ird-update-notice`) renders the bullets this package sanitized, which is why it assigns `innerHTML` for them; a change to the sanitizer's allow-list is a change to what that component renders. `published-changelog.test.ts` reads the committed `packages/iracing-actions/src/actions/data/changelog.json` by path — built by the same generator from the same `changelog.mdx` as the published artifact — and fails while there is still half of the byte cap and of every shape cap left, so a cap is raised before the feed goes dark in the field.

## One import path per name

The barrel `src/index.ts` is the package's only entry, and deck-core re-exports none of it: import every name it exports from `@iracedeck/app-updates`, and mock that package in a test that stubs one (`plugin-runtime`'s settings-phase and order tests mock it through `recordedModule`).

## Rules

The version check's policies, its iRacing deferral and the startup grace are in `.claude/rules/global-settings.md`; the update check's place in the settings window (the `/updates/status` route, the What's New tab, `ird-update-notice`) in `.claude/rules/settings-window.md`; the changelog's format, which the published artifact is parsed from, in `.claude/rules/changelog.md`.
