# @iracedeck/audio-assets

Voice lines for the Race Engineer, each voice's callout script, the radio sound effects (`sfx/`), and the ElevenLabs TTS generator that produces the voice clips.

See `.claude/rules/race-engineer-callouts.md` for the end-to-end "how to add a callout" walkthrough that includes this package; the notes below cover the audio-assets-only mechanics.

## Where voice lines live

Each voice has its own `configs/<voice-id>.voice.json` file. The filename stem (e.g. `default` from `default.voice.json`) is the voice id and the on-disk directory name (`voice/<voice-id>/...`) — the id the pack's `voice-pack.json` declares, so the loader holds the stem to the pack format's own `packId` rule from `@iracedeck/callout-script` (the rule the plugin's scanner admits a voice id by, #1134) and names the file when it fails; once installed, the plugin refers to the voice as `<pack id>::<voice id>` (`default::default`, #1144). The generator auto-discovers every `*.voice.json` in `configs/` — adding a new voice is a drop-in file plus a manifest rebuild, no enumeration list anywhere.

Voice files are **self-contained**. Each carries its own `model_id`, `voice_settings`, optional `output_format` / `apply_text_normalization` / `enable_logging` / `optimize_streaming_latency` / `pronunciation_dictionary_locators`, and its own `groups` map of entries. There is no shared root config — different ElevenLabs models often need different settings (different `speed`, different stability/similarity), so sharing defaults across voices would be a footgun.

Per-entry overrides fall back to the voice's value when omitted, so an individual line can pin a different model, language, normalization, etc. Supported per-entry override fields: `model_id`, `voice_settings` (shallow-merge), `output_format`, `apply_text_normalization`, `apply_language_text_normalization`, `optimize_streaming_latency`, `pronunciation_dictionary_locators`, `use_pvc_as_ivc`. Every audio-affecting override field feeds the per-entry hash, so flipping one on a single entry invalidates only that entry's cache.

Each entry:

- `name` — kebab-case file stem; the suffix `-01` reserves room for variants (`-02`, `-03`, …).
- `text` — the spoken line; `<break time="0.3s" />` inserts a natural pause. **No hyphens, dashes, ellipses, colons or semicolons** in `text`, `previous_text` or `next_text` (#1518): ElevenLabs reads each as a pause and often fills it with a hesitation sound ("ahhmm…"). Write a period where a pause is needed, even when the grammar then reads oddly (`"Change. You're behind"`), and drop the hyphen from a compound (`left front`, `double check`). `src/generate/pause-marks.ts` defines the set; the generator refuses such text, dry run included, and `src/clip-text.test.ts` fails on it. The clips cut before the rule are not changed: `pause-marks.grandfathered.json` freezes each by its text, so a re-cut a dependency or a voice-wide setting forces still runs (with a warning) while an edited or new line is refused. The list only shrinks — never add to it; the test freezes each voice's count, which an entry coming off the list lowers in the same change.
- `seed` (optional) — fixed integer for reproducible prosody across regenerations. **On new entries, omit it** (the generator schema defaults an omitted seed to `1`) or set it explicitly to `"seed": 1` — never author a new entry with an arbitrary or random-looking seed. The seed only selects which take ElevenLabs produces, so a random default has no benefit and makes the value look meaningful when it isn't. Bump the seed deliberately (2, 3, …) only when the generated clip doesn't sound right and you want a different take. The seed feeds the entry hash, so changing it re-cuts just that clip.
- `previous_request_ids` / `next_request_ids` (optional) — IDs of clips that semantically precede/follow this one; biases ElevenLabs toward continuous prosody. Either a `<group>/<entry-name>` reference (resolved per-voice at generate time) or a raw ElevenLabs request id.

## The callout script — `scenarios`, `frames`, `pools`, `fragments` → `voice/<voice-id>/callouts.json` (#1064, #1065)

The same `configs/<voice-id>.voice.json` also carries the voice's **callout script**, under four optional top-level keys beside `groups`: `scenarios` (scenario id → what to say when the code-declared contract fires — `sequence`, or `skip: true`, plus the `comment` and `test` lines the published reference is built from), `frames` (named open/close wrappers, `radio` by default; `none` is reserved and can never be defined), `pools` (pool name → `{ group, base }` — an alias facility, usually absent: a sequence addresses its clips directly as `pool:<group>/<base>`, and a name is given only where it carries a decision), and `fragments` (#1065: name → `{ comment, sequence }`, a sub-sequence several entries of the SAME script include as `"@<name>"` — the compiler inlines it, so it is sharing between scenarios, never an escape hatch for complexity inside one; the bundled voice has two, `readback-body` and `gap-readout`). One file per voice, on purpose: it is what a pack author is handed. The grammar — types, Zod schema, `parseCalloutScript` — is `@iracedeck/callout-script`; the how-to and the vocabulary a script can reference live in `.claude/rules/race-engineer-callouts.md`.

That file never ships (the ElevenLabs voice id, the TTS settings and every line of text stay here), so the four maps are **extracted** into a committed artifact inside the voice tree:

```bash
pnpm generate:callout-scripts     # every configs/*.voice.json → voice/<voice-id>/callouts.json
```

The artifact is the four maps under a `schema: 1` header, keys in the author's order (it is the reading order of the reference), two-space LF JSON. A voice that authors none of the keys still gets one, with empty maps — a valid, clips-only voice whose callouts are all skipped. `scripts/generate-callout-scripts.mjs` loads the configs through `loadVoiceConfigs`, so a malformed key fails there naming the file and the path (`Invalid default.voice.json:` + one `<path>: <message>` line per issue), re-checks each extracted script with `parseCalloutScript`, and writes nothing until every voice has passed. The freshness test `src/callout-scripts.test.ts` fails when any artifact drifts from its config, naming the command — same pattern as `manifest.json` and `changelog.json`. In a Claude Code session the post-edit hook runs it whenever a config is saved; run it by hand outside one, or when the hook reports a failure — and commit the artifact with the config either way.

Placing the artifact **inside** `voice/<voice-id>/` is what lets it ride every path a voice already travels with no extra wiring: the plugin build copies it (below), the packer stages it (voice packs, below), the installer's seed copies it, and the voice-pack scanner (`@iracedeck/voice-packs`) reads it beside the clips it admits. It is not a clip: `manifest.json` never lists it (`src/manifest.test.ts` pins that) — the voice-pack service reads it and hands the engine a per-voice map.

## What ships is not the committed mp3 — the build-time loudness gain and radio filter

The committed `voice/**/*.mp3` files are the **dry TTS source clips**, not what plugins play, and the build never rewrites them. At plugin build time every voice clip goes through `processClipIntoCache` (`src/build/index.mjs`), which runs ffmpeg **twice** on one in-memory snapshot of the source:

1. **Loudness measurement (#1657).** `measureLoudness` reads the clip's integrated loudness (ITU-R BS.1770, ffmpeg's `ebur128`) on the clip looped 8× (`-stream_loop 7`), so even a sub-400 ms clip fills the meter's gating window; looping leaves the reading unchanged. `loudnessGain` turns it into one static gain to `VOICE_LOUDNESS_NORMALIZATION.targetLufs` (−22 LUFS, Default's own median, so Default keeps its level), rounded to 0.1 dB so float noise between machines never changes the bytes, and clamped to ±12 dB. A reading below −50 LUFS is taken as silence and gets 0 dB. A failed run or an unreadable summary fails the clip, as a failed encode does: a gain is never guessed.
2. **Encode.** `volume=<gain>dB,` in front of `RADIO_ENGINEER_FILTER` (`src/presets.mjs`): a 250–3500 Hz bandpass + 8 dB pre-gain into a `tanh` soft-clip, then a brick-wall limiter — plus a re-encode to 16 kHz mono 32 kbps (`ENCODE_ARGS`). The gain sits **ahead** of the filter so every clip drives the soft clip and the limiter equally hard: with mismatched input a loud batch was saturated more than a quiet one, and two clips joined in one callout differed in tone as well as level (the reported case: the Short callouts voice's lap-time seconds quieter than its decimals).

So a clip always sounds different in-plugin than the source mp3 — that difference is this pipeline, not a generation problem. Why static, BS.1770 and before the filter, and the rejected alternatives (normalizing at generation time, per group, at playback), are in `docs/superpowers/specs/2026-11-08-issue-1657-voice-clip-loudness-normalization.md`. Third-party packs are not normalized: a pack someone builds plays what its author exported.

**Loudness warnings.** A clip that hits the clamp or reads as silence gets a warning naming it — `Voice clip <voice-id>/<group>/<clip>.mp3: measured …; fix the clip` — through the `warn` option of `processAndCopyAudioAssets`, `prebuildAudioAssetCache`, `processVoiceTree` and `packVoice` (a Rollup `(!)` warning in a plugin build, `console.warn` in the prebuild, `pack:voice`, `stage:dev-voices` and the publish script, `warn` level in the harness log); a caller with no `warn` gets it through `logger`, prefixed `WARNING: `. Fix such a clip at the source, never wave it through. The reading is not cached, so a clip warns **only when the run re-encodes it**: a warm cache prints nothing, while a cold build — CI, the publish workflow, the first build after the pipeline identity changes — re-encodes and so reports every clip.

Processed outputs are cached under `.cache/<pipeline-hash>/`, where the hash is `pipelineCacheKey()`, the first eight hex digits of `pipelineIdentityHash()` over `PIPELINE_IDENTITY` in `src/build/index.mjs`: `filter` (the filter chain), `loudness` (the whole `VOICE_LOUDNESS_NORMALIZATION` descriptor — target, clamp, rounding step, silence floor and measurement loops/filter, whose ffmpeg arguments are built from it so what runs cannot drift from what is hashed), `encodeArgs` and the installed `ffmpeg-static` version (#1667; before it the key missed the binary, so an `ffmpeg-static` bump went on serving the old binary's output from a warm cache). Editing either preset, the encode args or bumping `ffmpeg-static` invalidates every processed clip once, and a cold re-encode costs two ffmpeg runs per clip. That identity is also the pack record's `inputs.pipeline` (*Voice packs* below), so the cache and the record cannot disagree about what "the pipeline changed" means: anything new that moves a clip's output bytes is ONE JSON-safe field added there, as `loudness` was, never a separate key, and it marks every committed pack stale until re-packed (and, for a released version, bumped — #1657 took `default` to 1.4.2 and `iracedeck-terse` to 1.3.2). Per-file invalidation is **content-based** — each cached clip carries a `<clip>.src.sha256` sidecar holding the sha-256 of the source bytes it was built from, and the entry is fresh only while that still matches (an entry with no sidecar, i.e. every cache written before #1143, is stale once). It was mtime-based until #1143, a rule Windows breaks routinely: a copy (Explorer paste, `cp -p`, an extracted archive) carries the mtime of the file it came FROM, so replacing a clip left the new source looking OLDER than the output built from the clip it replaced, and both the plugin build and `pack:voice` went on serving the stale audio with nothing in any log to say so. This package's own `pnpm build` (`src/build/prebuild.mjs`) exists solely to warm that cache before the parallel plugin builds run, so each plugin's Rollup copy step (`processAndCopyAudioAssets`) only ever reads cache files instead of racing over the same ffmpeg writes (contention rationale documented in `src/build/index.mjs`).

The one file inside `voice/` that is **not** a clip, `voice/<voice-id>/callouts.json`, is copied as-is — bytes unchanged, never through ffmpeg, never into the cache — so it lands at `assets/audio/voice/<voice-id>/callouts.json`, exactly where the scanner opens it. Only the file directly under the voice counts; a `callouts.json` deeper in the tree is ignored like any other non-mp3. `src/build/index.test.ts` proves both, on a temporary tree, for the packer's walk (`processVoiceTree`) and the plugin's (`processAndCopyAudioAssets`).

The build task has one dependency, declared in the root `turbo.json`: `@iracedeck/audio-assets#build` depends on `@iracedeck/callout-script#build`. `src/build/index.mjs` imports the grammar (for the script's file name), and the packer imports its parser — and the package-specific turbo entry carries **no** `^build`, so without that edge nothing orders the grammar's `dist/` before the very first build task, nor before the manual *Publish voice packs* workflow, which builds only this package. It is the narrow edge rather than `^build` so the ffmpeg pass — a cold build's critical path — does not also wait for `deck-core`. The grammar and `ffmpeg-static` are this package's `dependencies`, not devDependencies (#1375): the `./build` entry that loads them is run by other packages (`plugin-build`, the harness), and Node resolves both from this package's own folder, so as devDependencies they were found only because a workspace install links every package's devDependencies too. Everything else here — `fflate`, `semver` and `zod` for the packer, the pack record and the generator, `voice-packs` and `track-data` for tests — stays a devDependency.

Consumer surface (`package.json` exports): `./build` (`processAndCopyAudioAssets` / `processAndCopyAudioAssetsPlugin` / `prebuildAudioAssetCache` / `wipeProcessedCache`, used by the plugins' shared Rollup config in `@iracedeck/plugin-build` and the scenario harness — `processAndCopyAudioAssets` also takes `srcRoot` / `cacheDir`, test seams that let its test run the whole copy over a temporary tree, with the same "a foreign root needs its own cache" rule as the packer; `processVoiceTree`, the same pipeline for one voice's subtree, used by the voice-pack packer, returning the clips it wrote as `files` and the copied script as `script` — kept apart on purpose, since the packer counts and grammar-checks `files` as clips; and the `VOICE_PACKS` / `BUNDLED_VOICE_IDS` registry below), `./presets` (`RADIO_ENGINEER_FILTER`, `VOICE_LOUDNESS_NORMALIZATION`), `./manifest.json` (the authored manifest) and `./manifest.bundled.json` (the slice a plugin distributable carries), `./catalog/*.json` (the committed catalog entries), `./voice/*/callouts.json` (the callout-script artifacts), and `./sfx/*` (the sound effects as committed, which `iracing-actions`' press-sound clip test resolves by name, through a devDependency, rather than by a relative path into this package — #1375).

## Voice packs — packing a voice for the catalog (#1034, stage 2)

`src/build/voice-packs.mjs` is the **one list** separating what ships inside the plugin from what is downloadable: every entry is published to the catalog, and `bundled: true` additionally keeps the voice's clips in the plugin distributable (the plugin build's audio copy step filters `voice/` to `BUNDLED_VOICE_IDS`). Stage 3 of the rollout flipped `default` to `bundled: false` (2026-09-07), so **no plugin ships a voice**: `BUNDLED_VOICE_IDS` is empty and `assets/audio/` is the `sfx/` tree alone. Setting `bundled: true` on an entry puts that voice's clips back in the distributable, but since #1144 it is no longer the whole job: the voice-pack service's read of a bundled voice's script went with the reserved-voice rule, so a re-bundled voice would load with no script and speak no callout until that read is restored. A pack's `version` is its own, independent of the plugin's; bump it whenever the archive changes under a version that has been released (the pack record below says which). `voices` lists voice ids only — each voice's label comes from its `configs/<id>.voice.json`.

```bash
pnpm --filter @iracedeck/audio-assets pack:voice                          # every pack in VOICE_PACKS
pnpm --filter @iracedeck/audio-assets pack:voice default                  # one pack
pnpm --filter @iracedeck/audio-assets pack:voice default --no-catalog     # stage + zip only, catalog entry and pack record untouched (#1143)
pnpm --filter @iracedeck/audio-assets pack:voice default --stage-only     # stage only: no zip, no catalog entry, no pack record (#1214)
pnpm seal:voice-packs default                                             # check, then seal the current version as released (#1667) — before a between-releases publish
pnpm --filter @iracedeck/audio-assets stage:dev-voices                    # stage every pack --stage-only, iff development voice mode is on at the default root (#1214); `pnpm stage:voices` from the root
```

`scripts/pack-voice.mjs` runs the pack's voices through the **same** loudness + radio-filter + encode pipeline as the plugin build (`processVoiceTree`, sharing `.cache/<pipeline-hash>/`, so a packed clip is byte-identical to a shipped one), stages `voice-pack.json` + `voice/<voice-id>/callouts.json` + `voice/<voice-id>/<group>/<name>.mp3` under `dist/voice-packs/<id>/` (gitignored — the shape the voice-pack scanner accepts, and a maintainer can sideload it as-is), zips it to `dist/voice-packs/<id>-<version>.zip` (**skipped under `--stage-only`**, #1214, which stops after the stage), and — **unless `--no-catalog` is given** (#1143), which stops after the zip — writes the **committed** catalog entry `catalog/<id>.json` (bytes, sha-256, release URL) and beside it the **committed** pack record `pack-records/<id>.json` (below). The script is validated with `parseCalloutScriptText` — the grammar's one text stage, the very function the scanner runs over the same bytes — **before** the voice is staged, and a script that fails (unreadable, or refused by the grammar — a file that is not JSON is the grammar's first problem, `(document): not valid JSON: …`) fails the pack naming the file and every problem: the scanner drops a voice with a bad script, so such a pack would install cleanly, claim nothing and be silent. The file is found by its exact name in a directory listing, the same rule the walk stages by — never `existsSync`, which is case-insensitive on Windows and once let a `Callouts.json` validate and then not ship — and a wrong-cased name is refused naming the lowercase one; it must also be a regular file by `lstat`, since the walk stages only what `Dirent.isFile()` admits and `readFileSync` would follow a symlink to a script the walk then leaves out. A voice with no script file is a clips-only voice and packs fine. `processVoiceTree` copies the file as-is and reports it separately from the clips, so the per-voice "staged N of M source clips" check and the `clips` count in the output (`Packed default@1.4.0: 4810 clips, 1 callout script, …`) stay mp3-only. The archive is attached to the GitHub release the entry's `url` names (`voices-<id>-<version>`) by `scripts/publish-voice-packs.mjs`, which the plugin's tag workflow runs on every release and the manual *Publish voice packs* workflow runs between releases (#1116) — it holds every pack record to the four rules before it packs anything, verifies the runner's archive against the committed entry, refuses to publish a mismatch, and under `--publish` refuses a pack whose current version is not sealed in its record. Nothing is uploaded by hand. The website assembles the entries into `voice-catalog.json`.

**The packer is byte-deterministic, and that is the contract**: the catalog's `sha256` is what decides whether a user downloads, so a packer that produced new bytes from unchanged clips would make every user re-download 12.5 MB per build. Entry order is sorted, every entry's timestamp is the DOS epoch (built from *local* date fields, because fflate converts through local-time getters), compression level, origin OS and attributes are pinned, no extra fields or comments are written, and `voice-pack.json` is serialized with sorted keys and LF endings. `callouts.json` is the one text file copied from the working tree rather than generated in memory, and it stays reproducible across a Windows checkout and the Linux release runner because `.gitattributes` pins `*.json` to LF — the packer adds nothing and normalizes nothing. `src/pack-voice.test.ts` packs twice through the whole pipeline — separate caches, so ffmpeg runs both times — and compares hashes, runs the real schemas and scanner over the output (`VoicePackManifestSchema` from `@iracedeck/callout-script`, where the pack format's rules live since #1134; the catalog schema and the scanner from `@iracedeck/voice-packs`, by package name (a devDependency, #1375) — the voice comes back with its parsed `script`), and proves the archived script is byte-for-byte the source. The packer's own pre-stage checks are those rules imported, not restated. Before anything is read from disk: `packId` for the pack id and every voice id (they become paths before a manifest exists), and the pack's `version` and `minPluginVersion` in their CANONICAL spelling — a string `isSemverVersion` accepts, with no surrounding whitespace and no leading `v`. That is stricter than the plugin on purpose: `isSemverVersion` is what the plugin accepts (it trims and allows a `v`), while the packer writes the version verbatim into the release tag, the archive name and the catalog url; a number fails naming the field. Then, still before staging, the very object `buildVoicePackManifest` produces goes through `validateVoicePackManifest` — the scanner's own schema, so an empty `author` or a label with a control character fails in the plugin's words, naming the pack — and a voice listed twice is refused with `dedupeDeclaredVoices`: a build failure, where the scanner would only keep the first. Each voice's config `label` is checked with `displayLabel` naming the config file, and `USABLE_VOICE_CLIP` per staged clip. The manifest's `schema` is the leaf's `VOICE_PACK_MANIFEST_SCHEMA_VERSION`. Only the catalog entry's 300-character description bound is still spelled out here, because that rule is `voice-packs`' catalog schema's and this plain-node script cannot import it. No test re-derives the committed entries' `bytes`/`sha256` (that needs the full encode); the pack record is what ties the entry to the tree. Re-run `pack:voice` — flagless, so the entry and the record are written — after any clip, script, config `label` or pack-definition change, and commit `catalog/<id>.json` **and** `pack-records/<id>.json` together.

**`--no-catalog` and `--stage-only` are per run rather than modes** (#1143, #1214). `--no-catalog` stages and zips exactly as a flagless run does and stops there; `--stage-only` is stricter, stopping once the stage and its manifest are written — every check a full run makes before the zip still runs (the script's grammar, the staged-vs-source clip count, `USABLE_VOICE_CLIP`, the manifest), but no archive and no catalog entry is written, and an archive an earlier run left beside the stage is left alone. Given both, `--stage-only` wins. Either leaves `catalog/<id>.json` and `pack-records/<id>.json` (which describes it) byte-untouched, because that entry is the release contract: its `sha256` is what the installer compares an installed pack against and what the publish workflow refuses to ship a mismatch of, so a run whose only purpose is a staged tree for a repo developer to hear must not rewrite it. The release workflow keeps calling the script without either flag. So never reach for a flag when the entry genuinely needs regenerating: a clip or script change with no flagless re-run leaves a stale record, which `src/pack-record.test.ts` fails on (below). The development loop itself no longer names a flag: `scripts/stage-dev-voices.mjs`, the `stage:dev-voices` turbo task every plugin `#build` depends on, stages every pack in `VOICE_PACKS` with `--stage-only` (`writeArchive: false`) whenever development voice mode is on at the default root — `IRACEDECK_DEV_VOICES=1`, or a `dev.local.json` naming `dist/voice-packs` — and stages nothing when it is off or the marker names a hand-picked root. At the default root it first removes any directory that is not an authored pack id, so a dropped or renamed pack stops being scanned; files (zips) are left alone. The task is `cache: false` with no `outputs` — it does not own `dist/voice-packs/`, and a restore could resurrect reverted clips. So, with the deck host running, the loop is edit → `pnpm stage:voices` → **Rescan voices** → drive; `pnpm build` restages too but reruns all three plugin builds after a voice edit, which a running host would not load before its next start, so build with the host stopped and then start it; the resolution rules and the turbo hashing live in `@.claude/rules/platform-feature-flags.md`. `--no-catalog` remains for a zip nobody should commit (a sideload, an inspection). An unknown option is refused rather than taken for a pack id, since a mistyped `--nocatalog` would otherwise write the very entry the author typed the flag to spare.

**The pack record — a stale entry fails `pnpm test` (#1667).** Until #1667 only the publish script re-derived an entry, so #1582 changed both packs' `callouts.json` with every PR check green and the `v3.8.1` tag run was the first thing to fail (#1665). Now each pack in `VOICE_PACKS` has a committed `pack-records/<id>.json`, written by the flagless `pack:voice` run that writes its entry and only by it (`packVoice` takes `catalogDir` and `recordsDir` together or neither, so a scratch run such as the publish script's cannot rewrite the committed record). It holds the pack's `id`, `version` and archive `sha256`, then `inputs`: `pipeline` (`pipelineIdentityHash()`, above), `archiveFormat` (the installed `fflate` version plus `ZIP_ENTRY_OPTIONS`), `manifest` (the sha-256 of the exact `voice-pack.json` bytes the packer writes — so the version, the pack label and author, and every voice's config `label`), and per voice `clips` (the count), `clipsSha256` (one digest over every source `.mp3`'s POSIX path and content, never mtime) and `script` (the `callouts.json` sha-256, or `null`). Optionally `released: { version, sha256 }`. `src/build/pack-record.mjs` owns the computation and the four rules, and the packer, the tests, the release hook and the publish script import it rather than restate it: **1** every published pack has a record and no stray record exists; **2** the record's `id`/`version` match the definition and its `sha256` matches the entry; **3** the recomputed inputs equal the recorded ones, each differing part named; **4** with `released`, the version is at or above `released.version` (semver; a published version is bumped, never rolled back), and when equal the `sha256` must still be `released.sha256`. `src/pack-record.test.ts` holds the real tree to them in the ordinary `pnpm test` (so in the `ci-test` shards, under a second, no ffmpeg, no network, no git), hashes the tree once (rule 3 inside `checkPackRecords`), and floors each voice's clip count (`countSourceClips`, the walk the digest uses) against both the record and a fixed minimum so an empty walk cannot agree with anything; the rules themselves are unit-tested over a temporary tree in `src/build/pack-record.test.ts`. A failure names the pack and the part, and the fix: when the version is released and a clip, the script or `voice-pack.json` drifted, bump `version` in `src/build/voice-packs.mjs`; when the version is released and ONLY `inputs.pipeline` or `inputs.archiveFormat` drifted (an `ffmpeg-static` or `fflate` bump), re-pack first and bump only if the packer refuses, since a needless bump changes the archive and makes every user re-download it; either way, `pnpm --filter @iracedeck/audio-assets pack:voice <id>` and commit `catalog/<id>.json` and `pack-records/<id>.json`. **Sealing** — `released` is written only by the release hook and by the seal command, both through `sealPackRecords`, which checks every pack and throws (with `.problems`) before it writes anything. The hook (`scripts/release-hooks.mjs`, `before:bump`) refuses a version that is not semver, then runs the four rules on every release as a dry seal — a problem aborts with a clean tree, printing `formatPackRecordProblems` — and on a version with no `dev` prerelease identifier (`semver.parse(version).prerelease.includes("dev")` is false: stable, `-rc`, `-beta`; a `-dev` bump checks and seals nothing) writes the seal after the changelog fold and before the version bumps, so the fold's part-way messages stay true and a seal that fails leaves no bumped version file, then stages the records with the version files in the one `git add` of the `chore(release)` commit, whose `git add --dry-run` preflight already named them. Its dry branch (`RELEASE_IT_DRY_RUN=1`, which `pnpm release:dry` reaches by running the hook itself, since release-it 21.1.1 skips hooks in a dry run) prints `Would seal N voice-pack records as released:` with each path, version and sha-256. `pnpm seal:voice-packs [<id> …]` (`scripts/seal-voice-packs.mjs`; every pack when none is named; an unknown id is refused naming the known ones before anything is read) does the same checks and seal and nothing else, prints `Sealed packages/audio-assets/pack-records/<id>.json: <id> <version> released (sha256 …)` per record and the hint to commit `packages/audio-assets/pack-records/` to `master` before *Publish voice packs* is dispatched with `publish` on, or `Nothing to seal: … already sealed as released.`; exit 1 on any refusal. `scripts/publish-voice-packs.mjs` runs `checkPackRecords` in pass 1 before any pack is encoded, and with `--publish` refuses every pack not sealed at its current version: `<id> <version> is about to be published but is not sealed in pack-records/<id>.json — seal it on master first.`, followed by the seal command to run; a dry run needs no seal. `isSealedAt(record, version)` is the one predicate every reader of a seal uses. **A seal for a version that never shipped** — the hook seals in the `chore(release)` commit, before the tag: if the tag is then declined at release-it's prompt, or the tag run fails before the pack upload, the record says `released` for a version nobody ever published, and the pack's next change would be pushed to a needless bump. Check with `gh release view voices-<id>-<version>`: when there is no such release (or it has no archive asset), remove `released` from `pack-records/<id>.json` by hand in the same change that re-packs the pack, and say so in the commit. That is safe because nothing was published under that version, so no user holds an archive those bytes could disagree with; the rule a seal protects — a published archive never changes under its version — has nothing to protect yet. Never do it for a version `gh release view` shows with its asset: that one is out, and gets the bump. **The packer's refusals** — a flagless run preserves `released` untouched; under a sealed version it still packs (the archive is left in `dist/` to inspect), but if the new sha-256 differs from `released.sha256` it writes neither the entry nor the record and names the bump, and if it is equal (an `ffmpeg-static` bump that left the output identical, say) it writes the record with the new inputs and no bump is needed — inputs decide when a re-pack is due, bytes when a bump is. It also refuses to write either file if the source tree changed while it was encoding, since the record would then describe an archive never built from it.

The byte rule has a corollary worth stating: the archive's bytes may only change under a version that has never been published. Adding `callouts.json` to `default` changed its bytes, and `default` stayed at `1.0.0` with `catalog/default.json` regenerated (decided 2026-09-04) — because `1.0.0` had not shipped; the 3.2.0 tag run is what creates its release. Had it been out, the same change would have been a `version` bump, since the publish workflow refuses an archive whose bytes differ from the committed entry. That is exactly what happened next: #1138 moved nine script `if`s into contract gates after `voices-default-1.0.0` had been published with 3.2.0, so `default` went to `1.0.1` in `src/build/voice-packs.mjs` and the flagless `pack:voice default` regenerated the entry — the shape every later script or clip change takes. Since #1667 the tree itself knows which version is published (the record's `released`), so this corollary is enforced at authoring time by rule 4 and the packer's refusal, not first discovered by the publish step.

## Sound effects (`sfx/`)

`sfx/` holds the non-voice assets: the walkie-talkie tick-open/close pair, the ambient pit loop, and the radar proximity tones (`sfx/radar/`). The ticks and the loop are referenced by each voice's `frames` (the `radio` frame in `configs/<voice-id>.voice.json` — since #1064 there is no `radio-frame.ts` in code) and by the PI background-volume test (`@iracedeck/audio-scenarios` `background-test.ts`), which plays them only as the fallback for a voice with no `radio` frame — otherwise it previews the voice's own frame (#1124); the tones by the radar engine (`radar-engine.ts`). Deliberately **not** radio-filtered at build time: everything outside `voice/` is copied into the plugin output unchanged (see `src/presets.mjs`), so the ticks and tones stay clean.

## Voices may diverge — the within-pack coverage check (issues #664, #1065)

Pools are derived per-voice from the clips that actually exist (a pool is every `voice/<voice>/<group>/<base>-NN.mp3` plus the bare `<base>.mp3`, resolved by the `@iracedeck/audio-scenarios` engine at fire time), so voices do **not** need identical clip sets: a voice may record fewer or more `-NN` variants of a line, or omit a callout entirely — that voice simply doesn't play it. Missing keys are allowed; wording can vary per voice (different engineer personalities).

What IS checked is that each voice's own script covers its own clips — `src/generate/script-coverage.test.ts`, which replaced `voice-parity.test.ts` in #1065. The old test refused a non-default voice any `<group>/<base>` that `default.voice.json` lacked, on the grounds that a base the canonical voice does not know is referenced by no pool; that held only while every pool came from a code registry, and once a voice ships its own script its own base is referenced by its own sequence — not dead, just not ours. The replacement is per voice and stronger. For every `configs/<voice-id>.voice.json`: (a) **orphans** — every `<group>/<base>` authored in a group the script addresses must be referenced by the script (a step, a frame, a fragment or a `pools` alias); an unreferenced base is a misspelled take or a line that lost its consumer, and it is what the old test could never see in `default.voice.json` itself; (b) **dangling** — everything the script references, in either spelling, must be authored, and every plain pool name it draws from (a `{ connector: true }` step included) must be defined under `pools`, since a reference to nothing is a fire-time abort (#835); (c) a vacuity floor for the bundled voice. A group NO step addresses (`position-number`, `names`, the lap-time digits, …) is var-driven — a code resolver returns `poolRef(group, base)` at fire time — and is skipped whole, because the vocabulary lives in `@iracedeck/audio-scenarios`, which lists this package as a devDependency for its tests. A group a script addresses for some bases while a resolver produces the rest (`session-start`, `incidents`, `pit-limiter`) is declared in the test by shape, each entry naming its resolver and guarded against going stale. A clip that is authored but deliberately never spoken (`pit-readback/windshield-off` — the readback never speaks the negative, since open-wheel cars have no windshield and telemetry cannot tell) is listed in `DELIBERATELY_UNSPOKEN` with its reason, and the test insists each entry is still authored and still unreferenced.

**Where the rules live since #1066.** The three rules — `coverageOf`, `orphansOf`, `danglingOf`, and `checkCoverage` over them — are `@iracedeck/callout-script`'s `coverage.ts`, pure over `{ script, authored, sharedClips }` where `authored` is a plain `<group>/<name>` list and `sharedClips` the plugin's built-ins (the runtime manifest's clips outside `voice/`, which a frame's `sfx/…` literals are checked against — the test reads them off the committed `manifest.json`), so that `pnpm lint:pack` (`packages/audio-scenarios/src/reference/lint-pack.ts`, run over the clip FILES a pack ships) is held to the very same rules as the bundled voice and cannot become a second source of truth. They could live in neither consumer: `@iracedeck/audio-scenarios` lists this package as a devDependency (its tests read the manifest and the voice scripts through it), so an import back would be a cycle, and this package's `src/generate/` is run by `tsx` and never built, so the grammar package both already hold is the one place both reach. `src/generate/script-coverage.ts` is the glue from a config to those rules: `authoredNamesOf(config)` (the `groups` as that list), `coverageOfConfig(config, sharedClips)` (through `buildCalloutScript`), and `unscriptedGroupsAreVarDriven(coverage)` — the var-driven reading a caller WITHOUT the vocabulary has, handed to `orphansOf` as its predicate. The test keeps `VAR_DRIVEN_BASES` and `DELIBERATELY_UNSPOKEN` because they are facts about the bundled voice, not rules, and holds every voice to `unusedAliases` being empty — a `pools` alias no live step names is a name that stopped carrying a decision; the linter reads the var-driven groups off the vocabulary's descriptions instead (`descriptionNamesGroup`) and carries no allowlist, so a lint of the bundled tree is not expected to be clean.

## Manifests

`generate.manifest.json` is the **generator's hash cache** — per-entry hash + ElevenLabs request id, used to skip unchanged entries. Don't hand-edit; let the generator manage it. Keys are `voice/<voice-id>/<group>/<name>.mp3`, so per-voice cache isolation is automatic — changing one voice's settings invalidates only that voice's entries. The two hand edits it does take are whole rows: a copied clip's row (step 1 of *Adding an entry* below), and a retired clip's — the generator never prunes, so an entry removed from a config leaves its mp3 and its row behind; `git rm` the clip, delete the row, and rebuild the runtime manifest (#1167 retired `flags/one-pace-lap-to-go` this way). The file is `JSON.stringify(manifest, null, 2)` plus a newline, so a parse → edit → write in Node round-trips byte-for-byte and the diff shows only the rows meant.

**A merge or rebase over an audio change conflicts here as one giant hunk, and keeping both sides is wrong in a way nothing reports.** The file is a per-clip cache keyed by clip path, so a union lets whichever branch is older win every shared row — and a stale hash is not a failure, it is a cache miss. Resolve it as a keyed union in which **master wins every shared row**, carrying over only rows your branch genuinely added. Then prove it with `pnpm --filter @iracedeck/audio-assets generate:dry-run`: the *would-generate* count must be **unchanged from clean master's** — whatever that number happens to be, since it is master's own staleness rather than a target — and your new clips must show up as extra *skipped*, not extra generated.

Nothing fails if you get this wrong, which is the whole problem. Tests pass, the build passes, and the packed archive is byte-correct, because the cache only decides whether a clip is **re-cut**, never what ships. The bill arrives later and for someone else: one paid ElevenLabs call per lost row, and fresh bytes for clips nobody meant to touch — which changes the pack's `sha256` and so needs a regenerated catalog entry. #474 is the worked example: a naive keep-both turned a handful of genuine re-cuts into 143.

Contrast `changelog.json`, where the rule was **regenerate, never hand-merge** — and since #1386 it is not committed at all: a turbo task rebuilds it from its sources before every plugin build, so it can no longer conflict. That is the better rule wherever a generator can rebuild the artifact from its source, and it is why this cache is the exception rather than the precedent — it cannot be rebuilt without re-cutting the very thing it exists to avoid re-cutting.

`manifest.json` is the **runtime manifest**, and since #1034 stage 3 it has a sibling: `generate:manifest` writes both, from one generator. `manifest.json` names every **authored** voice — every `voice/<id>/` directory — and is what this package's own generators and tests read as "the authored voice". `manifest.bundled.json` names only the **bundled** slice (`BUNDLED_VOICE_IDS`): the manifest a plugin compiles in, describing what the distributable itself provides. (It was also where the reserved voice ids came from, the ones that stopped a downloaded pack claiming a voice the plugin already had; #1144 retired that rule, since a pack's voice is `<pack id>::<voice id>` and cannot collide with anything.) They were identical until stage 3; since the flip the bundled slice is the `sfx/` clips and nothing else.

**The wiring since #1034 stage 3, task 2:** all three plugins (`iracing-plugin-stream-deck`, `iracing-plugin-mirabox`, `iracing-plugin-ulanzi`) import `@iracedeck/audio-assets/manifest.bundled.json` through `plugin-runtime`'s voice-pack phase (`src/phases/voice-packs.ts` and its scan step `voice-packs/scan.ts`, one phase for all three, #1349, #1377) — never `manifest.json` — so a plugin's compiled-in manifest can never outgrow what its own build actually copies. The scenario harness, this package's own generators/tests, and any other consumer that needs every authored voice import `manifest.json`.

The bundled manifest a plugin carries is only the **built-in half** of what that plugin plays: installed voice packs under `%LOCALAPPDATA%\iRaceDeck\Race Engineer\Voices` contribute their own clips at runtime, each pack acting as its own audio root and its clips reaching the engine as `voice/<pack id>::<voice id>/…` (#1144), and the scenario engine consumes the union (`mergeManifests` in `@iracedeck/audio-scenarios`). So a voice missing from these files is not necessarily missing at runtime. They list clips only — never a voice's `callouts.json`, which ships beside the clips but is read by the voice-pack service, not resolved as a clip. Rebuild after adding/removing clips with:

```bash
pnpm --filter @iracedeck/audio-assets generate:manifest
```

## Adding an entry to an existing group

The most common case — a new callout in an existing family (e.g. another flag):

1. Add the entry to the group in `configs/default.voice.json` **and in every other first-party voice** — every voice `VOICE_PACKS` publishes, today `configs/shawn.voice.json`, the Terse pack (#999) — with that voice's own wording; a first-party voice makes every callout Default makes, and `bundled-scripts.test.ts` fails on a contract its script does not carry. Generate the Terse line scoped to its voice (`generate:dry-run --voice shawn --group <group>`, then `generate --voice shawn --group <group>`); an entry whose text, settings and seed are verbatim Default's can instead be copied — the clip and its `generate.manifest.json` row under `voice/shawn/…` — and the dry-run reports it as a cache hit. A third-party voice config *may* add the same `<group>/<entry-name>` key but doesn't have to — a voice without the clip just skips that callout (issue #664). Omit `seed` (or set `"seed": 1`) — never an arbitrary value.
2. Preview: `pnpm --filter @iracedeck/audio-assets generate:dry-run --group <group>` — it must report exactly the new entries as "WOULD GENERATE" and everything else as cache hits.
3. Generate scoped: `pnpm --filter @iracedeck/audio-assets generate --group <group>`.
4. Rebuild the runtime manifest: `pnpm --filter @iracedeck/audio-assets generate:manifest`.
5. Commit the new `voice/<voice>/<group>/<name>.mp3` clip(s) together with the regenerated manifests (`generate.manifest.json`, `manifest.json`, `manifest.bundled.json`) — clips are tracked in git.

## Adding a new group

1. Add the new top-level key under `groups` in `configs/default.voice.json` (the canonical voice) and in every other first-party voice, as in step 1 above (#999); a third-party voice may adopt the group later — parity is not required of it, issue #664.
2. Author the entries (text, no `seed` — or `"seed": 1`; conditioning fields per **Clips that join other clips** below).
3. Generate (scoped by `--group`), after a dry-run preview.
4. Rebuild the runtime manifest.
5. Point the callout at its clips: for a scripted family the `sequence` step in the voice's `configs/<voice-id>.voice.json` addresses them as `pool:<group>/<base>` (the post-edit hook re-extracts the script in a Claude session; `pnpm generate:callout-scripts` by hand otherwise) — a `pools` entry only where a name carries a decision, an alias or a separate no-repeat tracker, with the reason in its `comment`. Every family is scripted since #1065, so there is no code-side pool to declare; the family's TypeScript file lists the `(group, base)` in its literal `<FAMILY>_CLIP_SOURCES`, and the coverage check above fails on a clip the script never references.

## Clips that join other clips — how ElevenLabs reads the conditioning fields (#1163, #1571)

A callout is clips played back to back, so every join is a seam the listener hears. ElevenLabs shapes a clip from the text around it, and these rules are what Niklas settled on 2026-11-01 while the compact lap-time readout was drafted:

- **Every clip has `previous_request_ids`, and every clip something follows has `next_text`.** Niklas's rule: "Each clip must have a previous_request_id set, and things that have something following, must have the next_text set." Without `previous_request_ids` each clip is generated cold, and clips played together sound like different takes of the voice. They are ElevenLabs request stitching: the model hears the referenced clip's actual audio and continues its tone, energy and pace. Point them at the clip the new one really follows where that is fixed: a tail after a car number points at a `car-number` clip. Where the predecessor varies, point them at one fixed representative of it: a time after an intro points at "Last lap was", and a "point …" tail points at a minute-and-seconds phrase. Up to three ids. A referenced clip must exist first, so generate in passes in reference order. `previous_text` (text-only conditioning) is not used: ElevenLabs ignores it whenever `previous_request_ids` is supplied, which here is always.
- **`next_text` decides how a clip ends, and only its first sound counts.** The model shapes the last word to run into whatever `next_text` says, and Niklas's rule is: "For the next text, only the next word, and the very first letters (how they are pronounced) actually matter." So cut a clip once for each distinct ONSET SOUND that can follow it, give each take one representative word of that class as `next_text`, and have the resolver map the following value to its class at speak time. "Oh five" and "oh seven" share one take, and so do "twenty" and "ten" (/t/). An onset cut is for a clip that must run into a varying word with no break; a line that can end its sentence instead should (next rule but two). Where the follower is constant ("point" after the seconds, "car" before a car number, "pee" before a position), one take with that word as `next_text` is enough. A clip that ends the line gets no `next_text`.
- **Fewer, longer clips beat a chain of short ones.** Every join is a seam the listener can hear, and a phrase TTS reads in one breath sounds natural where spliced single words do not. The compact lap time is therefore intro + "one twenty three" (minute and seconds as one clip, 600 of them) + "point four five six" (all three decimals as one clip, 1000 of them). An earlier draft spliced a bare minute word, a seconds word, "point N" and a pair, and Niklas heard it as unnatural (2026-11-01). Spend clips to remove joins: a thousand whole phrases cost less than a digit-by-context matrix and leave no seam inside the number.
- **Read decimals digit by digit**, the way a timing screen is read aloud ("point four five six"), not in pairs ("point four fifty six"). The pair reading was tried and sounded unnatural.
- **A clip followed by a script `pause` ends its sentence: no `next_text`, and its text ends with a period.** It keeps its `previous_request_ids`. Niklas's rule: "When there's a pause after the clip, we can't have 'next text' there, and in this case the clip must end with a period." The fastest-lap "just took the fastest lap from you." is the case (followed by `"pause:150"`, then the time), and so is the tenths tail "point four." before the gap clause.
- **A line that leads into a figure ends its sentence.** "Last lap was." then the time, not "Last lap was" cut to run into it: one take with a period, no `next_text`, `previous_request_ids` kept. Niklas, 2026-11-01: "the period makes it end cleanly and sharp". The intros were first cut once per onset class of the time's first word, nine takes each, and still ended on a thump; the sentence-final take replaced them all.
- **Otherwise no periods in a clip's text.** A period reads as a pause, and the clip then ends on one. The same goes for hyphens, dashes, ellipses, colons and semicolons, which the generator refuses (#1518).
- **Seeds stay omitted or `1`.** Niklas changes a seed himself, after hearing a clip on the review page, when a take sounds wrong.
- **Reuse a group whose `next_text` already matches** before cutting a new one: the compact readout's seconds under a minute are #555's `lap-time-second`, whose words were already cut to run into "point" and conditioned on their predecessors. A group whose clips carry a fixed lead word (every `car-number` clip says "car") cannot stand in for the bare figure.

Measured on the clips (ffmpeg `silencedetect`, -40 dB): a clip cut with `next_text` starts with no measurable lead and ends within about 40 ms of its last sound, so a join needs no trim. A sentence-final clip trails about 0.2 s, which is right at a sentence end.

## Adding a new voice

1. Create `configs/<voice-id>.voice.json` with its own `id` (ElevenLabs voice id), `label`, `model_id`, `voice_settings`, and `groups`. The groups do **not** need to match `default.voice.json` — a partial voice loads fine and simply skips the callouts it lacks (issue #664), until step 5 makes it first-party. The only constraint is the coverage check above: every clip you author in a group your script addresses must be referenced by your script, and everything your script references must exist — a `<group>/<base>` the bundled voice lacks is fine when your script speaks it.
2. Run `pnpm --filter @iracedeck/audio-assets generate --voice <voice-id>` to render its clips into `voice/<voice-id>/...`.
3. Rebuild the runtime manifest. The runtime auto-discovers voices from the manifest's `voice/<id>/...` paths, so the new voice appears in the PI dropdown automatically.
4. Author the voice's callout script — `scenarios`, `frames`, `pools`, `fragments` in the same config — and extract `voice/<voice-id>/callouts.json` (the post-edit hook runs `pnpm generate:callout-scripts` in a Claude session; run it by hand otherwise). Without one the voice is clips-only: it loads, appears in the dropdown, and says nothing, because absent means skipped. Commit the artifact with the config; the freshness test insists.
5. Registering the voice in `VOICE_PACKS` (`src/build/voice-packs.mjs`) makes it first-party, and every first-party voice is held to script completeness (#999): add it to `FIRST_PARTY_SCRIPTS` and `CLIP_SOURCE_FLOOR` in `@iracedeck/audio-scenarios`' `bundled-scripts.test.ts`, which fails until you do and then fails on any contract its script does not carry. Third-party packs are not held to that — for them absence still means skipped. The pack reference and `lint:pack`'s engine keep reading the reference voice `default`.

## Conventions

- One group per callout family (flags, pit-actions, pit-status, track-conditions, …). Mixing families in one group makes the cost-scoping flag `--group` less useful.
- Variants use a `-NN` suffix (`blue-01.mp3`, `blue-02.mp3`). A pool is *all clips sharing a base name* — every `voice/<voice>/<group>/<base>-NN.mp3` **plus the bare `<base>.mp3`** (issue #836: a bare value clip like `position-number/7.mp3` is a size-1 pool) — derived per-voice from the runtime manifest (issue #664), so **adding or removing a variant is just adding or removing an entry + clip**: no pool edit, no code change. Playback picks uniform-random with a no-immediate-repeat guard (not in numeric order).
- Value clips (numbers, temperatures, speeds, names, lap-time digits) define their own speakable range by existing (issue #836): there are no code-side bounds or clamps, so widening a range (e.g. more temp values, higher position numbers) is purely a generate-clips job.
- The `<group>/<base>` pair is the stable identifier — a voice's script addresses pools by it (`pool:<group>/<base>`, or through a named `pools` alias onto it), and a code var resolver returns it as `poolRef(group, base)`, so renaming a base is a breaking change for every script that references it. A rename is also a generator-cache migration: rekey the `generate.manifest.json` paths, refresh the stored hash of every entry whose `previous_request_ids`/`next_request_ids` reference the renamed entries (the raw reference strings feed the entry hash), and prove zero re-cuts with `generate:dry-run` — the #837 acknowledgment migration is the worked example.

## Known re-render triggers

Adding a new audio-affecting field to `EntrySchema` that feeds the hash invalidates every entry's cache (a one-time invalidation). Don't add hashed fields casually — accept the regenerate cost or stage the rollout carefully.
