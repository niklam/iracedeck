# Scripts

Repo-level Node `.mjs` utilities, mostly backed by root `package.json` scripts. Everything runs on plain `node` **except** `generate:action-comms`, which runs via `tsx` because `generate-action-comms.mjs` imports the TypeScript `comms-catalog.ts` directly — moving it to plain node breaks it.

## Build & release

- `build.mjs` — the root `pnpm build` entrypoint (runs `turbo run build`).
- `build-with-restart.mjs` — `pnpm build:with-restart`: stops a running Stream Deck app, builds, and restarts it so the new build is loaded (a host reads its plugins at start only). Since #1258 a running host no longer fails the build — a native addon it has loaded is moved aside and rebuilt (`lib/native-addon-build.mjs`) — so the restart, not the stop, is the point.
- `install-runtime-deps.mjs` — every plugin's `postbuild`: `npm install` in the plugin's `bin/`, against the `package.json` `lib/runtime-deps.mjs` emitted (#1177). It keeps only the `npm_config_*` keys npm takes without a warning — judged as npm's own `checkUnknown` does, against the keys `npm config ls -l --json` lists with no `.npmrc` loaded — because npm warns about each key it does not know, and `pnpm run` exports some: pnpm 10 exported its own keys and every `.npmrc` key (#1205); pnpm 11 and later export only well-known ones, which still include a pnpm-only key when a pnpm 10 on PATH hands over to the pinned version (#1245). Behaviour in `lib/runtime-install-env.mjs` (`installRuntimeDeps(binDir, { env, exists, missingPath, run, log })`, returning an exit code).
- `release.mjs` — `pnpm release` / `pnpm release:dry`: wraps `release-it` (pulls `GITHUB_TOKEN` from `gh`, strips pnpm's `--` sentinel, sets `RELEASE_IT_DRY_RUN=1` on `--dry-run` so the hook doesn't write files).
- `release-hooks.mjs` — the `.release-it.json` `before:bump` hook (`node scripts/release-hooks.mjs ${version}`). Auto-discovers every `packages/*/package.json` and plugin manifest (`*.sdPlugin` / `*.ulanziPlugin`) via `lib/version-discovery.mjs` and bumps them (`*.sdPlugin` manifests get 4-part `x.y.z.<git commit count>`, which Elgato's schema requires; `*.ulanziPlugin` manifests get plain `x.y.z`, the only form the Ulanzi marketplace accepts — `lib/manifest-version.mjs`, #1298); stamps the changelog date on stable releases via `lib/changelog-stamp.mjs` (policy: `.claude/rules/changelog.md`); preflights with `git add --dry-run`, then stages everything.
- `stamp-ulanzi-package-version.mjs` — `node scripts/stamp-ulanzi-package-version.mjs <archive> <version>`, run by `release-pack.yml` right after it packs the Ulanzi plugin: `@elgato/cli pack` pads every manifest `Version` to four parts inside the archive (and on disk), whatever the folder says, so the zip would carry the form the Ulanzi marketplace refuses (#1298). It writes the committed `x.y.z` back into the archive's `<folder>/manifest.json`, refuses a version that is not `x.y.z`, and exits 1 unless the archive reads it back. Archive handling in `lib/packed-manifest.mjs` (fflate, which is why `fflate` is a root `dependency` rather than a dev one: the workflow prunes dev dependencies before packing).

## Generators (committed JSON output, guarded by freshness tests)

**The post-edit hook runs a generator whenever its source file is edited in a Claude Code session** — the source → generator map is `claude-hooks/rules-post.mjs`, the policy `.claude/rules/hooks.md`. That covers everything here except `generate-pack-reference.mjs`, which needs a built dist and gets only a reminder. Run any of them by hand outside a Claude session, or when the hook reports a failure; the freshness tests are the guard in every case.

- `generate-action-comms.mjs` — `pnpm generate:action-comms` (tsx) → `action-comms.json` from `comms-catalog.ts`.
- `generate-action-profiles.mjs` — `pnpm generate:action-profiles` → `profiles.json` from the Elgato manifest's `Profiles` array.
- `generate-icon-previews.mjs` — previews for the icon SVGs under `packages/icons/`; `generate-icon-defaults.mjs` — the PI colour/border defaults, from `packages/icons/` and `packages/iracing-actions/icons/`. Policy in `.claude/rules/icons.md`.
- `generate-pack-reference.mjs` — `pnpm generate:pack-reference` → `packages/website/src/data/pack-reference.json`, the Voice Packs reference the website renders (#1066), built from the Race Engineer catalog's `contracts()` + `vocabulary()`, the reference voice's `callouts.json` (`default`), its `configs/default.voice.json` and the authored runtime manifest. Run after changing a contract, its `description`, the vocabulary, the reference voice's script or its clips. **Needs the BUILT `@iracedeck/audio-scenarios` dist** — the root scripts are plain Node — so `pnpm build` (or `pnpm exec turbo run build --filter=@iracedeck/audio-scenarios`) first; `generate-pack-reference.test.mjs` fails on drift naming this command, and names `pnpm build` when the dist is missing or stale. Data assembly in `lib/pack-reference-data.mjs`; the engine comes from `lib/catalog-engine.mjs` (below).

## Voice-pack linting (#1066)

- `lint-pack.mjs` — `pnpm lint:pack <packDir>` (the folder holding `voice-pack.json` and `voice/`), run from the repo root after `pnpm build`. **This section is the one home of the linter's contract**; the `race-engineer-callouts.md` rule row and the `audio-scenarios` package `CLAUDE.md` keep the paths, the command and a one-line summary and point here, so a behaviour change is one edit. It says loudly what the plugin would only skip quietly, over the clip FILES a pack ships, per voice in the scanner's own order: every problem the plugin's own manifest schema finds in `voice-pack.json` — the schema itself, not a copy: since #1134 the manifest schema, the id-vs-folder rule, the voice de-duplication, the usable-clip grammar and the script size cap live in `@iracedeck/callout-script`'s `voice-pack.ts`, and the scanner and the linter import the same functions (`readVoicePackManifestText` — the manifest's one text stage, BOM strip, `JSON.parse` and schema, which the scanner reads through as `parseVoicePackManifest` — `packIdMatchesFolder`, `dedupeDeclaredVoices`, `USABLE_VOICE_CLIP`, `VOICE_SCRIPT_MAX_BYTES`) — each reported in the schema's own words as `voice-pack.json: <path>: <message>; the plugin refuses the manifest` (text that is not JSON as `voice-pack.json: not valid JSON: …; the plugin refuses the manifest`), the first problem per field only, as the leaf's `validateVoicePackManifest` returns it (zod reports every check a field fails, so an `id` holding `::` would otherwise read twice; the separator's sentence is the one kept, because the schema checks it first and iRaceDeck joins a pack id and a voice id with it, #1144), with a missing or zero `schema` reported as the ordinary line and only a higher schema number as a pack built for a newer iRaceDeck, and a `version` accepted exactly as the plugin accepts it (`v1.2.3` included, which the regex the linter carried until #1134 refused); an `id` the schema accepts that does not equal the folder name lowercased (the scanner compares case-insensitively); a voice declared twice in a manifest the schema accepts, in the scanner's words (the first wins) — a manifest the schema refuses loads nothing, so its repeats are folded away silently and each voice is linted once. When the manifest gives no usable voice (missing, unreadable, not JSON, or no declared id the schema's `packId` accepts), the voices under `voice/` are linted instead, and `; the voices under voice/ were linted anyway` is appended to the last read or schema problem — the one that explains why — never to the folder-mismatch line that may follow it. A voice id another pack also declares is NOT a problem: since #1144 a voice is `<pack id>::<voice id>` outside its pack, the scanner no longer refuses one, and the managed-voice-id check the linter carried until then went with that rule. `lib/lint-pack-scanner-parity.test.mjs` holds the linter and the scanner to the same verdict over one set of packs — each fixture names its verdict and both sides are held to it — and gives the three findings that are the linter's alone (a clips-only voice, an unplayable file beside playable clips, a `voice/` folder the manifest does not declare) a case each; grammar problems in a voice's `callouts.json`; a `callouts.json` over the scanner's 1 MiB cap (the shared `VOICE_SCRIPT_MAX_BYTES`), reported as the plugin treats it — read, then refused before it is parsed, and the voice dropped; a missing `callouts.json` (a clips-only voice — valid to the plugin and silent for every callout, which is what the missing-script banner is for); every compile skip the pack did not mean, with the compiler's reason — compiled through the engine's own `compileScript`, so the deps are the plugin's (a code-registered pool is known, a legacy scenario is no contract); frames and fragments that fail; clips shipped that nothing references (orphans); `pools` aliases nothing names (reported as orphans too — a name that decides nothing); references to clips not shipped (dangling), `sfx/…` literals that name no built-in the plugin ships (`sharedClips` — the authored manifest's clips outside `voice/`, so a misspelled tick in a frame is caught before it aborts every framed callout) and literal paths the check cannot place; and a per-voice `<voice>: N of M callouts scripted` summary. Named-pool and unknown-include findings are the compiler's, which names the entry. **One limitation, stated for authors too (the tutorial's lint step):** a clip in a group a variable draws from is never reported as an orphan — the linter cannot tell which clips a variable resolves to; the exemption is per group, read off the var's description (`descriptionNamesGroup`), and declared sources on `defineVar` are the follow-up that would close it. Exit 0 clean, 1 on any problem, 2 when it could not run (usage, a path that is not a directory, a missing dist — `pnpm build` first, as for the generator). The rules are `lintPack` in `packages/audio-scenarios/src/reference/lint-pack.ts` (the module's design — the injected filesystem port, the manifest fallback, the injected compile — is in that package's `CLAUDE.md`); `lib/lint-pack-run.mjs` is the argument handling and the `node:fs` port (`runLintPack(argv, io) → exit code` — injected `io`, a code returned rather than `process.exit` called, the same testable shape as the `lib/` helpers below) and owns `PLUGIN_PLAYED_CLIPS`: the clips plugin code plays by path with the active voice, outside any script, as `{ group, base, playedBy }` — `toggle/radio-check` (the connect radio check, `packages/iracing-actions/src/actions/pit-crew/pit-crew.ts`), `toggle/going-silent` and `toggle/resuming` (`packages/iracing-actions/src/audio/audio-toggles.ts`, `playToggleAck`), `toggle/corner-names-on` and `toggle/corner-names-off` (`audio-toggles.ts`, `toggleCornerNamesFeature`), `welcome/greeting` (what the settings window's Race Engineer **Test** button plays after the driver's name, `packages/iracing-actions/src/audio/voice-test.ts`) and `names/*` (the driver-name clips, one per name, the name chosen at runtime — `ANY_BASE` marks the one group played whole). **The exemption is per CLIP**, handed to the pure linter as `pluginPlayedBases` (`group/base`, `group/*`): the plugin plays each by its exact name (the `-01` take), so `toggle/radio-chek` is the orphan it is and `welcome/hello` — which nothing plays — is one too. The same list is the ARTIFACT's single carrier: `lib/pack-reference-data.mjs` hands it to `buildPackReference` as `pluginPlayed`, each entry's `playedBy` is written onto its recording line, and the website renders those words from `pack-reference.json` and keeps no list of its own. Each entry names the file that plays it, `lint-pack-run.test.mjs` holds every exact entry to a clip in that manifest, and a new by-path consumer is a new entry — in one place. Two of these are the second step of a chain that stops at the first clip it cannot start: the radio check and the Test button play `names/<driver>` first, so a pack that records either without a `names/` clip for the name the user is set to hears nothing; the `playedBy` texts say so. A lint of the `packages/audio-assets` tree is still not expected to be clean: the reference voice's exceptions live in its coverage test, not in the linter (`pit-readback/windshield-off` is `DELIBERATELY_UNSPOKEN` there and an orphan here), and it ships clips nothing references — `acknowledgment/acknowledgment`, `openers/*`, `units/*` and `welcome/hello` — which are a question for the maintainer, not a linter allowlist.

Both read the catalog through `lib/catalog-engine.mjs`: `registerCatalogEngine()` registers the real `registerPitCrew` off the built dist against a stub bus/audio/logger **once per process** and hands every later caller the same engine (the radar / spotter / pit-speeding sub-engines are module singletons — a second registration throws). The engine reports the reference voice as active and nothing changes it: neither script fires a callout — the generator names the voice whose clips it reads, the linter reads a pack's files — so there is no voice switch to offer.

## Dev linking and host control (Mirabox, Ulanzi)

Elgato is absent from all of these on purpose: its linking uses the `streamdeck` CLI and its start/stop scripts hardcode the one install path (see root `package.json`).

- `link-mirabox.mjs` / `unlink-mirabox.mjs` — `pnpm link:mirabox` / `unlink:mirabox` / `relink:mirabox`: junction-links the built Mirabox plugin into the host's plugins dir (default `%APPDATA%\HotSpot\StreamDock\plugins`; override with `MIRABOX_PLUGINS_DIR` in a gitignored `.env.local`).
- `link-ulanzi.mjs` / `unlink-ulanzi.mjs` — the Ulanzi equivalents (default `%APPDATA%\Ulanzi\UlanziDeck\Plugins`; override with `ULANZI_PLUGINS_DIR`). Added in #1040.
- `host-app.mjs` — `pnpm start:ulanzi` / `stop:ulanzi` / `start:mirabox` / `stop:mirabox`, dispatched as `node scripts/host-app.mjs <start|stop> <host>`. The executable comes from `ULANZI_APP_PATH` / `MIRABOX_APP_PATH` with a `%ProgramFiles(x86)%` default, because two Mirabox-compatible hosts are commonly installed side by side (StreamDock, VSD Craft). `start` first prints which worktree the link points at — the junction serves exactly ONE checkout, which is the usual cause of "my fix isn't working".

All four link scripts are thin descriptors over `lib/plugin-link.mjs`, and `host-app.mjs` is argv handling over `lib/host-control.mjs`; the behaviour lives in `lib/`, not in the entry files. Every lib function takes injected `env`/`platform`/`log` and **returns an exit code instead of calling `process.exit`**, which is what makes it testable — follow that shape when adding to them. The entry scripts set `process.exitCode` rather than calling `process.exit`, because a Windows TTY's stdout is asynchronous and exiting outright can truncate the line naming which worktree now owns the host.

Three subtleties there are load-bearing and must survive any edit:

- `lstat` rather than `exists` throughout, so a dangling junction whose target is gone is still detected.
- The unlink branch on entry type. A junction gets `unlinkSync`; a **real** directory is **moved aside** to `<folder>.replaced-<timestamp>`, never deleted. (`rmSync(recursive)` on a Windows junction with a missing target silently no-ops and leaves the junction behind, which is why the branch exists at all; the move-aside is because the folder carries the plugin's own logs and `relink` runs inside `switch-test-env`, where a printed warning scrolls past unread.) The aside suffix must keep breaking the host's `*.sdPlugin` / `*.ulanziPlugin` scan pattern.
- `taskkill` exit codes: 0 stopped, **128 = not running**, anything else is a genuine failure. Collapsing the last two reports a refused kill as success, and the chain then builds and relinks under a host that is still running the old plugin and holding its files open.

**A warning printed inside a composite command is not a warning.** `relink` runs inside `switch-test-env`, behind `pnpm install && pnpm build`, so anything these scripts print scrolls past thousands of turbo lines unread and unconfirmed. That is why the real-directory case moves the folder aside instead of deleting it and explaining itself: the explanation cannot be relied on to reach anyone. Any destructive step added here should assume its own output is never read, and be reversible instead.

**The dev loop's order is not arbitrary.** `pnpm stop:<host> && pnpm switch-test-env:<host> && pnpm start:<host>`: the stop comes first because the relink runs inside `switch-test-env`, straight after the build, and a running host holds the plugin folder's files open (`lib/plugin-link.mjs`); and both hosts read their plugins directory at start only, so a relink or a build without a restart changes nothing. A running host no longer fails the build itself on the native addons — since #1258 a loaded `.node` is moved aside into the package's `.locked-native/` and rebuilt, and `pnpm build:force` measured green on 2026-10-03 with a separate process holding loaded all eight native binaries a plugin process holds. Not measured: a `bin/` runtime-dependency bump that changes keysender's or `@resvg/resvg-js`'s binary while a host holds the old one, where the postbuild `npm install` would have to replace a loaded file and may still fail.

## Dev voice packs (#1143, #1214)

- `dev-voices.mjs` — `pnpm dev:voices on|off|auto`: the per-worktree override of the machine-wide `IRACEDECK_DEV_VOICES` opt-in. `on` writes the gitignored `dev.local.json` marker with the default root (keeping a hand-picked path), `off` writes `voicePacksRoot: false` (never deletes, since an absent marker now follows the variable; refuses over a hand-picked path, pointing at `auto`), and `auto` removes the marker (naming a hand-picked path it removed). It loads `.env.local` for the host plugin directories but never takes `IRACEDECK_DEV_VOICES` from it (a plain `pnpm build` would not see it), warning instead; the variable belongs in the user environment. Each validates the variable before writing, then rebuilds the three plugins with turbo (the marker is a declared build input and the variable a declared `env`, so the resolved root reaches every `bin/config.json` as `devVoicePacksRoot` or leaves it, and the plugin builds' `stage:dev-voices` dependency stages the packs while on), and relinks only the deck hosts whose link already points at this worktree — a host linked elsewhere is reported and left alone rather than silently switched out from under someone. **The marker change is transactional**: the file's previous state (absent, or its exact bytes) is captured first and put back if the build fails, because the build is what carries the marker into every `bin/config.json` and a marker left changed after a failed one claims a mode none of the three plugin folders is in — which nothing in the plugin can report, since every reader reads the BUILT config. A running deck host no longer fails that build on the native addons (#1258, see the note under _Dev linking_ above), but a build still fails for ordinary reasons — and possibly on a `bin/` runtime-dependency bump against a binary a running host holds — and the restore covers every one. The script names the hosts linked here ahead of the build, as the ones to stop: the relink after the build expects them stopped, and a running host reads the new `bin/config.json` only when it next starts. Argument handling only; the behaviour is `lib/dev-voices.mjs`'s `runDevVoices(mode, { root, env, log, exec, platform, links })`, covered by `lib/dev-voices.test.mjs`.
- `assert-release-build.mjs` — `node scripts/assert-release-build.mjs <path to bin/config.json>`: exits 1 when a built plugin folder carries `devVoicePacksRoot` (naming the key, the file and `pnpm dev:voices off`), when the config is missing (the plugin is not built), unreadable or not an object; 0 otherwise, 2 with no path. Wired as the FIRST step of every plugin's `pack:plugin` script, chained with `&&`, so a development build stops the command instead of being packed. It answers a different question from `dev-voice-root-guard.test.mjs`, which proves the SOURCE cannot emit the key unconditionally: `pack:plugin` packs whatever is on disk, and on a maintainer's machine that folder is routinely a development build — by marker or by `IRACEDECK_DEV_VOICES=1`. PRESENCE of the key is the property, never its value — it arrives through a conditional spread, so a blank or `null` one is still a development build. Behaviour in `lib/assert-release-build.mjs` (`assertReleaseBuild(configPath, { fs, log })`, returning an exit code), covered by `lib/assert-release-build.test.mjs`.
- `lib/dev-local.mjs` — `resolveDevVoicePacksRoot(root, { env, fs })` / `readDevLocal(root)` / `readDevVoicesEnv(env)` / `DEV_LOCAL_FILE` / `DEFAULT_DEV_VOICE_PACKS_ROOT` / `DEV_VOICES_ENV`. `resolveDevVoicePacksRoot` is the one place the marker (shape `{ voicePacksRoot: "<path>" | false }`) and the `IRACEDECK_DEV_VOICES` variable are combined — the marker wins when it says anything, the variable decides otherwise — returning `{ voicePacksRoot, source, isDefaultRoot }`; it is shared by `dev-voices.mjs`, `@iracedeck/plugin-build`'s factory (which carries the resolved path into every plugin's `bin/config.json` the way it already reads `feature-flags.local.json`) and `packages/audio-assets/scripts/stage-dev-voices.mjs`, so the build cannot stage without pointing the plugin at the stage. Unlike `feature-flags.local.json`, both readers are strict: an unknown marker key throws rather than warns, and the variable accepts exactly `1` and `0` — a typo would silently build development mode off, a failure a developer would chase in-game rather than in a build log. `lib/dev-local.test.mjs` covers the readers and the resolution matrix; `dev-voice-root-guard.test.mjs` at the `scripts/` root (discovering every plugin the way the manifest tests do) guards the properties keeping the mechanism build-time-only: the marker is gitignored and untracked, no workflow mentions the variable, the key is emitted through a conditional spread in the shared factory and no plugin config emits it itself, every plugin build and the stage task hash the marker and declare the variable in `env`, and every plugin build depends on the stage task.

## Tests

`*.test.mjs` files are colocated here and run under the root vitest (`scripts/**/*.test.mjs` in `vitest.config.ts`). `test-package.mjs` is every package's `test` / `test:watch` script (#1021): it turns the package directory pnpm starts it in into the filter `packages/<name>/` and runs the root suite with the root `package.json`'s own Vitest arguments, so `pnpm --filter <pkg> test` runs that package's tests under the root config; `package-test-scripts.test.mjs` holds every package with tests to exactly those two scripts and every package without to neither, and `test-package.test.mjs` runs the real runner against `packages/logger` as its positive control. `manifest-actions-order.test.mjs` discovers every plugin manifest dynamically (same discovery as the release bump) and enforces alphabetical action order, name uniqueness, and cross-manifest action-set parity — `ECOSYSTEM_SPECIFIC_ACTIONS` (currently `Switch Profile`) is exempt from parity only. `generate-action-profiles.test.mjs` and `release-hooks.test.mjs` are the generator/release guards. `generate-pack-reference.test.mjs` is the one guard here that reads a **built** package: it asserts `packages/audio-scenarios/dist` exists and exports the builder before comparing, so a missing or stale dist fails naming `pnpm build` rather than reporting drift (CI builds before it tests; locally, build first).

## Structure

the summary by its sibling `pack-reference-data.test.mjs` over a hand-built reference, which does not), `lint-pack-run.mjs` (the linter's runner, `node:fs` port and `PLUGIN_PLAYED_CLIPS`). `dev-local.mjs`, `rollup-logs.mjs` and `runtime-deps.mjs` are imported by relative path from the shared plugin Rollup factory (`packages/plugin-build/src/plugin-rollup.mjs`, #1349), which is why they stay here.
- **Spawning a `.cmd` shim** (`pnpm`, `npx`, `tsx`, `streamdeck`) goes through `lib/spawn-shim.mjs`'s `spawnSyncShim(cmd, args, options)`, never `spawnSync(cmd, args, { shell: true })`. Windows cannot spawn a `.cmd` without a shell (`EINVAL`, the CVE-2024-27980 hardening), and Node 24 deprecates an args array beside `shell: true` (DEP0190, announced to become an error) — so the helper joins the arguments into ONE quoted command line for the shell on Windows and spawns directly, with no shell, elsewhere. It refuses an argument `cmd.exe` would not carry intact (a `"`, which flips `cmd.exe`'s quote state and can expose an operator in a later argument; `%`; a line break) rather than mangling it, and quotes an empty argument and doubles a quoted argument's trailing backslashes so neither is lost. `claude-hooks/lib.mjs`'s `run()` sends everything but `git`/`gh`/`node` through it (`shim: false` opts another `.exe` out) and returns a refused argument as a failed run rather than throwing, since a hook that throws denies; a command given as one string with no args array (`install-runtime-deps.mjs`) is not the deprecated shape and needs no helper. `lib/spawn-shim.test.mjs` spawns `pnpm --version` through it under `--throw-deprecation`, beside a positive control showing the old shape fails that harness.
- `data/` — script-owned inputs, e.g. `icon-title-defaults.json` (consumed by `add-title-metadata-to-icons.mjs`).
- `radio-effect/` — self-contained ffmpeg clip-processing spike with its own README; not wired into any build.
- `local/` — Personal automation scripts, excluded from version control via `.gitignore`. Each developer can place their own scripts here without affecting the repository.
